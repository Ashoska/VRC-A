# Onboarding, ToS, boot screen

_Scope: First-open tutorial, on-demand tutorial images, ToS gate, the boot screen (`BootScreen` + `AppBoot`, every build) + when it shows (warm resume, after updates), backend-name sanitization._

- **Shown after an app update too (all builds)**: `VrcaApp` stores the version that last got past boot (`vrca_remote` `last_boot_version_code`); a different (or missing) value adds `justUpdated` to the warm-resume test, so the first open of each new version shows the boot screen once.
- **Boot screen (`app/BootScreen.kt` UI + `app/AppBoot.kt` runner, EVERY build; the old `BootstrapScreen`, its 3-row checklist, `BootVrcStatus` and the `ChatboxStats` lifetime counter were removed)**: shown under the warm-resume rule below (swipe-reopen / boot launch / first install / first open after an update). Intro: the logo alone at the centre, then it slides left and the Status card + checklist unfold SAO-style (a line stretches out, then splits onto the top and bottom edges as the part opens, so nothing lingers mid-panel). Left: logo (`vrca_logo_vector`, sharp at any zoom; `WIDE_LOGO_HEIGHT`, top lined up with the checklist) over the Status card: Internet (`internetStatus()`: link type + Android's speed estimate, re-read every 1 s), VRChat (status.vrchat.com indicator → `ServiceState`), VRC-A servers (device-session result + Worker `/health`; never names the backend). Right: header "Welcome back, <stored VRChat name>" + count chip + one bar segment per row, then 7 rows in dependency order: Device session, Terms of Service, Account standing, VRChat sign-in, Discord, VRChat on this headset, Updates.
  **Layouts**: wide (>= 720x560dp: the headset panel, tablets) = logo + Status on the left, checklist on the right, pill meeting at the gap; phone = one centred column (logo 150dp, Status, checklist, pill, version under it), max 480dp wide, scrolling only when a short screen (< 760dp tall: logo 104dp, rows 32dp, 6dp gaps) can't fit it, and scrolling itself down to the pill when it opens. **Rows per build** (`Row.inThisBuild`): "VRChat on this headset" is headset-only, Updates is not on the admin build (it never checks); Device session's icon is the drawn VR headset on the headset, a phone elsewhere. The logo flies into the top bar only on the headset (phone/admin top bars show the name in words); elsewhere it fades.
  Every row shows ONE fixed word from `BootNote` / `ServiceState` / `InternetLink` (no free text, so rows never grow or get cut off); rows are a fixed height. Marks are shared (`Mark`/`StateMark`: spinner, tick, amber !, wrench, red x, grey dash) and swap with a spring pop; an outline shows while a row needs attention and flashes green once when it lands; a failed row shakes once. A row shows "waiting" until it has fully appeared (so checks that finished during the intro still tick on screen). When all rows settle a light sweeps the bar (the Ready moment).
  **Runner (`AppBoot`)**: nothing starts until the panels begin to unfold (`BootScreen` `onOpening`, ~1.5 s into the intro; at once without an intro). User call: the checks used to start on the first frame and were all done before the rows were even visible, and the intro had to share its first frames with the network/device-session work. The VRChat status-page fetch waits too; only the cheap Internet re-read runs from the start. Then all checks start at once; Terms + Account standing (and Updates) start once the device session (`bootstrapFirebaseAndCache`) succeeds. BLOCKING (boot waits for them): Device session, Terms, Account standing, VRChat sign-in, Updates. VRChat sign-in (user rule: no booting into the app without a working VRChat session): first run (tutorial not done) is skipped, the tutorial's login step handles it; otherwise the saved session is re-read for up to 4 s (cold-start Keystore race), then `validateSessionDetailed` (UNKNOWN retried twice): VALID → Signed in; 401 → silent `autoRelogin`, else "Sign in needed"; UNKNOWN → amber "VRChat issues" and boot goes on ONLY when the status page says VRChat isn't Online, otherwise "Sign in needed". "Sign in needed" (red) holds boot and shows a "Sign in to VRChat" pill that opens `VrchatLoginScreen` over the boot screen; a successful sign-in re-runs the row. `startPipelineWarmup` once the session is good (not waited on). Not blocking: Discord (`discordRpcEnabled` off → Skipped "Off", else follows `DiscordRpcState`), VRChat on this headset (`InstanceRosterManager.flow`: LIVE/IDLE → Found, NO_LOG → "VRChat not open", no access → "No log access"). New terms / a ban / an update are only noted (amber); the existing ToS, ban and update gates after boot handle them.
  Hand-off: blocking rows done AND the screen fully opened (`onShown`) AND every other row has succeeded or failed (user rule: a non-blocking row can't stop boot, but boot still waits for its answer; each row has its own timeout: Discord 12 s, after which it shows amber "Timed out", VRChat on this headset 2.5 s). Only then does the header see every row settled and play the Ready sweep, and `READY_HOLD_MS` (0.9 s, longer than the 650 ms sweep) runs from that moment (user report: the hold used to start when the blocking rows finished, so a still-connecting Discord or log search meant no sweep at all, and a late last row had its sweep cut off by the fold); then the way out (`exit`): the panels fold back into their lines and the wall fades; when the main app opens next (terms accepted, not restricted, signed in to VRChat, onboarding done) the logo glides + shrinks into the top bar's logo spot (`TOP_BAR_LOGO_HEIGHT` 56dp, centred at 32dp), otherwise it fades in place; `onExited` then opens the app with no hard cut: `VrcaApp` wraps everything in a Box with `BootRevealOverlay` on top, and `BootReveal.start()` keeps the boot backdrop over the freshly composed app for `REVEAL_MS` (650 ms) while it fades away (taps swallowed meanwhile); when the logo went to the top bar a copy holds exactly over the app's own top-bar logo until the fade ends, so it never blinks. A failed device session shows the joined Retry/Continue pill (5 s auto-retry ring; Continue only if this headset has signed in before). Reuse, no double reads: `BootResults` hands the ban result and release check to `VrcaApp` (its phase-1 ban check and first release check are skipped, the phase-2 screen isn't shown). The only new read is one `config/app` get per cold boot for the Terms row (cold boots are rare). Lab: `show boot <mid|error|done|incident|offline|live|livefail|demo>` (samples) and `show headsetboot` (the real runner, offline).

- **Onboarding flow** (`ui/onboarding/OnboardingFlow.kt`): first-open tutorial pager (takes the app-scoped `vm` — `OnboardingFlow(vm, …)`), 8 steps in FINAL order — Welcome+ToS (hard gate, embeds the redesigned `TosGate`) → VRChat login (hard gate, embeds `VrchatLoginScreen`, shows a **platform-status warning** from a one-shot `status.vrchat.com/api/v2/summary.json` fetch since the pipeline's status poll only runs post-login) → Permissions (POST_NOTIFICATIONS runtime, Notification Access, battery exemption, **Install updates** (`canRequestPackageInstalls` / `ACTION_MANAGE_UNKNOWN_APP_SOURCES` — needed for in-app APK updates), **Overlay (optional)**; statuses re-checked on `ON_RESUME`; Samsung "Never sleeping apps" note. **POST_NOTIFICATIONS is requested ONLY here / in Settings — `MainActivity` no longer fires the runtime prompt on first open**; KeepAliveService starts regardless, its notification just stays hidden until granted.
  A collapsed `CompactSectionCard` ("Turn off background restrictions", `persistExpansion=false`) explains long-press icon → App info → 3-dot menu → "Allow background activity"/Unrestricted, and to keep VRC-A out of any restricted/sleeping-apps list — the Samsung note nests inside it. A SECOND collapsed card at the TOP of the step ("A permission won't turn on?", `persistExpansion=false`) explains the **"Allow restricted settings"** gateway: Android 13+ blocks SIDELOADED apps from granting Notification Access / Accessibility (the switch is greyed out / shows "Restricted setting") until the user opens App info → 3-dot menu → "Allow restricted settings". Placed first so it's seen when a toggle won't enable — this is the real reason a permission appears ungrantable on a non-Play-Store install) → IP entry (**auto-saves what you type** — a 500ms-debounced `LaunchedEffect(ip)` writes slot 1 + active IP via repo, so NO button press is needed to persist; the button is now an OPTIONAL "Check reachability" `pingHost` test only, per user complaint that users didn't realise they had to click to save.
  The typed IP becomes the **live OSC target** automatically because `VrcaViewModel.init` now collects `userPreferencesRepository.ipAddress` into `remoteVrcaOsc.ipAddress` — previously the app-scoped VM, constructed during onboarding before any IP existed, kept sending to `127.0.0.1` until the user manually tapped Apply in Home. The "Good to know" card on this step is a collapsed `CompactSectionCard` (`persistExpansion=false`) so the IP input sits in view without scrolling) → Enable OSC (numbered instructions with the 4 `osc_tutorial_N` TutorialImage frames, all on the single step;
  **the images are downloaded on-demand — see `TutorialImageStore` below — not bundled**) → Notification types (**the FULL per-type `NotificationToggleSection(vm)` — the same 27-toggle expandable UI as Settings**, replacing the old 5 master section switches, so first-time users pick and choose every type; toggles persist via the VM/DataStore directly) → Discord RPC (consent checkbox → `DiscordLoginWebView`; sets risk/seeded/enabled flags) → Test message finale (scoped `VrcaOsc(ip,port)` loop sends "VRC-A connected ✓" every 2s while active, empty-send clears on stop/exit; deliberately bypasses the Start/Stop gate — no toggles touched, `FeatureSessionStore` never armed). **The test step is a HARD PING GATE** (non-replay): Finish stays hidden until `testDone`, and `testDone` flips ONLY when the saved IP answers a ping — while the test runs, `pingHost` attempts repeat every 3s and the step passes the moment one succeeds; there is deliberately **NO manual "it showed up" bypass** (per the user: a wrong IP must be fixed, not waved through). A troubleshooting card (same Wi-Fi / right IP / headset awake / OSC enabled) with a "Fix the address" jump-back shows while waiting.
  **`pingHost(address)`** (public, in `OnboardingFlow.kt`) is the robust reachability check: `InetAddress.isReachable` first (often fails on Android — no raw ICMP socket), then the system `/system/bin/ping -c 1` binary fallback; the Home Connection card's 20s reachability chip uses it too so the chip and the tutorial gate agree. No saved IP → a "Go to the address step" button jumps back to step 4 (`onGoToIpStep`). **No em dashes in any tutorial-visible string** (user said they look bad — also swept `VrchatLoginScreen`'s copy, which the tutorial embeds; don't reintroduce them in onboarding/login UI text). **Footer**: a "Step N of 8" label + animated progress pills (current step is an elongated 24dp pill via `animateDpAsState`, visited pills are tappable to jump back). **The flow root clears text-field focus on any empty-space tap** (`detectTapGestures` → `LocalFocusManager.clearFocus()` — a parent gesture detector only sees taps children didn't claim); the same pattern lives in the main app's `PageContainer` (`VrcaScreen.kt`) so every tab dismisses a stuck focused field/keyboard.
  The IP step's Quest instructions are 4 expanded numbered steps + a "Good to know" card (IPv6 warning, same-Wi-Fi, IP-changes note, PC ipconfig path) — written to stand alone since Quest Settings screenshots are DRM-blanked. Gating in `VrcaApp`: `OnboardingPrefs` (`vrca_onboarding` prefs, `complete` + resume `step`); **pre-seeded complete when `TosPrefs.acceptedVersion > 0`** so existing installs never see it. **Replay**: Settings → App → "Replay setup tutorial" sets `OnboardingState.replayRequested` (process-level mutableStateOf); replay renders hard gates as completed checkmark cards and has an "Exit tutorial" button. Phase-2 ban check + pipeline start still run via the normal post-gate logic in `VrcaApp` (the login-gate `remember` first executes after onboarding returns, so it correctly reads the now-logged-in state).

- **On-demand OSC tutorial images (`ui/onboarding/TutorialImageStore.kt`)**: the 4 `osc_tutorial_N.png` instruction images are **NOT bundled in the APK** — they were ~617 KB for a screen most users see once, so shipping them was pure bloat. They're downloaded on-demand from the shared image-store repo (`https://raw.githubusercontent.com/Ashoska/VRC-A-Image-store/main/osc_tutorial_N.png` — the SAME repo, renamed from `VRChat-rpc-display`, that hosts the Discord RPC default image `vrchat-1102x620.jpg`; `DiscordRpcService.DEFAULT_VRCHAT_IMAGE_URL` was updated to the new name in the same change) into `filesDir/tutorial_images/` and deleted the moment the tutorial ends. `ensureDownloaded(ctx)` is idempotent (skips cached, `.part`-file-then-rename so a partial download never looks complete); `clear(ctx)` deletes them. **`TutorialImage(index, …)` (PublicUiKit)** resolves the local file, shows a `CircularProgressIndicator` while it downloads, renders via Coil (`AsyncImage` inline + `rememberAsyncImagePainter` in the pinch-zoom dialog), and calls `ensureDownloaded` itself as a fallback. **Lifecycle (the "no stale images" design)**: (1)
  **New-user boot** — `AppBoot`, for a logged-out user whose onboarding is `!isComplete`, spends the boot-screen time PREFETCHING the images (`withTimeoutOrNull(TUTORIAL_PREFETCH_CAP_MS = 8s)`, a hidden blocking step) — the intro + Ready hold already keep the screen up, so there is no separate floor; (2) **Replay** — `OnboardingFlow` re-downloads on entry (`LaunchedEffect(Unit) { ensureDownloaded }`, idempotent); (3) **Tutorial complete OR replay exit** — `VrcaApp`'s `onFinish` (the single convergence point for both first-run completion via `advance()` and replay's "Exit tutorial" via `finishNow()`) calls `TutorialImageStore.clear(ctx)`; (4) **A new user who closes/kills mid-onboarding KEEPS the images** — onboarding is still `!complete`, so no cleanup runs and boot re-prefetches any missing → resume works; (5)
  **A replay killed mid-way** leaves strays, so `VrcaApplication.onCreate` runs `clearStaleTutorialImages()` on a fresh process — if onboarding is already `complete` (i.e. not a genuine new user), it deletes the dir (replay state is process-level `OnboardingState.replayRequested`, always false at a cold process start, so a killed replay self-cleans). Net: images exist only while a tutorial is actually in progress; the APK ships zero tutorial images.

- **ToS gate redesign** (`VrcaApp.kt`): `parseTosBlocks()` converts the admin-configurable plain text into styled blocks — numbered headers (`^\d+\. `) render primary-colored (error-colored for Risk/Moderation/Acceptable Use sections), `*`/`-` lines become real bullets, literal markdown links `[x](y)` are collapsed by `sanitizeTosLine`. Layout: sticky title + version pill header, scrollable body, pinned accept bar with a **Checkbox** (was a Switch). `TosGate` is `internal` so onboarding embeds it.

- **Cold-start anon-auth retry (`bootstrapFirebaseAndCache`, the Device session row)**: its only hard network dependency is `FirebaseAuth.signInAnonymously().await()` (the rest is `runCatching`/non-fatal). On a brand-new install's FIRST open the network + Firebase stack is often still cold, so a single attempt failed transiently (the "Device session sometimes fails on first open" report). Fix: a bounded retry (up to 4 attempts, backoff 400ms→3s, each attempt capped at `ANON_AUTH_ATTEMPT_MS`) inside the row's 30 s timeout, so a cold-start blip self-heals instead of surfacing Retry.
- **When the boot screen shows (warm resume)**: ONLY on a genuine, deliberate cold start. Its gate state is Activity-scoped `remember`, so without a rule ANY new Activity composition (OEM/force kill restore, headless revival, plain re-create) re-ran boot.
  **Boot screen shows ONLY on a clean swipe-reopen or first install (the "boot screen shows every time the app is brought back after an OEM/force kill, not just on a real open" fix)**: the boot screen exists to cover a genuine, deliberate cold start.
  **The decision now mirrors how the Quick Toggles / `FeatureSessionStore` restore tell a deliberate swipe apart from an OS/OEM kill: the persistent `swiped_away` flag** (`AppShutdown.isSwipedAway()`, set ONLY by `onTaskSwiped`, which an OS/OEM/force kill never runs). `MainActivity.onCreate` captures **`VrcaApplication.openedFromSwipe = AppShutdown.isSwipedAway(ctx)` at the TOP, BEFORE `clearSwipedAway()` wipes it**. `VrcaApp` computes `val warmResume = !(openedFromSwipe || !everBootstrapped)` where `everBootstrapped` = a non-blank cached `auth_uid` in `vrca_remote` prefs (bootstrap writes it and it persists), and seeds `bootOk` from it (now also `|| openedFromBoot || justUpdated`, see "Shown after an app update"). So the boot screen shows **only** on (a) a clean **swipe**-reopen (a deliberate fresh start) or (b) a true **first install / data clear** (no cached auth uid → bootstrap MUST run to sign in anonymously + cache the uid the ban check reads);
  **every other relaunch — OEM/force kill, Activity recreate, headless revival — is a recovery and drops straight into the app with no boot screen.** Skipping boot on a swipe-less relaunch is safe because the auth uid + device hash already persist in prefs and the VM's `ensureAnonAuth` re-signs-in if the cached Firebase session lapsed. On a warm resume the phase-1 ban check runs in `VrcaApp` (`LaunchedEffect(bootOk)`, skipped when a boot just did it via `BootResults`) so `phase1BanId` is still populated and the downstream ban gate works — the UI isn't blocked on it; `startPipelineWarmup`/`bootstrapFirebaseAndCache` are correctly skipped on warm resume (the VM/services own pipeline start + liveness). (The earlier `runtimeVmAlive` attempt was abandoned — `MainActivity` always starts `KeepAliveService` → `ensureRuntimeViewModel()` on EVERY open, which flipped that flag true and raced the composition, producing the inverted "swipe-reopen skips boot but everything else shows it" behavior; the swipe flag is unaffected by the service start.)

- **Backend-name sanitization (`sanitizeBackendRefs`, `VrcaApp.kt`)**: every USER-VISIBLE error/debug string is scrubbed of backend-implementation names before display (replaces `com.google.firebase…`/`com.google.android.gms…` class paths with "backend" and any `Firebase*`/`Firestore*` token with "server") so exception text can't reveal the server stack to users (exploit-surface hygiene, per the user). Applied at: the boot `bootError`, the `CrashScreen` crash-text display (stored log stays raw for debugging), and Settings → Debug ("Sync (last issue)" — renamed from "Firebase (last issue)" — and the moderation-listener error). Logs keep raw text. Route any NEW user-facing error surface through this; never hardcode "Firebase"/"Firestore" in public-build UI strings (admin build is exempt — not distributed).
