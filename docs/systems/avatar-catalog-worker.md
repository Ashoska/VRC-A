# Avatar catalog Worker, search index + catalog bots

_Scope: Cloudflare Worker (cloudflare/avatar-db/worker.js) flush/reconcile/fold/index behaviour by version, fill worklist, contribution dedup, liveness shard-walk bots, author renames, sweep recovery; daily db.json backup in R2; R2 outage runbook. Older version notes (v12-v39, the removed GitHub Action) are in avatar-catalog-worker-history.md. Client-side clone resolution is in avatar-catalog.md._

## Planned: live feed (not built; user, 2026-10-30)
- **Goal**: server state that moves the moment it changes, first in the admin revamp (`docs/revamp-2.md` item 11), later on the website as a public live-stats page for users. Build it once for both.
- **Shape**: the Worker hands a one-line event to a Durable Object the moment something happens; viewers hold a WebSocket to it (hibernation API: no duration billed while idle). A small recent-history ring (last ~200 events) so a new viewer isn't empty; `/health` stays the snapshot. Events, not storage: no extra R2/KV writes.
- **Events**: contribution received (who, count, names) and, at the flush, how many were really new; bot pushes (fills, calm refreshes, removes, author renames); reports in/resolved; each flush (shards, index buckets, ms, failures); queue depths and `writesToday` ticking; backup and author-rename progress; errors (R2 outage).
- **Two views of one stream**: admin (full detail, ADMIN_KEY) and public (read-only, rate-limited, no device ids or admin data; contributor names only if the user decides they're public). Decide the public field list before the website work.
- **Cost**: one tiny DO request per event; a busy day is a few thousand, inside the Workers Paid included DO requests, so about $0. Check before adding anything that writes per event.

## Version 49 (2026-10-30): cheap shard writes, calm lane, font flags, no automatic re-index
- **Why** (Cloudflare audit with the account token): ~1M R2 writes/month normally, ~3.3M writes + ~15.9M reads in a re-index month (the $34.41 September and $9 October bills; normal is the $5 plan). Two sources: every bot `checked` bump rewrote a whole shard just to move a date (the "R2 +0 -0 (1 shards)" flush every tick), and the automatic re-index laps (FOLD_VER/FOLD_STAMP_V bumps and the 30-day re-arm) read every shard and re-queued search ops. Target after v49: ~150-250k writes/month.
- **Writes only when an avatar changes.** No "last checked" date any more: the bots walk every shard continuously (local per-app `sweptAt`, oldest first, with claims), so a server date added nothing. `walkPass` sends nothing for an unchanged avatar. A `checked` op (old apps still send them) is now only a font check in the flush: it re-folds a fancy entry whose `fz` is stale and stamps `fv`, and the shard is written only if something actually changed. The stale counter (`staleCount`, the liveness "queued" number) is gone: manifest `staleCount` and meta/`/health` `stale` are always 0.
- **Two lanes for bot upserts** (`POST /admin`). Fast lane `admu:`: fills, re-keys (new file id), removals and contributions (`pend:`) land on the next flush, with an instant CDN purge of the changed search files (capped at `IDX_PURGE_CAP` 150 per flush; the rest expire in 5 min). Calm lane `admc:<ts13>:<uuid>` (`body.calm === true`, sent by the app for refreshes of an avatar already in the catalog with the same file id): durable in KV, drained when the oldest batch is `CALM_HOLD_MS` (30 min) old or `CALM_MAX_KEYS` (300) are waiting, so one shard write carries many refreshes. A Worker restart doesn't lose them (keys are in KV). `/health.calmWaiting` shows the count.
- **No false positives (user's requirement), enforced in the flush:** every bot batch carries `__ts`; every entry stores `mt` (time of the op that last wrote it); an upsert older than the stored `mt` is ignored, and within one flush the newest op per file id wins. A calm op never creates an entry (so a calm refresh can't bring back an avatar removed in the meantime, or add one that was never contributed). `carryWorkerFields` keeps the Worker-owned fields (`fz`, `fv`, `added`) across an upsert when the text didn't change.
- **Font flags** (replace the automatic fold laps): the manifest publishes `foldV` (= `FOLD_STAMP_V`), every non-ASCII entry (name+author+bio, any UTF-16 unit > 127, `hasNonAscii`) gets `fv` when it is folded. The bots read `foldV` from the manifest (`BotController` → `AvatarCatalogSweep.setManifestFoldV`), parse `fv` from shards (`AvatarGlobalDb.Entry.fv`), and send a `checked` id only for a fancy avatar whose `fv` differs (`needsFontCheck`). So a fold change reaches every fancy avatar on the next bot lap, one write per shard that actually needs it, and plain-ASCII avatars never cost anything.
- **No automatic re-index.** `reconcileIndex` returns at once while `meta.rcDone` is set; FOLD_VER/FOLD_STAMP_V bumps and the 30-day re-arm no longer start a lap (`FOLD_VER` is historical, only shown in `/health`). A full recount lap runs only when armed by hand (`GET /admin/reconcile?key=`).
- **The daily backup does the old recount's jobs** (it already reads every shard): exact unfilled count (`lastUnfilled`), shards holding unfilled avatars (`fill`, unioned into the fill hint), and the "unconverted" font report (`unconverted.json`, sample capped at `BACKUP_UNCONV_SAMPLE_CAP` 400). The flush adopts the unfilled count once per backup like the v48 entry count (`ufAt`/`ufSum`: count + fills/adds since). Each backup step stops after `BACKUP_STEP_CHARS` (16 MB of JSON) so memory stays inside the 128 MB isolate as the catalog grows (5M avatars ≈ a few hundred steps a day, still well inside free R2 Class B reads).
- **`/health`** adds `writesToday`/`writesYesterday` (`{d, sh, ix, ot}`: shard, search-index and other R2 writes, from meta `wr`/`wrPrev`), `calmWaiting`, `foldV`, `version` 49.
- **Tested locally in Miniflare** (real worker.js, fake KV/R2): no automatic lap; contribution clonable + searchable in the same flush; fill fast; old-app `checked` on a plain avatar = no write; font flag = one write then none; calm refresh waits then lands; 3 calm refreshes to one shard = 1 write; removed avatar stays removed; newer fast op beats older calm op, and an op older than the stored `mt` is ignored; calm batch survives a restart; identical refresh = no write; calm can't create; backup computes unfilled/fill/unconverted and the flush adopts them.
- **Resharding later** (not done): at ~1.5-2M avatars shards average ~400-500 entries; going to 65,536 shards (4 hex) via the manifest `shardScheme` keeps each shard small (clone reads stay one small file). Doubling to 8192 isn't a clean hex split, so the next step is 65,536 when needed.
- **App side** (`AvatarCatalogSweep`): `pendingCalm` buffer + `enqueueCalm` (a fast op buffered for the same id wins), sent in its own pushes with `calm = true` (`AvatarGlobalDb.adminPush(..., calm)`). Re-keys stay fast. Flush readout: `+new ~calm ✓font −removed`. The Reports bot's "helping" label is Fill while there are unfilled avatars, else Liveness.

## Version 40 (2026-10-26): index queue unjammed, fonts in a priority lane, faster recount, fill-first bots
- **Why**: `/health` showed `iqDepth` pinned at 1000 (the list cap) and plain "white tiger" did not find ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ's 8 avatars. Causes found in the code: (1) the drain capped OPS (142) but `applyIndexOps` costs ~1 read + <=1 write per distinct BUCKET (~10 tokens per op → ~1,400 reads), past the ~1000-subrequest ceiling; every R2 call after that failed inside a `try/catch`, the batch still counted as applied and was deleted, so updates were silently lost. (2) Every liveness `checked` bump re-asserted a fancy entry's FULL token union, flooding the queue. (3) Each reconcile run read ~1,600 `avtr/` buckets (24 shards x ~82 entries), also past the ceiling; a failed read counted as "missing" and queued a full re-add (most of `reconcileFixed` 105k).
- **Drain** (`flushR2`): budgets distinct buckets (`opBuckets`, `bucketCap` = (600 - 2 x shard prefixes) / 2, leaving room for the same cron's reconcile/prune/rename); an op is applied only if its buckets fit, the rest stays queued. Order: this flush's contribution ops, this flush's fold ops, the `iqp:` priority lane, then the `iq:` backlog; at most 40 backlog keys read per flush (`KEY_READ_CAP`). Pre-v40 re-asserts (`isLegacyReassert`: no frag/avtr/del/rem, no `fz` marker) are dropped as they're read (`iqDropped` in `/health`). Leftovers requeue by lane. `applyIndexOps` never writes a bucket whose read threw (writing "empty + batch" would wipe it) and throws on any failed read/write so the caller requeues the whole batch (idempotent). An index-only backlog also chains (`INDEX_CHAIN_DEPTH` 10 extra steps per cron, `iqRemaining`/`iqProgressed`), so a backlog clears in about an hour; same total ops.
- **Fold stamp** (`foldSig`, entry field `fz`): a fancy entry's plain-text tokens are queued once per fold result (`foldOp`: only the folded tokens the raw ones lack, marked `fz:1`), not on every check. Adds/upserts stamp `fz` since their ops already carry the folded tokens. A CONFUSABLES change alters `foldSig`, so affected entries re-queue automatically on their next check or recount. Fold ops ride the `iqp:` lane; its keys are named `iqp:<opCount>:<uuid>` (`iqpKey`/`iqpCount`) so `/health.foldPending` ("Fonts waiting") is exact from the key list alone.
- **Recount** (`reconcileIndex`): shard reads only, `RECONCILE_SHARDS_PER_RUN` 120 → a full lap is ~4,100 Class B reads in ~70 min (was 6h+). It also queues fold ops for fancy entries without a current `fz` into `iqp:` (`reconcileFoldQueued`). `FOLD_STAMP_V` is a fingerprint of CONFUSABLES + SMALLCAPS (v41), so any fold-rule change re-arms this lap by itself on deploy and unchanged fancy avatars get the new fold within ~70 min (no manual bump). Removed, edited (name/author/bio/platforms/perf/image) and unfilled avatars are pushed by the bots on the check that finds them; only an unchanged avatar's `checked` waits for the 20-day threshold. The per-entry presence check is now an on-demand HEAL (`GET /admin/reconcile?key=…&heal=1`, `rcHeal`, `HEAL_AVTR_READS_PER_RUN` 300; a failed `avtr/` read = unknown, skip). Plain `/admin/reconcile` re-arms the fast lap.
- **CONFUSABLES** added (Worker + both client copies, still byte-identical): я/Я→r, σ→o, Σ→e, Λ/Δ→a, ł/Ł→l, Ɇ/ɇ→e, Ð/ð→d, ɛ→e, ƈ→c, ɨ→i, Ҝ/ҝ→k, and upside-down ʍ ɥ ʇ ƃ ɹ ʎ ɯ ʞ ɟ ʌ (the top of the `/unconverted` registry). Negative-squared/circled and flag letters never appear in real names (0 hits) and stay unmapped.
- **Bots** (`AvatarCatalogSweep.walkPass`): fills first. `nextFillPrefix` takes a shard from the Worker's `_worklist.json` (shared queue, refreshed at most once a minute, refilled whenever nothing in it is due; a taken shard is held `FILL_REWALK_MS` 5 min, and one a bot finished or found empty is held `FILL_DONE_HOLD_MS` 30 min even while still listed, since its fills only leave the list after the push batch + flush + cache; a rate-limited visit keeps the 5-min retry) and checks only its unfilled avatars, without stamping it swept. A full re-verify is always FINISHED before a waiting fill (the user's call: fills queue after the current shard, no dropped shards); every pass checks the fill list first, so the fill is the bot's next job. Only the Reports bot (reports pending) and the Fill-role bot (fill waiting) drop a shard mid-walk. A dropped shard goes on `droppedShards`, which any bot takes right after fills and before the oldest-first walk, so the rest of it is carried on by the next free bot; its old sweep stamp is restored and saved at once (`persistSwept`), so a restart still finds it at the front. Already-checked avatars are skipped by the shared recent-process guard (`processedAt`, 25 min, all bots). An unchanged avatar's `checked` is pushed only once it is `CHECKED_PUSH_MIN_AGE_MS` (20 days) old, so a clean lap no longer rewrites every shard.
- **v42 (same day, after watching it live)**: each drain flush took ~100 s because bucket reads/writes ran one at a time, and the index chaining kept a chain running nonstop, so the 2-min cron (which skips its whole cycle while `chainBusy`) never got to run reconcile/prune/author-rename (`lastReconcile` froze). Now `applyIndexOps` runs bucket IO `INDEX_IO_CONCURRENCY` (6) at a time (`runPool`, same subrequest count), and a chain step runs the cron's maintenance itself when due (`cronTasksIfDue`, KV stamp `crontasks`, every `CRON_TASKS_EVERY_MS` 110 s) under the same lock. Do not trigger a plain `GET /flush` by hand while a chain runs: it doesn't take the lock and its meta write can overwrite reconcile progress.
- **Fill-role bot (2026-10-26, user's call)**: with "finish the shard first", new fills waited for whichever walking bot freed up first (seen live: all four mid-shard while fills waited). The slot whose only role is Fill (`slotLoop` `fillDedicated`) now works like the Reports bot: it walks when nothing needs filling, and mid-walk checks the fill list every `FILL_IDLE_MS` (8 s); when a fill is due it drops the shard (sweep stamp restored, so it stays at the front) and fills. `WORKLIST_TTL_MS` is 20 s (was 60). The other bots still finish their shard and check the fill list before the next one (the fallback when the Fill bot is logged out; with fewer bots roles share slots). The card labels it "Fills + walk".
- **Bot card shard label**: `walkPass` sets `curShard` on every shard it reads, with `curShardTotal` 0 when nothing in it needs work, and the card then shows "shard X: nothing left to check". Before, the label kept the last shard that had work while "shards swept" counted the empty visits too (fill-list shards just filled by another bot, still listed until the Worker's next flush), which looked stuck.
- **v46 fill list + "Fills waiting" (2026-10-26)**: live check found 1,012 listed fill shards and `unfilled` 1,176, but only 7 real unfilled avatars (all <6 h old): the counter and the list had drifted, and `pruneFillWorklist` never ran because it skipped while the list was within `unfilled + 20` of that same drifted counter. Now it always runs while the list is non-empty (`PRUNE_BATCH` 100 shards per cron, dropping fully-filled shards, rotating kept ones), and after each full pass over the list (`prunePassLeft`/`prunePassUnfilled`) sets `unfilled` to the count it found (`lastFillRecount`). Unfilled avatars only live in listed shards (new ones are added by the flush), so the count self-corrects every pass. Simulated: 1,012 → 7 shards and 1,176 → 7 in 11 runs.
- **v47 chain steps nest (2026-10-26)**: each `/flush?cont=` step used to fire the next through `ctx.waitUntil` and respond. A fetch handler's `waitUntil` only lives ~30 s after the response, and a step takes ~60-70 s, so every step after the cron's first child was cut off mid-flush (meta never saved, lock left held so the cron skipped, the same reads/writes redone later): flushes landed every 2-5 min instead of back to back. Now `fireContinuation(..., awaitIt = true)` and the chain handler awaits the next step before responding, so each request stays open; the cron root still uses `waitUntil` (a scheduled invocation lives up to 15 min). `MAX_CONTINUATION_DEPTH` and `INDEX_CHAIN_DEPTH` are 8 (≈10 min, inside the cron's limit). Simulated with a real self-call: steps 1→8 nested, none used `waitUntil`, lock released.
- **v48 exact count + fancy bios (2026-10-29)**: the avatar count had a one-off +~7,000 phantom (counter 353,369 vs 346,391 real, counted from all 4,096 shards; the gap held flat for days, so not ongoing). The running count only moves by deltas, so a miscount never healed. Now each finished daily backup snapshots `totalAdded`/`totalRemoved` (`addedAt`/`removedAt` in KV `backup`), and the next flush adopts `lastCount` + what moved since, once per backup (`countFromBackup` in meta), rewriting the manifest so `/health`'s max() drops too. The reconcile lap no longer sets `entries` (it counts over ~70 min while flushes add). `needsFold` now includes the bio: it was name + author only, so 49k bio-only fancy avatars never got plain words ("Rainworldǃ" not found by "rainworld"; 35 of 150 sampled). `FOLD_STAMP_V` gained "+bio" so the lap re-arms once and queues them in the font lane (Fonts waiting rises, then drains). Live check of fancy names/authors: plain words found; the remaining misses are common words ("and", "from", "model") capped by `INDEX_HOT_TOKEN_CAP` for every avatar.
- **Admin** (Bots tab, Avatar catalog card): "Fills waiting" (`/health.unfilled`), "Fonts waiting" (`foldPending`), "Index queue" (`iqDepth` keys + `iqpDepth` font keys).
- Tested on a simulated KV/R2: a 9,000-op heavy backlog drained with at most 621 calls per run and every sampled op applied; 15,000 legacy re-asserts dropped while a real ADD among them applied; "white"/"tiger" index ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ, Tιgєя and ʍɥıʇǝ; "Fonts waiting" matched the real queue mid-drain (2,806, 2,652, 0).

**Daily `db.json` backup built inside R2 (Worker v45, replaces the removed Action's backup)**: `maybeFireBackupStep` (run at the top of every cron, before the `chainBusy` check) reads the KV `backup` state and, when a backup is due (`BACKUP_EVERY_MS` 24 h) or in progress, fires `GET /admin/backupstep?key=…` through the `SELF` binding as its OWN invocation (own subrequest budget, never holds the flush lock, never writes `meta`). `backupStep` reads `BACKUP_SHARDS_PER_STEP` (200) shards and appends their entries in the master's line format (`"file_…":{…}` one per line, which `reshardFromMaster` parses), uploads every full `BACKUP_PART_BYTES` (5 MiB, R2's uniform part size) chunk of an R2 multipart upload, and carries the remainder in KV `backup:buf`. The last step (~21 steps, ~40 min) writes the footer (`"count"` at the end) and completes the upload, which swaps the new `db.json` in atomically; a failed shard read aborts the step without saving (retried), an upload older than `BACKUP_STALE_MS` (6 h) is aborted and restarted. Cost per day: ~4,100 Class B + ~35 Class A + ~45 KV writes. `/health.backup` (`backupLine`) and the admin Bots tab "Backup" row show progress or the last finished time, avatar count and size. Simulated test: 105,330 avatars in 21 steps, at most 205 calls per step, old file intact until completion, valid JSON and every line readable by the recovery parser.

R2 billing showed 1.44M Class A + 8.1M Class B in 10 days (~144k writes and ~290k reads a day), matching 72 runs a day. The user chose to delete it outright (workflow + script). The search index, manifest and worklist are Worker-only. Its backup job now lives in the Worker (see the daily `db.json` backup note above).
