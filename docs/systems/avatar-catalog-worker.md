# Avatar catalog Worker, search index + catalog bots

_Scope: Cloudflare Worker (cloudflare/avatar-db/worker.js) flush/reconcile/fold/index behaviour by version, fill worklist, contribution dedup, liveness shard-walk bots, author renames, sweep recovery; daily db.json backup in R2; R2 outage runbook. Older version notes (v12-v39, the removed GitHub Action) are in avatar-catalog-worker-history.md. Client-side clone resolution is in avatar-catalog.md._

## Planned: live feed (not built; user, 2026-10-30)
- **Goal**: server state that moves the moment it changes, first in the admin revamp (`docs/revamp-2.md` item 11), later on the website as a public live-stats page for users. Build it once for both.
- **Shape**: the Worker hands a one-line event to a Durable Object the moment something happens; viewers hold a WebSocket to it (hibernation API: no duration billed while idle). A small recent-history ring (last ~200 events) so a new viewer isn't empty; `/health` stays the snapshot. Events, not storage: no extra R2/KV writes.
- **Events**: contribution received (who, count, names) and, at the flush, how many were really new; bot pushes (fills, calm refreshes, removes, author renames); reports in/resolved; each flush (shards, index buckets, ms, failures); queue depths and `writesToday` ticking; backup and author-rename progress; errors (R2 outage).
- **Two views of one stream**: admin (full detail, ADMIN_KEY) and public (read-only, rate-limited, no device ids or admin data; contributor names only if the user decides they're public). Decide the public field list before the website work.
- **Cost**: one tiny DO request per event; a busy day is a few thousand, inside the Workers Paid included DO requests, so about $0. Check before adding anything that writes per event.

## Version 53 (2026-10-30): search in D1, clone name files (nm/), guaranteed cache purge
- **Why**: search files (`index/` + `fragments/`) were ~80% of R2 writes (~12 writes per new avatar; October went over the 1M Class A + 10M Class B included). Clone resolve is by log name(+author) now (VRChat hides the worn avatar and its image), so it searches the catalog constantly: it must stay free (CDN), while the Search button can cost one Worker request.
- **Search step** (`searchStep`, its own invocation via `SELF /searchstep?cont=<ADMIN_KEY>`, fired by the cron after the flush, single-flight hub lock `search`): the flush only records change records `{id, f, nw, old}` per touched avatar (`searchChange`: searchable = has id + name + filled; only search-relevant field changes) into the hub queue `srq`. The step applies them to D1 + nm/ and works the purge queue. Failed or over-budget records are re-queued (idempotent), so nothing is lost.
- **D1** (binding `SEARCH`, database `vrca-search`): `av` (k = 60 bits of the avatar uuid as INTEGER PRIMARY KEY, so no extra index rows; id, f = fileId, n, nk = folded name, nb = nm bucket, ai, p = platform mask, pf = packed perf, ad), `au` (author id → name + folded name, WITHOUT ROWID; an unchanged author costs 0 writes), `avx` (contentless FTS5 over name + author + bio, raw and font-folded words, unicode61, prefix 2/3). Measured (local D1): ~3 rows per new avatar (~2 when the author exists); a search reads ~3 rows per result. Removals are conditional on the fileId (`(k,f) IN`), so a re-filed avatar's old image never deletes its new search row; in a step a put always wins over a delete for the same avatar.
- **`GET /search?q=&o=&au=`** (gremlininc.app; workers.dev works too): every word must match, the last also as a prefix; exact folded name first, then FTS rank; 500 per batch (`more` = a 501st exists); `au` = that author only (folded). Edge-cached 60 s (saves D1 reads; the request still counts).
- **nm/<bucket>.json** (4096 buckets by Java hashCode of the folded name, same fold as the app's `fancyFold`; `_manifest.json` `nmBuckets` tells the app the count so it can change without an app update): `{ v, e: { "<folded name>": [ {a, f, n, au, ai, p, pf} ] } }`. The app's clone rules run on it: no author → serve only a unique exact name; author → that author's entry. Rare fallback (author given, no exact name): D1 with `au=`. 7-day cache, purged on every write.
- **Guaranteed purge** (`purgeStep`, hub queue `pq`): every CDN write (shards, nm/) queues `{u, etag, t0}`. A job leaves the queue only when the purge API returned success AND the CDN serves the ETag R2 gave on put, or the file's CURRENT R2 ETag (a newer write superseded the job; without that an older job retried forever, seen with nm/4bd.json); otherwise it is retried every minute. `/health` `search.purgeStuck` flags a job failing for over 30 min. With that, `SHARD_TTL` is 7 days (was 6 h).
- **Backfill** (starts by itself the first time the search step sees the D1 binding with no record; `POST /admin/searchfill {key}` restarts it): phase 1 copies every shard into D1 (24 shards a step), phase 2 builds every nm/ file from D1 (256 buckets per D1 scan); rides the search step once a minute; progress in `/health` `search.fill`.
- **Kept**: the shards (4096: cloning by image id, backup, bots), `avtr/` (the free "do we have this avatar id?" check apps and the crawler do before sending), and the shards. **Old search files removed** (user, 2026-10-31): `applyIndexOps` only writes `avtr/` now (the `fragments/` + `index/` writers, `LEGACY_SEARCH_FILES` and the bot font-flag re-fold are deleted); `legacyFilesCleanup` (search step) bulk-deleted the ~8,200 old objects once (1,000 per step, then hub flag `legacyGone`). The `iq:` drain and the recount stay (they carry the avtr/ ops and the catalog count).
- **Keeping the catalog from being ripped (user, 2026-10-30)**: the full `db.json` backup and `unconverted.json` are written to the PRIVATE bucket `vrca-avatar-private` (binding `PRIVATE`, no public domain); the first private backup deletes the old public copies (and purges them). `/db` and `/unconverted` need the admin key (`?key=`); `/catalog/` only serves the files apps read (`shard|nm|avtr|index|fragments/<3hex>.json`, `_manifest`, `_worklist`). App-only reads: every app read of `cdn.gremlininc.app` sends `X-VRCA-App: <AvatarGlobalDb.CDN_APP_MARK>` (also `CDN_APP_MARK` in wrangler vars for the Worker's purge-verify fetch), and a Cloudflare WAF custom rule on the zone blocks cdn requests without it; a WAF rate-limit rule caps per-IP pulls. Older apps (no header) lose clone/search reads until they update (user accepted, 2026-10-30); contributions go to the Worker and keep working. Honest limit: the marker is in the APK, so a determined person can still copy slowly; the rate limits and the planned scraper watch (revamp-2, Admin) cover that.
- **Search speed limit** (`searchRateLimit`, user: one search per 3 s, enforced by the server so a modified app can't skip it): a new search (o = 0) once per 3 s per IP + `X-VRCA-Device` (a random install id the app sends), a further batch (o > 0, prefetch) once per 1.5 s, and 12 per 10 s per IP overall (shared Wi-Fi is fine, faked device ids don't help). Kept in Cloudflare's free per-datacenter cache under the zone's own host (`/__rl/` keys; a foreign host is silently not stored), so `/search` is served only on gremlininc.app (workers.dev has no cache: 403 there; tests set `SEARCH_ANY_HOST`). Over → 429 `{ retryAfterMs }`; the app waits it out and retries once. The app's Search button has the same 3 s cooldown (countdown Boot Cat).
- **Admin (v53)**: the Bots tab's catalog card shows `Search` (backfill: copying N/4096 · avatars, then name files N/4096, then `live · last N changes, R rows`) and `Cache clears` (`ok · last N cleared, M retrying` or `STUCK <age>`), both from the same `/health` poll; the old `Fonts waiting` / `Index queue` rows are gone. The bots no longer send font flags (`needsFontCheck` removed). The library diagnostic's `search=Y/N` reads the free name file (`isInSearchIndex(id, name)`, null until `nmReady`). The website (`/live`) only reads `/health` and `/live/ws`, so it needs nothing for v53.
- **Hub**: durable queues `/q/push` `/q/take` `/q/ack` (chunks under 100 KB, deleted only on ack) and `/lock` `/unlock`.

## Version 52 (2026-10-30): the hub (Durable Object), every minute again, and the live page
- **Hub** (`export class Hub`, binding `HUB`, SQLite-backed, `[[migrations]] v1`): one Durable Object instance (`idFromName("main")`) holds the run lock (`flushlock`), the records (`meta`: every counter, total and `wr`) and `recent` (admin recent contributions). Every run reads them fresh, so 1-min runs no longer skip each other or overwrite counts (the v50 problem). All access goes through `hubGet`/`hubPut`/`hubDel`; `meta` and `recent` are mirrored to KV on every write (a rollback to a KV-only Worker loses nothing), and on first use the hub takes over KV's copy. Without the binding the helpers fall back to KV (tests, rollback).
- **Cron every minute** again (`* * * * *`). Backup steps fire only on even minutes (their state and carry buffer stay in KV); maintenance keeps ~2 min (`cronTasksIfDue`).
- **Live feed**: each run that does something sends one event to the hub (`emit`): added, removed, shards, search files, ms, calm, queue depths, and up to 8 avatar names per batch, never who sent them. `/report` also emits. Events are broadcast over hibernating WebSockets (`GET /live/ws`, no duration billed while idle) with the last 60 kept as history. One hub request per run, not per contribution, so the cost stays flat at any volume (~130k hub requests/month at 1 min, inside the plan).
- **Live page** (`GET /live`, and `/` on gremlininc.app; `LIVE_HTML`): for testers and users, so no budget or cost data (user). VRC-A look: GremlinColors layers and Roboto, the real logo (inline SVG of `vrca_logo_vector.xml`), no gradients. Every time is UTC (clock in the top bar, labels say UTC). Laid out for the UI Lab's two sizes: headset 1024x640 shows everything on one screen (stat tiles, then a 3-column grid: catalog size + new avatars, removed avatars + waiting queues, the live activity feed spanning both rows and scrolling inside), phone 411x891 stacks to one column. Tiles: avatars (+net today), new today (+this hour), removed today (no longer on VRChat, +this hour), contributions today (batches). All-time added/removed totals are not shown (those counters only started part-way through the catalog's life, so they don't match the size). Graphs (single colour, hover tooltips): catalog size per day (30 days), new and removed avatars per hour (48 h), from the hub's totals (`/live/stats`: `hours` 48 kept, `days` 60 kept, one extra hub write per run). Feed: only runs that added or removed avatars (user), new in green and removed in red, each entry with a coloured marker; an Added group (green, each name opens its VRChat page) and a Removed group (red, struck through) built from what the flush really applied (`addedItems`/`removedItems`, up to 300 each, collected per shard only once the shard write succeeded), not from what was sent (sent batches include avatars the catalog already had) (collapsed entries show no names (user): one header row with the "+N added" and "−N removed" tags side by side, lined up with the time (no wrapping), then and "from N contribution batches" with a "Show names" button; it builds both groups on first open (up to 300 names each), "Hide names" folds them. No repeated info: the red tag carries "no longer on VRChat" as its tooltip instead of a second line. Grid columns carry `min-width:0` so long rows never widen the page). The viewer sends `hello` after connecting and the hub answers with the history plus the `hours`/`days` totals (a message sent before the 101 can be dropped).
- **Remove wins in one flush:** if the same avatar has an add/update and a remove in the same run (seen live: a fill update queued before the liveness bot found the avatar gone), the remove wins and the add, update or rename is skipped. Before this the flush re-created the avatar and then deleted it, so the catalog ended right but the live feed showed it as both added and removed and today's totals counted +1/-1. The feed's "from N contribution batches" line only shows when N > 0 (adds can come from update lanes, not batches).
- **Re-keys are not removals (feed):** when a bot sees an avatar's image changed it re-keys it: removes the old fileId and upserts the new fileId, same avatar id. The avatar never leaves the catalog, but the live feed used to show the old key as "removed" (seen 2026-10-30: four Moontail avatars, all verified still in `avtr/` presence and `fragments/`). Now the run event drops from `removedItems`/`removed` any removed avatar whose id is added or updated anywhere in the same run, and from `addedItems`/`added` any add whose id was removed in the run; `rekeyed` counts them. The hub's hourly/daily totals use these feed counts. Meta's `lastAdded`/`lastRemoved`/`entries` still count every key (exact).
- **Live page on touch screens (2026-10-31)**: charts don't select text or open the long-press menu (`user-select:none`, `-webkit-touch-callout:none`); a tap shows that bar's / point's value (a touch `pointerleave` is ignored; scrolling or tapping elsewhere hides the tip). A live update keeps the scroll position (`draw()` restores `scrollY`; a width-only resize redraws, so the phone URL bar showing/hiding doesn't), and a reconnect swaps the feed's history in one go instead of emptying it first (that collapsed the page and threw the reader back up). The feed has no scrollbar. `/health` `search.last.purgeRetry` names the files whose purge keeps failing.
- **Live page cost at scale (push-only, user: hundreds of people may leave it open):** the page never polls. On open (and on each reconnect) it makes one `/health` fetch and one WebSocket connect + `hello`; everything after that is pushed: each run event carries the counters (`entries`, `pending`, `reports`, `calmWaiting`) and the hub adds this hour's and today's totals (`hour`, `day`) so tiles and graphs update in place. Outgoing WebSocket messages are free and the hub is awake for the run anyway, so N viewers cost the same per minute as one. Keep-alive: the page pings only after 80 s with no message (runs push about once a minute, so normally never; Cloudflare drops a silent socket at ~100 s), answered by `setWebSocketAutoResponse` without waking the hub. Measured 2026-10-30: ~900 DO requests/hour (~650k/month of the 1M included), almost all the hub's own per-run reads/writes plus the apps' `/health`, `/report` and `/contribute`; viewers add ~2 per visit. Reconnects back off (3 s doubling to 60 s, jittered) so a deploy doesn't make every viewer reconnect at once. Cost per visit is about 3 requests however long the tab stays open. Don't add polling back; put new data in the run event instead. `/live/stats` is still served (30 s cache) but the page doesn't use it.
- **Tab-out reconnect (2026-10-31):** phone browsers freeze a background tab and drop its WebSocket after a few seconds, so the page used to show Reconnecting, wait out a 1.5-3 s backoff and rebuild the whole feed (collapsing what you had open). Now: while hidden it never retries (no wasted connects); on `visibilitychange` back it reconnects at once if the socket is closed or closing, and if the socket still looks open it sends one `ping` and replaces it if no reply comes within 3 s (a frozen "zombie" socket). The reconnect's `history` only adds events newer than the newest one shown (`newest`), so the feed, its open entries and the scroll position stay as they were. `drop(ws)` clears the old socket's ping timer.
- **v66 (2026-11-01) name files: meta-only changes every 12 h**: the 1 Nov cost check found R2 PutObject at ~5k/hour all day (92k on 1 Nov, a ~2.8M/month pace vs the 1M Class A allowance). Cause: the impostor correction wave (live-check bots re-checking every avatar after the impostor fix, `/health` search.last.today meta 110,016 in a day) fed name-file writes at their 150-a-step cap nonstop, and `nmApply` removed + re-appended an updated entry, which reordered a shared name's list so even unchanged files were rewritten (nmSame 14 of 86k). Now: a change that keeps the name (bio/platforms/perf only) writes D1 at once (search current) and marks its bucket in D1 `nmdirty`; `nmLazyStep` rebuilds dirty buckets from D1 every `NM_LAZY_EVERY_MS` (12 h; hub key `nmLazyAt`, isolate memory `nmLazyNext`), skipping files that come out identical (`canonNm`: names and lists in one fixed order). Adds, removals and renames still update name files at once. `nmApply` keeps lists sorted by avatar id. `/health` search.last adds `nmDirty`, `nmLazySame`. Worst case ~8k name-file writes a day (4,096 files x 2) on top of ~6k other writes: ~430k/month. (The user rejected a daily lag in v60 when cost wasn't the cause; on 1 Nov it was.)
- **v65 (2026-10-31) purge spot check**: after v64 every purge call succeeded but 150-250 files a step still "failed": checking all 400 purged files (one CDN fetch each) on top of ~300 nm/ reads+writes went past the Worker's subrequest limit, and every check past it threw and was retried. Now only `PURGE_VERIFY_MAX` (60) purged files a step are checked against the CDN (a stale one is still retried); the API's success is trusted for the rest, and a check that couldn't run is not a failure (`verifyErr` on `/health`, plus `purgeChecked`).
- **v64 (2026-10-31) purge API rate limit**: with v63 reading the whole backlog (~1,700 files were waiting), each step sent 10 purge calls of 30 and ~6 were refused every minute: the Free zone's purge API refills ~5 calls a minute (bucket 25; Cloudflare docs: developers.cloudflare.com/cache/how-to/purge-cache). That was also the older "periodic 36-40 failed" (one 30-file call refused). Now a step makes at most `PURGE_CALLS` (4, one a minute left for the manifest/worklist/index purges that call the API directly) of `purgeBatch` (100) files, stops at the first 429, and files it didn't send go back as `later`, not failed. If the API refuses 100 in a call it drops to 30 for that isolate and resends. Capacity 400 files a minute vs ~150 name files + shards written. `purgeOldestMs` now counts the oldest job still waiting (failed or not yet sent), so a backlog the limit can't clear shows honestly. `/health` adds `purgeCalls`, `purgeBatch`, `purgeApiErr`.
- **v63 (2026-10-31) purge queue can't outgrow the step; leftover name files rebuild**: "files out of date" came back during a big meta wave (~9k bio/perf/platform changes). The hub `q/take` hands out whole chunks and stops when the next won't fit, so a step asking for 150 jobs took about ONE chunk, while every step pushed two or more (its name-file jobs + its own retries): the `pq` queue grew and a retried job waited behind it past 30 min. Now `purgeStep` reads up to `PURGE_TAKE` (2000) queued jobs, merges them per file (most are the same few hundred nm/ files), purges and checks up to `PURGE_PER_STEP` (300) files and pushes the rest back (`purgeLater`, keeps the step awake). `/health` `search.last` adds `pqTaken`/`pqFiles`/`pqChunks`. Also `nmLazyStep` had failed every step since v61 ("too many SQL variables": one `IN` list of 256 buckets; D1 allows 100 bound variables), so the files v60 marked never rebuilt; it now queries and deletes in chunks of 90. Same cost per file purged (one purge-API slot + one verify fetch); fewer repeat purges of the same file.
- **v62 (2026-10-31) no false "files out of date"**: the website showed "Having issues: some avatar files may be out of date" during the Quest/iOS correction wave. Hot shards were rewritten between a purge and its check; the check then saw the CDN serving the older version and retried a job whose file had already been replaced (the newer write queued its own job), and merged jobs kept the OLDEST time, so `purgeOldestMs` passed `PURGE_STUCK_MS` (30 min). Now a job whose file's current R2 ETag isn't the job's own counts as done (only a file still at that version served stale is retried), and merged jobs keep the newest job's time.
- **v61 (2026-10-31)**: name files update at once again for every change (user: platform/rank/bio edits are rare, a day's delay wasn't the cost). Hourly R2 writes showed steady state is only ~70-110 writes/hour (~2-2.5k/day); the high daily totals were one-offs: the 4,096-file `nm/` backfill (31 Oct 01:00) and the Quest/iOS impostor correction wave (31 Oct 16-19h, ~18k). Idle minute: 12-18 hub requests → 0 (only the 5-minute check does work). ## Version 51 (2026-10-30): back to every 2 minutes (1 min needs a Durable Object)
- **Why v50's every-minute cron was reverted the same day**: Cloudflare showed the schedule as every minute, but runs still landed ~2 min apart. KV is eventually consistent: a read on another machine can return a value up to ~60 s old. The next run read the finished run's deleted `flushlock` as still fresh (`chainBusy`, 90 s) and skipped every other minute. Worse, the flush reads `meta` (counters, totals, `wr`) at the start and writes it at the end, so a 1-min run could read the record from before the previous run and overwrite it (lost counts), and the `pend:` list could show already-cleared keys. At 2 min every run is past that window, which is also why it had been 2 min before.
- **To get 1 min safely**: move the lock and `meta` (and later the queues' bookkeeping) into a Durable Object, which is strongly consistent (one instance, reads always see the last write). The planned live-feed Durable Object can hold them (a few DO requests per run, ~65k/month at 1 min, inside the included 1M). Until then: 2 min.

## Version 49 (2026-10-30): cheap shard writes, calm lane, font flags, no automatic re-index
- **Why** (Cloudflare audit with the account token): ~1M R2 writes/month normally, ~3.3M writes + ~15.9M reads in a re-index month (the $34.41 September and $9 October bills; normal is the $5 plan). Two sources: every bot `checked` bump rewrote a whole shard just to move a date (the "R2 +0 -0 (1 shards)" flush every tick), and the automatic re-index laps (FOLD_VER/FOLD_STAMP_V bumps and the 30-day re-arm) read every shard and re-queued search ops. Target after v49: ~150-250k writes/month.
- **Writes only when an avatar changes.** No "last checked" date any more: the bots walk every shard continuously (local per-app `sweptAt`, oldest first, with claims), so a server date added nothing. `walkPass` sends nothing for an unchanged avatar. A `checked` op (old apps still send them) is now only a font check in the flush: it re-folds a fancy entry whose `fz` is stale and stamps `fv`, and the shard is written only if something actually changed. The stale counter (`staleCount`, the liveness "queued" number) is gone: manifest `staleCount` and meta/`/health` `stale` are always 0.
- **Two lanes for bot upserts** (`POST /admin`). Fast lane `admu:`: fills, re-keys (new file id), removals and contributions (`pend:`) land on the next flush, with an instant CDN purge of the changed search files (capped at `IDX_PURGE_CAP` 150 per flush; the rest expire in 5 min). Calm lane `admc:<ts13>:<uuid>` (`body.calm === true`, sent by the app for refreshes of an avatar already in the catalog with the same file id): durable in KV, drained when the oldest batch is `CALM_HOLD_MS` (30 min) old or `CALM_MAX_KEYS` (300) are waiting, so one shard write carries many refreshes. A Worker restart doesn't lose them (keys are in KV). `/health.calmWaiting` shows the count.
- **No false positives (user's requirement), enforced in the flush:** every bot batch carries `__ts`; every entry stores `mt` (time of the op that last wrote it); an upsert older than the stored `mt` is ignored, and within one flush the newest op per file id wins. A calm op never creates an entry (so a calm refresh can't bring back an avatar removed in the meantime, or add one that was never contributed). `carryWorkerFields` keeps the Worker-owned fields (`fz`, `fv`, `added`) across an upsert when the text didn't change.
- **Font flags** (replace the automatic fold laps): the manifest publishes `foldV` (= `FOLD_STAMP_V`), every non-ASCII entry (name+author+bio, any UTF-16 unit > 127, `hasNonAscii`) gets `fv` when it is folded. The bots read `foldV` from the manifest (`BotController` → `AvatarCatalogSweep.setManifestFoldV`), parse `fv` from shards (`AvatarGlobalDb.Entry.fv`), and send a `checked` id only for a fancy avatar whose `fv` differs (`needsFontCheck`). So a fold change reaches every fancy avatar on the next bot lap, one write per shard that actually needs it, and plain-ASCII avatars never cost anything.
- **No automatic re-index.** `reconcileIndex` returns at once while `meta.rcDone` is set; FOLD_VER/FOLD_STAMP_V bumps and the 30-day re-arm no longer start a lap (`FOLD_VER` is historical, only shown in `/health`). A full recount lap runs only when armed by hand (`GET /admin/reconcile?key=`).
- **The daily backup does the old recount's jobs** (it already reads every shard): exact unfilled count (`lastUnfilled`), shards holding unfilled avatars (`fill`, unioned into the fill hint), and the "unconverted" font report (`unconverted.json`, sample capped at `BACKUP_UNCONV_SAMPLE_CAP` 400). The flush adopts the unfilled count once per backup like the v48 entry count (`ufAt`/`ufSum`: count + fills/adds since). Each backup step stops after `BACKUP_STEP_CHARS` (16 MB of JSON) so memory stays inside the 128 MB isolate as the catalog grows (5M avatars ≈ a few hundred steps a day, still well inside free R2 Class B reads).
- **`/health`** adds `writesToday`/`writesYesterday` (`{d, sh, ix, ot}`: shard, search-index and other R2 writes, from meta `wr`/`wrPrev`), `calmWaiting`, `foldV`, `version` 49.
- **Tested locally in Miniflare** (real worker.js, fake KV/R2): no automatic lap; contribution clonable + searchable in the same flush; fill fast; old-app `checked` on a plain avatar = no write; font flag = one write then none; calm refresh waits then lands; 3 calm refreshes to one shard = 1 write; removed avatar stays removed; newer fast op beats older calm op, and an op older than the stored `mt` is ignored; calm batch survives a restart; identical refresh = no write; calm can't create; backup computes unfilled/fill/unconverted and the flush adopts them.
- **Resharding later** (not done): at ~1.5-2M avatars shards average ~400-500 entries; going to 65,536 shards (4 hex) via the manifest `shardScheme` keeps each shard small (clone reads stay one small file). Doubling to 8192 isn't a clean hex split, so the next step is 65,536 when needed.
- **App side** (`AvatarCatalogSweep`): `pendingCalm` buffer + `enqueueCalm` (a fast op buffered for the same id wins), sent in its own pushes with `calm = true` (`AvatarGlobalDb.adminPush(..., calm)`). Re-keys stay fast. Flush readout: `+new ~calm ✓font −removed`. The Reports bot's "helping" label is Fill while there are unfilled avatars, else Liveness.

## Version 40 (2026-10-26): index queue unjammed, fonts in a priority lane, faster recount, fill-first bots
- **Why**: `/health` showed `iqDepth` pinned at 1000 (the list cap) and plain "white tiger" did not find ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ's 8 avatars. Causes found in the code: (1) the drain capped OPS (142) but `applyIndexOps` costs ~1 read + <=1 write per distinct BUCKET (~10 tokens per op → ~1,400 reads), past the ~1000-subrequest ceiling; every R2 call after that failed inside a `try/catch`, the batch still counted as applied and was deleted, so updates were silently lost. (2) Every liveness `checked` bump re-asserted a fancy entry's FULL token union, flooding the queue. (3) Each reconcile run read ~1,600 `avtr/` buckets (24 shards x ~82 entries), also past the ceiling; a failed read counted as "missing" and queued a full re-add (most of `reconcileFixed` 105k).
- **Drain** (`flushR2`): budgets distinct buckets (`opBuckets`, `bucketCap` = (600 - 2 x shard prefixes) / 2, leaving room for the same cron's reconcile/prune/rename); an op is applied only if its buckets fit, the rest stays queued. Order: this flush's contribution ops, this flush's fold ops, the `iqp:` priority lane, then the `iq:` backlog; at most 40 backlog keys read per flush (`KEY_READ_CAP`). Pre-v40 re-asserts (`isLegacyReassert`: no frag/avtr/del/rem, no `fz` marker) are dropped as they're read (`iqDropped` in `/health`). Leftovers requeue by lane. `applyIndexOps` never writes a bucket whose read threw (writing "empty + batch" would wipe it) and throws on any failed read/write so the caller requeues the whole batch (idempotent). An index-only backlog also chains (`INDEX_CHAIN_DEPTH` 10 extra steps per cron, `iqRemaining`/`iqProgressed`), so a backlog clears in about an hour; same total ops.
- **Fold stamp** (`foldSig`, entry field `fz`): a fancy entry's plain-text tokens are queued once per fold result (`foldOp`: only the folded tokens the raw ones lack, marked `fz:1`), not on every check. Adds/upserts stamp `fz` since their ops already carry the folded tokens. A CONFUSABLES change alters `foldSig`, so affected entries re-queue automatically on their next check or recount. Fold ops ride the `iqp:` lane; its keys are named `iqp:<opCount>:<uuid>` (`iqpKey`/`iqpCount`) so `/health.foldPending` ("Fonts waiting") is exact from the key list alone.
