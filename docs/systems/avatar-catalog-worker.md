# Avatar catalog Worker, search index + catalog bots

_Scope: Cloudflare Worker (cloudflare/avatar-db/worker.js) flush/reconcile/fold/index behaviour by version, fill worklist, contribution dedup, liveness shard-walk bots, author renames, sweep recovery. Client-side clone resolution is in avatar-catalog.md._

**Fancy-Unicode search index fold (Worker `version 17` + client union — makes plain-text search AND cloning find fancy-named/authored avatars)**: our catalog's search index tokenized name/author RAW, so a fancy-font avatar (ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ / 𝗪𝗛𝗜𝗧𝗘 / ＷＨＩＴＥ) was indexed under the decorative codepoints → unsearchable by plain "white tiger" in the search box AND the roster catalog resolve. Three coupled changes: **(a) Worker `tokenizeFields` NFKC-folds** each field before tokenizing (`String(f).normalize("NFKC")…`), so NEW contributions index the plain-ASCII tokens; the STORED display fields (`fragSummary.n/au`) stay RAW so the UI still shows the styled name. **(b) One-time fold re-index (`FOLD_VER`, `meta.foldVer`)**: `reconcileIndex` forces a fresh lap when `foldVer` is behind and, for every `needsFold(e)` entry (name/author whose NFKC form differs), emits an ADD index op so its folded tokens enter the index (old fancy tokens stay as harmless orphans; `applyIndexOps` no-op guards mean only the new folded tokens actually write). `foldVer` is stamped on clean lap completion; `/health` exposes it.
  **Cadence bumped `RECONCILE_SHARDS_PER_RUN` 8→24** so the one-time fold lap completes in **~5h** (was ~14h) — a real user testing plain-text search for their fancy-authored avatars was waiting out the slow lap. This is **cost-neutral vs the R2 bill emergency**: it only adds Class B shard READS per run (the near-free tier); it does NOT raise `MAX_INDEX_OPS_PER_FLUSH` (the write-rate cap). Stays far under the subrequest budget alongside flushR2 (~40 extra reads/run). **IMPORTANT drain-lag reality (verified live, corrects an earlier optimistic note)**: at 24 shards/run the reconciler EMITS fold ADD ops FASTER than the flush drains them (`MAX_INDEX_OPS_PER_FLUSH`=150/flush ≈ 75/min), so a large `iq:` backlog (tens of thousands of ops — `reconcileFixed` ≈ 48.6k on the first real fold lap) builds up DURING the lap. Because the `iq:` queue is TTL-free NOTHING is lost, but **full searchability TRAILS the read-lap completion by hours**: after the lap finishes (foldVer stamped) the backlog keeps draining at ~75/min with no new emission, taking ~4–5h to clear.
  Symptom seen on-device: a fancy author's 8 avatars where only 1 surfaces under plain "white tiger" immediately post-lap, the rest appearing gradually (random `iq:` UUID key order) as the queue drains. This is the drain cap acting exactly as expected — the raised shard-read rate speeds up when ops are ENQUEUED, not when they APPLY (that's still 150/flush, deliberately, for the R2 cost cap). **Observability (Worker `version 19`)**: `/health` now exposes **`iqDepth`** — the `iq:` queue depth in KEYS (~150 ops each), stamped into `meta.iqDepth` from the flush's existing `iq:` drain list (NO extra list op on the 15s-polled `/health`; saturates at the listPrefix 1000-key cap). Watch it tick to 0 to confirm a fold/rebuild has fully applied.

**Fold desync — "searchable in fancy font but not plain text" (Worker `version 20`, `tokenizeFields` raw ∪ folded, `FOLD_VER 3`)**: a real on-device case — an avatar authored by `ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ` was found under the fancy name but NOT under plain "white tiger", even though it was found under BOTH earlier. **Root cause**: the index stored an entry's tokens as TWO separate sets that drift apart — the **raw** fancy tokens (`ᵂᴴᴵᵀᴱ`/`ᵀᴵᴳᴱᴿ`, written by the ORIGINAL pre-fold contribution, when `tokenizeFields` did NOT fold) and the **folded** plain tokens (`white`/`tiger`, added later by the reconcile fold ADD). Since `tokenizeFields` folded, `tokensOf(entry)` returned the folded view ONLY, so `buildIndexOp`'s `rem` (computed as `tokensOf(old) − tokensOf(new)` on any rename / re-key / dedup / cull-then-partial) could strip `white`/`tiger` while leaving the raw `ᵂᴴᴵᵀᴱ`/`ᵀᴵᴳᴱᴿ` orphaned in their buckets — and vice versa. Verified live: for "Fox eboy" by `ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ`, `fox`/`eboy` (name) + `ᵂᴴᴵᵀᴱ`/`ᵀᴵᴳᴱᴿ` (raw author) were present but `white`/`tiger` (folded author) had been removed; `foldPass` was off (foldVer done) so nothing re-added them. **Fix**:
  `tokenizeFields` now emits **raw-lowercased ∪ NFKC+smallcaps-folded tokens as ONE set** from a single call, so `tokensOf` returns the union and `buildIndexOp` add/rem ALWAYS touch an entry's raw and folded forms TOGETHER — they can never desync again (a rename/remove strips both, an add adds both). The client union query (raw ∪ folded QUERY tokens) already matches either form, so both search modes work off the union index; **Worker-only, auto-deploys, no client change**. **`FOLD_VER` bumped 2→3** re-arms the one-time reconcile fold lap so every existing `needsFold` entry is re-emitted with the union tokens (restores stripped folded tokens like Fox eboy's + adopts the raw orphans as legitimate). **Cost**: no new mechanism — the fold ADDs are mostly no-ops (tokens already present → cheap R2 Class B reads, no write/purge via the existing no-op guards); only entries genuinely MISSING a token get a bucket write (the irreducible, one-time cost of making them searchable). The re-lap rides the existing `iq:` drain (watch `iqDepth`); it lands gradually while the drain is backed up by passive-harvest inflow — throttling that harvest is the lever to clear it fast (and it also cuts the R2 bill).

**Flush overrun jammed the whole pipeline — `MAX_SHARDS_PER_FLUSH` 180→60 + reconcile-before-flush (Worker `version 21`)**: after the `FOLD_VER 3` re-arm, the fold lap NEVER started — `/health` sat at `reconcileDone:true`, `reconcileCursor:0`, `foldVer:2` across many cron cycles. Root cause found by timing a manual **`GET /flush` which timed out at >60s**: under the harvest backlog, `flushR2` (180 dirty shards, each a PUT + a ~100-300ms CDN purge, plus the iq: drain) exceeded the cron invocation's wall-time budget, so it was KILLED before the cron's LATER tasks ran — `reconcileIndex` (3rd in the `ctx.waitUntil` chain, after flush + prune) therefore NEVER executed, so the fold re-arm never fired and the `iq:` queue never drained. The whole pipeline was jammed behind one overloaded flush (the ~1000-subrequest COUNT budget was fine; WALL time was the limit — CDN purges are slow HTTP calls). **Two coupled fixes**: (1) **`MAX_SHARDS_PER_FLUSH` 180→60** so `flushR2` completes well within budget (fewer PUTs + purges = also cheaper; contribution intake is slower, which is fine/desirable while harvest is the overload); (2)
  **`scheduled()` reordered so the CHEAP critical tasks run FIRST** — `reconcileIndex` → `pruneFillWorklist` → `propagateAuthorRenames` → `flushR2` LAST — so an overloaded flush can never again starve the fold lap; reconcile advances + enqueues its iq: ops every invocation, and the now-lightweight flush (last) drains them same-cycle. This is what actually lets the `FOLD_VER 3` re-index (and the general `iq:` drain) run. Watch `/health` `reconcileCursor` advance + `reconcileDone` flip to confirm the lap is progressing. Worker-only, auto-deploys, no client change, net cost REDUCTION.

**New contributions jump ahead of the drain backlog (Worker `version 22`)**: a freshly-added avatar's index op used to be APPENDED after the queued `iq:` backlog in the flush drain (`all = [...queued, ...indexOps]`), so during a big backlog (a fold re-lap leaves hundreds of `iq:` keys) a new avatar wasn't searchable until the whole backlog drained (~many flushes). Fixed: `flushR2`'s drain now puts THIS flush's own new contribution ops FIRST (`all = [...indexOps, ...queued]`) and reads only enough backlog keys to fill the remaining per-flush budget (`indexOps.length + queued.length >= MAX_INDEX_OPS_PER_FLUSH`), so a new avatar is searchable within a flush or two regardless of backlog depth while the backlog still drains with the leftover budget. Pairs with v20 (new contributions are already indexed under raw ∪ folded tokens at contribution time), so a newly-added fancy avatar is plain-text-searchable almost immediately. Worker-only, no client change, no added cost.

**Search-index stale-cache flicker + queue balloon (Worker `version 23`, `INDEX_TTL` + `MAX_INDEX_OPS_PER_FLUSH` 150→300)**: on-device symptom — a fancy-authored avatar appeared under plain "white tiger" one night, then was GONE from plain search the next morning (still found in fancy font). **Root cause 1 (the flicker): the search-index buckets (`fragments/`/`avtr/`/`index/`) were written with the 6h `SHARD_TTL`** (`applyIndexOps`'s `ttl`). That's right for the rarely-changing CLONE shards, but the search index changes constantly and is read for freshness — so a CDN purge that missed an edge (or a stale re-cache between the write and its purge) served a **6-hour-old** index bucket, making a freshly-folded avatar visible then vanish for hours. **Fix: `INDEX_TTL` = 300s (5 min)** for those three bucket types only (clone shards keep `SHARD_TTL`); a purge-miss now self-heals in 5 min and search stays consistent (costs a few more cheap R2 Class B reads on the search path; clone lookups untouched).
  **Root cause 2 (why it took hours + the tail never landed): the `FOLD_VER 3` re-lap + the reconcile's missing-from-avtr ADDs emit faster than the old 150-ops/flush drain**, so `iqDepth` ballooned (478 → 1131 keys, past the drain's 1000-key listPrefix window) and never converged — the fold lap sat at ~45% (cursor 1848/4096) after 8h. **Fix: `MAX_INDEX_OPS_PER_FLUSH` 150→300** — most queued ops are NO-OP re-adds (cheap reads, no write/purge via the guards) and `MAX_SHARDS_PER_FLUSH` is now 60 (was 180), so the flush has wall-time headroom; 300/flush out-drains the emission so the queue shrinks + the index converges. Together: the fold lands AND stays visible. Worker-only, no client change. **Note (why the per-user "passive harvest throttle" was NOT done)**: with the admin avtrdb crawl off (the default), per-user library/search harvest is small + deduped (`bulk=true`, MISS-only — a user's own already-catalogued avatars don't re-send), so it is NOT the backlog driver; the backlog is the one-time reconcile fold lap emitting faster than the 150-ops/flush drain.
  Throttling users' apps would cost an APK rollout + slower growth for ~no relief, so it was dropped in favor of the Worker-side v21/v22 fixes. **(c) Client union (`AvatarGlobalDb.unionQueryIds`)**: `searchSharded`/`candidatesFor` (→ `searchShardedPage`/`searchShardedAll`) now AND-intersect the query's RAW tokens AND its NFKC-FOLDED tokens and UNION the results (`nfkcFold`/`queryTokens`/`orderedIntersect`). Raw matches the fancy tokens still in the index (works NOW, zero transition regression — a fancy-input search keeps working); folded matches the re-indexed plain tokens (so plain "white tiger" finds a fancy avatar once its shard is folded). Ranking folds both query + entry name/author. **Cloning benefits for free**: `resolveByNameAndAuthor` searches via `searchSharded`, so its catalog query (`"$nameVariant $logAuthor"`, raw/possibly-fancy) unions raw+folded → it can't miss a fancy-authored avatar during the re-index window. Client + Worker (auto-deploys on push).

**Fold pass ate its own drain — gated+lean fold re-emit + one-time iq: compaction + no index-purge (Worker `version 24`, `FOLD_VER 4`)**: v23 still didn't surface the fancy author's 8 avatars. **Root cause (measured live, decisive)**: `entries`/`totalAdded` were FLAT and every flush was `R2 +0 -0 (59 shards)` → **no new-avatar inflow** (pend: 280–295 was a duplicate churn, no writes). `iqDepth` sat ~1181–1424 and would NOT drain because the reconcile **fold pass re-emitted an ADD for EVERY `needsFold` entry EVERY lap** (foldVer stuck at 2 → `foldPass` always on), refilling `iq:` at ~1 key/cron — exactly the rate the drain removes (~300 ops ≈ 1 key/flush). **Drain ≈ refill = permanent stalemate**, so the queue never emptied and the 8's genuine fold-repair ops stayed buried in ~1400 keys of mostly-no-op re-adds in random UUID order (a day-plus to surface, which is why "wait overnight" kept failing). The drain can't simply be cranked: `applyIndexOps` reads one R2 object per distinct fragment/avtr/index bucket, so 300 full ops already near the ~1000-subrequest ceiling alongside 60 shard writes (the v21 wall-time lesson). **Four coupled fixes (all Worker-only, auto-deploy):** **(a)
  GATE the fold re-emit** — reconcile now checks each `needsFold` entry's FOLDED tokens against their index buckets (a per-run `idxCache`, same pattern as `avtrCache`) and emits ONLY when the id is genuinely ABSENT from a folded-token bucket. Already-folded entries (the vast majority) emit nothing → the stalemate breaks, the queue stops refilling, and `foldVer` can finally stamp. **(b) LEAN fold op** — the re-emit is `{frag:null, avtr:null, add:[...tokensOf(e)]}` (fragment + avtr presence are already correct for an indexed entry), so it touches ONLY index token buckets and same-author folds (white/tiger) COLLAPSE into the same 2 buckets — a fraction of the old per-id frag+avtr read cost. **(c) ONE-TIME `iq:` COMPACTION** (`meta.iqCompactV`, `IQ_COMPACT_DELETE_BUDGET`=500/flush) — the existing ~1400-key flood is all no-op re-adds (safe to drop: `applyIndexOps` no-op-guarded them, and the re-armed gated lap + reconcile presence-heal re-emit anything genuinely missing into the emptied queue). The flush dedicates a few 1-min ticks to bounded `iq:` deletes until empty, then flips the flag. This clears the lake so genuine repairs drain in a flush or two instead of ~47h.
  **NEW contributions are untouched** — they ride `indexOps` (v22 priority) and are folded raw∪folded at contribution time (v20), so a freshly-added avatar is plain-searchable immediately regardless; compaction only drops the OLD backlog, once. **(d) NO edge-purge on index buckets** — the `fragments/`/`avtr/`/`index/` writes carry the 5-min `INDEX_TTL`, so the drain drops the slow CDN purge (the real WALL-time hog, the v21 jam cause); search freshness lags ≤5 min, clone-shard purges (user-facing) unchanged. **`FOLD_VER` 3→4** re-arms a fresh lap so the GATED pass re-scans every shard once and re-emits only the genuinely-broken (the 8 + any real desync) into the compacted queue → they surface within ~one lap (~a few hours) and it never re-floods. **Deliberately NOT done: capacity levers** (1-min cron, split cron budgets) — the measurement proved there's no inflow crisis, so adding cron frequency would raise idle KV-read cost for no benefit; the cure is reducing WORK (the flood), which is strictly cheaper.  **(Worker `version 25`: `MAX_SHARDS_PER_FLUSH` 60→120 — v24 freed the flush wall-time the index purges consumed, so intake can place ~2× the shards/avatars per tick; small batches already fuse by shard WITHIN a flush via `shardOps`+`reserve`, so this is a pure throughput raise with no ingest change, budget ~800 subrequests under the ~1000 cap.)** Shard-major cross-flush `pend:` coalescing was also deferred (within-flush coalescing already exists via `shardOps`, and duplicate batches write nothing, so cross-flush repetition costs only cheap reads, not the R2 writes that drive the bill).

**Fold lap stamped `foldVer` without covering the whole catalog — `foldLapV` dedicated-lap guard (Worker `version 26`, `FOLD_VER 5`)**: after v24/v25, `/health` showed the fold complete (`foldVer 4`, `iqDepth 0`, `reconcileDone`), growth resumed — yet plain "white tiger" STILL surfaced 0 of ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ's 8 avatars. **Verified live via the CDN index buckets** (`indexBucketFor(tok)=(javaHash(tok)&0xfff)`): all 8 were present in the RAW fancy buckets (`ᵂᴴᴵᵀᴱ`→`e74`, `ᵀᴵᴳᴱᴿ`→`a8c`, each holding exactly the 8) + their name buckets (`fox`/`eboy`) + the `avtr/74f` presence set, but ABSENT from the folded `white` (`c29`) / `tiger` (`0bf`) buckets — a genuine miss (cache-busted read confirmed, not a stale-CDN artifact). NFKC of the stored author folds cleanly (`ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ`→`white tiger`, all U+1D42-range MODIFIER LETTER CAPITALs), and `tokenizeFields`/`tokensOf` (raw∪folded), the fold gate, `buildIndexOp`, and `applyIndexOps` are all individually correct — so the code path *would* have added the folded tokens.
  **Root cause = the "one full 4096-shard lap" guarantee was not actually guaranteed for the fold pass.** The reset-to-cursor-0 that starts a fresh fold lap was gated `if (meta.foldVer !== FOLD_VER && meta.rcDone)` — so a `FOLD_VER` bump that landed **mid-lap** (`rcDone=false`, the normal state on a deploy during active churn) did NOT reset the carried-over `meta.rc` cursor + `meta.reconcileScanned` accumulator. `foldPass` (`meta.foldVer !== FOLD_VER`) then rode on top of that partial lap, which "completed" the instant `reconcileScanned` crossed 4096 (from steps already accumulated before the bump) and stamped `foldVer` having run the fold GATE over only the TAIL slice of shards scanned after the bump. Every fancy-authored entry whose clone shard fell OUTSIDE that slice (ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ's `80d` among them) kept its raw tokens but never got the plain folded ones, and with `foldVer` now stamped `foldPass` went dormant so it never retried — a general bug hitting any fancy author outside the covered slice.
  **Fix (Worker-only, auto-deploys): a `meta.foldLapV` marker makes the fold lap self-contained + idempotent.** The reset now fires on `meta.foldVer !== FOLD_VER && meta.foldLapV !== FOLD_VER` (regardless of `rcDone`): the first run where `foldLapV` is behind force-resets `rc=0`/`reconcileScanned=0`/… and sets `meta.foldLapV = FOLD_VER`, so a clean dedicated 0→4096 lap always starts; subsequent runs see `foldLapV===FOLD_VER` and don't re-reset, so the lap proceeds to completion. The completion branch stamps `meta.foldVer = FOLD_VER` **only when `meta.foldLapV === FOLD_VER`** — a partial/carried lap that merely crosses 4096 can never mark the fold done. `FOLD_VER` bumped 4→5 re-arms the corrected lap; `/health` now also exposes `foldLapV` (== `FOLD_VER` while the fresh lap runs, for monitoring). The lap re-scans every shard once (~5–6h at `RECONCILE_SHARDS_PER_RUN`=24) and emits the gated fold-repair ADDs for the genuinely-broken fancy entries (the 8 + any others) into the now-healthy `iq:` drain, so plain-text search surfaces them within roughly one lap — this time actually covering the whole catalog, not a slice.
  No cost change (same gated/lean re-emit, no index purges); only the lap-coverage correctness changed. **Confirmed live**: with the `foldLapV` lap running, a swept-vs-unswept shard comparison showed **95% of fancy fold-only entries in already-swept shards now plain-searchable vs ~8% (the contribution-time baseline) in not-yet-swept control shards** — the corrected lap repairs fancy entries as it passes, catalog-wide.

**`foldFancy` overhaul for near-total fancy-font coverage + the "unconverted" registry (Worker `version 27`, `FOLD_VER 6`; client mirror needs an APK)**: the `foldLapV` fix proved the fold WORKS but only covered fonts NFKC + the small-caps map handle — a measured scan of real data found ~5.7% of fancy name/author strings still carried a non-ASCII letter after folding (unsearchable by plain text). Root categories: **cross-script LOOK-ALIKES** (Cyrillic `аеостнмукрі`, Greek `αοευιρτκν`, IPA `ɾɳ`, Cyrillic `ғ`→f) that VRChat users spell Latin words in but NFKC does NOT fold; **decorative combining marks** (zalgo / stacked diacritics like `sʟᴇᴇͥᴘͫʏᴍͣᴏʟʟɪᴇ`) which are token SEPARATORS so they FRAGMENT a name into junk (`slee`/`ym`/`ollie`); **accented Latin** (`café`, `Nöel`); and **decorative letter-punctuation** (`ǃ`→"!" as in "ǃ ESME", `ʚ…ɞ` brackets). **`foldFancy` (+ the client mirrors `AvatarGlobalDb.nfkcFold` / `VrchatAuthManager.fancyFold`, byte-identical) is rewritten** to, after NFKC, per char: (1) DROP `\p{M}` combining marks (kills zalgo fragmentation → `sleepymollie`);
  (2) map small-caps **and** a curated **`CONFUSABLES`** table (Cyrillic/Greek/IPA look-alikes → ASCII, decorative letter-punct → `.` a separator) to plain ASCII; (3) **accent-fold ONLY accented Latin** via a per-char NFKD whose base is an ASCII letter (`café`→`cafe`) — composed non-Latin (**Hangul `가`, CJK**) NFKD-decompose to a NON-ASCII base so they're left composed and searchable in their own script (NFKD on the WHOLE string was rejected because it shreds Hangul syllables into jamo). Measured on real data this cut residual from **5.7% → 2.7%**, and the remaining 2.7% is overwhelmingly **genuine non-Latin scripts** (kana/CJK/Georgian/Hangul — real names, correctly left alone, searchable in-script), i.e. **~97% of fancy strings now fully convert and true fancy-FONT coverage is effectively complete** (100% of all non-ASCII is neither achievable nor desirable — genuine scripts aren't "broken fonts"). **The "unconverted" registry is the incremental-fix tool** (the user's ask — "a term I can fetch to find everything that didn't convert"):
  `foldResidualCps(e)` flags any entry whose folded name/author still holds a non-ASCII LETTER; the reconcile lap tallies these across the pass into a per-codepoint **histogram** + a capped **sample** of `{id,name,author}`, and on clean lap completion writes `unconverted.json` (R2, edge-cached) exposed at **`GET /unconverted`** (+ `/health` `unconverted` = distinct residual codepoint count). Workflow: `curl …/unconverted` → see which codepoints/fonts still don't convert + example avatars → add the genuine look-alikes to `CONFUSABLES` (all three files, byte-identical) → bump `FOLD_VER` → they clear on the next lap; genuine-script residuals are simply left. **`FOLD_VER` 5→6** re-arms one fresh full lap (under the `foldLapV` guard) to re-fold the whole catalog under the corrected `foldFancy` + populate the registry. **Client caveat**: the Worker (index side) benefits this lap with no app update; the client `CONFUSABLES`/accent mirror only affects the QUERY-fold + clone-resolution author compare, which needs an APK rollout — but a plain-text query (no fancy chars) already matches the Worker-folded index regardless, so the main win lands server-side immediately.

**FILL worklist was BLOATED — bots swept hundreds of already-filled shards (Worker `pruneFillWorklist`, version 14)**: `_worklist.json`'s `fill` array lists the shards the FILL bots walk (shards holding ≥1 unfilled avatar), maintained incrementally in `flushR2` (`fillHintAdd`/`fillHintDone`). But `fillHintDone` only removes a shard the bots PUSH ops for — a shard that becomes fully-filled AND all-fresh-checked (no work → no ops) is never pruned, so the worklist LEAKED (observed live: **761 listed shards, ALL fully filled, vs ~47 real unfilled avatars**). The bots then swept ~714 already-done shards for nothing → the "queued N" sat flat (nothing being filled to subtract via `filledSinceManifest`) and the walk looked endless. Fix: `pruneFillWorklist` (cron, after reconcileIndex) checks the FRONT `PRUNE_BATCH`(40) shards of the worklist each run, drops any with 0 unfilled avatars, and rotates checked-and-kept shards to the back — so the whole list self-corrects to the true set in a few minutes. It runs ONLY while the worklist is implausibly larger than `meta.unfilled` (`length > unfilled + PRUNE_SLACK`(20)), so once clean it costs 0 reads and re-arms automatically if the leak recurs. `/health` now exposes `unfilled` (live per-flush count, not just the coalesced manifest) + `fillShards` (worklist size, should track unfilled).

**ENDLESS whole-catalog shard-walk — the worklist never listed PRE-EXISTING unfilled shards (Worker reconcile + client, version 15)**: even after the prune fix, the bots' fill walk NEVER TERMINATED — it kept blind-walking all 4096 shards ("shard walk still going, should only loop once"). Root cause: `_worklist.json` (`meta.fillHint`) was maintained ONLY in `flushR2` via `fillHintAdd`, which fires only for a shard a FRESH CONTRIBUTION touches. An avatar contributed `filled=false` long ago, sitting in a shard no recent contribution touches, was NEVER added to the worklist. When the reconcile recount corrected `meta.unfilled` UP to the true value (e.g. drifted 44 → real ~500), the client saw `manifestUnfilled > 0` with those ~500 shards ABSENT from the worklist, so it fell into the client's whole-catalog oldest-swept FILL fallback (`fillOrLivenessPrefix`, bounded per `fillScanStartMs`) to FIND them — and that fallback re-armed every time the count grew (recount corrections + harvest inflow), so it blind-walked the entire 4096-shard catalog forever, slowing the app. **Fix (two halves): (1)
  Worker — the reconcile recount (which already reads EVERY shard) now collects every shard holding an unfilled avatar (`fillSeen`, accumulated across the multi-run lap in `meta.rcFill`) and, on a CLEAN lap completion, UNIONs them into `meta.fillHint` + writes `_worklist.json`** (union not replace, so a mid-lap contribution's shard is preserved; the prune trims any filled during the lap → converges to the exact set). So the worklist is now AUTHORITATIVE for every unfilled shard — freshly-contributed AND pre-existing. **(2) Client (`AvatarCatalogSweep`) — fill is now STRICTLY work-list-driven**: `fillOrLivenessPrefix`/the `fillBacklog` whole-catalog sweep + the `fillScanStartMs` machinery are REMOVED; the empty-worklist fallback is `livenessPrefix` (the due-only 30-day liveness trickle) ONLY. The bots walk the worklist, fill it, and the walk TERMINATES when it drains; an empty worklist genuinely means no fill work (no more hunting the whole catalog). Requires a reconcile lap to complete once to populate the pre-existing backlog into the worklist (it re-arms every 30 days + is maintained incrementally by the flush between laps). `/health` version→15.

**Duplicate contribution flood — bulk harvest re-POSTed already-known avatars (client, contribute `bulk` flag)**: the admin Bots tab showed a large, growing `pendingBatches` (observed 40 → 129) where EVERY flush drained `R2 +0 -0 (177 shards)` — near the `MAX_SHARDS_PER_FLUSH` cap yet adding ZERO new avatars. Cause: a single `/contribute` batch is 200 avatars and avatars scatter uniformly across all 4096 shards, so ONE batch touches ~177 distinct shards = nearly the whole per-flush shard budget → only ~1 batch clears per 2-min cron, while active-harvesting clients enqueue new ones faster → the backlog climbs. The batches were overwhelmingly DUPLICATES: `contribute()`'s authoritative dedup (`lookupShardedResult(...).status == HIT` against the fresh clone shard, `AvatarGlobalDb.kt`) only SKIPPED on a definitive `HIT` and **fell open on `UNAVAILABLE`** — and under a heavy harvest the concurrent clone-shard reads get rate-limited/time-out → `UNAVAILABLE` → the already-known avatar was re-queued and re-POSTed (a `+0` batch that still eats a whole flush). Fix:
  `contribute(..., bulk = true)` makes the BULK harvest paths queue only on a DEFINITIVE `MISS`; an `UNAVAILABLE` (can't confirm new) DEFERS instead of re-sending, and the next harvest cycle retries when reads are calm. **Liveness = ONE continuous oldest-first shard walk (replaces worklist + due-trickle + blitz)**: per the user's design, all bots now run a single unified `walkPass` that forever grabs the OLDEST-swept shard (unswept = oldest, `oldestSweptPrefix(dueOnly=false)`), one shard at a time together (shared `shardClaims`/`inFlight` so no two bots take the same shard/avatar), checks **EVERY** avatar in it (dead / author-rename / desc / perf / platform — no 30-day "due" gate), and pushes **ONE grouped write per shard** (only for avatars that actually changed; a clean shard costs just the R2 read, which is CDN-cached). On completion the shard is re-stamped `sweptAt` → back of the line, so the walk rotates through all 4096 shards endlessly and every avatar is re-verified once per full lap (~15h at 4 bots × `PACE_MS`). This is the cheapest possible steady state: reads are near-free (CDN), writes are one-per-changed-shard, and it never idles.

**Fill bots starved by the flush drip-rate — `MAX_SHARDS_PER_FLUSH` 120 → 180 (version 16)**: a large pending backlog (thousands of queued avatars across many `pend:` batches) was converted into processable `unfilled` at only 120 shards per 2-min cron, so the fill bots drained the ~400 that made it through and then sat IDLE waiting for the next flush while thousands of batches waited ("only ~400 to process even though there are so many batches"). Raised the per-flush shard cap to 180. **Explicitly NOT a cost increase**: it's the SAME set of dirty shards written once each, just drained in fewer crons instead of starving the bots (a no-op dupe shard is only a Class B read). 180 shards ≈ 360 R2 ops; with the grouped index work (≤150), prune (40), reconcile (8) and author-rename (8) sharing the cron invocation the worst case is ~700 subrequests, still comfortably under Cloudflare's ~1000/invocation limit (the reason the cap exists — a flush that exceeds it dies before clearing `pend:`, so the batches retry forever). Raising the cron FREQUENCY was rejected — it would double idle-tick KV reads (a real cost increase); more-per-flush is the no-cost lever.

**Liveness backlog (`staleCount`) was a FROZEN phantom — now computed for real (Worker, version 13)**: the Bots tab's per-bot liveness "queued N" is `manifestStale / (bots)` (e.g. `staleCount 291 / 4 ≈ 73`). The **recount** (`reconcileIndex`, already reading every entry) tallies `rcStale` (entries whose `checked` < cutoff) and adopts `meta.stale` on a clean lap; the **flush** drains it live (`staleDelta` — a `checked` bump that lands on a due entry, or a due entry removed, decrements it, folded only after the shard write succeeds, `staleCount` written into the coalesced manifest).

**Bot metadata refresh — perf rank now persists (Worker `entryEquivalent`/`buildIndexOp`, version 12)**: the bots' `liveRefresh`/`fillRefresh` already re-read per-platform **performance rank** (`perfPc/perfQuest/perfIos`, from `unityPackages[].performanceRating`) on every check and push a changed entry, but the Worker was DROPPING a perf-only change: `entryEquivalent` (shard-write skip) and `buildIndexOp`'s `relevant` (index-op skip) compared name/author/authorId/desc/filled/platforms but NOT perf — so a re-uploaded/optimised avatar's new perf rank never persisted and the search perf badge (`fragSummary.pf`) stayed stale. **RE-KEY strip — a re-keyed avatar vanished from search ("appeared then disappeared", esp. fancy authors) — `applyIndexOps` apply-ORDER fix (Worker `version 29`)**: an on-device symptom — a plain-text search for `ᵂᴴᴵᵀᴱ ᵀᴵᴳᴱᴿ`'s avatars showed one, then it dropped and a different one showed, never accumulating. **Verified live** the index buckets were STABLE + fragments intact (not a cache flicker, not the v20 raw/folded desync): the affected avatar (`Idek`) was present in the RAW fancy `ᵂᴴᴵᵀᴱ`/`ᵀᴵᴳᴱᴿ` buckets but STRIPPED from the folded `white`/`tiger` buckets, its stored author unchanged. **Root cause = `applyIndexOps` applied all ADDs then all REMs per token/avtr/frag, so a same-flush same-`avatarId` conflict resolved REM-wins.** When an avatar's image changes the Worker RE-KEYS it — `remove(old fileId)` + `upsert(new fileId)`, **same avatarId, accumulated into ONE `applyIndexOps` call** (the remove-op and add-op land in different shard iterations but the same flush `indexOps`).
  Both carry the same avatarId in the same token's posting list (`add:{id}` + `rem:{id}`); the old `for add … then for rem …` order made the stale rem DELETE the id the add just inserted → the still-alive avatar VANISHED from search until the next fold lap re-added it, then the next re-key stripped it again (the oscillation). The liveness bots re-key actively-updated avatars, so fancy-authored entries kept getting clobbered. **Fix: apply REMS before ADDS** for the index-token posting lists AND the `avtr/` presence set, and **SET before DEL** for the `fragments/` map (collect del+set independently, then let SET win) — so a same-id conflict resolves ADD/SET-wins and a re-keyed avatar STAYS searchable; a genuine delete (rem/del only, no add/set) still removes it. **No `FOLD_VER` bump / no re-lap**: the already-running fold lap's re-adds now STICK instead of being re-stripped, so the backlog converges on its own. Worker-only, auto-deploys, zero added cost (pure ordering fix).

**Fold is now maintained SOLELY by the LIVENESS bots' continuous walk — the separate reconcile fold lap is REMOVED (Worker `version 30`→`31`)**: per the user, keep BOTH the fancy (raw) and plain (folded) tokens, but stop running full fold re-laps (each `FOLD_VER` bump = a catalog-wide re-lap = write spike + the churn that kept desyncing search) — the liveness bots re-verify every avatar continuously (oldest-swept-first, ~15h/full lap at 4 bots), so they can own folding. **How the bots maintain both sets:** (1) a liveness sweep of an UNCHANGED avatar pushes a `checked` timestamp bump (`AvatarCatalogSweep.walkPass` → `okChecked` → `pushOps(..., checked)`); the flush's `checked`-bump handler, for a fancy entry (`needsFold`), emits a LEAN fold-ensure op `{del:false, frag:null, avtr:null, add:[...tokensOf(e)]}` (the FULL union, using the CURRENT `foldFancy`), `applyIndexOps` no-op-guarded per token — so both token sets are re-asserted as the bots walk, riding the `checked` write they already do (no new reads/VRChat/APK; ~1 index read per fancy avatar per ~15h lap; `needsFold` fast-skips non-fancy).

The reconcile lap still does the recount / `unconverted` registry / fill-worklist + the genuinely-absent index heal (an avatar completely missing from the index → full add), just NOT folding. Any entries currently desynced heal within ~one liveness lap. Worker-only, auto-deploys, no write spikes.
