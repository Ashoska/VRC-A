# Instance roster (headset)

_Scope: VRChat log reader, live instance member list, platform/trust/status badges, friend button, roster to admin. Clone-button resolution lives in avatar-catalog.md._

- **Instance-roster — LOG READER CONNECTED (M2 hookup shipped; roster is LIVE from the log)**: `VrcLogParser` (`com.vrca.vrchat`, PURE Kotlin, throwaway-testable) turns VRChat output-log lines into a `LogEvent` stream (`Joining wrld_…:instance~nonce`, `Entering Room:`, `OnPlayerJoined/Left <name> (usr_…)` — usr id optional for the older name-only format, `OnLeftRoom`, `Switching <name> to avatar <avatar>`) and folds them via `apply(state, event, nowMs)`/`replay(lines,…)` into an immutable `InstanceState` (location/world/nonce + a `roster` map keyed by userId, or `name:<name>` fallback). **`InstanceRosterManager` (`com.vrca.vrchat`, headset-started only)** is the glue: an idempotent `start(ctx)` launches an IO loop that folds the newest log via `VrcLogParser`, enriches each member's platform via `VrchatAuthManager.fetchUserInfo`→`prettyPlatform` (cached per userId, 300ms-paced;
  **only a SUCCESSFUL lookup is cached — a failed one (429/network) is left uncached so the 2s publish loop retries it, capped at 6 attempts; this fixed "non-friends never show a platform", they're fetched after friends so they were the ones hitting the rate limit on the initial burst and getting permanently cached as blank**), and publishes a `RosterUi{status(NEEDS_PERMISSION/NO_LOG/IDLE/LIVE), worldName, location, members[displayName,userId,platform,avatarName], logPath}` `StateFlow`. **Log-derived self-presence (plan §9 — headset only)**: on every fold the manager also calls `VrchatPipelineState.applyLogPresence(active, inWorld, location, worldName, playerCount, seedUserId, seedName)`, feeding the log-derived **location / world name / instance / player count** into the shared `VrchatPipelineState.presence` so the Discord RPC + VRChat-tab UI read it — instant, log-accurate (the roster tally matches the in-game panel), and **instance HOPS are picked up the moment the log writes `Joining wrld_…`** (no REST poll for these fields).
  The `presence` SETTER applies a **headset log override** (`applyHeadsetLogOverride`, gated `IS_HEADSET_BUILD && headsetLogActive`): every presence write (REST poll, WS self-location event, or the log seed) has those four fields replaced by the current log values while **profile fields (status/rank/pic) pass through untouched** — so REST/WS can never clobber the log location/count, yet still populate the profile. When the log isn't available (no All-files/SAF access → `headsetLogActive=false`) the setter is a passthrough so REST drives presence normally; **mobile (public/admin) is completely unaffected** (no log, `IS_HEADSET_BUILD=false`). **VRChat-closed detection → force offline**: VRChat writes no "left" line on a force-close / headset power-off, so the last state would otherwise show the user in an instance FOREVER (and the presence-driven uptime/RPC timer would never stop). "VRChat is open" is detected **primarily via `VrcaOscQuery.isServiceUp()`** — the OSCQuery client already GETs VRChat's HTTP endpoint every 250ms, so a real close (HTTP unreachable) clears its `host` within ~250ms; this is fast, reliable, and **immune to an AFK user whose log goes quiet for minutes**.
  **Log-mtime staleness (`LOG_STALE_MS` = 5 min) is the FALLBACK only** for when OSC is disabled in VRChat (no OSCQuery service): `alive = VrcaOscQuery.isServiceUp() || (now - LogRef.lastModified < 5min)`. The longer 5-min fallback avoids false-closing an idle no-OSC user; the file mtime persists across a reboot, so a fresh boot doesn't re-read a very old log as "in-instance". On stale it publishes `applyLogPresence(active=false, inWorld=false, location=null,…)`; the **active→inactive edge** in `applyLogPresence` forces the current presence to `location="offline"/isOnlineInVRChat=false/state="offline"` immediately (REST confirms on its next poll; if VRChat reopens the fresh log goes active again and re-seeds). This is what makes `VrchatUptime` (the "in VRChat" uptime + the Discord RPC counter, both keyed on `isOnlineInVRChat`) actually STOP when VRChat closes, and clears the stale instance location. Log-staleness was chosen over polling the VRChat REST location for this because it's free/on-device/no-lag (REST is the authoritative backstop once `active=false` hands presence back to it).
  This is increment 1 (log AUTHORITATIVE for those fields); the REST presence poll still runs on the headset for profile fields — a follow-up increment can gate it off for the full "zero VRChat API calls for presence" win (status via WS `user-update`, rank/pic via a one-time `/auth/user`). **Log access mirrors the reference companion (`docs/vrc-nexus-teardown.md` §4.7) — this was a REAL bug the first attempt got wrong**: (1) VRChat's Quest package is **`com.vrchat.VRChatAndroid`** (legacy `com.vrchat.oculus.quest`), NOT the guessed `com.vrchat.mobile.*`; (2) candidate dirs also include the SHARED `/sdcard/Documents/Logs`, `/sdcard/Documents/VRChat`, `/sdcard/VRChat/Logs`, `/sdcard/VRChat`; (3) direct File read (needs `MANAGE_EXTERNAL_STORAGE`) is tried first, then a **SAF folder grant** (`ACTION_OPEN_DOCUMENT_TREE`, persisted via `takePersistableUriPermission`, re-resolved from `persistedUriPermissions`, listed/read via `DocumentsContract`+`ContentResolver` with offset-skip tailing) — the SAF route is what works when `Android/data/<vrcpkg>` is File-API-blocked (Android 11+/most Horizon OS).
  It tails the newest `output_log*.txt`/`player.log`/`vrchat*.log` by byte offset (replays a new/rotated file from 0; folds only up to the last complete line). **`VrcLogParser` also parses `Joining or Creating Room: <name>`** for the world name (in addition to `Entering Room:`). **CRITICAL user-facing requirement: VRChat must have Logging = FULL** (Settings → Debug) or `OnPlayerJoined`/`Joining` lines are never written — the panel's NO_LOG state spells this out. `InstanceRosterPanel` (`com.vrca.ui.screen`, its own file, observes the flow, starts the manager on headset) renders the four states via `AccessState`: NEEDS_PERMISSION/NO_LOG show a "Grant file access" button (only when All-files is missing) + a "Choose log folder" SAF button + (NO_LOG) the Logging=FULL checklist; IDLE/LIVE show the not-in-a-world hint or live member rows (initial-circle avatar + name + platform **brand SYMBOL** — Windows-blue / Android-green / Apple-light circular glyph via `PlatformSymbol`, matching VRChat's own instance-card badges + the event-alert `PlatformSymbols`, replaced the old text chip).
  **Roster ordering + friends/self**: members are sorted **you first, then friends, then everyone else** (self via `VrchatAuthManager.getStoredUserId`, friends from the local `FriendsCacheStore` keys, 15s TTL — no API cost), each by join time; YOUR name renders **purple** (0xFFB388FF), a friend's **yellow** (0xFFFFD54F). Platform enrichment walks this SAME order as a **single-flight** pass so chips fill in top-to-bottom. **Row avatars**: each member shows their VRChat pic (VRChat+ icon → worn-avatar thumbnail, from the SAME `/users/{id}` call as platform — zero extra requests) via `VrchatImageLoader` (session-authed) with **disk cache DISABLED** so it's memory-only/temporary (evicts on leave / memory pressure, never builds up on disk); initial-circle fallback. **Self reuses the VRChat tab's already-loaded pic + platform from `VrchatPipelineState.presence`** (no fetch — self is excluded from enrichment). `pfpCache` (userId→url) clears on leaving the instance alongside `platformCache`.
  **Instant hop detection**: a `FileObserver` on the direct-file log path wakes the read loop the moment VRChat writes a line (no extra permission — rides All-files access; less CPU than polling), with the 1s poll as the fallback + the only path for SAF content URIs (unwatchable). **Non-friend platform — the REAL bug was FIELD PRECEDENCE, not rate-limiting (proven via an on-device diagnostic)**: `VrchatAuthManager.fetchUserInfo` read the `platform` field FIRST, falling back to `last_platform`. But VRChat's `/users/{id}` returns `platform="offline"` for a NON-friend (and for offline friends) while `last_platform` holds the REAL platform (e.g. `"android"`). `"offline"` isn't blank, so the fallback never fired, and `prettyPlatform("offline")→""` blanked the chip. Friends resolved only because their live `platform` field held a real value. **Fix: read `last_platform` FIRST** (`j.optString("last_platform","").ifBlank { j.optString("platform","") }`) — the reliable field for everyone, exactly what VRC-NEXUS uses (`e.last_platform`).
  Enrichment still paces (`ENRICH_PACE_MS`=500ms, 5s 429 backoff, up to `MAX_ENRICH_ATTEMPTS`=40 retries) as light insurance, but each user now resolves on the FIRST 200 — rate-limiting was never the cause (the diagnostic showed `code=200 lp='android' p='offline'`). **No disk persistence / no storage buildup**: the reader writes NOTHING per-user to disk (only the SAF tree URI pref); `platformCache`/`enrichAttempts`/`enrichInFlight` are in-memory and **cleared on leaving an instance** so RAM stays bounded to the current instance. **The BASE All-files permission ALSO has a headset-only row in Settings → Permissions** (next to Overlay/Battery, `InstanceRosterManager.allFilesAccessIntent`); the rest of the setup (folder pick, Logging=FULL) lives only on the Home panel. **`MANAGE_EXTERNAL_STORAGE` is in the HEADSET manifest ONLY** (public/admin never start the reader). **Per-user platform lookup**: `VrchatAuthManager.fetchUserInfo(ctx, userId)` (`GET /users/{id}`, PUBLIC endpoint so non-friends resolve) returns `VrcUserInfo(displayName, platform, trustRank, status, statusDescription, location)`;
  `prettyPlatform(raw)` maps `standalonewindows→PC`, `android→Quest`, `ios→iOS`, `web→Web`, blank/offline→"". **Roster→admin (Firestore) SHIPPED**: `VrcaViewModel.buildInstanceRosterJson()` (headset only, LIVE + non-empty) serialises the roster to a compact JSON array (`[{name,platform,friend,self}]`, capped 80) written as `instanceRoster` on the watched 10s `buildLivePayload` write — **zero extra Firestore cost** (rides the existing watched write). The admin detail (`UsersTab.DetailBlock`) parses it into an "Instance roster (N)" card (self purple / friend yellow names + platform pills). `firestore.rules` `selfMutableKeys()` includes `instanceRoster` (self-written, admin reads only).

**Friend button stayed greyed after the request was accepted even though the NAME already turned friend-colour**: the roster DID flip `m.isFriend` on acceptance (name recolours instantly) but the button stayed in its greyed "sent" look. Root cause: `FriendButton`'s local `sent`/`unfriended` state is `remember(m.userId)` and SURVIVES recomposition, so `justSent = sent && !isFriend` could keep the greyed styling even as `m.isFriend` turned true. Fix: the call site wraps it in **`key(m.userId, m.isFriend) { FriendButton(...) }`** — when the friendship flag flips, the button is REBUILT with fresh local state (`sent=false` → `justSent=false`) so it snaps to the Unfriend glyph in lockstep with the name colour. (Optimistic unfriend still works: tapping Unfriend sets the local `unfriended` override while `m.isFriend` is still true, so the key is unchanged and the add-glyph shows immediately; when `friend-delete` later flips `m.isFriend` false the key changes and rebuilds clean.)

**Friend button stayed greyed after the request was accepted (VRChat doesn't reliably emit `friend-add` to the REQUESTER)**: the OTHER half — when `m.isFriend` genuinely never flips because the accept never reached the cache. After you tap Add, the button greys ("sent" = `justSent = sent && !isFriend`) and only flips to Unfriend once `m.isFriend` becomes true. That relied on the `friend-add` pipeline event reaching the sender when the other person accepts — which VRChat does NOT reliably deliver to the requester, so the button sat greyed forever. Fix (`InstanceRosterManager.markFriended(userId)` + a bounded reconcile in `FriendButton`): while the button is in the greyed "sent" state, a `LaunchedEffect(m.userId, justSent)` polls `VrchatAuthManager.getFriendStatus` at 4/8/15/30/60/60s and, on `isFriend==true`, calls `markFriended` — which records the userId in a `locallyFriended` override set (`ConcurrentHashMap.newKeySet`) that is ORed into the isFriend derivation in BOTH `publish()` and `onFriendsChanged`, and immediately re-emits the flow with that member's `isFriend=true`.
  So the button flips add→Unfriend AND the name colour turns friend-yellow the moment VRChat confirms, independent of the pipeline event. Bounded (~3 min, ≤6 GETs, user-initiated only after a manual send) and self-limiting (the effect only runs while `justSent`); `locallyFriended` clears on instance leave/hop (by then the real `FriendsCacheStore` has caught up via the periodic friends refresh). Client-only.

**Friend STATUS was minutes-stale — now read from the LIVE friends cache (`friendMap`)**: a friend's status dot/text used to come only from the enrich-time `statusCache` (refreshed on the 3-min ≥10-min pfp sweep) plus the tier-2 WS push, so in practice it lagged minutes. The roster's friend snapshot is now the FULL `FriendsCacheStore` map (2s TTL, was a 15s key-set), which the pipeline WS keeps current on every friend event; `publish()` reads a FRIEND member's `status`/`statusDescription`/`trustRank` straight from that live map (falling back to the enrich cache when blank), so a friend's status reflects within ~2s at WS cadence with ZERO extra REST. Non-friend status still comes from the enrich cache + pfp poll-diff (rate-limit). Tier-2 `onFriendStatusUpdate` stays as the instant-push complement.
