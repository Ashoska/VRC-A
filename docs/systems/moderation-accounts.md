# Moderation, bans, kill switch, account lock, login transfer

_Scope: Account standing (warnings, restrictions, bans, disabled features, evidence), ban-evasion capture, kill switch, single-session hard deny, admin remote logout, move-login handoff, account-wide moderation fan-out._

### Ban-evasion capture (tri-directional)

`VrchatBanChecker` (`com.vrca.vrchat`) implements deferred ban-evasion detection across three identifier types. Identity index: `bannedIdentifiers/{identifier}` → `{ banId, type, active }`. Full record: `bannedRecords/{banId}` → `{ deviceHashes[], vrchatIds[], authUids[], displayNames[], evasionAttempts[], ... }`. **Phase 1** (on bootstrap, deviceHash + authUid known): checks `bannedIdentifiers/{deviceHash}` and `/{authUid}`; if active, defers the ban screen and stores `pendingBanId` so the new alt VRChat ID can be captured after login. **Phase 2** (after VRChat login): checks `bannedIdentifiers/{vrchatId}`; if the VRChat ID is banned, the current device/auth are appended (new-device evasion); if Phase 1 flagged the device, the new VRChat ID is captured. **`appendIdentifiersToRecord` writes atomically via a single `WriteBatch`** — the up-to-3 new `bannedIdentifiers` index entries, the `bannedRecords/{banId}` array unions (`deviceHashes`/`authUids`/`vrchatIds`/`displayNames`/`evasionAttempts`), and the `moderationEvents` audit doc all commit all-or-nothing.
  Before this, they were 5 sequential awaited writes; a mid-way process death left the record inconsistent (an index pointing at a banId whose record never listed it, or a captured identifier with no audit event). The moderationEvent uses an auto-id doc reference added to the batch via `batch.set(collection.document(), ...)`. The whole operation is wrapped in try/catch (logged, non-fatal).

**Admin kill switch**: Admin force-quits a user's app via "Kill App" (UsersTab) → account-wide batch writes **`killSignal` + `offlineAt` + `isOnlineInApp=false`** (all `serverTimestamp()`/false in the SAME `applyAccountWide` write — one write, no extra cost). The user's moderation listener reads `killSignal` and calls **`AppShutdown.killNowNoWrite(app)`** — NOT a bare `Process.killProcess`. A bare killProcess only BOUNCED the app: the four `START_STICKY` services + the `PipelineWatchdogWorker` promptly revived it. `killNowNoWrite` mirrors the swipe shutdown's guards (stamps `manual_kill_at` + `swiped_away`, cancels the watchdog, disarms `FeatureSessionStore`, stops the services, then `killProcess`+`exitProcess`) so the process STAYS dead — and the dying app still writes **zero** Firestore (the offline marker is written by the ADMIN in the kill batch, which is guaranteed to land, instead of relying on the dying process). A real user reopen clears the swipe flag (MainActivity) so the app works normally again — a kill is a force-quit, not a ban.
  - **One-shot per kill (the "reopen closes again a few times" fix)**: `killSignal` stays fresh (<60s) and is NEVER cleared, and the old `killSignalHandled` guard is IN-MEMORY (resets each process) — so a reopen within 60s re-read the same fresh signal and re-killed, bouncing repeatedly until it aged out. `handleAdminKill(killMs)` now persists **`last_handled_kill_ms`** (`vrca_remote` prefs, `commit()`) and only kills when `killMs > last_handled` (plus the ≤60s age window that blocks an ANCIENT signal on reinstall). A reopen sees the same `killMs` → skips; a genuinely NEW kill (newer serverTimestamp) still fires.
  - **Prompt + durable offline with a 7s reopen grace**: the kill batch's **`offlineAt`** is the durable marker — `isUserOnline`'s `offlineAt > lastActiveAt` flips the row offline immediately and keeps it there until the user actually reopens with a newer `lastActiveAt` (works whether or not the admin is watching; the incremental directory query already keys on `offlineAt`, and the 10s detail poll reads it, so zero extra reads). The **`killSignal`-scoped grace** (`KILL_GRACE_MS = 7s`) adds `if (killSignal within 7s of now) → offline` to `isUserOnline`, so a reopen within 7s can't instantly bounce the row back online (kill-scoped, so a normal swipe→instant-reopen still shows online right away). `killSignal` is carried on `UserRow`/`UserDetail`/`parseUserRow`/`UsersDirectoryCache`/the detail merge/`onUpdateUserRow` (all from the already-read snapshot — no new field written by the client, no extra reads).
    **Residual edge** (no worse than a normal OS force-kill): if the admin kills in the exact sub-second the user is cold-opening AND the user never reopens AND nobody's watching, the racing `lastActiveAt` can read newer than `offlineAt` → shows online until the 65-min staleness decay (or ~45s watched-stale). Deliberately NOT closing this with a tolerance on `offlineAt > lastActiveAt` — any tolerance wide enough to catch the race also risks pinning a genuine quick-reopen offline until the next hourly write.

**Single-session HARD-DENY (multi-device, same VRChat account) — replaced the old take-over**: only ONE device may use VRC-A per VRChat account. The lock doc `accounts/{vrchatUserId}` = `{ activeDevice, activeSince }` is now enforced as a **hard deny** (the previous newest-wins "take-over" + "Use here" reclaim was REMOVED). `VrcaViewModel.startAccountLockWatcher()` (re-attached per login via `presenceFlow`) reads/listens the lock: when it's free/ours → **claim** it (`claimAccount`, write `activeDevice=myHash`); when another device holds it → **`accountDenied=true`** → OSC blocked at the shared chokepoint (`refreshOscBlockGate` ORs it with `vrchatLoggedOut`/`forceUpdatePending`/`notActiveDevice→accountDenied`), Discord RPC disconnected locally (`disconnectDiscordLocally`: clears `discord_rpc_enabled`/`discord_session_seeded` + wipes WebView cookies + stops the service so it can't auto-restart), and `VrcaScreen` shows **`AccountDeniedScreen`** — a reassuring "account already registered, contact support" message (NOT scary "signed in on another device" wording) with a **"Join the support server"** button (the `config/app.discordInvite` link).
  The VRChat session + the lock LISTENER stay attached, so recovery is **automatic with no reopen**: when the holder signs out or an admin frees the lock (next snapshot absent), this device claims it and clears the deny. **Claiming now happens on EVERY login** (not just multi-device) so the next device sees a lock to be denied by — single-device users write one lock doc on login (the old "single-device never touches accounts" optimization is gone, traded for the deny guarantee). **Escape hatches (the only two)**: (1) the holder **properly signs out** of VRChat → `loggedOutSignal` → `releaseAccountLock()` deletes `accounts/{vrchatUserId}`; (2) **admin remote-logout** (below). A swipe/uninstall/reinstall leaves a stale lock → denied on the new device until one of those frees it (deliberate friction, per the user). `applyCrossDeviceSync` no longer touches the lock (content-pull only). `firestore.rules`: `accounts` `delete` is now `isOwner() || signedIn()` (a device frees its own lock on sign-out; same bounded threat as create/update — needs the high-entropy `usr_` id, only ever frees the account for its real owner).

**Admin remote-logout (VRChat + Discord, the deny escape hatch)**: UsersTab detail has **"Log out VRChat"** and **"Log out Discord"** buttons (account-wide via `AccountModeration.applyAccountWide`). VRChat: writes `logoutVrchatAt = serverTimestamp()` to every device doc on the account AND **deletes `accounts/{vrchatUserId}`** (frees the lock so the user can sign in on a new device — works even if the old device is offline). Discord: writes `logoutDiscordAt`. The user's moderation listener reads both (fresh within 60s, once per timestamp via `lastVrchatLogoutMs`/`lastDiscordLogoutMs`): `logoutVrchatAt` → `handleAdminVrchatLogout()` (`VrchatAuthManager.logout` clears the session INCLUDING saved credentials so auto-relogin can't revive it → `loggedOutSignal` → OSC gate + `releaseAccountLock` + pipeline `ACTION_STOP`); `logoutDiscordAt` → `disconnectDiscordLocally()`. Both keys are in `firestore.rules` `ownerOnlyUserKeys()` (admin-only write).

**Admin-mediated "Move VRChat login to another device" (end-to-end encrypted handoff)**: for the "user is still authed on their phone but forgot their password so they can't sign in on the headset" case. The admin (UsersTab detail → **"Move VRChat login to another device"**, shown only when the source has a `vrchatUserId`) picks a TARGET device (`TransferTargetPicker` over the raw `users` list, so a not-logged-in headset install — its own row, blank `vrchatUserId` — is selectable) and `AuthTransferCoordinator` (`com.vrca.admin`, process-lifetime scope + a `state` StateFlow the detail card observes) orchestrates a relay in which **the admin only ever sees ciphertext — never the credentials**. Flow:
  (1) admin writes a `transferRole="target"` intent to the target doc → the target's moderation listener (`VrcaViewModel.handleTransferSignal`, gated on a fresh `transferAt`, 5-min `TRANSFER_WINDOW_MS`) generates a one-time **RSA-2048 keypair** (`AuthTransferCrypto`, JCA — RSA-OAEP-SHA256 wrapping a random AES-256-GCM content key), stashes the private half transiently (`VrchatAuthManager.stashTransferPrivateKey`, in the encrypted prefs keyed by reqId), and publishes only its **public** key (`transferPubKeyOut`); (2) admin relays that pubkey to the SOURCE as a `transferRole="source"` intent → the source builds a credential bundle (`VrchatAuthManager.exportSessionBundle`: username+password+`twoFactorAuth` cookie+uid; **returns null → "no_saved_password" error** when the phone has no stored password, which the target needs since the auth cookie is IP-bound and dead on a different device), **seals it to the target's public key** (`AuthTransferCrypto.seal`), and writes the ciphertext (`transferPayloadOut`);
  (3) admin relays the sealed payload to the target → it opens with its private key (`AuthTransferCrypto.open`), imports via `VrchatAuthManager.importSessionBundle` (seeds creds+2FA cookie, then a Basic-auth `login()` — VRChat recognizes the **trusted-device cookie and skips 2FA**, minting a fresh IP-bound auth cookie; returns true **only** on a real login success), starts the pipeline headless-safely, clears its private key, and reports `transferStatus="imported"`; (4) on success the coordinator **signs the SOURCE out** (`applyAccountWide(logoutVrchatAt)` + deletes `accounts/{uid}`) so the single-session lock frees and the target's account-lock watcher claims it — making this a true **move** (only one device can hold the login). Per-phase in-memory dedup (`transferKeygenReq`/`transferSealReq`/`transferImportReq`); every device write reports status/error back so `AuthTransferCoordinator.awaitStep` (one snapshot listener per phase, 45s timeout, keyed on `transferAckReqId == reqId`) surfaces friendly errors (a target that still needs a 2FA code → `login_failed`, so **nothing changes on the source** — the transfer only completes when the target actually signs in).
  **If the target's login fails the source is never logged out**, so a bad transfer is a no-op. New keys in `firestore.rules`: `ownerOnlyUserKeys()` gains `transferReqId`/`transferRole`/`transferAt`/`transferPubKey`/`transferPayload`/`transferPeerHash` (admin-written relay/signal — the payload is ciphertext); `selfMutableKeys()` gains `transferAckReqId`/`transferPubKeyOut`/`transferPayloadOut`/`transferStatus`/`transferError`/`transferStatusAt` (the device's own side). The self-update rule checks only `changedKeys()`, so a device writing its status while admin-written owner fields coexist on the doc is allowed. The admin build's own VM never processes transfer signals (moderation listener early-returns on `IS_ADMIN_BUILD`). **Honest caveats**: both devices must be online; the source must still hold a saved password (a session established via a path that didn't store one can't be moved); and VRChat may still demand a 2FA code if the trusted-device window lapsed (surfaced as `login_failed`, source untouched). `AuthTransferCrypto` uses `java.util.Base64` (minSdk 26) so the seal/open roundtrip is JVM-unit-testable.

**Single-session lock (multi-device, same VRChat account)**: only ONE device may use VRC-A per account — now a **HARD DENY** (see "Single-session HARD-DENY" above for the full model; the old take-over/"Use here" reclaim described here was REPLACED). The lock doc `accounts/{vrchatUserId}` = `{ activeDevice, activeSince }` is claimed on every login and denies any other device. `firestore.rules` for it: `get` signed-in, `list` owner-only, `create`/`update` `signedIn()` constrained to the two keys + valid deviceHash, `delete` `isOwner() || signedIn()` (lock release on sign-out / admin remote-logout). Admin build never participates (`!IS_ADMIN_BUILD`).

**Account-wide moderation fan-out (`AccountModeration.applyAccountWide`)**: since the directory collapses all of an account's devices into one row, moderating that row must hit EVERY device on the account (else a banned user just opens VRC-A on their other phone and dodges it). `AccountModeration.applyAccountWide(db, targetDocId, fields)` reads the target's `vrchatUserId`, finds every `users/{deviceHash}` doc sharing it, and writes `fields` (merge) to all of them — target included — in a single `WriteBatch`. A target with a blank `vrchatUserId` (never logged into VRChat) has no siblings, so it writes just the target (identical to the old per-device behavior). Wired into the **account standing save** (`AdminStandingStore.save`; the old `ModerationTab` warn/ban was removed 2026-10-31), the **kill switch** (`UsersTab` `killSignal` — only the currently-open device acts on a fresh signal), and `AdminViewModel.warnUser/banUser/clearPunishment`. **Device bans (`bannedDevices/{deviceHash}`) are intentionally NOT fanned out** — a device ban is by definition per-physical-device.
  **Admin directory dedup (`UsersTab.filteredUsers`)**: the directory now COLLAPSES rows that share the same `vrchatUserId` (the multi-phone duplicates) into one representative — `preferRow()` keeps the online row, then the most recently active. Rows with a blank `vrchatUserId` (never logged into VRChat) are never merged. Dedup happens at render time over the cached list (preserving sort order); the underlying separate device docs are untouched.


### Account standing (revamp 2, 2026-10-31)

Discord-style standing: the admin gives an action (warning, restriction or ban), switches features off each for its own length, attaches evidence, and the user sees it all in the standing popup. Approved mock-ups: `uilab/StandingMocks.kt`, `ModActionMocks.kt`, `DisabledMocks.kt`.

**Data.** Full records: `standingActions/{id}` (admin-only rules): account (`vrchatUserId`, else the doc id), docId, kind, reason, title, message, adminNote, given, editedAt, active, `off` {featureKey: until ms, -1 forever}, banUntil (0 none, -1 forever), banAccount/banDevice/banOthers, level ("auto" or a level key), evidence [{id, kind, shown}], bannedHashes. The user's view: map field `standing` on every `users/{deviceHash}` doc of the account (admin-only key in `ownerOnlyUserKeys()`): {rev, level, actions[{id, kind, title, message, given, active, off, banUntil, ev[{id, kind}] (shown files only)}]}. Admin note and hidden files never reach it.

**Writes (`AdminStandingStore.save`).** Each save loads the account's records (one query), rebuilds the view and writes it with `AccountModeration.applyAccountWide` plus the legacy `warned`/`warnReason`/`banned`/`banReason` (older apps). Device bans go to `bannedDevices/{hash}` (`byStanding: true`); a hash is un-banned only if a standing record banned it before. Level: the newest live record with a manual level, else auto (ban → Banned; features off across live records: 1 Limited, 2 Very limited, 3+ At risk). A record is live while admin-active and something hasn't run out (a warning: 30 days).

**Reads (app).** The `standing` field rides the moderation listener the app already has on its own users doc: no extra reads, every admin edit shows live. `Standing.publish` → `Standing.state` (watched). Boot reads the doc once (`AppBoot` Account row) so the popup can open before the hand-off. Lengths end by the server's clock: `Standing.anchorServerTime` from the `/status` reply's `Date` header + elapsed time since power-on (a changed phone clock does nothing). `Standing.startClock` wakes when the next length ends (and each minute) and re-applies the gates.

**Feature switches (`Standing.Feature`) and where they're enforced.** `chatbox_all` (OSC block gate, `startSending`, Start sending button), `chatbox_manual` (`sendMessage`, `onMessageTextChange`, live loop, Manual Send card), `voice` (`startDictation`), `avatar_search` (`AvatarSearch.searchBatch`, search box), `avatar_clone` (`VrchatAuthManager.selectAvatar`, clone buttons), `avatar_contribute` (`AvatarGlobalDb.contribute`), `discord` (`DiscordRpcService.onStartCommand`, stopped by `applyStanding`). An active ban turns everything off (`isBanned` includes `Standing.isBanned()`). A disabled control is greyed with `StandingDisabledLine` (draining Boot Cat, "X disabled · time left", tap opens the popup). **Server blocks (Worker v58/v59, D1 table `std`, one primary-key lookup per request)**: search and contributing are also blocked by the Worker. The app sends `X-VRCA-Who: <deviceHash>.<vrchatUserId>` on `/search` and `/contribute`; every admin save posts the account's ids with the latest end for each (`/admin/standing`; a live ban blocks both); a blocked id gets 403, and its IP is marked for up to 24 h so a modified app that drops or fakes the header on the same network is still blocked (marks clear when the admin lifts or changes the block). A save whose Worker update fails says so and stays open. Clone can't be blocked by the server (it reads static catalog files and calls VRChat directly), so it stays app-side; a determined modder on a different network can still fake ids until the account system's signed pass (docs/account-system-plan.md). The app drops a contribution batch on 403 instead of retrying.

**Popup (`StandingPopup`, `app/StandingPopup.kt`).** Opens with boot's SAO `Unfold`; standing card (level, meter, disabled list with countdown cats) and actions card (collapsed feed rows: note, evidence, what it disabled); Close + Support server under the cards (banned: no Close; Support server is always enabled and reads `config/app.discordInvite` itself if the link hasn't loaded yet, e.g. during boot). Shown: from Settings ("Account standing" row), from a disabled line (`StandingPopupOpen`), and by itself when `Standing.shouldPop` (rev newer than `vrca_standing/seen_rev`, or banned) both during boot (boot holds the hand-off until it's closed; banned never hands off) and live in the app. Closing marks the rev seen.

**Evidence.** Worker v57 PRIVATE bucket (`/admin/evidence`, `/evidence/<id>`, see avatar-catalog-worker.md). The app loads shown files with the `X-VRCA-App` header and no disk cache (Coil memory only, ExoPlayer streaming); a file hidden by the admin 404s at once and drops out of the live view. Admin: `AdminStandingDialog` (UsersTab detail → "Standing", which replaced the old "Moderate" button; the Moderation tab itself is still there for raw device-ban ids): action list, add/edit page (type, reason chips, title, message, admin note, per-feature switches with lengths (switching one on picks 1 d; the picked length chip stays lit, kept per feature in `picked`), ban length + account/device/other devices, standing Auto or manual, Active, evidence upload with a User/Admin switch that re-saves at once, remove). Admin key = the Bots tab key. The evidence viewer sizes each file to its own shape (picture: drawable size on load; video: ExoPlayer `onVideoSizeChanged`, incl. pixel ratio) fitted to the screen; a fixed 16:9 video box squished phone/Quest captures. Dates in the editor and the user popup always use English month names (`Locale.UK`), never the phone's language. The Settings "Account standing" row is public/headset only (admin devices aren't moderated).

**Old ban screens and the Mod tab removed (2026-10-31).** `BannedScreen` (both copies: `VrcaApp` after the phase-2 check and `VrcaScreen`'s Home), the old warning banner (`GlobalStatusBanner`) and the admin "Mod" tab (`ModerationTab`, `ModerationTarget`) are gone; there were no old-style bans yet. Every ban and warning shows in the standing popup. The evasion check (`VrchatBanChecker` phase 1 at boot, phase 2 after a VRChat sign-in) still runs, now fed by the standing page: a save with a live ban writes `bannedIdentifiers/{id}` `{banId, type, active}` for the banned device hashes and (when "VRChat account" is on) the VRChat id, and removes only ids a standing record added (record field `identifiers`). When it finds a ban on a phone the save never reached, or the old `banned` / `bannedDevices` flags are set with no standing record, `Standing.ensureBanned` shows the popup in its banned state (a local ban kept until the app restarts, so later doc updates can't drop it; the flag case waits 3 s so a lift arriving as two updates can't leave a stale ban). The boot row says "Banned". `bannedRecords` is still admin-only, so a phone can't read the reason ("Account banned") or append to it.
