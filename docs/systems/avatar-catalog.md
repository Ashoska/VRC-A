# Avatar clone resolution + crowdsourced avatar catalog

_Scope: Roster clone button (worn-avatar id resolution), AvatarGlobalDb, avatar search, Cloudflare Worker (cloudflare/avatar-db/), search index + fancy-Unicode fold, admin catalog bots._

- **Avatar clone/wear — EXACT id resolved on tap (Quest does NOT log remote avatar ids)**: proven from a real device log — every remote avatar load is `Switching <name> to avatar <avatarName>` + `Unpacking Avatar (<name> by <author>)` + `[AssetBundleDownloadManager] Starting download of Avatar @ N MB`: **name + author only, never an `avtr_`** (the ONLY `avtr_` ids in a Quest log are the LOCAL player's own `Loading/Saving Avatar Data` lines). VRChat's API also HIDES other users' current avatar id. On **PC** the log writes the remote id in the download URL (how VRCX/NEXUS clone on PC) — Quest omits it. So a naive "harvest bare `avtr_`" approach is WRONG (it grabs your OWN id and mis-attributes it → cloning just re-selects your avatar); that earlier attempt was removed. **Instead the id is resolved ON TAP by a UNIQUE 1:1 key, not a fuzzy name guess (`VrchatAuthManager.resolveWornAvatarId`)**: (1) read the worn avatar's IMAGE file id from `/users/{id}` (`currentAvatarThumbnailImageUrl` → `file_…`, via `VrcUserInfo.wornAvatarThumbUrl`); (2) search avtrdb by the log's avatar NAME (`AvatarSearch`); (3)
  **CONFIRM** a candidate by fetching its PUBLIC `GET /avatars/{id}` and matching that avatar's `thumbnailImageUrl` file id to the worn file id (`fetchAvatarThumbFileId`/`fileIdOf`) — the image file id is unique per avatar, so this is immune to name collisions; the log's `author` (from `Unpacking Avatar (… by …)`) ranks candidates first, and a lone name+author match is the fallback when no image confirmation is possible. **Two stronger paths run BEFORE the name search** (added because the name search greyed out renamed/oddly-named avatars): **(0) NAME-INDEPENDENT image-file-id lookup** — `AvatarSearch.searchCandidatesByImageFileId(wornFileId)` queries the VRCX mirrors by the worn `file_…` id itself (invariant per upload, so it resolves even when the log name is renamed/truncated/generic/colliding; a mirror hit whose image file id equals the worn one is exact, zero VRChat calls); the NAME search then runs over **`avatarNameVariants`** (raw, bracket-descriptor stripped e.g.
  `"Ball Python (handpuppet / head puppet)"→"Ball Python"`, and the part before a ` - `/` | `/` / ` separator) merged/deduped, with forgiving fallbacks (unique name+author, then unique normalized-exact-name) so a DB whose stored name omits the log's descriptor still matches; every path stamps `AvatarSearch.Diag.lastReason` so the on-headset diag shows WHY each resolve landed (`via image file id`/`via name confirm`/`0 candidates in any DB`/`N candidates, none confirmed`); **(0b) OFFICIAL author-avatars listing** — `resolveViaAuthorAvatars`: `GET /file/{wornFileId}`→`ownerId` (the avatar AUTHOR's usr id, exact) then `GET /avatars?userId={author}&releaseStatus=public&n=100`, matching the avatar whose thumbnail file id == the worn one. A PUBLIC avatar is BY DEFINITION in its author's public list, so when VRChat permits this listing it's a true 100%-for-public path with NO third-party DB; if VRChat blocks enumerating another user's avatars (401/403) it SELF-DISABLES for the session (`authorAvatarsListingBlocked`, never burns rate limit on a blocked endpoint — logged so on-device testing reveals whether the listing works).
  Returns the `avtr_` id or **null only when the avatar is in no public database AND the author listing is blocked/doesn't contain it** (private/unindexed avatars — the one unavoidable miss). **HARD CEILING (be honest with the user)**: there is NO 100%-guaranteed method for arbitrary players — VRChat deliberately strips the avatar id from the API (`/users/{id}` hides `currentAvatar`), the website, AND Quest logs (anti-ripping); the id physically exists only in VRChat's local asset cache, which on a NON-ROOTED Quest lives in inaccessible internal storage (`/data/data/com.vrchat.VRChatAndroid/`, NOT the `Android/data/.../files` log tree — confirmed: the user sees only `output_log_*.txt` where they have access). So the DB + author-listing stack above IS the achievable ceiling — WIDENED by the crowdsourced catalog below.
  **Crowdsourced avatar catalog (`AvatarGlobalDb`, `com.vrca.vrchat`, ALL builds, ZERO Firestore) — increment 1 shipped**: a growing "extra database" that covers avatars no public DB has indexed, because **every VRC-A user can read their OWN avatar id** (from `/auth/user`) and contribute it keyed by the avatar's image FILE ID — the exact key a stranger's `/users/{id}` exposes, so an id one user contributes resolves for everyone. It reads ONE file (`avatars/db.json` in the `Ashoska/VRC-A-Image-store` repo) over the GitHub **raw CDN** with an **ETag conditional GET** (on app open + every 30 min; a 304 costs ~nothing), cached to `filesDir/avatar_db.json` for offline. `resolveWornAvatarId` consults `AvatarGlobalDb.lookup(wornFileId)` FIRST (exact, offline, reason `via global catalog`) before the DB stack, and **contributes back** every image-confirmed exact resolve (image-file-id / author-listing / name→fileid / name-confirm paths) plus the user's own current avatar (`currentAvatarCatalogEntry`→`avatarCatalogEntry`, `GET /auth/user`→`GET /avatars/{id}`).
  Contributions are queued locally (`vrca_avatar_db` prefs, survives Worker/network outage, drains on retry) and POSTed to a **Cloudflare Worker** (`AvatarGlobalDb.WORKER_URL`, `cloudflare/avatar-db/`), which is the SINGLE writer of the file: it validates FORMAT only (`avtr_`/`file_`), stashes in KV, and a **10-min cron** merges pending into the file in ONE commit; verification/culling is crowdsourced (`POST /report` dead/renamed → the Worker applies renames immediately, removes on a 2-report quorum). `GET /health` is a cheap KV-only status endpoint (entries/pending/lastFlush) for the admin live panel. The Worker holds the GitHub token as a server-side secret (never in the APK).

  `AvatarCatalogSweep` walks `AvatarGlobalDb.snapshot()` paced 1.5s/avatar via the bot session: 404/410 → remove; 200 → refresh name/author/authorId/platforms/image if changed (a changed image file id RE-KEYS: remove old + upsert new), batched (20) and pushed authoritatively to the Worker **`POST /admin`** (guarded by an `ADMIN_KEY` secret; upserts overwrite, removes hard-delete).   **The enrich INSTANT catalog-hit shortcut (`InstanceRosterManager.enrichPlatforms`) bypassed the resolver's guards — the real "clonable → robot, reopening fixes it, per-user differences" bug.** It did a bare `lookupSharded(wornFid)` and cached the result while ALSO setting `avatarIdResolvedFor`, which PERMANENTLY blocks the guarded `resolveWornAvatarId` from ever running for that member — so this unguarded shortcut was authoritative. Fixed: the shortcut now skips when `isSystemFileId(wornFid)` (loading → let the guarded loading path handle it), uses `lookupShardedResult` **HIT-only** (a transient UNAVAILABLE must NOT pin — leave it for the guarded resolver to retry), and guards `isSystemAvatar(hit)`.   **Re-add of re-published avatars (public→private→public now re-enters the catalog).** A dead report (`AvatarGlobalDb.report(...,"dead")`) now `forgetLocal`s the pairing (drops it from `map`/`avatarIds`/`sessionContributed`/`sessionContributedFiles`) so the stale local entry can't permanently short-circuit a later re-contribute; and the owner-library harvest's OWN PUBLIC uploads are checked against the **AUTHORITATIVE live clone shard directly** (`lookupShardedResult`, not the lagging `avtr/` presence index `libKnownSet`, and not the local `map`/`sessionContributedFiles` sets): MISS → re-contribute with a new `contribute(bypassLocalDedup=true)` flag that SKIPS the local `map`/session dedup (those can hold a STALE entry the admin liveness bot culled while the avatar was private — this device never ran `forgetLocal`, so the stale local entry blocked the re-add until an app restart); HIT → already present (no-op); UNAVAILABLE → transient, retry next harvest.   **Clone-button flicker + ">40s loading" — the two loops disagreed on the button state.** `publish` (every ~1s + every FileObserver wake) computed the button as SPINNER whenever a member wasn't finally resolved, while `resolveAvatars` republished it as GREY in the slow phase — so the button bounced between spinner and grey/blue every second, and the spinner reappeared past 40s. (1)
  **Worker-side reconciler (`reconcileIndex`, `cloudflare/avatar-db/worker.js`, runs every cron after `flushR2`)** — the incremental flush maintains the search index (`fragments/`+`avtr/`+`index/`) for NEW changes, but NOTHING repaired avatars whose index op was dropped in the past (the GitHub `catalog-rebuild` Action was the only reconciler, and per the user GitHub is OUT of the pipeline). `reconcileIndex` walks the clone shards round-robin (`RECONCILE_SHARDS_PER_RUN`=4/min, cursor `meta.rc` 0..4095) and, for every entry NOT present in its `avtr/<bucket>` presence set, enqueues an ADD index op to the TTL-free `iq:` queue — healing every cloneable-but-unsearchable avatar over ~one full pass (~17h at 4/min), then looping as insurance. `/health` exposes `reconcileCursor`/`lastReconcile`/`reconcileScanned`/`reconcileFixed` (the GitHub `rebuildDispatch`/`lastRebuildError` fields were removed).
