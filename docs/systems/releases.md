# Releases + in-app updates

_Scope: GitHub release upload, directed/global releases, forced updates + OSC block, per-variant fleets, update dialog + browser fallback._

- APK distribution: GitHub Releases. `githubUploadAsset()` and `githubCreateRelease()` in `ReleasesTab.kt` use OkHttp. **`githubUploadAsset` uploads to the canonical `upload_url` template returned by `githubCreateRelease`** (e.g. `https://uploads.github.com/repos/OWNER/REPO/releases/ID/assets{?name,label}`) — it strips the `{?name,label}` suffix and appends `?name=<encoded>`. It does NOT rebuild the URL from `BuildConfig.GITHUB_OWNER`/`GITHUB_REPO`. This matters because if those are a renamed/old repo, `uploads.github.com` responds with a redirect *early* (before the streamed APK body finishes), which closes the okio sink mid-`writeTo()` and surfaces as `IllegalStateException: closed` on every retry. `githubCreateRelease` already follows the moved-repo redirect during create, so its response `upload_url` is canonical — using it sends the binary straight to the right host with no redirect. The owner/repo for create-release come from `RELEASE_OWNER`/`RELEASE_REPO` GitHub Actions secrets (CI overwrites `keystore.properties` from them at build time; the committed `keystore.properties` is only used for local builds).
  `githubUploadAsset` still uses `followRedirects(false)` + a manual `Location` redirect loop (fresh `buildBody()` per hop, repeatable file stream) as a fallback. Both functions use `retryOnConnectionFailure(true)` and retry up to 5 times with exponential backoff. Error messages include the exception class name and cause chain for diagnostics.

- **Directed releases via `releases/{deviceHash}`**: Admin writes a per-device release doc to `releases/{deviceHash}` using the same schema as the global `releases/latest` doc (versionCode, versionName, downloadUrl, requiredMinCode, notes, publishedAt, publishedByDevice). The client's `checkFirestoreRelease()` checks `releases/{deviceHash}` first, then falls back to `releases/latest`. **Real-time detection**: `VrcaApp` attaches a Firestore snapshot listener on `releases/{deviceHash}` that immediately shows the update dialog when the admin pushes a targeted release — no polling delay. **The whole update-check block (VM creation + release check + listeners + `UpdateDialog`) runs BEFORE the onboarding gate in `VrcaApp`**, so a forced update overlays the first-run tutorial too — a brand-new user installs the latest version before setting anything up (the app-scoped VM is therefore created during onboarding; its init is login-independent and this is safe). The download uses Android's `DownloadManager` for in-app APK download, then triggers the system package installer. **Browser fallback (`VrcaApp` `onDownload`)**:
  `DownloadManager` is disabled/unavailable on some OEM builds (reported on Samsung Galaxy — `getSystemService` returns null or `enqueue()` throws), which made the update popup silently do nothing. The `onDownload` handler now null-checks the service and wraps `enqueue()` in try/catch; on ANY failure it falls back to `startActivity(ACTION_VIEW, downloadUrl)` to open the APK link in the browser (surfacing "opened the update in your browser instead" via `downloadError`), and if even that fails it shows the raw URL for manual download. Old app versions that only know about `releases/latest` can still be reached via the global "Release to All" flow; once they update to a version with per-device support, directed releases work forever. **ALL releases are FORCED automatically (both global and directed)** — `requiredMinCode` is no longer consulted; any newer `versionCode` makes the client treat the update as required (`InAppUpdate.parseReleaseSnap` + the `VrcaApp` per-device listener + the legacy `targetedUpdateUrl` path all hardcode `forced = true`). The `UpdateDialog` is then a non-dismissable wall (`onDismissRequest` no-ops, no "Later" button).
  **Forced updates also hard-block OSC output**: `VrcaApp` calls `VrcaViewModel.applyForceUpdateGate(true)` when a forced update is pending, which sets `VrcaOsc.blocked = true` on both the remote and local OSC senders. `VrcaOsc.sendOscMessage` early-returns when `blocked`, so EVERY chatbox transmission (typing/input/realtime, from any sender loop) is dropped at that single chokepoint — the user can't keep driving the VRChat chatbox by backgrounding the app. The gate lives on the **app-scoped VM**, so it persists after Activity destruction; it's cleared only if the pending update resolves. **Caveat (cannot be backfilled)**: force-update logic must already be present in the installed APK. Versions predating `InAppUpdate.kt`/this gate never read `releases/*` or the forced flag, so no Firestore field can compel them — the only lever they honor is the moderation ban screen (repurposable as an "update required" wall via `banReason`, but that's a manual hack, not wired up). Force-update is forward-only by nature.
  **Per-variant global releases + package guard (Option B — headset/mobile fleets are independent)**: the three flavors have DIFFERENT applicationIds (`com.scrapw.chatbox` / `.admin` / `com.gremlin.inc.headset`), so a single global `releases/latest` with one APK could soft-brick the other variant (a mobile APK force-installed on a headset can't update it → stuck on the forced wall). Two coupled fixes: (1) **variant-specific global doc** — `globalReleaseDocId()` returns `latest_headset` on the headset build, `latest` otherwise, so `checkFirestoreRelease` + the `VrcaApp` global `DisposableEffect` listener read the headset fleet's OWN doc; a headset "release to all" can never reach mobile and the existing mobile `releases/latest` is untouched (keeps updating old mobile users to the current public version). (2) **package guard** — release docs carry a `packageName` field; `releaseTargetsOtherVariant(pkg)` = `pkg.isNotBlank() && pkg != BuildConfig.APPLICATION_ID`; `parseReleaseSnap` + both `VrcaApp` listeners (global AND targeted) IGNORE a release whose `packageName` targets a different variant (blank = legacy → applies, fully backward compatible).
  Admin side (`ReleasesTab`): the publish ROUTES by the picked APK's own package (`parseApkPackage`) — a `com.gremlin.inc.headset` APK auto-publishes to `releases/latest_headset` (stamped `packageName`), anything else to `releases/latest`; the live-release panel + Retract follow the same routed doc (`currentGlobalDoc`), and a UI line spells out the target fleet. Targeted releases (`UsersTab`, `AdminRuntime.PickedApk.packageName`) also stamp `packageName` so a mistargeted APK is ignored, not soft-bricking. `firestore.rules`: `packageName` added to the `releases` `hasOnly` allowlist; `latest_headset` excluded from client self-delete like `latest`. **Rollout**: the ADMIN build gains publishing immediately; existing HEADSET clients must be updated ONCE (via a targeted release — safe, per-device, never touches mobile) to a build that reads `latest_headset` + honors the guard, after which headset "release to all" works globally; the MOBILE build needs NO update and is never endangered (nothing is written to `releases/latest` unless a mobile APK is deliberately published).

- **Update dialog redesign** (`VrcaApp.kt`): patch notes render through the same `StyledBlocks` parser inside a **scrollable area capped at ~45% screen height** (long notes used to clip the dialog). Header = title + version pill. Forced variant (the default — all releases forced) = single full-width Download button; Later only on the legacy non-forced path. Browser-fallback link kept.

### Update dialog browser fallback

The `UpdateDialog` (`VrcaApp.kt`) has a browser-download fallback TextButton ("Download failed? Tap here…") below the Download/Retry buttons that opens `info.downloadUrl` via `ACTION_VIEW` for devices where DownloadManager fails (storage perms, OEM download restrictions).
