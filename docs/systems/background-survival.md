# Background survival

_Scope: App-scoped ViewModel, headless revival, swipe vs OEM kill, watchdog, safe foreground start, OEM guidance, wakelock, WiFi lock._

### Background Survival ("works as if on-screen; only a swipe stops it")

The runtime is decoupled from the Activity so everything keeps running while backgrounded, and recovers after an OS kill:

- **App-scoped ViewModel**: `VrcaApplication` implements `ViewModelStoreOwner` with a process-lifetime `ViewModelStore` (cleared only by `AppShutdown` on swipe). `VrcaViewModel` is obtained against it (`VrcaApp.kt`, `OverlayService.kt`), so the chatbox OSC senders, moderation/kill listener, NowPlaying consumer, and Firestore sync loops survive Activity destruction (`onCleared` only fires on a real swipe). The Factory uses `VrcaApplication.instance` (CreationExtras has no `APPLICATION_KEY` against an app store) and a plain `SavedStateHandle()` (an app `ViewModelStoreOwner` has no `SavedStateRegistry`, so `createSavedStateHandle()` would throw).

- **Headless ViewModel recreation**: after an OS kill the watchdog / `START_STICKY` / `BootReceiver` bring back `KeepAliveService` with no Activity — so everything the app-scoped VM owns would stay dead. `KeepAliveService.onStartCommand` calls `VrcaApplication.ensureRuntimeViewModel()` (idempotent, main-thread `ViewModelProvider` create) **ALWAYS on revival** (after the swipe guard, which returns `START_NOT_STICKY` for a deliberate swipe — so this only runs for a genuine OS kill). **This is NOT gated on `sending && anyEnabled`** — that gate was a real bug: the VM owns the chatbox senders AND the hourly liveness heartbeat (`startHourlyHeartbeat`)
  AND the moderation/watch/kill listener, so withholding it from a non-OSC-sending user (e.g. a Discord-RPC-only user) left their process genuinely alive (services + Discord RPC running) but reporting itself **permanently offline** to the admin — `lastActiveAt` froze (no heartbeat), and the moderation listener never re-attached so `watcherActiveAt` was never read → `AdminWatchState.isWatched` never flipped → neither the VM live-sync loop nor the service presence loop wrote → **the admin detail never updated and Kill/toggles never reached the device** (the symptom: "user is clearly online in Discord but shows offline / detail won't update no matter how long I spectate"). Liveness + moderation are runtime concerns independent of whether OSC is sending, so the VM must always come back. **OSC transmission stays separately gated** — `restoreFeatureSession()` only calls `startSending()` when the persisted session had `sending && anyEnabled`, so always-rebuilding the VM never makes a configured-but-idle user start transmitting. The cost of an idle revived VM is trivial (1 hourly heartbeat write + 1 moderation listener — the same cost any online user pays) and the process is already awake via the foreground services + wakelock.

- **Discord RPC / presence / notifications / timer** self-restore via the service layer: `VrchatPipelineService` restarts (sticky/watchdog/boot), auto-relogins from EncryptedSharedPreferences, and on `onOpen` re-reads `discord_rpc_enabled`+`discord_session_seeded` (DataStore) to auto-start `DiscordRpcService`; the RPC online timer has its own grace-window restore.

- **`PipelineWatchdogWorker`** (WorkManager, ~15 min): if logged in and the pipeline isn't connected, restarts `KeepAliveService` + `VrchatPipelineService`. Backs off when `AppShutdown.isManualKillFresh() || AppShutdown.isSwipedAway()` — the persistent `swiped_away` flag is what prevents this worker (which fires ~15 min after a swipe, long past the 15s freshness window) from resurrecting a deliberately-swiped app. An OEM/OS kill leaves the flag false, so the watchdog still recovers that. `BootReceiver` clears the swipe flag, restarts `KeepAliveService`, and reschedules the watchdog. `onTaskSwiped` best-effort calls `PipelineWatchdogWorker.cancel()`; `MainActivity.onCreate` re-schedules it on reopen.

- **Safe foreground promotion (`Service.startForegroundSafely`, `com.vrca.app.ForegroundUtil`) — the "OEM kill → crash-loop on every reopen until reboot" fix**: the app targets **SDK 34**. On Android 12+ starting a foreground service from the BACKGROUND throws `ForegroundServiceStartNotAllowedException`, and on Android 14 the `dataSync` FGS type is itself background-start-restricted. After an OEM process kill, three background paths re-enter the FGS-promoting services — the OS's queued `START_STICKY` restarts (every service returns `START_STICKY`), the `PipelineWatchdogWorker` (`startForegroundService` from a background Worker), and the pipeline `onOpen` Discord-start. The `startForeground()` calls in `VrchatPipelineService.onStartCommand`, `DiscordRpcService.onStartCommand`, and `OverlayService.startAsForeground` were **UNWRAPPED**, so a background-initiated start threw an uncaught exception that crashed the whole (shared) process.
  This became a CRASH LOOP: every queued sticky-restart re-crashed the process, which **also took down the Activity the instant the user reopened the app** — so the app "kept crashing on open" until a phone REBOOT cleared the OS's pending sticky-restart queue (after which `BootReceiver`, an FGS-start-EXEMPT boot context, started the pipeline cleanly → `isConnected` → later starts re-assert safely). **`KeepAliveService` had the SAME latent crash by a different name**: its `startForeground` WAS wrapped, but the catch did NOT `stopSelf()`, and since the service is launched via `startForegroundService()`, a caught failure that leaves the service running triggers `ForegroundServiceDidNotStartInTimeException` ~5s later → crash. **Fix**: `startForegroundSafely(id, notif, tag)` wraps `startForeground` in try/catch and, on failure, logs + calls `stopSelf()` (satisfying the `startForegroundService` 5-second contract without a crash) + returns false; each `onStartCommand` returns `START_NOT_STICKY` on a false result so the OS does not immediately sticky-restart back into the same throw.
  Applied to all four services (KeepAlive's catch now also `stopSelf()`s; the pipeline's 10s notif-repost loop is wrapped too). Consequence: after an OEM kill the background watchdog/sticky paths can no longer crash — they degrade to a clean no-op, and the app recovers normally on the next user-foreground launch (or once battery-optimization exemption permits a background FGS start). This is purely a crash-safety fix; it does NOT change when a foreground start is *allowed* (still gated by Android's background-FGS rules), only that a *disallowed* one no longer kills the process.

- **OEM-specific power-management guidance (`OemPowerGuidance`, `com.vrca.ui.common`)**: the four FGS + wakelock + watchdog keep the process alive on stock Android, but Samsung/Xiaomi(MIUI/HyperOS)/Huawei-Honor/Oppo-Realme(ColorOS)/Vivo-iQOO/OnePlus ship proprietary killers that force-stop background apps **regardless** of the standard battery-optimization exemption — the only fix is the user adding VRC-A to that OEM's allow-list (Autostart / Protected apps / Never sleeping apps / App launch). `OemPowerGuidance.forThisDevice()` matches `Build.MANUFACTURER`/`Build.BRAND` and returns a `Guidance(brand, steps)` with exact per-OEM menu paths, or **null** on stock/Pixel/Motorola (UI shows nothing extra). Surfaced in the onboarding Permissions step's "Turn off background restrictions" card (replaced the old Samsung-only `TrustNote`) and in Settings → Help "Stops sending with screen off" FAQ. No em dashes (onboarding copy rule). This is the highest-leverage real-world survival improvement — no app code can override these killers, so guiding the user to the right setting is the only lever.

- **Bounded re-acquired wakelock (`KeepAliveService`)**: the `PARTIAL_WAKE_LOCK` is acquired with a 6h timeout (`WAKELOCK_TIMEOUT_MS`) and **re-acquired on every 30s tick** (`TICK_MS`) instead of a single indefinite `acquire()`. Android explicitly warns against indefinitely-held wakelocks and some OEMs force-release them; a bounded acquire reset each tick is "held forever" in practice while self-releasing the moment the tick loop dies (process teardown). Non-reference-counted, so a fresh timed `acquire(timeout)` just resets the timeout — no release/re-acquire dance.

- **WiFi lock (`KeepAliveService.ensureWifiLock`, both builds)**: alongside the wakelock, KeepAliveService holds a `WifiManager.WifiLock` (`WIFI_MODE_FULL_LOW_LATENCY` on API 29+, else `FULL_HIGH_PERF`; non-ref-counted, re-asserted each 30s tick, released on destroy/swipe; `ACCESS_WIFI_STATE` in the manifest). **This mirrors the reference companion (its ChatboxService holds `PARTIAL_WAKE_LOCK` + a WiFi lock) and is the second half of the headset "chatbox/avatar-size randomly stops, reopen fixes it" fix** (the first half is the OSCQuery-host send reroute above). Root cause of the fault: Wi-Fi power management sleeping/re-associating the radio re-evaluates the PROCESS's default-network binding (fwmark/`SO_MARK`), and after that transition outbound UDP to `127.0.0.1` is stamped for the Wi-Fi routing table (no loopback route → silently dropped, `send()` still "succeeds") — per-process, so a fresh socket doesn't help but an app reopen does (fresh process re-binds to a healthy network). The WiFi lock keeps the interface awake + the binding STABLE so that transition never fires.
  It also keeps the VRChat WebSocket / Discord gateway / Firestore alive when backgrounded/screen-off (a general background-survival win, not headset-only). `WIFI_MODE_FULL_LOW_LATENCY` degrades to `FULL` when backgrounded — still radio-awake, which is exactly the stay-connected behavior wanted. Tradeoff: higher Wi-Fi power draw 24/7 (consistent with the app already holding a wakelock + foreground services); acceptable for a companion app whose premise is "works as if on-screen."

- **Revocable-grant ON_RESUME re-check (Home `SetupHealthCard`)**: an OEM update (notably Samsung One UI) can silently REVOKE the battery-optimization exemption or Notification Access while VRC-A is backgrounded. The Home page's `LifecycleEventObserver` re-reads `isIgnoringBatteryOptimizations` + `NotificationManagerCompat.getEnabledListenerPackages` on `ON_RESUME` (not just composition entry), so the setup-health card re-surfaces the now-red item the moment the user returns instead of staying falsely green until a full recomposition.

- **Limits (be honest with users)**: no app can guarantee the OS never kills it. Survival depends on the **battery-optimization exemption** (requested via `VrcaViewModel` / surfaced on Home + Settings) and the OEM allow-list guidance above (`OemPowerGuidance`). The architecture above maximizes survival AND makes the residual kill invisible via auto-restore.
