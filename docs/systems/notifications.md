# Notifications (Android + backfill + dedup)

_Scope: Channels/toggles, offline backfill, group posts/events/calendar, baselines, seenNotifIds, tap actions, reconnect notification behaviour, app update/admin announcement/status-page notifications, persistent notification icons._

- **Notification system**: Seven Android notification channels — `vrca_pipeline` (background service, MIN), `vrca_friends_activity` (online/offline/world/status/avatar/rank), `vrca_friend_requests` (incoming requests + new friends + messages), `vrca_friend_removals` (unfriends), `vrca_invites` (world + group invites), `vrca_groups` (announcements/queue/role/etc.), `vrca_connection` (pipeline disconnect + sign-in alerts + server alerts). Legacy `vrca_vrchat_events` is deleted on upgrade. The "VRChat connected / Monitoring VRChat events" notification is intentionally NOT fired — the persistent foreground service notification already conveys that state, and the duplicate notification was redundant. `fireConnectionNotification(true)` only cancels any leftover disconnect notification from a previous cycle. Notifications use `setGroup()` keys (`vrca_group_friends`, `vrca_group_social`, `vrca_group_invites`, `vrca_group_groups`) so multiple events stack in the shade with summary notifications; summary notifications use `GROUP_ALERT_CHILDREN` to prevent double notification sounds. Per-friend cooldowns (60s) on chatty events (location, status, avatar).
  Bio uses the grouped notification model instead of cooldowns — every bio change is captured as a separate event in the in-app alert group. **Bio change detection fires on edit, clear (text→empty), AND add (empty→text)** — the prior code required both old and new bio non-blank, so clearing a bio or adding one to an empty bio never fired. The live `handleFriendUpdate` path gates on `user.has("bio")` so partial location/status payloads (which omit the field) don't false-fire; empty sides render as `(empty)` in the diff. Notification titles reflect the action ("cleared their bio" / "added a bio" / "updated bio"). All 27 toggles live in `VrchatNotificationPrefs` keys + `UserPreferencesRepository` flows. The UI lives in `LegacyPagesAndSettingsPage.kt`'s `NotificationToggleSection` (public, called from `VrcaScreen.kt`). Each `ToggleRow` has an optional `description` parameter showing muted `bodySmall` text explaining what the toggle does. Organized into 5 collapsible sections with sub-section labels for visual grouping:
  Friend list (4 toggles), Friends activity (10 toggles, sub-grouped into Presence / Profile changes / Alerts), Invites (3 toggles: world invites / invite requests / group invites), Groups (6 toggles, sub-grouped into Updates / Management), App and connection (6 toggles, sub-grouped into App / VRChat). Each section is expandable/collapsible via `AnimatedVisibility` with fade+slide animation. The `SubSectionLabel` composable renders muted-color `labelMedium` text between toggle groups. The `KEY_NOTIF_INVITE_REQUEST` flow falls back to `KEY_NOTIF_INVITE` until the user explicitly toggles it, so existing users who had the combined invite preference enabled keep getting invite-request notifications.
  - **Offline notification backfill**: On every successful pipeline connect, `backfillOfflineNotifications()` runs a REST sweep across VRChat endpoints (`/auth/user/notifications`, `/auth/user/notifications/v2`, `/users/{id}/groups` + per-group `/groups/{id}/posts` and group events). The posts sweep is the sole announcement source — `fetchGroupAnnouncement()` (the single pinned announcement) was removed from both backfill and poll loop because the posts endpoint already returns the pinned announcement as one of its posts, and having both caused duplicate notifications (`ga_` vs `gp_` dedup IDs for the same content). **`fetchGroupPosts` parses VRChat's wrapped response** (`{"posts":[...],"total":N}`) as well as a bare array. **`fetchGroupCalendarEvents`** hits the correct VRChat group-calendar endpoint **`GET /calendar/{groupId}?n=N`** first (returns `{"hasNext":bool,"results":[...],"totalCount":N}`), with the legacy `/groups/{id}/events` and `/groups/{id}/calendar` paths kept only as 404 fallbacks.
    The prior code used `/groups/{id}/events`/`/scheduledEvents`/`/calendar` which all 404'd — so the calendar sweep always returned null and events created while the app was closed never surfaced (the only event source was notification-v2, which VRChat drops from the pending feed once marked seen server-side). Parses `results`, `events`, `calendarEvents`, `scheduledEvents` array keys or a bare array. `fireGroupCalendarEvent()` is the shared helper (backfill + poll loop) that fires each new event (dedup `${groupId}_event_$eventId`, seen-marker = `startsAt`) into the `event_$groupId` in-app alert group with URL `/home/group/$groupId/calendar/$eventId`. `seedBackfillBaseline()` seeds recent post IDs and calendar event IDs so the first run doesn't flood pre-existing items. A one-time migration (`posts_events_baseline_v2` DataStore flag) re-seeds posts/events into the existing seenMap for users who installed before `fetchGroupPosts` was fixed — `seedPostsAndEventsIntoExistingMap()` merges without overwriting.
    A SECOND one-time migration (`calendar_baseline_v3` flag) runs `seedAllCalendarEventsBaseline()` which seeds **ALL** current calendar events (past AND upcoming) into the seenMap + event fingerprint set without firing — necessary because the old calendar endpoint always 404'd, so no events were ever seeded; without this baseline the first working `GET /calendar/{groupId}` sweep would fire every pre-existing upcoming event at once. After this baseline only events created later surface as new. A THIRD one-time migration (`posts_events_baseline_v4` flag) re-runs `seedPostsAndEventsIntoExistingMap()` because the **group posts/calendar fetch window was RAISED** (posts `20 → 50`, events `→ 100` in both the backfill sweep and `seedPostsAndEventsIntoExistingMap`) so a group's many repeating-event occurrences can no longer crowd genuine posts/events out of the fetch. Raising the window exposed OLDER posts + past events that were never in the seen baseline (seeded at the smaller window) — the catch-up path then fired them as "new" (the tester-reported "spammed with a bunch of old announcements from ages ago, only on the new version" regression).
    The v4 re-seed covers the now-larger window once (all posts + PAST events only; genuinely upcoming events stay unseeded so they still surface once as intended), so the newly-visible older items don't fire. Runs in `backfillOfflineNotifications` right after the v2/v3 gates, before the posts/events sweep. **INSTALL-TIME cutoff (`notif_install_time_ms` Long — the real fix for the tester-reported "Announcement from &lt;group&gt; spam on login, on ALL branches")**: the v2/v3/v4 one-off migrations only patch specific window changes; the next window growth floods again. The robust fix is a hard **install-time cutoff**: a group announcement (post) whose `createdAt` is BEFORE install is **ignored forever** (recorded seen, never fired), while post-install ones still fire even if missed — exactly "only ignore announcements made before the app was installed." `ensureInstallTime()` loads `notif_install_time_ms` (set to `now` on first-run for a fresh install; for an existing user with none recorded it anchors `now` once on the first backfill after this fix, so their pre-fix backlog is ignored once and only new announcements fire thereafter).
    `isPreInstallAnnouncement(createdMs)` = `createdMs in 1 until installTimeMs` (a 0/unknown timestamp or unloaded cutoff fires as before). Applied at ALL THREE catch-up firing points: the backfill posts sweep, the 5-min poll posts sweep, and `processV2Notification`'s announcement/post branch. **Deliberately NOT applied to EVENTS** — an event created pre-install can still be UPCOMING (keyed on `startsAt`), so it should still fire; only `createdAt`-based announcements use the cutoff. This REPLACED an earlier per-version-reseed attempt (which wrongly swallowed the whole current backlog on every update, dropping post-install-but-unseen announcements — the user wanted only PRE-install ones ignored). It seeds ALL posts but **only PAST calendar events** (startsAt already elapsed); upcoming events are intentionally NOT seeded so the backfill sweep fires them once and users see events they missed while closed (per-event dedup stops re-fires). **Cross-dedup, two flavors**: (1) announcements/posts use a CONTENT fingerprint (`announcementContentFingerprint(groupId, title, text)`) added to `seenNotifIds` when fired from any path, checked by the other paths.
    **The fingerprint is BODY-based** (`ann_fp_<groupId>_<normalized-body.hashCode()>`, body = `text.ifBlank{title}` lowercased + whitespace-collapsed + first 120 chars). The title is intentionally EXCLUDED: the live notification-v2 path keys on the `message` field while the REST group-post path keys on the `text` field and they title the same post differently, so a title-inclusive key produced two different fingerprints for one announcement and the dedup missed. **The 5-min poll posts sweep now calls `isContentFingerprintSeen()` before firing** (it previously only checked its own per-post `notif_group_announcement_seen` timestamp map, never the fingerprint the live path set) — this was the cause of "an announcement fires once when the group posts it, then AGAIN a few minutes later" (the live WS path fired immediately; the poll re-fired because it didn't consult the live fingerprint). Now the poll records the seen timestamp and skips when the body fingerprint is already present. (2)
    **EVENTS use an ID-keyed fingerprint** (`eventFingerprint(groupId, eventId)` → `evt_fp_<groupId>_<eventId>`) shared across the WebSocket live handler, `processV2Notification`, and `fireGroupCalendarEvent` (the REST sweep). The content fingerprint was WRONG for events: distinct events frequently share a generic title ("Event starting") and the same 80-char text prefix, so a content key collided and suppressed all but the first event — the cause of "only one event shows even when the group made several". The eventId-keyed fingerprint dedups the SAME event across the three paths (all extract the same `cal_xxx` id) without colliding sibling events. Fires missed notifications through the same `fireEventNotification` flow with dedup IDs. **Staleness filters**: only *transient* notifications older than 24h are skipped via `parseVrcTimestampMs()` on the `created_at` field — V1 invites/requestInvite/votetokick/message, and V2 invite/queue/join-request/instance. **Catch-up types are exempt from the age cutoff** and fire regardless of age:
    V1 `friendRequest` (pending state until accepted/declined), V2 announcement/post/event/calendar and role/transfer, and group announcements/posts (backfill + poll loop). This is safe because the per-item dedup (`seenNotifIds` for V1/V2, the `notif_group_announcement_seen` per-group timestamp map for group REST) already guarantees each one fires exactly once. A user offline for a week still receives the friend requests, role changes, and group announcements/events they missed, while already-seen items never resurface. The first-run baseline guard (below) prevents a flood on fresh install. Announcements from the same group are grouped together via `alertGroupKey = "announcement_$groupId"`. **Group name resolution**: a `groupNameCache` (groupId → name) is populated whenever `fetchUserGroups()` runs; `resolveGroupName(groupId, sender)` looks up the cache first, falls back to the sanitized sender username (rejecting `null`/blank/`someone`), then `"a group"` — so notifications never render "Announcement from null".
    `resolveGroupNameAsync()` is the suspend variant used by live + backfill group announcement/event paths: when the groupId isn't cached and the sender name is missing, it fetches the group's real name once via `VrchatAuthManager.fetchGroupName(groupId)` (`GET /groups/{id}` → `name`) and caches it — this fixes group **events** rendering "Event from a group" because event payloads frequently omit `senderUsername`. **Event/announcement timestamps**: `fireEventNotification` accepts `eventTimestampMs`; announcement paths pass the parsed `created_at`/`createdAt` so the in-app alert shows when the announcement was actually posted. **Calendar EVENTS show when they BEGIN, not when the series was created (tester-found "events show a really old date like 65d ago").** The old code used `createdAt` for the event display timestamp — but for a REPEATING event `createdAt` is when the SERIES was created (often months ago) even though each occurrence is upcoming, so it read "65d ago". Fixes: (1)
    `formatRelativeTime` (`VrchatPage.kt`) is now **future-aware** — a future timestamp renders "in 1d" instead of clamping to "just now" (the negative-delta bug that originally forced the `createdAt` workaround); (2) the display timestamp is now the event's scheduled **`startsAt`** (falling back to `createdAt` only if absent); (3) the shared **`buildCalendarEventBody(desc,title,startsMs,endsMs,createdMs)`** helper builds the alert body as `description` + **`Starts: <date·time>` / `Ends: <date·time>` / `Posted: <date>`** lines (device-local via `formatEventDateTime`/`formatEventDate`), so the alert surfaces made-time AND begin/end together. All THREE event paths use the helper + `startsAt` display: `fireGroupCalendarEvent` (REST sweep, reads `startsAt`/`endsAt` off the calendar object), the live WS notification-v2 handler, and `processV2Notification` (both pull `startsAt`/`endsAt` from the payload top-level or nested `data`/`details`). The change marker (re-fire detection) still tracks `startsAt` then `createdAt` so an edited start time re-fires. **Periodic group polling**:
    `startGroupAnnouncementPollLoop()` polls every 5 minutes independently of the WebSocket — fetches recent posts via `fetchGroupPosts()` and calendar events, AND re-sweeps pending `notification-v2` (events/announcements/role changes) via `processV2Notification()`. Its first poll runs ~45s after start (not a full 5 min) so catch-up surfaces quickly on reopen. **This is the retry path** for the one-shot connect backfill: that backfill makes 50+ REST calls rapidly and can miss items on a transient 429/timeout or a cold-start race, with no built-in retry — the poll loop re-attempts the V2 sweep every cycle so nothing made while the app was closed is lost. `processV2Notification(obj)` is the shared per-notification handler used by both the connect backfill and this retry sweep; `seenNotifIds` dedup makes re-processing safe (each fires at most once). The V2 sweep is skipped until `notif_backfill_initialized` is set (first-run baseline). This catches announcements that the WebSocket missed or delayed. Notification-v2 handler explicitly matches `post` types as announcements and `event`/`calendar` types as group events, with proper URLs (`/posts` for announcements, group page for events).
    Per-group announcement timestamps are persisted in DataStore (`notif_group_announcement_seen`) to avoid re-firing on reconnect. `seenNotifIds` set (**UNBOUNDED — no cap, no eviction, deliberate**) deduplicates between REST backfill and websocket replay — **persisted to SharedPreferences as a JSON array** (`vrca_seen_notifs/ids_ordered`, `commit()` not `apply()`) so IDs survive service restarts and prevent repeat notifications. **The "friend requests resend on every app restart" bug lived here (tester-found)**: the set was capped (500, later 4000) with eviction, and it holds EVERY dedup key (V1/V2 ids + `ann_fp_`/`evt_fp_` fingerprints + per-person `fr_` keys) — months of use filled it permanently, so every new id evicted an old one. Worse, the legacy `putStringSet` persistence is a HashSet: **insertion order was LOST on reload, so post-restart eviction removed effectively RANDOM entries** — including fresh `fr_` keys. A pending friend request is RE-LISTED by VRChat on every backfill until accepted/declined, so an evicted `fr_` key = the same request re-fired on the next restart/reconnect (and each fire appended another event to the in-app "Friend request (N)" card).
    **The fix is NO eviction at all** (per the user: cap removed entirely): membership alone decides — once an id is in, that notification can structurally never refire. Growth is human-rate (~40-60 chars per real notification; even years of heavy use is a few MB, loaded once at service create). One-time migration from the legacy `ids` StringSet. `persistSeenNotifIds` uses `commit()` because the swipe shutdown hard-kills the process without waiting for QueuedWork — an async `apply()` could lose the write and re-fire that notification next launch. **`addContentFingerprintToSeen`/`addEventFingerprintToSeen` persist immediately on genuine add** (they're not always followed by a `fireEventNotification` persist — an unpersisted fingerprint lost to a kill re-fired the announcement/event after restart, same bug class). Do NOT re-introduce a cap/eviction here — any eviction of a pending-state key recreates the refire bug. The admin-announcements set (`vrca_seen_announcements/ids`) is likewise uncapped, and its first-snapshot seed re-covers everything active on every restart without firing. **Ordering matters**: `fireEventNotification` checks the per-type toggle (`enabled`)
    BEFORE adding the dedup id to `seenNotifIds`. Adding it first would permanently poison the id if `enabled` read false transiently (e.g. DataStore not fully loaded during the cold-start connect/backfill race) — the notification would be dropped AND marked seen, so it could never fire on any later path. This was a cause of group announcements/events inconsistently never appearing on app open. REST calls are paced with 250-300ms delays; groups capped at 50 to stay under VRChat rate limits. Group announcement notifications include the group name in the title ("Announcement from GROUP_NAME"). Event notifications use calendar URLs (`/home/group/$groupId/calendar/$eventId`) when available. The `groupId` is extracted from `relatedGroupId`, `groupId`, `data.groupId`, `details.groupId`, or `senderUserId` (if `grp_` prefix), and the `eventId` from `eventId`, `data.eventId`, `details.eventId`, or `id` (if `cal_` prefix). As a final fallback BOTH fall back to `findIdWithPrefix(payload, "grp_"/"cal_")` — a recursive scanner that walks the entire notification-v2 JSON (including nested `data`/`details` blobs and embedded URLs) for the first value with that prefix.
    This is what makes event notifications reliably link to the calendar URL (`/home/group/grp_xxx/calendar/cal_xxx`) instead of falling back to `/home/notifications`. The notification-v2 `when` block has an **`else` catch-all** that logs the unmatched `type` string at INFO and still fires a generic group notification (gated by `KEY_NOTIF_GROUP_EVENT`) — so no notification-v2 is ever silently dropped just because VRChat used an unexpected type string. All handlers (WebSocket, poll loop, backfill) share `seenNotifIds` for dedup — WebSocket events now pass `dedupId = notifId` to prevent duplicates between real-time and polling. Each endpoint is wrapped in try/catch — failures are logged and skipped for this connect cycle. Bio/name change detection also runs on reconnect by diffing the old `friendsCache` against fresh API data before the cache is overwritten.
  - **First-run baseline guard**: A `notif_backfill_initialized` DataStore boolean blocks the first-ever backfill from firing anything. On the first pipeline connect, `seedBackfillBaseline()` walks user groups and silently records recent post IDs and calendar event IDs into `notif_group_announcement_seen`, then pre-seeds `seenNotifIds` with all V1 and V2 notification IDs (without firing), then sets both `notif_backfill_initialized` and `posts_events_baseline_v2`. This prevents both historical group announcements and pending friend requests/invites from firing on first install. From the second connect onward, the regular backfill flow runs and fires only events that arrived after setup.
  - **Newly-joined-group silent baseline (`seedGroupBaselineSilently` + `__known` markers)**: the first-run baseline only covers the groups the user was in AT first launch. A group **joined later** had none of its pre-existing posts/events baselined, so the backfill + 5-min poll swept them all as "new" and fired old announcements/events as notifications on join (tester-reported). Fix: a persisted **known-groups set** stored as reserved keys INSIDE the `notif_group_announcement_seen` map — `__known_groups_init` (the set-initialized flag) + `${groupId}__known` per group. The FIRST sweep on this version records every current group as known WITHOUT seeding (so existing groups still fire genuinely-missed items on upgrade — nothing is swallowed), then any group whose `__known` marker is absent is one joined LATER, so `seedGroupBaselineSilently(groupId, seenMap, updatedMap)` records ALL its current posts + calendar events into the seen map (and their `ann_fp_`/`evt_fp_` fingerprints into `seenNotifIds`) WITHOUT firing, marks it known, and `continue`s (skips firing that group this cycle). Wired into BOTH `pollGroupAnnouncements` and `backfillOfflineNotifications` (shared guard).
    After a group is baselined once, only content created after joining surfaces. The reserved keys are safe: the seen map is only ever read via `.optString(specificKey)`, never iterated as `groupId_post_`/`groupId_event_`.
  - **Expandable notifications**: Status change, rename, and bio update notifications use `BigTextStyle`. Expanding shows before/after comparison text.
  - **Notification click actions**: Invite, group, and friend offline notifications open relevant VRChat web pages (`vrchat.com/home/notifications`, `/home/group/$groupId`, `/home/user/$userId`) instead of just opening the app. Group v2 notifications fall back to `vrchat.com/home/notifications` when `groupId` is missing from the payload.
  - **Notification-tap ACTIONS (`NotificationActionReceiver`)**: world-invite and invite-request notifications perform a VRChat REST call on tap instead of opening a web page. `fireEventNotification` gained `tapActionType`/`tapActionData` — when set, the tap `PendingIntent` is a `getBroadcast` to `NotificationActionReceiver` (registered in the manifest, `exported=false`) instead of `ACTION_VIEW`. The receiver runs the call on `goAsync()`, Toasts the result, and cancels the notification id on success. Two action types, shared by the in-app buttons via `NotificationActionReceiver.perform(ctx, type, data)`: **`invite_me`** (`data` = the invited instance `{worldId}:{instanceId}` location → `VrchatAuthManager.inviteSelfToInstance`, re-invites you so you can join) and **`invite_user`** (`data` = the requester's userId → `VrchatAuthManager.inviteUserToInstance(uid, location)` where `location` is read LIVE from `VrchatPipelineState.presence?.location` at tap time, inviting the requester to your current instance). `inviteUserToInstance` = `POST /invite/{userId}` with `{instanceId}`.
    **Both invite methods (and `inviteSelfToInstance`) return `VrchatAuthManager.InviteResult(ok, error)`** — on failure `error` carries VRChat's own reason parsed from the response body (`error.message`/`message`, quote-trimmed; falls back to "That instance has closed or no longer exists" on 404, "not accessible" on 403). The receiver/in-app Toast and the admin "Invite me" result surface this verbatim so the user is told WHY (instance closed/0-people/full or invite/invite+ not accessible) instead of a generic failure. World-invite extracts the location from the invite `details` (`worldId` if it contains `:`, else `worldId:instanceId`); if it can't parse a `wrld_` location it falls back to the old `home/notifications` web tap. The same action wiring is mirrored in the offline V1 backfill.
  - **In-app coverage (every type)**: friend request + new friend collapse into ONE per-person card (shared `friend_$userId` alertGroupKey); unfriend (`unfriend_$userId`), trust-rank (`rank_$userId`, text "X is now **a** Trusted User" — the article reads better), VRChat message (`msg_$senderUserId`, or `msg_$notifId` for System/no-sender messages), and ALL group notifications (keyed `group*_$baseId`). **Invite fusing (two distinct modes)**: **invite requests** fuse PER-PERSON (`invreq_$senderUserId`) as a **single-event** group (`alertSingleEvent=true` → only the latest is kept in-app, no "(N)" count) — you only need to know a person is asking, not every request. **World invites** fuse PER-INVITER (`worldinvite_$senderUserId`, like bios) as an **accumulating** group keeping the full history, with **same-instance dedup** (`alertDedupByActionData=true` → repeat invites to the SAME instance location collapse to one entry; different instances stay separate). Both `alertSingleEvent` and `alertDedupByActionData` are `fireEventNotification` params threaded into `InAppAlertState.addGroupedEvent`. The generic `group.*` catch-all always shows (no `message.length > 100` gate).
    **Filter chips**: `isGroupAlert()` routes `announcement_`/`event_`/`group*` to "Groups"; the rest to "Friends"; `bio_` to "Bio".
  - **Gift notifications**: `gift`, `giftCredits`, and `giftBundle` notification types are handled in `handleNotificationEvent` and fire via `KEY_NOTIF_GIFT_RECEIVED`.
  - **Invite response notifications**: `requestInviteResponse` (someone accepted your invite request) and `inviteResponse` (someone accepted your invite) are handled and fire through the invite channel.
  - **Unknown event logging**: Unhandled pipeline event types are logged at DEBUG level for discovery. Known non-notification events (`user-location`, `see-notification`, `hide-notification`, `clear-notification`, `response-notification`, `content-refresh`) have explicit no-op branches.
  - **Reconnection notification fix**: `scheduleReconnect()` now calls `startPipeline()` (which handles session recovery and proper notification updates) when the user isn't logged in, instead of silently falling through with stale "Reconnecting in Xs..." text. Also updates to "Connecting..." before calling `connectWebSocket()`. If `connectWebSocket()` finds no cookie/auth token, it falls back to `startPipeline()` instead of silently returning.
  - **Reconnect dedup (`scheduleReconnect` `if (wsJob?.isActive == true) return`)**: a single socket failure fires BOTH `onFailure` AND `onClosed`, and the ~50s health check can also call `scheduleReconnect()` — each previously launched its OWN backoff coroutine, each opening a NEW WebSocket, so several overlapping pipeline sockets raced (every one of which can independently fail/close and spawn yet more), which itself reads as "the pipeline keeps disconnecting." The guard early-returns when a reconnect is already pending (mid-backoff) or in progress. `wsJob` completes quickly once `connectWebSocket()` hands the socket off (the socket lives independently), so a genuine later failure still schedules a fresh retry; the guard only suppresses the duplicate-trigger stack.
  - **Cookie write atomicity (`captureRolledCookies` `synchronized(cookieWriteLock)` + `commit()`)**: every authenticated REST response routes through `captureRolledCookies`, and the heavy `fetchPresence` chain + the friends sweep fire several CONCURRENTLY on `Dispatchers.IO`. Without a lock, two responses doing `edit()`/`apply()` at once race on the shared `auth`/`twoFactorAuth` store the pipeline WebSocket also reads as its connect token — a stale-IP cookie could win nondeterministically. The lock makes each read-decide-write atomic and ordered. Timestamp/roll-forward semantics are unchanged (every present cookie still refreshes its stored-at clock, which `shouldRefreshCookies` and the trusted-device window depend on) — only the concurrency was hardened.
  - **Persistent notification resilience**: A 10s loop re-posts the foreground notification if it gets swiped away. The notification channel uses `setSound(null, null)` and the builder uses `setSound(null)` + `setVibrate(null)` to ensure silence. The notification also refreshes automatically when Discord RPC status changes.
  - **App update notifications**: `startAppUpdateCheckLoop()` runs on service creation (public build only), checks `checkFirestoreRelease()` immediately and every 6 hours. Fires via `fireAppUpdateNotification()` with `KEY_NOTIF_APP_UPDATE` (defaults to enabled). Uses stable notification ID `NOTIF_ID_APP_UPDATE` so repeated checks update in place. Shows version name and release notes in expandable notification.
  - **Admin announcement notifications**: `attachAnnouncementsListener()` sets up a Firestore snapshot listener on `announcements` collection (active=true). First snapshot seeds `seenAnnouncementIds` without firing. Subsequent snapshots fire via `fireEventNotification` with `KEY_NOTIF_ANNOUNCEMENTS` for new doc IDs. Seen IDs persisted to SharedPreferences (`vrca_seen_announcements/ids`). **This service listener is the background-surviving one** (fires the NOTIFICATION when the app is off-screen / the user is on another tab). The public UI (`VrcaScreen.kt`) attaches a **FOREGROUND-scoped** `where active==true limit 60` snapshot listener (a `DisposableEffect` — attaches while the screen is composed, detaches `onDispose`) so the in-app announcements list updates LIVE while open and costs nothing while backgrounded (see "Live-while-open reads"). (History: this was briefly a one-shot `get()` on screen entry to cut a duplicate persistent listener, but the user wanted the in-app list to update live while open; the foreground listener's first callback is the same single read as that `get()`, then bills only when a push actually lands while you're looking — so it's the same baseline cost plus live-while-open, and still works when the user isn't logged into VRChat.)
  - **VRChat status page integration**: `startStatusPagePolling()` polls `https://status.vrchat.com/api/v2/summary.json` every 2 minutes. Parses Atlassian Statuspage format (indicator: none/minor/major/critical, components, incidents). Updates `VrchatPipelineState.statusPageState` for UI consumption. Fires ongoing notification on incidents via `KEY_NOTIF_VRCHAT_ALERT`, auto-dismisses after 20 minutes of all-clear. Tapping opens status.vrchat.com. `VrchatStatusBanner` composable shows on Home and VRChat tabs with color-coded warnings. Uses `ElevatedCard` with elevated shadow for the outer container. The banner is collapsible (header row with status dot, title, subtitle, and chevron toggle); its expand/collapse state lives in a shared observable `StatusBannerState.expanded` (`mutableStateOf`, process-scoped singleton) so collapsing it on one tab (e.g. Home) instantly collapses it on every other tab (e.g. VRChat) — previously each tab held its own local `remember` state and counted as a separate card. It defaults to expanded and resets to expanded on a cold process restart so a new outage re-surfaces. When collapsed, shows an "N affected" chip.
    Affected components are grouped under an "Affected systems" sub-heading inside a nested `Surface` card — each component row has a small status dot, the system name, and a colored status chip; rows are separated by thin dividers. Incidents are grouped under "Latest updates", each in its own nested `Surface` card with incident name and latest update text. A "View VRChat Status Page" button-style Surface link sits at the bottom.

- Notification icons use a dedicated `ic_notification.xml` drawable (95% scale, less padding than adaptive launcher icon) for better visibility in the notification shade. **ALL persistent foreground-service notifications** — `VrchatPipelineService.buildPersistentNotification`, `KeepAliveService`, `DiscordRpcService.buildNotif`, and `OverlayService` — use `ic_notif_sync.xml` (the Material "sync" circular-arrows glyph, matching the Automations tab icon). Since all four services share `NOTIF_ID = 1001`, any service that rebuilds its notification overwrites the others in the shade — so they must all use the same icon or the sync glyph would revert to the old icon when another service updates. Event alert notifications (friend activity, invites, groups, etc.) still use `ic_notification.xml`. **Duplicate-`ACTION_START` notification guard**: because the services share `NOTIF_ID = 1001`, a duplicate `ACTION_START` (app reopened after pressing Back, or a sticky restart) must NOT reset the shared persistent notification to a startup state.
  `VrchatPipelineService.onStartCommand` only posts `"Connecting..."` when NOT already connected; when already connected it re-asserts `startForeground` with `lastConnectedNotifText` — otherwise `onOpen` never fires again to restore "Connected as X" and the notification gets permanently stuck on "Connecting..." even though presence/RPC are live. Likewise `DiscordRpcService.onStartCommand` posts `"Discord RPC active"` (not `"Discord RPC starting..."`) when already running.
