# VRChat auth, pipeline + presence

_Scope: VrchatAuthManager (login, 2FA cookies, relogin, REST), VrchatPipelineService (WebSocket, presence, instance counts), sign-out / auth-dead OSC gates, login screen._

### VRChat Integration

- **VrchatAuthManager**: Singleton handling VRChat API auth (Basic auth + 2FA), cookie storage via EncryptedSharedPreferences, presence fetching, and friends list retrieval. Also saves credentials to EncryptedSharedPreferences for auto-relogin when sessions expire. Credentials are saved BEFORE the login HTTP request so they survive app kills during response processing. **Basic-auth credentials are URI-encoded (`encodeUriComponent`, an `encodeURIComponent`-equivalent) BEFORE base64** — VRChat's backend URL-decodes them, so a password containing `@ + # : & %` etc. fails with 401 if sent raw. This was a real "permanent 2FA bypass broke" cause: the raw-bytes login 401'd → `clearCredentials()` wiped the saved creds → auto-relogin died → the next launch forced a full manual login *including* the 2FA prompt. **The 401 handler now only calls `clearCredentials()` when the error message actually indicates bad credentials** (`invalid`/`incorrect`/`credential`/`password`/`username`); a transient/session 401 (e.g.
  IP-invalidated session — VRChat binds the `auth` cookie to the client IP, which changes constantly on mobile) keeps the saved creds so auto-relogin can recover instead of forcing manual 2FA. On re-login after auth-cookie expiry, the Basic-auth request sends ONLY the persisted `twoFactorAuth` cookie via `getTwoFaOnlyCookieHeader()` — never the expired `auth=` cookie, which can cause VRChat to reject the request as a session conflict. VRChat recognizes the trusted device and skips the 2FA prompt. **The `twoFactorAuth` cookie is ALWAYS sent regardless of age — there is NO client-side expiry drop.** The web client keeps a remembered device trusted effectively indefinitely (rolling it forward on use), so any hard client-side cutoff (the old `TWO_FA_COOKIE_MAX_AGE_MS` 30-day guard, now removed) only ever HURTS — it forced an avoidable 2FA prompt that VRChat itself would not have asked for. Sending a stale cookie is harmless: worst case VRChat ignores it and returns `requiresTwoFactorAuth`, which is exactly what dropping it would have produced — so the SERVER is the sole authority on trusted-device validity. `KEY_2FA_COOKIE_STORED_AT` is kept for diagnostics only.
  On successful Basic-auth login, the auth cookie + user info are written via a direct prefs edit; **if VRChat re-issued a `twoFactorAuth` cookie in that login's `Set-Cookie`, it is captured and its 30-day clock RESET so the trusted window keeps extending**; if it did NOT (the common bypass-login case), the existing 2FA cookie and its original stored-at timestamp are preserved untouched (without this preservation, the 2FA cookie would get wiped on every successful relogin and the SECOND auth-cookie expiry would always force manual 2FA). **Trusted-device cookie roll-forward (`captureRolledCookies`)**: VRChat's web client never re-prompts because the server rolls the `twoFactorAuth` cookie forward on EVERY use — the browser's cookie never reaches its ~30-day Max-Age. The app previously captured that rotation ONLY on the explicit login/verify paths and discarded the `Set-Cookie` on every other authenticated call (`fetchPresence`, `validateSession`, `refreshProfilePic`, …), so the app's stored trusted-device cookie aged out and ~30 days after the last login VRChat demanded a fresh 2FA code even though the website would not.
  **`captureRolledCookies(context, rawCookies)` now persists any refreshed `auth`/`twoFactorAuth` cookie (resetting its stored-at clock) after every authenticated success** — wired into `fetchPresence` (runs every 10s while watched / on the slow loop, so the cookie stays continuously fresh), `validateSession`, and `refreshProfilePic`. It is strictly additive (only overwrites when a non-blank refreshed cookie is present), so it keeps the app's trusted-device window as fresh as the browser's and stops the spurious "keeps asking for 2FA" re-prompts. (A user whose stored cookie already expired under the old behaviour will be asked once more, then stays trusted.) **`captureRolledCookies` is now wired into EVERY authenticated REST call, not just three** — `fetchFriends`, `fetchPendingNotifications`/`V2`, `fetchUserGroups`, `fetchGroupName`/`Announcement`/`Posts`/`CalendarEvents`, `verifyStillFriend`, the `fetchPresence` `/users/{id}` + `/instances/{location}` sub-calls, and the post-2FA `/auth/user` fetch all roll the cookie forward. This matters for a NORMAL (unwatched) user:
  `fetchPresence` only hits the VRChat API while an admin is watching (the unwatched slow loop is local-only), so previously the sole roll-forward point for most users was the 6-hour `validateSession`; now the every-connect REST sweep keeps the `twoFactorAuth` cookie continuously rolled forward like the browser's cookie jar. **CRITICAL double-prefix fix**: `extractCookieValue()` already returns the full `name=value` pair (e.g. `twoFactorAuth=VALUE`), but the old `verify2FA()` re-wrapped it as `"twoFactorAuth=$it"` → stored the MALFORMED `twoFactorAuth=twoFactorAuth=VALUE`. VRChat rejected that as an invalid trusted-device cookie, so EVERY VRChat global logout forced a fresh manual 2FA prompt even though the website (whose cookie jar stored the correct value) would not. This was the real "trusted device never sticks" cause. `verify2FA()` now stores `extractCookieValue`'s return verbatim.
  A read-side self-heal (`normalizeCookie`/`readCookie`, used by `getCookieHeader`/`getTwoFaOnlyCookieHeader`) collapses any historically-stored double prefix in place (persisting the corrected value, so the WebSocket and all paths get the clean cookie) — existing users are migrated automatically on first read. `getPrefs()` has a recovery fallback: if EncryptedSharedPreferences init fails (MasterKey corruption), it deletes the corrupted prefs file and retries. `diagnoseAuthState()` logs the presence/age of all auth-related preferences for debugging. `VrchatPipelineService` runs a 6-hour `startAuthRefreshLoop()` that — because the 12-day age threshold rarely fires before the cookie actually dies — also **actively validates the session each cycle (`validateSession()` → `GET /auth`) and `autoRelogin()`s when it's dead regardless of cookie age**. `scheduleReconnect()` likewise re-validates and re-logins after repeated WebSocket failures (`reconnectAttempt >= 2`) instead of spinning on a present-but-dead cookie — `isLoggedIn()` only checks the cookie is PRESENT, not valid. Also provides REST helpers for offline notification backfill:
  `fetchPendingNotifications()`, `fetchPendingNotificationsV2()`, `fetchUserGroups()`, `fetchGroupAnnouncement(groupId)`. Trust rank extraction (`extractTrustRankFromTags`) reads the highest `system_trust_*` tag from VRChat's tags array. All REST `get()` calls set `useCaches = false` + `Cache-Control: no-cache` so Android's HttpURLConnection never serves a stale cached response — this fixes the instance player count (`/instances/$location`) showing minutes-old values in both the app and Discord RPC. **Instance headcount source (`extractInstanceUserCount`)**: VRChat's `/instances/{loc}` object exposes THREE candidate counts that disagree by a few users. **`userCount` is the field that matches the in-game client's instance panel** (what the player and everyone in the instance actually see in-headset). `n_users` AND the per-platform breakdown (`platforms`: `standalonewindows` + `android` + `ios`, which sums to the **website / VRCX** number) AGREE with each other but run a few HIGH — they count users mid-join / in-transit / timing-out that the in-game client has already dropped.
  The helper **prefers `userCount`**, falling back to `n_users` then the platforms-sum (iterating ALL keys so new platforms are future-proof) only when `userCount` is absent. (History: this thrashed before it was settled empirically. Original code preferred `n_users`; the user compared against the *website* and found it "wrong", so it was switched to the platforms-sum; a later screenshot showed the platforms-sum over-counting the *in-game* client (21 vs 18) so it was switched to prefer `n_users` — but `n_users` ALSO over-counted in-game (47 vs 36). A temporary in-app debug overlay logging all three fields finally proved `userCount` == the in-game panel (36) while `n_users`/`platformsSum` both read 47. Ironically `userCount` had been sitting in the code as the never-reached final fallback the entire time.) Both `fetchInstanceCount` and `fetchPresence`'s `/instances/{location}` parse go through this helper. Queue size is deliberately NOT added (irrelevant for normal instances).

- **VrchatPipelineService**: Foreground service with OkHttp WebSocket to `wss://pipeline.vrchat.cloud`. Handles real-time events (friend online/offline/active/location, friend-update, unfriend, invites, group events) and manages friends cache. Writes VRChat presence to Firestore **only while an admin is watching** this user (gated by `AdminWatchState.isWatched`); when unwatched, in-app presence still updates locally via WebSocket events but no traffic hits Firestore. The `syncPresenceToFirestore()` function gates the Firestore WRITE behind `AdminWatchState.isWatched`. When watched, presence polls every 10s. A slow 10s loop runs when unwatched with `forceLocalUpdate=true` to keep local presence state current (it does NOT write Firestore when unwatched, but it DOES call `fetchPresence` — the in-app VRChat tab + Discord RPC read the resulting `VrchatPipelineState.presence`; an earlier note claiming "no VRChat API calls when unwatched" was wrong). **Instant instance player count (`fetchInstanceCount`)**: the in-app/RPC player count (`n_users`) used to lag *minutes* behind the VRChat website.
  Root cause: the count is the 3rd of `fetchPresence`'s sequential calls (`/auth/user` → `/users/{id}` → `/instances/{location}`), so it only refreshed when the WHOLE chain landed — minutes apart on mobile under cookie IP-invalidation / rate limits — whereas the website hits ONLY `/instances/{loc}` per refresh (1 call, instant). Fix: `VrchatAuthManager.fetchInstanceCount(location)` does that single lightweight call (live `platforms`-sum count via `extractInstanceUserCount` / `capacity`). It is fired (a) **immediately on every self `user-location` world-hop** in `applySelfLocationEvent` (the WS location event carries no count, so the count previously sat at 0/stale until the next full chain — now it's fresh the instant you change instances), and (b) as a **null-fallback inside `syncPresenceToFirestore`** when `fetchPresence` returns null (the heavy chain failed) — it patches just the count on the last-known location so the count tracks reality instead of freezing. (When the cookie is *fully* IP-invalidated even this single call fails; that's the session-recovery path, separate.)
  **Light presence fallback (`VrchatAuthManager.fetchSelfPresenceLight`)**: when the heavy `fetchPresence` chain returns null, `syncPresenceToFirestore` first tries ONE `GET /users/{id}` call to recover the true location/state (no `/auth/user`, no `/instances` — one request, far less likely to be throttled than three) and flows the result into the SAME `VrchatPipelineState.presence` + watched Firestore write path. When the location is unchanged it merges the last-known `worldName`/instance counts; a world hop leaves `worldName` briefly blank until the next heavy chain refills it. This is what stops a genuinely in-game user (whose heavy chain is failing on a partial 429) freezing as "not in a world" on the admin panel / "not in VRChat" on their RPC. If even this single call fails (cookie fully dead), it falls through to the count-only patch as before. **Reactive self-presence from the WebSocket (`applySelfLocationEvent` / `applySelfUserUpdate`)**: the user's OWN `user-location` (world-hop) and `user-update` (status) events now patch `VrchatPipelineState.presence` DIRECTLY from the event payload — no REST call.
  This fixes "the Discord RPC keeps counting but doesn't match my VRChat state": self presence used to refresh only via the periodic `fetchPresence()` REST poll, which returns null whenever the auth cookie is IP-invalidated (constant on mobile/backgrounded), so `presence` froze while the RPC (whose online timer is independent) kept pushing a stale world. The `user-location` event was previously a no-op for self. Now patching it emits on `presenceFlow` → the RPC's `collectLatest` pushes the real world instantly even when REST is dead. When an admin is watching, `pushSelfPresenceToFirestoreIfWatched()` also writes the patched `vrchatLocation`/`vrchatWorld`/`vrchatState` straight to Firestore (no REST round-trip), so the admin directory's VRChat location updates instantly and resiliently — this fixes "the user's VRChat location not updating on the admin menu". The periodic watched 10s `syncPresenceToFirestore()` REST poll still runs as the authoritative full-field refresh (now more reliable thanks to the cookie roll-forward above).
  **No periodic `lastSeenAt` heartbeat lives here anymore** — liveness is a single hourly write owned by `VrcaViewModel.startHourlyHeartbeat()` (see "Hourly liveness model" below); the only periodic Firestore write this service makes is the 10s watched-user presence sync (which also refreshes `lastActiveAt`). Connect/disconnect transitions fire connection-status notifications (gated by `notif_connection` pref).

- **VrchatPipelineState**: Shared in-memory singleton using `MutableStateFlow` for reactive cross-component state (connection status, presence data, VRChat status page). Compose UI observes via `collectAsState()`. `statusPageFlow` exposes `VrchatStatusPageData?` for the status banner.

- **Settings Accounts + VRChat-logout OSC gate (Phase 3)**: `VrcaSettingsPage` gains an **Accounts** section (VRChat row: display name + Sign out with confirm dialog → `VrchatAuthManager.logout`; signed-out state shows "Sign in" → full-screen `VrchatLoginScreen` takeover with Cancel. Discord row: status from `discordSessionSeeded`/`discordRpcEnabled` + Disconnect with confirm, mirroring the VRChat-tab disconnect logic). **OSC hard-block while signed out of VRChat**: `VrcaViewModel.startVrchatAuthGateWatcher()` (init, app-scoped VM) collects `VrchatAuthManager.loggedOutSignal` → `stopSending()` FIRST (so the chatbox-clearing send escapes before the block) then sets `vrchatLoggedOut=true`; `refreshOscBlockGate()` ORs `forceUpdatePending || vrchatLoggedOut` into `VrcaOsc.blocked` (both gates share the chokepoint without clobbering each other — `applyForceUpdateGate` also routes through it). **`VrchatAuthManager.loggedInSignal`** (new SharedFlow, emitted on Basic-auth Success + 2FA verify Success) lifts the gate; re-login never auto-starts sending. **There is NO forced login screen anywhere anymore** — the only hard login gate is the onboarding tutorial's login step on first run.
  `VrcaApp`'s standalone `if (!vrcLoginDone) VrchatLoginScreen` gate was DELETED: a cold start while signed out lands straight in the app with OSC blocked (per the user: "not being logged in should just make it so osc doesnt work"). To make that safe, **`vrchatLoggedOut` is seeded from the REAL auth state** (`!VrchatAuthManager.isLoggedIn(app)`) instead of `false`, and `startVrchatAuthGateWatcher()` calls `refreshOscBlockGate()` immediately — without this a signed-out cold start would have an OPEN gate until a `loggedOutSignal` that never fires. Sign-in surfaces: Settings → Accounts and the **VRChat tab** (`VrchatStatusPage` now owns its own `showLogin` full-screen `VrchatLoginScreen` takeover with Cancel — the old `onOpenLogin` param was wired to an EMPTY lambda in `VrcaScreen`, which was the "clicking login does nothing" bug; the param is gone). `VrchatStatusPage.isLinked` is now DERIVED from `vm.vrchatLoggedOut && isLoggedIn` (the old one-shot `remember { mutableStateOf(...) }` froze the cold-start value, so a Settings sign-out never updated the VRChat tab).
  Each re-login bumps `reloginTick`, which re-keys the Phase-2 ban check effect (a re-login could be a different, banned VRChat account) and restarts the pipeline; on a signed-out cold start the Phase-2 effect simply early-returns until `loggedInSignal` flips `vrcLoginDone`. **Notification toggles moved**: `NotificationToggleSection` now renders in Settings → Notifications (removed from the VRChat tab). **Storage row** (Settings → App): measures `cacheDir`+`externalCacheDir`+`codeCacheDir` on IO and deep-links to the system App Info page (apps can't fully wipe their own cache; the system Clear Cache button is the honest route — it never touches logins/settings, and `app_webview` lives in the DATA dir handled by the Discord 20 MB cap).

- **OSC auth-dead gate (confirmed-dead VRChat session)**: `isLoggedIn()` only checks the auth cookie is PRESENT, not valid — so a session that silently died (VRChat **password change**, **30-day trusted-device expiry**, cleared creds) left OSC working even though the user is effectively logged out (bad, since admins need users staying logged into VRChat). This gate stops OSC when the session is **confirmed dead-and-unrecoverable**, while tolerating transient issues. Detection lives in `VrchatPipelineService.evaluateSessionHealthOnReconnect()`, hooked into the existing reconnect path (`reconnectAttempt >= 2`, where a dead cookie surfaces as repeated WS failures — replaces the old inline `validateSession`+`autoRelogin`). It **never blames the environment**: guards return early (not dead) when the device lacks **validated** internet (`hasValidatedNetwork()`, `NET_CAPABILITY_VALIDATED` like the Discord RPC) or VRChat is in a **major/critical outage** (`isVrchatMajorOutage()` reads `VrchatPipelineState.statusPageState.indicator`).
  With a healthy environment it calls the new **tri-state `VrchatAuthManager.validateSessionDetailed()` → `SessionValidity` {VALID, UNAUTHORIZED, UNKNOWN}** (`GET /auth`: 200=VALID, 401=UNAUTHORIZED, 5xx/network/no-cookie=UNKNOWN — so "couldn't reach VRChat" is never "dead"); on `UNAUTHORIZED` it tries `autoRelogin()` — success clears, failure (2FA-required / bad creds / no saved creds) is the dead signal. A **`AUTH_DEAD_CONFIRM_MS` = 5-min window** (`authDeadSinceMs` timestamp, `markAuthDeadCandidate()`) must elapse with the state persisting before it flips `VrchatPipelineState.authDead=true` — rides out blips/brief outages. **The WS `onOpen` clears it** (`clearAuthDead()`): a successful handshake means the cookie is valid, so authDead can only ever be true while disconnected. `VrcaViewModel` collects `authDeadFlow` → `vrchatAuthDead` → `refreshOscBlockGate()` now ORs `forceUpdatePending || vrchatLoggedOut || accountDenied || vrchatAuthDead`; `stopSending()` fires first (chatbox-clearing send escapes before the block); `loggedInSignal` clears both `vrchatAuthDead` and `VrchatPipelineState.authDead`.
  **In-app only, NO notification** (per the user): a `VrchatSessionExpiredBanner` (`PublicUiKit`) shows on **Home** (button → navigate to the VRChat tab) and the **VRChat tab** (button → its `showLogin` takeover) — short copy naming the causes ("...after a password change or if VRC-A hasn't been opened in about 30 days. Sign in again to fix it."). Non-destructive: nothing is wiped; a successful sign-in clears the gate and lifts the block automatically (never auto-starts sending).

- **Login polish (Phase 7 same pass, `VrchatLoginScreen.kt`)**: the **VRChat platform-status warning** ("VRChat is having platform issues — login may fail, it's not you") now lives INSIDE `VrchatLoginScreen` (one-shot `fetchVrchatStatusWarning()` on entry + **re-fetch on a FAILED login attempt**), so ALL login surfaces get it — Settings takeover, VRChat-tab takeover, AND onboarding (whose own duplicate warning in `StepVrchatLogin` was removed since it embeds this screen). Explainer tightened to 2 lines; the 2FA step (both email + authenticator variants) adds "VRChat will remember this device — you won't be asked again." Resend-cooldown + segmented digit boxes (doc nice-to-haves) deliberately not built.
