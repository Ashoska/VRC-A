# Friends cache + friend change detection

_Scope: Local friends cache, live bio/name/rank diffs, pipeline serialization, refresh loop, unfriend / friend-add / friend-request dedup, friend activity suppression._

- **Friends cache**: Persisted **locally** in SharedPreferences (`vrca_friends_cache` / `friends_json`) via `FriendsCacheStore`. No Firestore involvement — friends data is only used by the user's own app for unfriend notifications and is meaningless to admins. Old `savedFriendIds`/`savedFriendNames` fields in user docs are removed via `FieldValue.delete()` on every offline write so legacy data doesn't linger.

- **Live bio/name/rank notifications (`handleFriendUpdate`) — the PRIMARY instant path**: The pipeline `friend-update` WebSocket event **DOES** carry `bio` / `displayName` / `tags` (verified on-device via a temporary debug log that dumped raw payload keys — every event showed `bio="..."`). So `handleFriendUpdate` fires bio/name/rank changes **instantly** for online friends, with no polling. (An earlier note here wrongly claimed VRChat doesn't send `bio` live and that the old "instant while active" was incidental — both were wrong; the live event has always carried it.) It gates on `user.has("bio")` so partial location/status payloads (which omit the field) don't false-fire.

- **Pipeline message serialization (`pipelineDispatcher`) — the cache-race fix**: `friendsCache` is a plain non-thread-safe `mutableMapOf`, but `onMessage` used to `serviceScope.launch { handlePipelineMessage(text) }` on the **multi-threaded** IO dispatcher — so two events touching the same friend ran CONCURRENTLY, one's cache write clobbering the other's and a diff reading a stale `prev`, **silently dropping a notification**. Symptoms: a fast back-to-back bio edit firing once or not at all, and a quick **friend→unfriend** where the `friend-delete` read the cache before `friend-add` had written the entry (`?: return` drop). **Fix:** a process-lifetime single-threaded `pipelineDispatcher` (`Executors.newSingleThreadExecutor().asCoroutineDispatcher()`, closed in `onDestroy`). `onMessage` now launches on it (`serviceScope.launch(pipelineDispatcher)`), so all WS handlers run serialized in VRChat's send order — each handler's read-modify-write is atomic (the cache write precedes the first suspension point), and `friend-add` is processed before the `friend-delete` that followed it.
  The two nested cache-touching coroutines (`friend-offline` cooldown handler, the connect second-fetch diff) and the REST refresh diff also run on `pipelineDispatcher`. The REST diff re-reads the **latest** cache entry before writing (`val latest = friendsCache[userId] ?: prev`) so a concurrent WS presence update isn't reverted.

- **Periodic friends-profile refresh (`startFriendsProfileRefreshLoop`/`refreshFriendsProfilesAndDiff`) — the BACKUP path**: the live WS path above covers online friends instantly; this loop exists only for the one case the WS can't deliver — a friend editing their profile from the **website or phone while their VRChat status is "offline"** (VRChat sends no `friend-update` for offline friends, so they appear ONLY in the `offline=true` friends-list pass). It re-fetches the FULL friends list (`fetchFriends(onlineOnly=false)`, both `offline=false`+`offline=true` passes) and runs the same name/bio/rank diff. Cadence **`FRIENDS_PROFILE_FG_MS` = 30s while on-screen**, **`FRIENDS_PROFILE_REFRESH_MS` = 60s when backgrounded** (foreground from `VrchatPipelineState.appForeground`).
  **Cadence was dialed back from 12s/60s to 30s/60s**: each sweep is TWO 2-pass REST fetches and every authenticated call rolls the shared, IP-bound `auth` cookie the live pipeline WebSocket ALSO uses as its connect token — so an over-tight 12s foreground cadence churned that cookie / hit 429s and made the WS (and the Discord RPC that reads its presence) disconnect far more often. 30s still catches an offline-friend edit within ~30s. Since notifications fire regardless of foreground state, the slower background cadence only delays the friends-LIST display refresh (which the user isn't looking at), never the notification itself. **Foreground-reactive sleep**: the inter-sweep wait is sliced into 2s chunks and breaks early when `appForeground` flips false→true, so reopening the app runs a fast sweep within ~2s instead of waiting out the full 60s background sleep (the screenshot bug: the loop was stuck on a 180s sleep after reopen). (`fetchFriends` 429-handles by waiting 5s + retrying, so the cadence self-throttles if VRChat rate-limits.)
  The diff **MERGES** profile fields onto cache entries and preserves the live presence fields (`location`/`worldName`/`status`) the WS events own WHILE ONLINE — EXCEPT it **reconciles the OFFLINE direction from REST**: this sweep includes the `offline=true` pass, so a friend listed with `status="offline"` here IS offline; if the cache still shows them online a `friend-offline` WS event was MISSED (socket throttled while backgrounded), so the entry is reconciled to offline (silently, no late notification). This stops the friends-online count drifting too HIGH mid-session without needing a reopen (previously only a full reload on reconnect/reopen fixed a missed offline). Only the offline direction is reconciled; a friend's live world/status while ONLINE stays WS-owned (the WS is more real-time than this up-to-60s-stale fetch). Skipped during warmup / when not logged in / empty cache. Dedup is shared with the live + reconnect paths via the cache (whichever updates the cache first makes the other see no diff → no double-fire) and the `bio_$userId`/`name_$userId`/`rank_$userId` group keys. `VrchatAuthManager.fetchFriends(context, onlineOnly=false)` still has the `onlineOnly` param (only the `offline=false` pass when true) but this loop always passes `false`.

- **Unfriend notification logic**: Two sources cooperate via a `notifiedUnfriendIds` dedup set. (1) Real-time `friend-delete` from the WebSocket fires immediately for unfriends during an active session — but is **skipped if the userId isn't in the cache** (queued event for an offline unfriend that loadFriendsCache already removed). (2) Offline diff uses **two-fetch confirmation** to eliminate API pagination flaps: after the first API fetch on connect, removed IDs are captured into `candidateRemovals` but NOT notified. After the second fetch (60s later), only IDs still missing in BOTH fetches (`candidateRemovals ∩ stillMissing`) advance to verification. **Final verification gate**: both paths call `VrchatAuthManager.verifyStillFriend(userId)` which hits `GET /users/{id}` and reads the `isFriend` field. If true → suppress notification and re-add to cache (false positive); if false or 404 → fire notification; if null (network error / 429 / expired session) → fall back to firing the notification so we don't silently drop real unfriends. The dedup set ensures at most one notification per userId per session.
  The notification text is neutral — "Friend removed" / "$name is no longer on your friends list" — since the app can't know who initiated the removal. **Last-friend (1→0) fix (`fetchFriends` returns `List<VrcFriend>?`)**: unfriending your ONLY friend never notified because the diff couldn't tell a genuine empty list from a failed fetch — `fetchFriends` returned `emptyList()` for BOTH, so the guards `if (fresh.isEmpty()) return` / `if (friendsCache.isEmpty()) return` swallowed the 1→0 removal. `fetchFriends` now returns **null on a HARD failure** (no cookie, or not a single page ever returned 200 — session dead / rate-limited-out) and a **(possibly empty) list on success** (a valid 200 with `[]` = genuinely 0 friends). `loadFriendsCache()` returns a `Boolean` and, on a null fetch, **preserves the existing cache instead of wiping it** (a failed fetch used to blank the cache → the next diff would read every friend as removed; now the preserved cache makes `candidateRemovals` empty on failure).
  `diffFriendsCache` **no longer bails on an empty `friendsCache`** — an empty cache after a successful fetch is a real 0-friends state whose removal must fire; the per-candidate `verifyStillFriend` gate + the two-fetch confirmation + the `< 80%` partial-fetch guard (which the 1→0 case passes since `1*4/5==0`) are the false-positive protection. `refreshFriendsProfilesAndDiff` uses `fetchFriends(...) ?: return` (null = failed → skip; empty = 0 friends → loops zero times). Net: unfriending your last friend now fires, while a failed fetch still never false-flags removals.

- **Friend-add / friend-request dedup (repeatable per-person)**: two coupled fixes for "New friend fires 2×" and "unfriend→refriend doesn't notify". (1) **`friend-add` SHORT-WINDOW dedup (`recentFriendAddMs` + `FRIEND_ADD_DEDUP_MS` = 5 min, in-memory)**: the `friend-add` pipeline event carries no `dedupId`, and VRChat re-emits/replays it (notably on a WS reconnect), so a duplicate fired "New friend" twice ("New friend (2)"). The handler now swallows a repeat within the window. It is NOT permanent — a genuine later re-add still fires, and `friend-delete` clears the stamp so an unfriend→refriend inside the window still notifies. (2) **Friend-request `fr_<userId>` key is now CLEARED on resolution** — `seenNotifIds` is permanent by design (correct for one-shot notifications), but the friend-request dedup key is REPEATABLE per person (a new request can come after a decline or an unfriend/refriend cycle). It was never removed, so a re-request from someone whose `fr_` key was already present was suppressed forever.
  `clearSeenNotifId("fr_<userId>")` (removes + persists) is now called on **`friend-add`** (request accepted) and on **`friend-delete`** (both the real-time handler AND the offline `diffFriendsCache` path), so a future request from that person notifies again. (3) **Declined/rescinded requests (`reconcileResolvedFriendRequests`, 5-min poll)**: VRChat sends NO pipeline event when a request is declined or the sender rescinds it, so accept/unfriend clearing alone missed those. VRChat re-lists a pending request until it's resolved, so a person who still has a live `fr_` key but is NO LONGER in the current pending friend-request list (V1 + V2 fetch) AND isn't now a friend had their request resolved → clear `fr_<uid>`. Guarded by a **2-consecutive-absence strike** (`resolvedFrStrikes`, in-memory) so a partial/failed pending fetch can't spuriously clear a still-pending request (which would re-fire it — the duplicate bug); never acts on a failed fetch. Runs on the 5-min poll.
  **Known narrow window**: if the same person RE-requests within ~10 min (before the 2 strikes clear), the still-set `fr_` key suppresses it — a NEW pending request looks identical to the old one under per-person keying, so it's kept; only a resolved-then-quiet gap clears. The common decline-then-later-request case is covered.
  - **Avatar change suppression**: Avatar change notifications are suppressed when the friend's location changed in the same `friend-update` payload OR when a `friend-location` event fired for the same friend within the last 15 seconds (`recentlyRelocated` map). This two-layer guard handles both same-payload location changes and the common race condition where `friend-location` updates the cache before `friend-update` arrives.
  - **Status change suppression during world hop**: `maybeFireStatusChange` is only called in `handleFriendUpdate` when the location did NOT change. VRChat sends status data redundantly with location changes, so firing both a "Friend moved" and "Friend changed presence" notification for the same event is noise.
  - **Warmup suppression**: For 30 seconds after pipeline connect (`WARMUP_MS`), all friend activity notifications (online, active, location, and handleFriendUpdate changes) are suppressed. This prevents the initial burst of WebSocket events from firing stale notifications for friends' existing state. Cache updates still happen during warmup so subsequent real changes are correctly diffed. Does NOT suppress friend-add, friend-delete, notification/notification-v2, or show-alert events.
  - `friendsCache` is now `Map<String, FriendCacheEntry>` (was `Map<String, String>`) carrying display name, status, location, world name, avatar thumb, bio, trustRank — used to detect change events from `friend-update` and fire targeted notifications (renamed, changed status, changed avatar, updated bio, trust rank changed).
