### NowPlaying

- Ad/DJ detection: Spotify uses text-based matching (`com.spotify.music` only) to prevent false positives on regular songs, plus a player-agnostic `advertisement*` (title OR artist) check. **YouTube and YouTube Music need DIFFERENT ad signals** (`NowPlayingListenerService`) — on-device traces proved seekability is NOT a universal tell:
  - **YouTube VIDEO app (`com.google.android.youtube`) uses seekability**: it strips `ACTION_SEEK_TO` from `PlaybackState.getActions()` during pre-roll/mid-roll ads (you can't scrub an ad), so `seek=N` + finite duration (≤5 min) → ad, `seek=N` + zero/absent duration → live stream. A **buffering gate** (ignore non-seekable samples while `STATE_BUFFERING`/`STATE_CONNECTING` — a loading track is non-seekable but buffering, an ad PLAYS) + **entry hysteresis** (`YT_AD_ENTRY_STREAK` = 2 consecutive non-seekable PLAYING samples, `ytSeekNStreakByPackage`) de-noise the raw signal so a song switch can't flash "Ad".
  - **YouTube MUSIC (`com.google.android.apps.youtube.music`) uses a RELATIVE DURATION COLLAPSE, not seekability and not a fixed ceiling**: an on-device trace proved YT Music reports `seek=Y state=PLAYING` for BOTH songs AND ads (a song read `dur=165s`, an ad read `dur=15s`) — so `ACTION_SEEK_TO` is useless here (the long-standing "YT Music ads never detected / show the song's name" cause — the old code assumed `seek=N`=ad, but YT Music ads stay seekable). Each title's **established (longest-seen) duration** is tracked (`songEstablishedDurByPackage`, seeded on a title change, raised whenever the same title later reports longer). An ad is flagged by EITHER of two shapes, **both NOT gated on `playing`** (a PAUSED ad keeps `title=song` + the ad's short duration — verified: a paused ad still read `dur=15s` — so detection must survive a pause; gating on `playing` was the cause of "pausing mid-ad reverts to the song title"):
    - **(1) COLLAPSE** — the title was already established LONG (a real song played) and the SAME title (`lastSongTitleByPackage`) is now suddenly playing a duration collapsed `≥ YT_MUSIC_AD_COLLAPSE_MS` (20s) below its established length (under a `YT_MUSIC_AD_ABS_MAX_MS` 3-min sanity cap). This is the classic mid-roll ad reusing the current song's title, at any ad length (44s/55s/90s — no fixed ceiling, which an earlier fixed 45s ceiling got wrong by missing 55s+ ads).
    - **(2) SHORT-UNCONFIRMED** — a short duration (`1..YT_MUSIC_AD_MAX_MS`, **60s**) on a title we have NEVER seen longer than an ad (`establishedDur ≤ 60s`). This catches the **PRE-ROLL ad**, which on YT Music shows the **UPCOMING song's title at the ad's short length** (confirmed on-device: an ad displayed the real song's title at `dur=30s`). Because that title's only-ever-seen length is the ad's 30s, there is no long baseline to collapse from, so the collapse rule alone missed it — this was the root "**first ad of a pod is missed, second one works**" cause (the second ad reuses a title the real song already established long → caught by COLLAPSE). Once the real song plays and establishes a length `> 60s`, the title is "confirmed long" and only COLLAPSE applies to it. **Tradeoff: a genuinely short (<60s) real song would be read as an ad** — accepted because the user confirmed those short durations are ads showing the song title, not real short songs. (`YT_MUSIC_AD_MAX_MS` was lowered 75s→60s per the user.)
    The 2-sample entry hysteresis (`YT_AD_ENTRY_STREAK`) rejects a transient short-duration frame at song start.
    - **(iTunes ground-truth, additive)** — `ITunesDurationLookup` (`com.vrca.nowplaying`) hardens the above by fetching the song's REAL duration from the free, key-less **iTunes Search API** (`https://itunes.apple.com/search?term=<artist title>&entity=song&limit=1` → `results[0].trackTimeMillis`). On each YT Music title it `prefetch()`es (background single-thread executor, process-lifetime `ConcurrentHashMap` cache incl. misses-as-0, in-flight de-dup so the 500ms poll can't storm it); when a real duration is cached it **RAISES** `establishedDur` (and `songEstablishedDurByPackage`) for that title. This catches the **pre-roll ad on its FIRST appearance** even when its duration exceeds the 60s short-unconfirmed cap: iTunes proves the upcoming song is long, so the ad's short duration trips COLLAPSE immediately instead of waiting for the real song to establish a baseline. Strictly additive — a network failure / no match leaves the device-duration heuristics untouched. (Caveat: if iTunes matches a longer alternate version of a genuinely-short real song it could over-flag, but that's the same documented short-song tradeoff.)
  - **Shared de-noising for both** (these caused three reported bugs — a false "Ad" flash on song switch, the real song title leaking mid-ad, and the ad number randomly climbing 1→2→3): **(3) Window-locked title** — once an ad opens the special window, `specialWindowIsAdByPackage[pkg]=true` and the redacted `title="AD"` is FORCED for the WHOLE 2s window (YouTube `isSpecialWindowActive` branch), so a single per-cycle flap can no longer leak the real song title; `lastAdInfoByPackage` preserves the parsed "X of Y" across the locked cycles. **(4) Per-break counter reset** — `VrcaViewModel.adSegmentCount` resets to 0 when `isAdNow` goes true→false (ad break ended), so each break starts at "Ad 1" instead of climbing across the session; combined with the window lock keeping `isAdNow` continuously true through one ad, the count no longer increments mid-ad. **Detection appears ~1s after the ad starts (the 2-sample hysteresis), not instantly.**
  - **Live stream detection** (video app only): `NowPlayingSnapshot.isLive` flows through `VrcaViewModel.nowPlayingIsLive`; `buildNowPlayingLines()` shows `"● LIVE"` instead of a progress bar. Live streams are not persisted to disk (restoring "LIVE" on next launch would be nonsense). (The temporary `NowPlayingDebug` on-device trace + its Settings → Debug "YouTube ad signals" card were REMOVED once detection was confirmed stable.)

- **EXACT chatbox line-width calibration (plan §8.4 — `ChatboxCalibration` + Settings→Debug harness)**: replaces `TitleCleaner`'s ESTIMATED `charWidth` weights + `VISUAL_LINE_UNITS=28.5` fudge with values MEASURED in-headset. The harness (`ChatboxWidthCalibrationTool`, Settings → Debug) sends a line of one repeated char via `vm.sendCalibrationLine`→`VrcaOsc.sendRaw` (verbatim, no minimal-bg suffix / manual hold); the user reads the wrap point in VRChat and records the **max count that stays on ONE line** per reference char (`ChatboxCalibration.REFERENCE_CHARS` spans the width spectrum incl. a fullwidth `Ｗ`). On Save, `ChatboxCalibration` (SharedPreferences, in-memory table loaded once via `attach()` in `VrcaApplication.onCreate` so `TitleCleaner` stays Context-free) stores `maxCount` per char. Model: each copy of char `c` consumes `1/maxCount(c)` of the line, so `visualWidth(s)=Σ 1/maxCount(char) ≤ 1.0` fits; `TitleCleaner.charWidth` returns the measured fraction for measured chars and the estimate SCALED (`calibScale` = avg of `(1/maxCount)/estimatedWidth` over measured chars, cached per `generation`) for unmeasured ones; `lineBudget()`=1.0 calibrated / 28.5 estimated.
  When uncalibrated it's the old estimate path (unchanged). `estimatedCharWidth` = the old `charWidth` logic, kept as the fallback.

- **One-line title fitting (`TitleCleaner`, `com.vrca.nowplaying`)**: YouTube / YT Music (and sometimes Spotify) titles are long and padded with non-identifying cruft, and the old `buildNowPlayingLines()` did a blunt `safeTitle.take(maxLine-1) + "…"` that chopped mid-word and could destroy the song's identity. `TitleCleaner.fitOneLine(title, artist, maxLine=42)` now fits `"artist — title"` onto ONE chatbox line via a cheapest-loss→most-loss ladder, stopping the moment it fits: **(1)** strip Tier-1 cruft (FREE, zero identity loss) — `(Official Music Video)`/`(Lyrics)`/`(Visualizer)`/`(Remastered 2021)`/`(HD)`/`(4K)`, the YT Music `- Topic` artist suffix, trailing `| Label` promo segments, Spotify's trailing ` - <tag>` version suffixes, `#shorts` hashtags, and emoji/pictographs; **(2)** de-dup an artist embedded in the title (`"Artist - Song"` → `"Song"` since the artist is shown separately); **(3)** if still over, drop Tier-2 borderline tags (`feat.`/`ft.`/`deluxe`/`radio edit`/`explicit`/`extended`…); **(4)** if still over, drop the separate artist (the song name identifies it);
  **(5)** last resort — word-boundary truncate with `…`, preferring a clean cut unless it wastes >12 chars (then hard-cut to keep more identifying text). **Tier-3 keep-words are NEVER stripped** (a bracket group / ` - ` suffix containing one is left intact even if it also contains a cruft word): `remix`/`vip`/`bootleg`/`acoustic`/`live`/`unplugged`/`instrumental`/`demo`/`cover`/`sped up`/`slowed`/`nightcore`/`taylor's version`/possessive- & language-`version`/`from "Movie"`/`soundtrack` — these denote a DIFFERENT recording, so removing them would change which track it is. Cruft is matched only inside `(...)`/`[...]` groups or after a `|`/` - ` separator (bare title words are never stripped, so a song literally named "Video Games" survives). Applied to both the live-stream line and the main music line. All regexes JVM-validated.
  **"Fits one line" is a DUAL constraint** (`fitsOneLine`): ≤ 42 chars AND ≤ `VISUAL_LINE_UNITS` (28.5f — backed off from the ~30 empirical edge for estimator-noise margin) estimated visual width via `visualWidth()`/`charWidth()` — VRChat's chatbox wraps centered PROPORTIONAL text at ~30 average-character widths, so a 41-char caps-heavy title within the char budget still wrapped to a second rendered line ("Theodore Roosevelt Would LOVE…" wrapped at ~29 chars; "…the DUMBEST mfs on earth" at ~31 — the empirical calibration). Weights: **`…`=2.0 — the ellipsis is three dots on ONE char; counting it 1.0 made `truncate()` emit a "shortened to fit" title whose appended `…` itself pushed the line over, wrapping the whole last word in-game**, `m w M W`=1.4, uppercase/digits=1.2, narrow (`i j l t f r`, space, light punctuation)=0.6, CJK/fullwidth=2.0, else 1.0. The 42-char cap is kept so a skinny all-lowercase title can still use every char that genuinely fits. The last-resort `truncate` walks the prefix by width (ellipsis included) before the word-boundary cut. **User opt-out**: `TitleCleaner.rawOneLine(rawTitle, rawArtist, maxChars)` is the "filters off" path (Media → Now Playing "Filter Titles" toggle) — it does NONE of the above (no cruft strip, no artist-dedup, no one-line fit), just `"artist — title"` with a hard char cap; the gate lives in `buildNowPlayingLines()` (`if (musicCleanTitles) fitOneLine(...) else rawOneLine(..., VRC_MAX_CHARS)`).

- **Ads keep the progress bar**: `buildNowPlayingLines()`'s ad branch renders a bare `"Ad"` label PLUS a progress bar driven by the ad's OWN position/duration (forced playing) — the bar used to vanish during ads, leaving a bare label. No brand/title is shown, so nothing leaks. When the ad reports no duration (some YT Music audio ads) it falls back to just the label.

- **Ad label is a bare `"Ad"`**: ads render as just `"Ad"` (no index). The player's ad index ("Ad 1 of 1") was unreliable, so it was dropped per the user — the label is a constant `"Ad"`. (`parseAdIndex`/`nowPlayingAdInfo`/`adSegmentCount` still exist and are still set, but the label no longer consumes them.) **The ad-label block in `buildNowPlayingLines()` is gated on a dedicated `nowPlayingIsAd` flag (set from the collector's `isAdNow`), checked BEFORE `isSpotifyDj` with an early `return`.** This fixes "the ad never shows": a Spotify ad blanks the artist (`title="AD"`, `artist=""`), which made `isSpotifyDj` (`safeArtist.isBlank()`) evaluate TRUE — so the old `if (nowPlayingSpecialActive && !isSpotifyDj)` guard was false and the whole ad block was skipped, falling through to render a bare "AD" title + progress bar. An ad and a DJ segment both blank metadata; only the explicit `nowPlayingIsAd` flag distinguishes them, so the ad path must be checked first and independently of `isSpotifyDj`.

- Special window: Spotify/generic ads use a 10s window (cleared immediately once real metadata appears). **YouTube ads use a short 2s window** refreshed every 500ms by the continuous poll while seek=N holds; after the ad ends the window expires naturally in ≤2s. YouTube packages are EXEMPT from the eager `clearSpecialWindow` + `stopPoll` in the `isSpecialWindowActive` branch — their `onMetadataChanged` callback can race with `onPlaybackStateChanged`, reading a stale `controller.playbackState` (still seek=Y from the previous song) before the PlaybackState update propagates. That race falsely triggered "ad ended" → cleared the special window AND killed the continuous pause-detection poll, so (a) the ad indicator never appeared (showed the song name instead of "Ad N") and (b) the pause detector stopped receiving samples. The fix: for YouTube packages, the `isSpecialWindowActive` branch is a no-op — the poll keeps running, the window stays alive while the ad is ongoing (refreshed each seek=N cycle), and expires organically after the ad ends.

- **YouTube / YouTube Music ARE detected** (earlier notes claiming they can't be were wrong — they DO publish a MediaSession with title/artist/position). Two quirks are handled in `NowPlayingListenerService`: (1) **Pickup delay** — a freshly-started session used to surface only when the app posted its media notification (a few seconds late). An `MediaSessionManager.OnActiveSessionsChangedListener` (registered in `onListenerConnected`, unregistered in `onListenerDisconnected`) now wires the controller the instant the session goes active, so detection is near-immediate (future-proof for ALL media apps, not just YouTube). (2) **Progress kept moving while paused** — YouTube keeps reporting `STATE_PLAYING` + `playbackSpeed=1f` even when PAUSED, so the only reliable pause signal is that the raw `position` stops advancing across snapshots.
  That position-stall check lives in `NowPlayingState` and needs fresh samples every ~500ms, but YouTube's `MediaController` fires almost no callbacks while paused — so `ensureControllerForPackage` now starts a **continuous 500ms poll for YouTube packages** (`startPollForRealTrack`, exempt from the 10-min cap that the Spotify ad/DJ poll uses; it self-stops on controller change / teardown / session-destroy / notif-removed). The poll pushes a snapshot EVERY cycle for YouTube (other players still push only on real change / every 4s), so the stall detector reaches its 2-cycle threshold within ~1s of a pause → forces `isPlaying=false` → `effectiveIsPlaying` goes false → `buildNowPlayingLines` stops extrapolating and freezes the progress bar at the real snapshot. On resume the real position is being pushed every 500ms, so the bar continues from the true timestamp with no teleport.

- Motion-based play detection with YouTube-specific stall tracking. **YouTube Music play/pause is the INVERSE case and must NOT use the position-stall hack**: its raw `position` field is unreliable — it can ADVANCE while paused and FREEZE while playing — so the motion/stall detector inverted it (playing showed as paused, paused showed as playing, with the progress bar moving/freezing backwards). YT Music's reported `PlaybackState.state` IS honest, so it is trusted directly: `NowPlayingState.update()` sets `inferredIsPlaying = snapshot.isPlaying` for `com.google.android.apps.youtube.music` (skipping the stall block, which now applies ONLY to the video app `com.google.android.youtube`), and `computeDisplayedPlaying()` short-circuits `return nowPlayingReportedIsPlaying` for YT Music before any motion logic. The video app keeps the `STATE_PLAYING`+`speed=1f`-while-paused stall workaround unchanged.

- **Anchor freeze-on-pause (`maybeFreezeNowPlayingAnchor`) — kills the "+2s jump" (headset browser source)**: the progress bar extrapolates position from an anchor `(nowPlayingPositionMs, nowPlayingPositionUpdateTimeMs)`. While NOT displaying-playing, `buildNowPlayingLines` shows the frozen posSnapshot, **but the anchor TIME kept advancing** — so the instant play resumes, `pos = posSnapshot + (now - anchorTime)` SNAPS forward by the whole paused gap. A dense/accurate source (mobile Spotify/YouTube — the latter gets the continuous 500ms poll) self-corrects in a frame so it's invisible; a SPARSE, flickery source shows a stark skip. **On the Quest the only media source is the browser MediaSession (`com.oculus.browser`), which is NOT in `youtubePackages` (so it gets NO continuous poll — only sparse ~3s callbacks) and momentarily reports `isPlaying=false` between pushes** — so its flicker freezes then snaps the bar every few seconds (the tester-reported "smooth in preview, +2s jump in VRChat, consistently every ~3s"). The NowPlaying position/anchor/send code is 100% SHARED between mobile and headset — nothing was changed per-flavor; the differentiator is purely the media source.
  **Fix (source-agnostic, also correct for a genuine pause)**: the UI tick calls `maybeFreezeNowPlayingAnchor(displayedPlaying)` before assigning `nowPlayingIsPlaying` — while not displaying-playing it holds the bar in place AND re-stamps `nowPlayingPositionUpdateTimeMs = elapsedRealtime()` every tick, so resuming continues from where the bar visually stopped instead of snapping forward by the gap; on the play→pause edge it captures the currently-shown extrapolated position (same 1x-speed fallback as `buildNowPlayingLines`) as the frozen value so pausing doesn't lurch the bar BACKWARD to a stale snapshot either. A real seek during pause still re-anchors via the next snapshot's keepAnchor drift check (seeks aren't lost); ads/live are unaffected (their branches force displaying-playing true, so the freeze no-ops).
  **Paired with dense sampling (`NowPlayingListenerService.continuouslyPolledPackages` = `youtubePackages + "com.oculus.browser"`)**: the browser now gets the SAME continuous 500ms poll YouTube does, so its position/play-state is sampled every 500ms instead of on sparse ~3s callbacks — the anchor stays fresh (any correction is <500ms, invisible) and a real pause is seen within ~1s. The set gates ONLY polling (poll-start, push-every-cycle, no-10min-cap, and NOT-stopping-on-a-normal-track); the YouTube-specific stall/ad-detection logic stays keyed on `youtubePackages`, so the browser still uses normal motion-based play detection, not the YT hacks. Together: dense sampling keeps the bar glued to reality, and the freeze-on-pause anchor handles any residual flicker without a snap.

- **Last-track persistence across revival (`NowPlayingState.attach`/persist)**: the snapshot lives only in process memory, so after an OS-initiated process kill + headless ViewModel revival (`KeepAliveService` → `ensureRuntimeViewModel`) a PAUSED track had no active MediaSession to re-push and the chatbox NowPlaying line just blanked out. `NowPlayingState` now persists the last *detected, non-special* track (title/artist/duration/position/package) to SharedPreferences (`vrca_nowplaying`) inside `update()` and `pauseIfActivePackage()`, and `VrcaApplication.onCreate()` calls `NowPlayingState.attach(context)` to re-seed `_state` from disk **as paused** (re-anchoring `positionUpdateTimeMs` to `now`, `speed=0`, `isPlaying=false`) before any ViewModel collects — so the previous track shows immediately instead of disappearing. `attach` is idempotent and only restores while the in-memory state is still blank (never clobbers a live one). Ads/DJ/special windows are never persisted (restoring "AD" would be nonsense). A genuine hard clear (`clearIfActivePackage`) removes the persisted entry so a real stop doesn't resurrect a stale track. Also fixes the plain cold-start case, not just headless revival.

- **Blank-metadata push keeps the last track (close-blanking fix)**: closing the media app (vs Spotify, which keeps its MediaSession alive in the background) tears its `MediaSession` down — YouTube/YouTube Music in particular fire `onMetadataChanged(null)` / the 500ms poll reads empty metadata right around teardown, pushing a `detected=false` (blank title+artist) snapshot. The old `NowPlayingState.update()` wrote that blank straight into `_state`, instantly wiping the preview AND the OSC chatbox line ("closing YouTube removes the text immediately; Spotify doesn't"). The disk persistence above did NOT rescue this — `attach` only re-seeds when in-memory state is blank at *process start*, but here the process is still alive. **`update()` now treats a blank push for an already-`detected` track as a PAUSE: it freezes the last known title/artist (`speed=0`, `isPlaying=false`, clears `specialActive`/`adInfo`) instead of clearing**, mirroring `pauseIfActivePackage`'s keep-last behavior — so YouTube freezes the last track on close exactly like Spotify. A genuine hard stop still goes through `clearIfActivePackage()` (the only remaining blank path).
  **YouTube ad detection remains a known limitation**: during a YouTube ad the MediaSession keeps the VIDEO's title but reports the AD's (short) duration/position, so the progress bar shrinks to the ad then jumps back. `classifySpecial()` only flags ads when the title/artist starts with `"advertisement"` (Spotify's behavior); YouTube exposes no reliable ad flag, so this is intentionally left as-is rather than adding a fragile duration-collapse heuristic that would false-positive on Shorts / short videos / chapters.

- Crystal progress bar (preset 3) uses filled diamonds (U+25C6) before the marker position

- **Progress bar time separator is plain `/`; the PAUSED bar drops one filler slot instead** (`pausedTrim` in `renderProgressBar` / `renderSoundwaveBar`). The real overflow culprit was the PAUSE marker: `⏸` (U+23F8) gets emoji presentation in VRChat's chatbox font (and Android's), rendering ~2-3× wider than the text-glyph playing dot `◉` — so the bar+time line wrapped when paused but not when playing. Rather than swapping the emoji, the bar sheds ONE identical filler slot while `dotIsPlaying == false` (hearts 8→7 inner, presets 2/3/5 10→9, soundwave 8→7); every slot is the same glyph so it just reads one char shorter, the marker index rescales automatically, and the slot returns on resume. If in-game testing shows paused still wrapping, the tuning knob is dropping one more slot. Separator-swap attempts that FAILED before this approach (don't retry them): ASCII `|` has wide punctuation side bearings (rendered `14:47 | 20:5` with gaps, wrapped); FRACTION SLASH `⁄` U+2044 triggers fraction composition (`41:³⁰⁄₅₁:08` super/subscript digits); dental click `ǀ` U+01C0 was fine but unnecessary once the real culprit (the pause emoji) was found. **YouTube video does NOT get extra title lines** — VRChat's chatbox renders centered proportional text at ~30 average chars width, so a wider char budget just keeps the artist prefix and wraps worse visually; the single-line `TitleCleaner.fitOneLine()` (42-char cap + 30-unit visual width) with artist-drop escalation is the correct behavior for long video titles.
