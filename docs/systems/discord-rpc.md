# Discord RPC (WebView gateway)

_Scope: DiscordRpcService, the JS shim, OP 3 injection, gateway health/recovery, offline parking, RPC counter, login WebView, background keep-alive and cache cap for the Discord WebView._

- **DiscordRpcService**: Foreground service running a hidden WebView that loads `discord.com`. Discord's own JavaScript handles the gateway connection (intents, capabilities, X-Super-Properties, TLS, /science telemetry) — all traffic looks like a real Discord web session, making detection effectively impossible. After page load, a JS shim hooks `WebSocket.prototype.send` to capture the gateway WebSocket reference, then exposes `window.VRCA_setActivity(json)` / `window.VRCA_clearActivity()` which send OP 3 (Presence Update) directly on the captured gateway connection. The Flux dispatcher approach was abandoned after Discord fully obfuscated all internal module names. The native side pushes activity updates via `evaluateJavascript` whenever `VrchatPipelineState.presenceFlow` emits (1.5s debounce) or every 10s as keep-alive. World thumbnails are squash-proxied via `images.weserv.nl` (`fit=fill`); the default VRChat image (`DEFAULT_VRCHAT_IMAGE_URL`) skips squashing.
  Image URLs are resolved to `mp:external/...` format via Discord's `POST /api/v9/applications/{app_id}/external-assets` endpoint (called from within the WebView JS using the session token read from `localStorage.token` or captured from Discord's own fetch calls — the token never leaves the JS context and is never sent to native code). Resolved URLs are cached in `window._vrca_asset_cache`. The user token is never extracted or stored natively — `DiscordLoginWebView` just seeds the `CookieManager` session. Auto-starts when VRChat pipeline connects if `discord_rpc_enabled` and `discord_session_seeded` are both true.
  - **OP 3 interception**: The `WebSocket.prototype.send` hook intercepts all outgoing OP 3 messages from Discord's own code. When our activity is set (`window._vrca_activity`), it's injected into the `activities[]` array of every Discord-originated OP 3. This ensures our RPC persists through Discord's own status changes, idle detection, and gateway reconnects — Discord can't overwrite our activity because it's included in every outgoing presence update. The hook also captures the user's current status (`online`/`dnd`/`invisible`) from each OP 3 so our direct sends use the correct status rather than hardcoding `'online'`.
  - **Anti-idle**: On mobile, Discord auto-sends OP 3 with `status: 'idle'` when the user backgrounds the app. The hook tracks the user's "intended" status (last non-idle status they set). When Discord tries to send `status: 'idle'` but the intended status is `'online'`, the hook overrides it back to `'online'` with `since: 0`. This keeps the user's Discord status online while VRC-A's foreground service is running. DND and invisible are respected (never overridden).
  - **Safety system (7 features):**
    1. **Risk gating UI**: First-time enable shows a consent dialog with checkbox acknowledgment + 4-second delay before the Continue button activates. Consent persisted in `discord_risk_accepted` DataStore key — only shown once. Bullet list explicitly warns that disconnecting may cause Discord to invalidate sessions on other devices, logging the user out everywhere.
    2. **Session state monitoring + gateway-health recovery**: A 30s background loop (`startSessionMonitor`) reads `window.VRCA_gatewayHealth()` via `evaluateJavascript` instead of just `readyState === 1`. The old raw-readyState check showed a **false "connected"** when the gateway socket stayed OPEN but the session was dead/zombied (e.g. a Discord outage black-holing presence) — the user saw "Discord presence connected" while their RPC was missing from their profile, and had to manually sign out/in. `VRCA_gatewayHealth()` classifies: `no_gateway` (shim lost the ref), `connecting` (socket opening → wait), `dead` (readyState closing/closed), `bad` (Discord sent OP 7 Reconnect / OP 9 Invalid-Session, or the socket fired `close`), `zombie` (open but no heartbeat ACK for >2.5× the `heartbeat_interval`), `alive`. **Reload thresholds are now per-class (NOT a flat "reload after 2 checks for everything", which turned transient blips into frequent visible RPC drops)** — a reload (`onSessionExpired()`) drops the RPC for its reload+re-inject window, so it only fires when the signal is real:
      `dead` (readyState CLOSING/CLOSED — compression-independent, reliable) reloads after `DEAD_RELOAD_THRESHOLD = 2` (~60s, one RESUME-grace cycle); `zombie`/`bad` are derived from heartbeat-ACK / OP7-9 tracking that needs READABLE inbound frames, which Discord's `zlib-stream` compression makes unparseable → they can FALSE-positive, so they require `DEGRADED_RELOAD_THRESHOLD = 4` (~2 min) before reloading — and a socket that's genuinely closing reports `dead` and takes the faster path anyway. Each non-matching state resets the others' counters (`deadHealthChecks`/`degradedHealthChecks`/`noGatewayChecks`). `onSessionExpired()` **reloads the WebView**, which re-establishes a fresh gateway and **auto-re-authenticates from the persistent `localStorage` token + `CookieManager` cookie (no password)** — doing automatically what the manual sign-out/in did.
      **`no_gateway` also escalates to a reload**: the first misses re-inject the shim (cheap — recaptures the gateway if Discord's JS still has a live one); after `NO_GATEWAY_RELOAD_THRESHOLD = 3` consecutive still-`no_gateway` checks, or if shim injection EXHAUSTS its retries still reporting `no_gateway` (the `injectShim` give-up branch — `lastShimResult.contains("no_gateway")`), it escalates to `onSessionExpired()` instead of the terminal **FAILED** state. This fixes the user-reported dead end where the RPC silently dropped, the app showed "Discord setup failed: no_gateway(hook=true)", and re-injecting/restarting couldn't recover it — only a manual Discord sign-out/in (which reloads the page → Discord's JS opens a fresh gateway → the hook recaptures it via `onPageFinished`) brought it back. Re-running the module finder on the SAME page can never recapture a gateway Discord's own JS hasn't reopened, so a page reload is the only real fix; `onSessionExpired()`'s `MAX_SESSION_RECOVERIES` cap still bounds it (after the cap → "sign in again").
      The shim (`WS_HOOK_JS`) tracks health via `_vrca_attachGatewayListeners(ws)` — a passive `addEventListener('message'/'open'/'close')` on each captured gateway socket (it only OBSERVES + re-pushes OUR activity; it never alters Discord's own frames, so the "real web session" anti-detection property holds). Heartbeat-ACK/OP-7/9/READY tracking needs **readable (uncompressed JSON) inbound** — when Discord uses `zlib-stream` compression those frames are binary and skipped, so `zombie`/`bad` degrade gracefully to `alive`; the **compression-independent** recoveries still work: a new gateway socket's `open` event re-pushes our activity at +3s/+8s (so a Discord-initiated reconnect re-lands the RPC even when frames can't be parsed), and `dead` (readyState) still forces a reload. **Known limit**: if the socket stays fully healthy (heartbeats ACKing) but Discord's presence BACKEND is down, there is no client-side signal — undetectable, resolves when Discord recovers. WebViewClient still detects login-page redirects (both `onPageFinished` and `shouldOverrideUrlLoading`) for true session expiry.
    2b. **Offline parking — no false "connected" while there's no network (`parkOffline` + validated-network callback)**: with **genuinely no network** (e.g. Wi-Fi off and no mobile data), the WebView still serves `discord.com` from its **HTTP cache**, so a page-load + shim-inject `MODULE_FINDER` returns `"ok"` and the old code declared the RPC **CONNECTED** even though the gateway WebSocket can never open — then a 10s presence push / 30s health check found the dead gateway, reloaded, the cached page loaded again, and the status **flickered CONNECTED → RECONNECTING every ~10s** (the user-reported "it shows reconnected to the RPC even though internet is off, then back to reconnecting, repeat").
      **Fix: never declare CONNECTED or churn reloads while offline — sit parked in "Waiting for network" until validated connectivity returns.** `parkOffline()` (called from the session-monitor top-of-loop offline check, `loadWebView`'s offline guard, the `injectShim` success path's `!hasNetwork()` guard, `onSessionExpired`'s offline branch, and `onReceivedError`) sets `awaitingNetwork=true` + `shimReady=false`, stops presence pushes, resets all health/freeze counters, and shows "Waiting for network" — `shimReady=false` makes every health probe / `pushActivity` a no-op so nothing can re-declare CONNECTED. **`hasNetwork()` now keys on `NET_CAPABILITY_VALIDATED`** (Android actually probed real internet reachability), NOT `NET_CAPABILITY_INTERNET` (which only means the interface *claims* internet — true for a connecting/captive network). **The network callback uses `onCapabilitiesChanged` gated on `NET_CAPABILITY_VALIDATED`** (recover only once internet is confirmed) instead of `onAvailable` (fires the instant any interface registers, before validation → would reload into the cached page and false-connect), plus `onLost` to park immediately. So a real reconnect (validated) drives one clean `loadWebView()` recovery; a flapping/connecting network never triggers the doomed cached-page reload.
    3. **Failure detection + response**: Non-silent — failures update `DiscordRpcState.status` (shared `MutableStateFlow`) and the notification. Session expiry shows a red "Sign in again" button in the UI. Module finder failure shows "needs update" status. UI status messages are user-friendly ("Setting up Discord connection...", "Reconnecting to Discord...", "Discord connection setup failed") rather than technical injection terminology.
    4. **Auto recovery**: On session expiry, up to 3 auto-recovery attempts with linear backoff (2s, 4s, 6s) reload the WebView page. On dispatcher loss, shim re-injection with exponential backoff (3s, 6s, 9s, 12s, 15s). On consecutive push failures (5), shim re-injection. All counters reset on successful reconnection.
    5. **Per-user failure isolation**: All state is service-scoped — failures only pause the Discord RPC service, never affect VRChat pipeline, Firestore sync, or any other system.
    6. **User feedback/transparency**: `DiscordRpcState` singleton exposes `statusFlow` (enum: IDLE/CONNECTING/CONNECTED/RECONNECTING/SESSION_EXPIRED/FAILED) and `failureMessageFlow`. UI shows a colored status dot + label (green=Connected, yellow=Connecting/Reconnecting, red=Expired/Failed) with detail message.
    7. **Safety guards**: Max 5 shim retries with backoff, max 3 session recovery attempts, max 5 consecutive push failures before re-inject, 1.5s minimum interval between JS evaluations (double-guarded: both delay and timestamp check), all counters capped.
  - **RPC counter persistence**: `onlineStartEpochMs` (the Discord activity `timestamps.start`, always milliseconds) is persisted to SharedPreferences (`rpcPrefs / online_start_epoch`). **The grace-window restore is keyed on a `last_online_seen` heartbeat** (refreshed in `buildActivityJson()` on every confirmed-online tick), NOT on `offline_at`: when the user returns online and `onlineStartEpochMs` is 0, the saved start epoch is restored only if `now - last_online_seen < ONLINE_GRACE_MS`. **`ONLINE_GRACE_MS` is 20 minutes** (applies to BOTH the in-VRChat and not-in-VRChat counters via `resolveElapsedStart`). It is deliberately >15 min so it **spans the `PipelineWatchdogWorker`'s ~15-min recovery gap**: after an OEM process kill the watchdog re-arms the services on its next ~15-min cycle, and the counter must still be inside the grace window at that moment for the timer to resume instead of resetting. Because `last_online_seen` freezes the moment the app stops tracking (process death, swipe), a longer untracked gap correctly resets the counter to a fresh start instead of bridging into a bogus multi-hour timer.
    **Critically, `onStartCommand` sets `onlineStartEpochMs = 0L` (it does NOT preload the persisted epoch)** so `buildActivityJson()`'s grace check always runs — preloading the stale epoch directly was the bug that shipped a day-old start to Discord as a "25 hours online" timer after a normal cold start (the grace block only runs when the in-memory value is 0). After 20 minutes untracked, a fresh counter starts. **Not-in-VRChat counter flicker guard (`OFFLINE_CLEAR_CONFIRM_MS` = 3 min)**: the two counters were asymmetric — the in-VRChat counter has grace carry AND its prefs are never cleared (so it's stable during active play), but the not-in-VRChat counter's persisted start (`offline_start_epoch`/`offline_last_seen`) was WIPED on the FIRST tick where `isOnline` read true, so a single spurious `isOnline=true` (a stale REST presence read / racy WS `user-update`/`user-location` event on a flaky connection) permanently reset it and the next offline tick restarted from 0 — the "not-in-VRChat RPC timer randomly restarts on connection blips" bug.
    Fix: the offline prefs are cleared only once the online session is CONFIRMED sustained (`nowMs - onlineStartEpochMs >= OFFLINE_CLEAR_CONFIRM_MS`). A transient flicker resolves a FRESH `online_start_epoch ≈ now` (the prior session went stale > grace ago), so the clear is skipped and the offline counter carries on across the blip within its own grace window; a genuine sustained visit still clears it so leaving VRChat restarts the offline clock as intended.

- **DiscordRpcState**: Shared in-memory singleton using `MutableStateFlow` for Discord RPC status reporting. Compose UI in the settings page observes `statusFlow` and `failureMessageFlow` via `collectAsState()` to show real-time connection status.

- **DiscordLoginWebView**: WebView-based Discord login flow. User logs into discord.com; login completion uses a 3-layer verification: (1) URL must contain `discord.com/channels` OR `discord.com/app` (Discord may redirect to either after login), (2) 2-second dwell timer ensures the URL is stable (cancelled if page navigates away), (3) JS authentication probe checks `#app-mount` has rendered children AND no login form (`input[type="password"]`, `input[type="email"]`) is visible — uses stable DOM structure rather than webpack chunk variable names which Discord may rename. The probe retries up to 4 times at 1.5s intervals when it returns false, since Discord's SPA can take a few seconds to hydrate after the auto-redirect from `/login` for users with valid cached cookies. All retry runnables are tracked and cancelled in `onPageStarted` so a navigation away cannot trigger a stale `onLoginComplete`. Only after all 3 layers pass does `onLoginComplete` fire and `discord_session_seeded` is set.

- **Discord WebView keep-alive WITHOUT an overlay**: the Discord gateway lives in a WebView whose JS Chromium throttles when it thinks the page is hidden (gateway drops ~45s after screen-off). Rather than a 1×1 `TYPE_APPLICATION_OVERLAY` window (which forces Android's "displaying over other apps" notification and looks sketchy), `DiscordRpcService` subclasses `WebView` and overrides `onWindowVisibilityChanged` to always report `View.VISIBLE`, plus `resumeTimers()` + `dispatchWindowVisibilityChanged(VISIBLE)` after creation. No overlay window, no system notification. **Three-layer defense against background JS throttling** (the one-time calls alone weren't enough — the RPC was silently dropping after extended background): **(1) Periodic `resumeTimers()` (every 10s via `pushActivity` + every 30s via session monitor)**: the 10s native presence timer calls `wv.resumeTimers()` before every `evaluateJavascript` push, keeping JS timers alive well within Discord's ~80s server heartbeat timeout; the 30s session monitor also calls `resumeTimers()` + `dispatchWindowVisibilityChanged(VISIBLE)` as a backstop. **(2) JS-level heartbeat keepalive**:
  `_vrca_sendPresence()` (called from native every 10s via `VRCA_setActivity`) checks if Discord's heartbeat has stalled (`Date.now() - lastAck > interval × 1.5`) and manually sends OP 1 (Heartbeat, `d: _vrca_lastSeq`) to keep the gateway alive even when Discord's own `setInterval` is frozen by Chromium. `_vrca_lastSeq` tracks the last sequence number from readable (uncompressed) inbound frames; `null` is valid per Discord's spec. **(3) Native JS freeze detection**: `lastJsResponseMs` (`@Volatile`) tracks when the last `evaluateJavascript` callback fired (updated in every push/health/shim callback). If no callback fires for `JS_FREEZE_RELOAD_MS` (120s), the session monitor forces `onSessionExpired()` (page reload) to recover — catches the case where even `resumeTimers()` doesn't work (some OEMs). Additionally, `sessionRecoveryCount` resets after `HEALTHY_RESET_MS` (5 min) of sustained healthy checks so intermittent drops over a long session don't exhaust `MAX_SESSION_RECOVERIES`.

- **Discord RPC "socket healthy but RPC gone from Discord" — the asset-resolution dead end (`VRCA_setActivity`)**: the PRIMARY cause of the user-reported "the app says connected but the RPC isn't on my Discord profile". EVERY image (including the default VRChat image) is an `https://` URL that must be resolved to a `mp:external/...` path via Discord's `external-assets` API before it can ride the OP 3 activity. The old `VRCA_setActivity` set `_vrca_activity` for an uncached image URL but **only called `_vrca_sendPresence()` inside the resolve success callback** — so if resolution failed (token not yet grabbed from `localStorage`, `fetch` deferred under background throttling, or the image URL just won't resolve), it retried 10× then gave up and the activity was **NEVER sent to Discord** even on a perfectly healthy socket. Native treated the `'resolving'` return as success (`consecutivePushFailures = 0`), the health monitor reported `alive`, and the UI showed CONNECTED — while the RPC was silently absent. The next 10s push re-entered with the same uncached URL → same dead end → permanent.
  **Fix: send the activity IMMEDIATELY without the unresolved image** (a deep-cloned copy with `large_image` stripped — Discord rejects a raw `https` `large_image`), store that image-less version as `_vrca_activity` so re-pushes keep showing it, THEN resolve the image and re-send the upgraded version. On permanent resolution failure the RPC stays visible (just without the world thumbnail). The RPC can no longer be blocked by image resolution. `VRCA_setActivity` now returns `'ok'` (presence already sent) instead of `'resolving'`.

- **Discord RPC world-switch stale-resolution race (`_vrca_activityGen`)**: each `VRCA_setActivity` starts its own `tryResolve` loop (up to 10 retries × 2s = 20s) to resolve the new world's image. On RAPID world/instance hops a PREVIOUS world's resolve could complete LATE and overwrite `_vrca_activity` with the stale world, then re-send it — RPC flicker / wrong-world / re-send churn that gets worse the faster the user hops (the user-reported "RPC stops/glitches more when actively on VRChat and switching worlds"). Fix: `VRCA_setActivity` bumps a `_vrca_activityGen` token on every call and `tryResolve` captures `myGen`; a resolve that lands after a newer world took over (`myGen !== _vrca_activityGen`) is ABANDONED (no overwrite, no further retries). `VRCA_clearActivity` bumps it too so a pending resolve can't re-add an activity after a clear. The `_vrca_asset_cache` write still happens so returning to a world is instant.

- **Discord RPC renderer-process recovery (`onRenderProcessGone`)**: a long-running BACKGROUND WebView's renderer process is reclaimed by the OS under memory pressure — MUCH more likely while the user is actively on VRChat (the phone app is doing heavy VRChat REST + WebSocket + presence work, so the whole device is under load). Without an `onRenderProcessGone` override that returns `true`, the OS can terminate the whole service process; and even when it doesn't, the page goes blank and the RPC is dead until the 120s JS-freeze detector eventually reloads. The handler now destroys the dead WebView and calls `loadWebView()` (fresh gateway) immediately, recovering in seconds instead of up to two minutes — and returns `true` so a renderer reclaim can never crash the process. This is a primary contributor to "RPC stops more often when on VRChat".

- **Discord RPC JS-side presence re-assertion (`_vrca_pushInterval`) — the "works for a bit then disappears while still connected" fix**: presence was re-asserted ONLY by the native 10s `presenceTimerJob` → `evaluateJavascript`. A backgrounded WebView has those native→JS calls throttled/queued by Chromium, **while Discord's OWN internal `setInterval` heartbeat keeps the gateway socket OPEN** — so the health monitor saw `alive` and the UI showed Connected, but the instant Discord dropped our activity (an idle transition, a session RESUME, or its own status-change OP 3) our native re-push couldn't run and the RPC vanished permanently on a live socket. (This — NOT the asset-resolution dead end, which only affects the FIRST appearance since the resolved image caches — is the cause of an RPC that shows initially then disappears.) **Fix: the shim now runs a `setInterval(_vrca_sendPresence, 10000)` INSIDE the page**, coupling re-assertion to the same JS engine that keeps Discord's heartbeat alive — if the socket stays up, our re-assert stays running regardless of native→JS throttling.
  It's deduped against the native push (`_vrca_lastSentMs` stamped in `_vrca_sendPresence`; the interval skips if a send happened within 7s) so the foreground doesn't double OP 3 — the JS interval effectively only fires when native pushes are being throttled. Guarded against duplicate intervals on shim re-injection; dies with the WebView on teardown; no-ops while `_vrca_activity` is null (after `VRCA_clearActivity`).

- **Discord RPC activity persisted in `localStorage` (survives a page RELOAD) — the "reconnected but the RPC didn't reappear until I reopened the app" fix**: the in-page re-assert interval above only re-pushes when `_vrca_activity` is set, but a page **reload** (`onSessionExpired` session recovery / cache maintenance) starts a FRESH page with `_vrca_activity = null`. The only thing that would re-set it is the native `evaluateJavascript` push — which Chromium **throttles while the app is backgrounded** — so after a reconnect-via-reload the activity stayed null and the RPC was absent until the app was FOREGROUNDED (foreground unthrottles the native push). Compounding it: under Discord's `zlib-stream` compression the `READY`/`RESUMED` frame is binary, so the shim can't detect session-ready and the only post-reconnect re-push is the socket-`open` one-shots (+3s/+8s). **Fix: `_vrca_sendPresence` writes the activity to `localStorage['_vrca_last_activity']` on every send, and the shim init (`WS_HOOK_JS`)
  RESTORES it into `_vrca_activity`** — so a reloaded page has the activity immediately and the in-page `_vrca_pushInterval` (which runs even backgrounded, coupled to Discord's own JS engine) re-lands the RPC within ~10s of the gateway becoming ready, with NO native push required. `VRCA_clearActivity` removes the key so a reload can't restore a cleared RPC. (A restored activity may be image-less/slightly stale for one cycle; the next full native push upgrades it — far better than an absent RPC.)

- **Discord RPC compression-independent zombie detection (`_vrca_lastFrameMs`)**: the health probe's only zombie signal was "no heartbeat-ACK for >2.5× interval", derived from parsing op11 frames — but Discord's `zlib-stream` compression makes those frames binary/unparseable, so `_vrca_lastAckMs` never updated under compression and a dead-but-open socket falsely reported `alive` (a second "socket healthy but RPC gone" path). The shim now stamps `_vrca_lastFrameMs = Date.now()` on EVERY inbound `message` event (string OR binary — the event fires regardless of compression), and `VRCA_gatewayHealth()` returns `zombie` when no inbound frame of any kind has arrived for 90s on an open socket (a healthy gateway streams heartbeat ACKs ~every 41s plus event frames continuously). This rides the existing `zombie`/`bad` → `DEGRADED_RELOAD_THRESHOLD` (4 checks) reload path.

- **Discord WebView cache cap (`startCacheMaintenance`)**: the long-lived WebView loads the full discord.com app, which persists an HTTP cache + Code Cache that grow **unbounded** — the dominant contributor to the app's runaway on-disk "cache" size. The cap measures **ONLY `cacheDir/WebView`** (HTTP cache + Code Cache — the user-visible "Cache" number in App Info) against `WEBVIEW_CACHE_CAP_BYTES` (**64 MB** — deliberately ABOVE Discord's ~30-50 MB natural working set so the clear doesn't churn+re-download every check; do not lower it below that). Checks every 30 min with the first check 3 min after start. When over cap: clears the HTTP cache (`clearCache(true)`), best-effort deletes `cacheDir/WebView` contents directly (Code Cache is NOT cleared by `clearCache`; deleting from cacheDir is safe — the OS may wipe it anytime), then **tears down the RPC state (`shimReady=false` + `stopPresenceUpdates()` + status→RECONNECTING) BEFORE `reload()`ing**.
  **The teardown-before-reload is critical**: the reload destroys the page's injected shim (`window.VRCA_gatewayHealth`/`VRCA_setActivity`) and the gateway, but if `shimReady` stayed `true` the session monitor kept probing the reloading page. Its probe returned `no_probe` (health function undefined) which was grouped with `"alive"` as HEALTHY — so a reloaded/dead page kept reporting CONNECTED and **never recovered on its own; only toggling the RPC off/on fixed it** (the user-reported "RPC randomly stops after a while, a toggle fixes it, seems tied to the cache clearing"). Two coordinated fixes: (1) the cache reload now resets `shimReady`/presence like a planned reconnect (but does NOT consume a `sessionRecoveryCount` attempt — it's maintenance, not a failure); `onPageFinished` re-injects the shim and resumes presence + the monitor. (2) **`no_probe` is reclassified as a gateway-missing condition** (grouped with `no_gateway`, not `alive`) — because the health probe only runs while `shimReady==true`, an undefined `VRCA_gatewayHealth` can ONLY mean the shim was destroyed by a reload, so it re-injects then reloads after the threshold.
  Backstop: the JS-freeze detector (`JS_FREEZE_RELOAD_MS` 120s) runs BEFORE the `if(!shimReady) continue` guard, so even a reload that never re-injects (leaving `shimReady=false`) forces `onSessionExpired()` → full WebView recreation within 2 min. **`dataDir/app_webview` (profile data — cookies, localStorage, IndexedDB) is deliberately NEVER cleared**: Discord's `localStorage.token` is the gateway auth — the JS client uses it (not the cookie alone) for gateway Identify and API calls. The old code called `WebStorage.getInstance().deleteAllData()` which wiped `localStorage` including the token, killing the Discord session every time cache maintenance ran — the cause of "RPC shows for a bit then disappears" and the WebView not appearing as a logged-in device. Removing that call fixed it: the session now survives cache clears because only expendable HTTP/Code cache is touched. The loop is started when the WebView is created and cancelled in `teardown()`/`onDestroy()`. (Affects BOTH builds — Discord RPC isn't admin-gated.) **Coil's disk cache is also explicitly capped**: `VrchatImageLoader` sets `diskCache { maxSizeBytes(10 MB) }` at `cacheDir/image_cache` — Coil's DEFAULT is 2% of FREE disk space (hundreds of MB on a modern phone), the second silent "Cache" grower; the LRU journal trims any oversized pre-existing cache down to the cap on use.
