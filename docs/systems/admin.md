# Admin panel

_Scope: AdminUiKit, Dashboard, directory + detail (read model, polls, remote Start/Stop, invite-me/self-invite), AdminRuntime, public Discord button, live-while-open listener rule._

### Admin UI (Phase 6 redesign)

The admin panel shares one visual language defined in **`AdminUiKit.kt`** — all admin surfaces compose from these primitives so density + clarity stay consistent:

- `AdminTone` (Neutral/Primary/Success/Warn/Error/Info) + `toneColors(tone)` map a semantic tone to M3 container/on/accent colors.

- `AdminSectionCard(title, icon, tone, trailing) { content }` — an `ElevatedCard` with an icon-in-tinted-circle header. `AdminCardHeader(...)` is the standalone header for use inside an existing card/column (used to re-skin the detail sections without restructuring their bodies).

- `AdminStatTile(label, value, icon, tone)` — big-number dashboard tile.

- `StatusPill(text, tone)` — rounded status chip (replaces raw `Badge`s for ONLINE/VRC/BAN/WARN).

- `AdminLabeledRow(label, value, mono, labelWidth)` — label→value row (ids monospaced).

- `AdminAvatar(name, online, size)` — a first-letter **initial circle** plus an online/offline status dot. **Profile pictures are NOT shown in the admin UI at all** (final design): they were never stored in Firestore (deliberate cost decision), and the on-demand VRChat+ fetch through the admin's own session (`VrchatAuthManager.fetchProfilePicUrl(userId)` + Coil via `VrchatImageLoader`) **never worked reliably in practice and was removed entirely per the user** — `fetchProfilePicUrl` and its per-id cache are deleted from `VrchatAuthManager`, and `AdminAvatar` no longer takes a `vrchatUserId` param. Do NOT re-add admin profile pictures. **Discord profile pictures are likewise not shown** — the admin app has no access to another person's Discord account, so the only source would have been a stored `discordAvatarUrl` (removed long ago), and Discord is not auth-fetchable by userId.

**Profile-picture data flow (NONE — admin shows initials only)**: Profile pictures are deliberately **never stored in or read from Firestore** (cost), and since the on-demand admin-session fetch was removed (it didn't work), the admin UI renders **name initials only**. **No `vrchatProfilePic` or `discordAvatarUrl` fields are written anywhere** — removed from `VrcaViewModel.buildUserSnapshot()` + `captureStateForSync()`, from `VrchatPipelineService.onOpen` (the one-shot prompt write) and `syncPresenceToFirestore()`, and from `DiscordRpcService` (the avatar capture + prompt write are gone). `UserRow`/`UserDetail`/`parseUserRow` no longer carry avatar URL fields. (`firestore.rules` `selfMutableKeys()` still *permits* `vrchatProfilePic`/`discordAvatarUrl` for backward-compat with older public clients that may still write them — the keys are simply ignored on read; nothing in the current app writes them. `currentAvatarThumbnailImageUrl` / `vrchatAvatarThumb`, the *worn avatar's* thumbnail, is unrelated and still synced for friend-change notifications.) The `VrchatAuthManager.refreshProfilePic()` / `getStoredProfilePic()` helpers remain but are no longer wired to any write. **`VrchatImageLoader` (`com.vrca.admin`, Coil + session-cookie interceptor) still exists** but its only consumer is the PUBLIC build's VRChat tab (the user's OWN avatar + profile banner, authorised by that device's own session — which works).

**Dashboard** (`DashboardTab.kt`): a 2×2 stat grid (Users/Online/Warned/Banned via `AdminStatTile`) plus a **unified "Recent activity" feed** (`ActivityEvent` list) that replaced the old redundant "Live overview" count hero. The feed merges (sorted by time, capped 40) from: **moderationEvents** (ban/unban/warn/remove_warn/**ban_evasion_detected**), **announcements** posted (live/draft), and **VRChat platform status** incidents (`status.vrchat.com/api/v2/summary.json` via OkHttp — free, not Firestore). `ActivityEvent` carries a serializable `ActivityKind` enum (icon + tone derived at render time) so the feed can be persisted. **Read cost is near-zero by design — `DashboardFeedCache` persists the feed to the admin device** (SharedPreferences `vrca_admin_dashboard`, JSON) AND in a process-level cache: (1) re-entering the tab within `FEED_CACHE_TTL_MS` (60s) costs **0 reads**; (2) otherwise the fetch is **incremental** — `whereGreaterThan("createdAt", cursor)` per source, so it reads only genuinely-new docs (≈1 read per source = ~2 total when nothing's new, Firestore's per-query minimum).
  The full ~33-doc read happens **once** (first run), then the cursors (`newestModMs`/`newestAnnMs`) and cached events persist across app restarts. The refresh button (`feedTick`) forces an incremental fetch. Each row is an iconed circle + title + subtitle + compact relative time.

**Directory** (`UsersTab.kt` list): rows show `AdminAvatar` (initials) + name/secondary + world + a pill row (ONLINE/VRC/BAN/WARN), the user's **app version** (`versionName`, shown as muted `labelSmall` next to the pills — written by the public app as `BuildConfig.VERSION_NAME`. **`versionName`/`versionCode` ride `captureStateForSync()` (hourly/edit delta) AND `buildLivePayload()` (watched 10s loop)** so the admin's version column updates reliably after an app UPDATE — previously they were written only by `buildUserSnapshot()` + the bootstrap cold-boot `safeUser` write (which runs on a clean swipe-reopen/fresh install and is throttled 20 min), so a user who only warm-resumed could show a STALE version indefinitely. Now it self-corrects within an hour (or ~10s if watched); zero extra Firestore writes (piggybacks on writes that already fire) and carried on `UserRow`/`parseUserRow`/`UsersDirectoryCache`), and relative `lastActiveAt`. Header has search, warned/banned filters, count, refresh, +500 paging.

**Detail — remote OSC Start/Stop + sending/instance-type indicators (`UsersTab.kt`, zero bonus reads/writes)**: the detail's "Live Chatbox Output" card shows a **SENDING / IDLE `StatusPill`** in its header = the user's master OSC Start/Stop gate (`oscSending`, whether the chatbox is ACTUALLY transmitting — distinct from the per-feature Pinned/Cycle/Music/Time chips, which only say what's configured), plus a **single full-width Start/Stop toggle button** (like Home — red "Stop sending" while sending, filled "Start sending" while idle; device-only). **Optimistic UI (`optimisticSending`)**: the pill AND the button flip INSTANTLY on press (the user's app applies the command instantly too) instead of waiting on the sync; the override then reconciles to the AUTHORITATIVE synced `oscSending` — it's cleared when the synced value catches up to the command (success) OR after a 30s timeout (command didn't land → self-heals back to the real value). Because `oscSending` rides the watched 10s loop / 30s edit debounce / hourly delta, a genuine desync always corrects on the user's next liveness write. Cost model:
  `oscSending` is synced by piggybacking on writes that already fire — added to `VrcaViewModel.captureStateForSync()` (hourly delta) AND `buildLivePayload()` (the watched 10s loop, so it's live in the detail view within 10s) — it is display-only, NOT in any apply path (`applyOfflineToggleEdits`/`applyRemoteConfig` never touch it), so it never clobbers local runtime state; the admin reads it via the existing 10s detail poll → **zero bonus reads/writes**. Remote Start/Stop is the ONLY cost: **one write per press** — a single-doc `oscCommand`(`"start"`/`"stop"`)+`oscCommandAt`(serverTimestamp) to THIS device's doc (device-only, NOT `applyAccountWide`), read by the user's EXISTING moderation snapshot listener (`lastOscCommandMs` dedup, fresh <60s) → calls `startSending()`/`stopSending()`.
  **Clock-skew tolerance (`CMD_SKEW_TOLERANCE_MS` = 2 min)**: the freshness gate compares the SERVER `oscCommandAt` timestamp to the device's local wall clock; a device clock lagging the server made `(now - ms)` NEGATIVE on the admin's write snapshot, so the old `in 0L..60_000L` gate SKIPPED the command and it only applied on the NEXT 10-30s poll once the clock advanced (the tester-found "Start/Stop only happens on their 10-30s poll sync" bug). The gate is now `in -CMD_SKEW_TOLERANCE_MS..60_000L` so a skewed-but-fresh command applies on the FIRST snapshot. The SAME negative-lower-bound tolerance was applied to the `killSignal`, `logoutVrchatAt`, and `logoutDiscordAt` gates (identical latent bug). An **instance-type chip** (Public/Friends/Friends+/Group/Invite/Invite+ via `StatusPill`) sits next to the `📍 world (N/cap)` line, derived locally by `instanceTypeLabel(vrchatLocation)` from the already-synced/already-read location string (`~friends(`/`~hidden(`/`~group(`/`~private(`/`~canRequestInvite` markers, same logic as the public `parseInstanceType`) — no VRChat call, no reads/writes; hidden when the location is blank/redacted ("private"). `firestore.rules`:
  `oscSending` in `selfMutableKeys()`, `oscCommandAt`/`oscCommand` in `ownerOnlyUserKeys()`. `UserDetail` carries `oscSending`.

**Detail** (`UsersTab.kt` detail): **revamped** — a "Back to directory" row above an identity card with a large (60dp) `AdminAvatar`, prominent name + secondary name, status pills, optional world line, an `AdminLabeledRow` facts block (VRChat id / authUid / device / **a single "last seen"** liveness field — the old separate active/updated/synced rows were collapsed into one, sourced from the live 10s detail poll), and a tidy two-up action footer (**Moderate** + **Kill App** side-by-side instead of stacked full-width). `UserDetail` carries the live liveness timestamps so they refresh during watching. Below it, `DetailBlock` renders iconed `AdminCardHeader` sections: VRChat presence, Live Chatbox Output + remote toggles, Pinned message + presets, Cycle (interval editor in the header trailing slot), App & Updates + targeted APK push, and moderation flags. All prior admin capabilities are preserved — presentation-only over the same action logic.

**Moderation / Announcements / Log tabs**: re-skinned with `AdminCardHeader` (Gavel/Warning/Block/History/Campaign) and `StatusPill`s. Moderation's target card shows an `AdminAvatar` + BANNED/WARNED/DEVICE BAN/CLEAN pills and `AdminLabeledRow` ids. Announcements rows show LIVE/DRAFT + priority pills.

**Public-build Discord button** (`VrcaScreen.kt`): on the **public** build the top-bar navigation slot (where the admin Gavel sits on the admin build) shows a button with the **real Discord logo** (`res/drawable/ic_discord.xml`, the official Clyde mark as a tinted `VectorDrawable` rendered via `painterResource` — Material Icons has no brand logos, so the old `Icons.Filled.Forum` speech-bubble was a placeholder) when `config/app.discordInvite` is a non-blank link — tapping opens the invite externally. The admin sets the link in `ConfigTab` ("Discord invite link" field, saved to `config/app.discordInvite`). Blank link → button hidden. **The invite value rides `VrcaApp`'s single `config/app` snapshot listener** (the SAME listener that reads the ToS `tosVersion`/`tosText`/`tosUrl`) and is passed into `VrcaScreen(discordInvite=…)` — the old separate one-shot `get()` in `VrcaScreen` was deleted, so the config doc is read ONCE, and the button is now LIVE (an admin editing the link updates it without a relaunch).

**Live-while-open reads (foreground-scoped listeners)**: the design rule for admin-pushed content is a snapshot listener SCOPED TO THE FOREGROUND (a Compose `DisposableEffect` — attaches while the screen is composed, detaches on background/leave via `onDispose`). Its first callback is ONE read (same as a one-shot `get()`); it bills again only when a change actually lands while you're looking, and ZERO while backgrounded — so a push fans out only to currently-OPEN users. This is CHEAPER than a process-scoped (always-on VM) listener, which stays attached backgrounded and bills reads for changes nobody's viewing. Process-scoped listeners are reserved for things that must act while the app is CLOSED (the moderation/ban/kill listener in the app-scoped VM). Applied to: **ToS + `discordInvite`** (`VrcaApp` `config/app` listener, one doc), **in-app announcements** (`VrcaScreen` — `announcements where active==true` `DisposableEffect` listener, replacing the old one-shot `get()`; the background-surviving `VrchatPipelineService.attachAnnouncementsListener` is still the source of the NOTIFICATION when off-screen), **targeted releases** (`releases/{deviceHash}` `DisposableEffect` listener, already live), and **global "release to all"** (`VrcaApp` — a `releases/latest` `DisposableEffect` listener that shows the forced `UpdateDialog` live, never DOWNGRADING a newer targeted release already shown; the 6h `startAppUpdateCheckLoop` service poll stays as the backgrounded catch-up).

**Admin read model (Phase 3, admin-side only)**: The admin panel uses NO live collection listeners — those re-read on every user-doc change across the whole base, the dominant admin-side Firestore cost.

- **Directory** (`AdminScreen.kt` + `UsersDirectoryCache.kt`): **locally cached, zero-read on open.** The full user list is persisted to the admin device (`UsersDirectoryCache`, SharedPreferences `vrca_admin_directory`, JSON with timestamps as epoch-millis). Opening Dashboard/Users renders the cached list **instantly with 0 reads**; online/offline is recomputed locally from each row's cached `lastActiveAt`/`offlineAt` (`isUserOnline`), so cached rows decay to offline naturally without traffic. A full `get(Source.SERVER)` pull (limit `sharedLiveLimit`, default raised **500 → 2000** so the whole base loads — `+500` can raise further) happens ONLY when there's nothing cached (first-ever load) or the admin explicitly refreshed / paged (gated by `lastFetchedKey = "$sharedLiveLimit:$refreshTick"`). **Incremental liveness refresh (reads scale with ACTIVITY, not user count)**: because the cache freezes between full fetches, the online dots would go stale on a long-lived admin process. So when the directory is shown with a *populated* cache older than `DIRECTORY_REFRESH_TTL_MS` (10 min), an **incremental** query re-reads only users whose `lastActiveAt` advanced since the last refresh:
  `whereGreaterThan("lastActiveAt", cursor).orderBy("lastActiveAt", DESCENDING).limit(sharedLiveLimit)`. The cursor is `lastDirectoryRefreshMs - REFRESH_SKEW_MARGIN_MS` (5 min, to absorb client/server clock skew), or `now - ONLINE_STALENESS_WINDOW_MS` on a session's first refresh (so it reads exactly the currently-online set). **Idle/offline users have a stale `lastActiveAt` that doesn't match the inequality, so they cost nothing** — their cached rows decay to offline locally for free. As users settle offline the read count DROPS toward ~1 (an empty query's minimum) instead of staying at the full cached count; the only users read are those who came online or whose **hourly heartbeat just kicked in** (which advances `lastActiveAt` past the cursor, so the next refresh re-reads them and the merge REPLACES their stale cached row). **A swipe-away does NOT advance `lastActiveAt`** — it only stamps `offlineAt` (and deliberately does NOT bump `lastSeenAt`) — so the `lastActiveAt` query MISSES a swiped user once their `lastActiveAt` drifts older than the cursor, leaving their `offlineAt` stuck out of the cache and the row falsely "online" until the ~65-min staleness decay.
  To fix this the incremental refresh runs a **SECOND query — `whereGreaterThan("offlineAt", cursor).orderBy("offlineAt", DESCENDING)`** — and merges its docs (de-duped by id via `associateBy`) with the `lastActiveAt` query, so a recent swipe's `offlineAt` reaches the cache and the row flips offline on the next refresh. Costs ~1 extra read per swipe (Firestore's per-query minimum when none), so it stays bounded by activity. The merge (`LinkedHashMap` over cached + fresh) also ADDS newly-active users not yet in the cache. This NEVER scans the whole collection. Both queries are factored into a shared local suspend `incrementalDirectoryRefresh()`. **Three triggers feed it: (1) directory tab entry / cold launch (the directory `LaunchedEffect`); (2) app foreground-return — a `LifecycleEventObserver` bumps `resumeTick` on `ON_RESUME`, folded into the effect keys (but deliberately NOT into `lastFetchedKey`, so a resume never forces a full scan); (3) a LIVE periodic loop — a separate `LaunchedEffect(needsUsers)` re-runs `incrementalDirectoryRefresh()` every `DIRECTORY_LIVE_REFRESH_MS` (30s)
  WHILE the Dashboard/Users tab is composed.** Trigger (3) is the fix for "a swiped user never shows offline until the ~65-min mark": the TTL-gated triggers (1)+(2) only fire on tab-entry / resume, so an admin who just SITS on the directory never re-read — the swiped user's `offlineAt` landed in Firestore but never reached `sharedUsers`, and the only thing that flipped the row was the local `nowMs` ticker decaying `lastActiveAt` past 65 min. The 30s live loop re-reads the `offlineAt` query so a swipe surfaces within one cycle; it skips a cycle if a full/TTL refresh just ran (`now - lastDirectoryRefreshMs >= DIRECTORY_LIVE_REFRESH_MS`, so it never double-reads) and auto-cancels when leaving the directory tab (`needsUsers=false`). **The live loop is ALSO gated on `isForeground`** (the `LifecycleEventObserver` now tracks `ON_RESUME`→true / `ON_PAUSE`→false):
  Compose keeps a composed `LaunchedEffect` alive when the admin app is merely backgrounded, so without this gate an admin app **left open on the Dashboard/Users tab in the background polled Firestore every 30s indefinitely** — the dominant "reads keep climbing even though no admin is watching anyone" cost (it has nothing to do with watching a specific user; just sitting on the directory tab, even backgrounded/screen-off, drove it). With the gate the loop pauses the moment the app backgrounds and resumes on `ON_RESUME` (which also bumps `resumeTick` → a TTL-gated refresh re-freshens the directory). The TTL clock (`lastDirectoryRefreshMs`, a process-lifetime `AtomicLong`) is stamped on SUCCESS only (a full fetch also stamps it) so a failure or a resume-cancel retries on the next entry/resume; plain tab switches / brief resumes within the TTL cost **0 reads**. A `Refresh` icon button (Users header) and the Dashboard refresh button bump `refreshTick` — with a populated cache this runs the cheap **incremental** refresh, NOT a full pull; **`+500` (limit change)
  IS a genuine full pull** (`limitChanged` check on `lastFetchedKey`'s limit segment — the incremental path can only merge recently-active docs, it can never extend the loaded base). An open user's 10s detail poll also patches that one row live (`onUpdateUserRow`) regardless of the TTL. Sorted by `lastActiveAt ?? lastSeenAt` desc. **Count-mismatch reconcile (the "new user is counted on the Dashboard but missing from the directory" fix)**: a doc with NEITHER `lastActiveAt` NOR `offlineAt` — a brand-new user still on an app version predating the hourly liveness model, which only ever writes `lastSeenAt` — can **never** match either incremental `whereGreaterThan` query (Firestore inequality filters exclude docs missing the field entirely), so it would never enter the cache no matter how often the admin refreshed; before this fix only wiping the admin app's data (empty-cache full fetch) would surface it.
  The Dashboard's already-paid total `count()` aggregation exposes the divergence: after the count lands, if `totalUsersCount != sharedUsers.size` (cache populated, first load not in flight), `fullDirectoryFetch()` (the extracted full-pull helper, shared with the first-ever load) runs ONCE and replaces the cache — missing users appear, deleted ghosts drop. Throttled per count VALUE (`lastReconciledTotalCount`, process-lifetime `AtomicInteger`): if a reconcile didn't resolve the mismatch (a permanent skew between the count's `adminBuild==false` filter and the directory's self-filter), re-fetching won't either, so it waits for the count to actually change. **Legacy `lastSeenAt` sweep**: once such a legacy-version user IS in the cache, their liveness would still decay (their heartbeat advances only `lastSeenAt`, invisible to the two incremental queries) — so `incrementalDirectoryRefresh(includeLegacySweep)` runs a third `whereGreaterThan("lastSeenAt", cursor)` query, gated on the cache actually containing a row with `lastActiveAt == null && lastSeenAt != null` (self-extinguishing once stragglers update or vanish) and passed `false` from the 30s live loop (current-version users mirror `lastSeenAt` on every liveness write, so the sweep re-reads ~the whole recently-active set — ~2x reads per run — acceptable at tab-entry/TTL/manual granularity, not every 30s).

- **Aggregate stats** (`AdminScreen.kt` + `DashboardTab.kt`): `count()` server aggregations (total/warned/banned, ban-evasion) run **once on tab entry and on manual refresh** (keyed on `refreshTick`) — NOT polled on a timer. The old 60s poll burned reads for no benefit at that cadence. 1 read per 1000 docs counted.

- **Selected-user detail** (`UsersTab.kt`): the ONLY live read — a 10s `get(Source.SERVER)` poll loop scoped to the single open user, keyed on `selectedDocId` **AND `isForeground`**. Backing out (`selectedDocId → null`) cancels the coroutine so reads stop INSTANTLY. **Foreground-gated**: a `LifecycleEventObserver` in `UsersTab` flips `isForeground` on `ON_RESUME`/`ON_PAUSE`, and the poll's key includes it (with an early `return` when `!isForeground`), so leaving a user's detail page open and **backgrounding the admin app no longer keeps reading every 10s** — this was the dominant *"reads keep climbing even though no admin is browsing"* cost (the directory 30s loop was already foreground-gated; this 10s detail poll was NOT, the one loop that escaped the gate). The last loaded detail stays on screen while backgrounded and the poll resumes (re-fetching immediately) on `ON_RESUME`.
  **Live instance count**: the detail's `📍 world (N/cap)` count is fetched **live from the admin's OWN VRChat session** (`VrchatAuthManager.fetchInstanceCount` on the user's `vrchatLocation`, polled every 10s while the detail is open), overriding the Firestore-synced `vrchatInstancePlayerCount` so the admin sees an instant count independent of the user's sync chain; falls back to the synced value when the instance isn't visible to the admin / not logged in. **Self-invite ("Invite me to this instance")**: a footer button (gated on `VrchatAuthManager.isLoggedIn`) calls `VrchatAuthManager.inviteSelfToInstance(ctx, vrchatLocation)` → `POST /invite/myself/to/{location}` (the website "Invite Me" behavior) sending an invite to the ADMIN'S OWN VRChat account for the user's current instance — works for invite-only/friends+/group; the user is NOT notified. Reads the freshest location from `selectedDetail` (UserRow doesn't carry `vrchatLocation`); disabled when not a joinable `wrld_` instance. **Invite/invite+ nonce preservation (the fix that made self-invite work for those two instance types)**: the self-invite needs the `~nonce(...)` access token embedded in the synced `vrchatLocation`.
  `/users/{id}` REDACTS invite/invite+ locations to `"private"` (dropping the nonce) even for the user's OWN account — friends/friends+ are NOT redacted, which is why those self-invites already worked but invite/invite+ failed with "not accessible". Two guards now keep the full joinable location: (1) `fetchPresence` no longer lets `/users/{id}`'s `"private"` DOWNGRADE a full `wrld_` location from `/auth/user` (a real `wrld_` location or an `"offline"` departure still overrides, so stale-presence correction is unaffected); (2) `syncPresenceToFirestore` keeps the full nonce-bearing location captured by the WebSocket self `user-location` event when the REST poll returns `"private"` (`"private"` means still-in-instance, so this can't resurrect a left instance — a real departure reports `"offline"`). The user's OWN `invite_me` (from a world-invite notification) was always fine because the invite payload carries the full nonce. **Invite-only fallback — the USER's app invites the admin (`SelfInviteCoordinator`, `SelfInviteStore`)**:
  `inviteSelfToInstance` (the admin inviting THEMSELVES) is rejected for **invite-only** instances the admin has no standing in (the `~nonce` fix only covers invite/invite+). So the button tries `inviteSelfToInstance` first (covers public/friends/friends+/group/invite+) and, on failure, calls `SelfInviteCoordinator.runAdminSide`, which flips who invites: the **USER** (who IS in the instance, so may invite anyone) invites the admin.
  Signaling is a Firestore handshake on `users/{deviceHash}` — admin writes owner-only `selfInviteReqId`/`selfInviteAdminId`/`selfInviteLocation`/`selfInviteAt`; the user's moderation listener (`handleSelfInviteSignal`, deduped by the signal ms via `SelfInviteStore.lastHandledSignalMs`) runs `runUserSide`, which (1) tries a **direct** `inviteUserToInstance(adminId, location)`, and (2) only if VRChat rejects it, runs a hidden **friend → invite → unfriend dance**: user sends a friend request to the admin, writes back `selfInviteStatus="need_friend"` (self-mutable echo of the reqId), the admin (polling the doc) sends its own request so VRChat **auto-befriends on the mutual request**, the user re-invites once friends, then **force-unfriends 10s later no matter what**.
  **Safety invariants**: a counterpart is only ever unfriended if it was NOT a friend before the dance (checked via `getFriendStatus`; the fallback only runs when the direct invite failed, which already implies not-friends — a real friendship is never severed); the unfriend obligation is persisted to `SelfInviteStore.pendingUnfriend` **before** friending, so a connection dip / app death still cleans up on the next pipeline connect (`SelfInviteCoordinator.drainPendingUnfriend`, wired into `onOpen`, runs on both builds). **No indicators on either side**: `SelfInviteStore.isFriendNotifSuppressed(id)` (true for the global owner VRChat id OR any id in the local pending-unfriend set) gates the shared `VrchatPipelineService` friend-add / friend-delete / friend-request / offline-unfriend-diff handlers — cache/dedup bookkeeping still runs, only the notification is hidden.
  The **user** suppresses via the owner id (set from `config/app.ownerVrchatId` — written by the admin build in `runAdminSide` — AND from the signal's `adminId`) + the admin in its pending set during the dance; the **admin** suppresses the user's id (added to its pending set at signal time, before the user's request can arrive). **Only friend-list notifications are gated** — bio/name/rank/online/etc. about the owner still fire. **Suppression covers ALL friend firing paths** — the live `friend-add`/`friend-delete`/`friendRequest` handlers, the offline unfriend-diff, AND the REST **backfill** friendRequest (that last one was a hole: the live path suppresses by returning BEFORE recording the `fr_` dedup id, so the backfill re-fired it on the next connect). **The unfriend-event race**: the friend-delete WebSocket event arrives AFTER the unfriend REST call returns, so the cleanup keeps the counterpart in the suppression set a `SUPPRESS_GRACE_MS` (8s) window PAST the unfriend before `removePendingUnfriend` — otherwise "removed from friends list" slipped through on the admin side (the user side is permanently covered by `ownerVrchatId`). **Invite speed**:
  `runUserSide` **retries the invite directly** (every 1s) instead of polling `friendStatus` — the invite succeeds the instant they're friends server-side, sidestepping VRChat's `friendStatus` eventual-consistency lag (that lag was a ~10s stall before the invite fired); the admin's mutual-request poll is 1s. **The retry delay RAMPS (1s→3s, `INVITE_RETRY_MAX_STEP_MS`)** so the normal case still fires in ~2-3 tries but a never-forms failure can't hammer VRChat at 1/s (a full self-invite is ~5-8 VRChat REST calls; the status poll is Firestore, not VRChat). **The unfriend cleanup is DETACHED** (`scheduleCleanup`, a process-lifetime `CoroutineScope`) so `runAdminSide` returns the "invite sent" result the INSTANT the user's app reports it — the cleanup's 10s force-unfriend + 8s grace used to run BEFORE the return, so the admin UI sat on the "processing" spinner for ~18s after the invite had already landed (the reported "UI keeps acting like it's processing" bug). The persisted pending-unfriend backup + drain-on-connect still cleans up if the process dies before the detached coroutine runs. VRChat friend REST added to `VrchatAuthManager`:
  `getFriendStatus` (`GET /user/{id}/friendStatus`), `sendFriendRequest` (`POST /user/{id}/friendRequest`, mutual auto-friend), `cancelFriendRequest` (`DELETE …/friendRequest`), `unfriendUser` (`DELETE /auth/user/friends/{id}`). `firestore.rules`: signal keys in `ownerOnlyUserKeys()`, status keys in `selfMutableKeys()`. The loop shows a spinner on first load then refreshes silently. 10s matches the cadence at which the watched user app refreshes its volatile fields. **Watched fast-offline (`WATCHED_STALE_WINDOW_MS` = 25s, `WATCH_RAMP_MS` = 45s)**: a watched user's app writes a liveness timestamp every 10s — `lastSeenAt` via the ViewModel live loop (dependency-free, the RELIABLE heartbeat) and `lastActiveAt` via the presence loop (which can stall if VRChat's `fetchPresence` 401s on an IP-invalidated cookie) — so a heartbeat that stops advancing **while watched** means the app died/was swiped, far sooner than the 65-min unwatched window can prove. The detail poll tracks the **FRESHEST of `lastActiveAt`/`lastSeenAt`** (`maxOf`, so a stalled `lastActiveAt` never false-flags a live user whose `lastSeenAt` is still advancing) and the wall-clock time it last advanced.
  **Loop-confirmed detection**: once the poll has SEEN the heartbeat advance at least once (`loopConfirmed`), a stopped heartbeat flips offline after just `WATCHED_STALE_WINDOW_MS` (≈2.5 missed ticks) — no need to wait the full ramp; before the loop is confirmed (its 10s loop hasn't started yet, or **the user was already DEAD when the admin opened them** — force-killed/swiped with no `offlineAt` landing, so there is no heartbeat to observe) it falls back to the `WATCH_RAMP_MS` (45s, reduced from 90s) grace so a live user isn't false-flagged mid-ramp. The 45s ramp is the fix for "opening an already-offline user doesn't flip them offline": `AdminRuntime.setSelectedUser` fires the `watcherActiveAt` write IMMEDIATELY on open, so a genuinely-LIVE user's first heartbeat reaches the poll within ~15-25s — 45s clears that chain with margin while flipping a dead user offline far faster than the old 90s. (If the ramp ever false-flags a live user, it SELF-HEALS the instant the heartbeat advances.) When stale, the poll **synthesizes `offlineAt = now` on the in-memory `UserDetail`** (zero Firestore write).
  This flips `isUserOnline` offline in the detail AND, via `onUpdateUserRow`, in the directory + cache — and is the ROBUST swipe→offline path because it does NOT depend on the swipe-time `offlineAt` write landing during the chaotic shutdown (that write is the instant-when-it-lands bonus). It self-heals: when the heartbeat advances again the poll stops synthesizing and carries the doc's real `offlineAt`. **For this to clear correctly, both the detail-view row merge and `onUpdateUserRow` treat the loaded detail's `offlineAt` as AUTHORITATIVE (no `?:` fallback to the directory row's value) — a null `offlineAt` from the poll must be able to clear a stale/synthetic marker** so a healed user returns online.

- The `watcherActiveAt` heartbeat (`AdminRuntime`) writes every 30s while a user is selected. No periodic writes from the user app outside the watched-user live loop.

- **`AdminRuntime`** (`com.vrca.admin`): process-lifetime singleton owning the force-kill staleness sweep and `watcherActiveAt` watcher heartbeat — moved out of Compose `LaunchedEffect` so they keep running while the admin app is backgrounded. Compose only registers intent (`setBrowsing`/`setSelectedUser`/`updateSweepData`). (The `config/adminPresence.browsingAt` heartbeat it used to write was REMOVED — see "Browse heartbeat (FULLY REMOVED)" above; `setBrowsing` now only gates the local sweep.) **Foreground gating (`setForeground`)**: the latched intent is the problem when the admin merely BACKGROUNDS the app (no swipe / Activity destroy) — `onDispose` never fires, so `browsing`/`selectedUser` stay set and the watcher loop kept writing `watcherActiveAt` every 30s indefinitely, holding that user in 10s live-sync while no admin was actually looking. `AdminScreen`'s `LifecycleEventObserver` now calls `AdminRuntime.setForeground(true/false)` on `ON_RESUME`/`ON_PAUSE`, and the watcher heartbeat, the immediate-on-select write, and the staleness sweep all gate their WRITES on `foreground.value`.
  The intent stays latched (not cleared), so returning to the foreground resumes exactly where it left off — but a backgrounded admin emits **zero** periodic writes. (This deliberately narrows the earlier "admin watches while backgrounded" intent in favor of cost: an admin who isn't on-screen shouldn't keep a user in live-sync.) **Directed-release APK picker state (`pickedApkState`/`ingestPickedApk`/`clearPickedApk`)**: the admin detail view's "Pick APK" (directed release) launches the system file picker (DocumentsUI). The heavy admin app (Discord WebView + foreground services + Coil loader) is routinely EVICTED while DocumentsUI is foreground, so on return the admin **Activity is recreated** — `AdminScreen.sharedUsers` (plain `remember`) resets to empty, the detail view (gated on `if (rawRow != null)`, i.e. the selected user being present in `users`) is briefly disposed, and any plain-`remember` picker state inside it is lost AND the file-copy coroutine on the composition scope is cancelled. That was the "picking an APK doesn't apply and resets the detail view" bug.
  Fix: the picked APK (cache path + parsed `versionCode`/`versionName` + filename + error, keyed by `docId`) lives in `AdminRuntime` and the URI→cache copy + `parseApkInfo` run on `AdminRuntime.scope` (process lifetime), NOT the composition. `UsersTab` reads it back via `pickedApkState.collectAsState()` filtered to the open `docId`, so the rebuilt detail view re-shows the pick. `ingestPickedApk(appContext, docId, uri)` uses the APPLICATION context (the Activity may not survive); `clearPickedApk(docId)` is called after a successful push (also deletes the cached file).
