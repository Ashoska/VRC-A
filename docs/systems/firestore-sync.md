# Firestore schema, sync + cost model

_Scope: users/{deviceHash} fields, liveness (lastActiveAt/offlineAt), cold-open/hourly/debounced writes, watcher live mode, echo suppression, admin offline edits, cross-device sync, admin online detection, remote config, device hash, rules._

- **Device hash per build variant**: `MainActivity.ensureDeviceHash()` derives the `users/{deviceHash}` doc id from `computeBaseDeviceHash()` (`sha256("v2:$androidId:$signingCert")`, with a stored random fallback for blank ANDROID_ID). The **admin build** namespaces this as `sha256("admin:" + base)` so it resolves to a DISTINCT doc from the public build on the same phone — without this, both installs share one ANDROID_ID + signing key → one doc, so their presets/content overwrote each other AND the admin user-list self-filter (`it.id != myDeviceHash` in `AdminScreen`) hid the public install. With the distinct admin hash: (1) the two installs no longer sync (the admin build's moderation listener watches its own empty doc, not the public one); (2) the public install now appears in the admin Users tab / Dashboard so directed releases can be tested against it. The admin build never writes a user doc — `performSelfSync()`, `applyRemoteContentBeforeSync()`, and `applyRemoteConfig()` all early-return on `IS_ADMIN_BUILD`, so no orphan doc is created under the admin hash AND the admin's chatbox presets/messages live purely in local DataStore.
  (This gating was missing before: the admin build was reading its own `users/{adminHash}` doc back into DataStore on every launch via `applyRemoteContentBeforeSync`/`applyRemoteConfig`, which overwrote fresh local presets with a stale earlier snapshot — the "admin reverts to a past synced state on reopen" bug. With the three gates in place, DataStore is the sole source of truth for the admin build's content.) The admin hash is force-normalised on launch (overwrites any previously-cached public-equal hash). Public-only users are unaffected — their seed/hash is unchanged.

- Firestore rules: `firestore.rules` (uses `isOwner()` via `config/app.ownerUid`, NOT `sign_in_provider`). **Hardening (Phase 7)**: `selfMutableKeys()` includes `lastActiveAt` (hourly heartbeat write); `ownerOnlyUserKeys()` explicitly includes `killSignal` (defensive — self-update already can't touch it since it isn't in `selfMutableKeys()`). `announcements` read is `isOwner() || (signedIn() && resource.data.active == true)` — drafts (active==false) are owner-only and unauthenticated scraping is blocked; both client listeners already filter `active==true` so list queries pass per-doc. `users/{deviceHash}/live/{doc}` subcollection is readable by the owner or the device-doc owner, writable by the device-doc owner or admin. `bannedIdentifiers` `get` stays `signedIn()` (the client ban check reads its own vrchatId, unverifiable in rules) but `list` is owner-only so the collection can't be enumerated.

### Firestore Schema (users/{deviceHash})

Key fields written by the app:

- `isOnlineInApp` (bool): Set to `true` by the app-open write, `false` by the swipe-away shutdown and `VrcaViewModel.onCleared` (GlobalScope fallback). **Swipe-away shutdown is centralised in `AppShutdown.onTaskSwiped(context)`** (`com.vrca.app.AppShutdown`), called from the `onTaskRemoved` of EVERY foreground service. This was a real bug: the kill used to live only in `VrchatPipelineService.onTaskRemoved`, but the pipeline isn't always running, and **`KeepAliveService` — which IS always running (started from `MainActivity.onCreate`) and holds a `PARTIAL_WAKE_LOCK` — had no `onTaskRemoved` at all**, so after a swipe the wakelock-holding service kept the whole process alive and nothing ever killed it.
  Now an `AtomicBoolean` in `AppShutdown` makes the heavy work run exactly once no matter which service fires first: it stamps the `manual_kill_at` flag, stops the other services (`VrchatPipelineService`/Discord/KeepAlive/Overlay, releasing wakelocks AND removing the "Connected as X" persistent notification promptly — without stopping the pipeline service here its notification lingered for up to 5s, the offline-write await, before `killProcess`, which looked like the swiped app was still "running / connected as username"), then on a background thread **awaits the offline Firestore write (5s timeout) and hard-kills the process** (`Process.killProcess` + `exitProcess`). `KeepAliveService.onTaskRemoved` is the reliable entry point since it's always running. The await ensures the going-offline write has a chance to reach Firestore before the kill; if it times out, the admin-side staleness sweep still flips the user offline once `lastActiveAt` ages past the ~65-min window. (Previously it waited a fixed 10s before killing, leaving the app running in the background that whole time.) **Sticky-restart guard**:
  `VrchatPipelineService`, `DiscordRpcService`, and `KeepAliveService` all return `START_STICKY` (so a memory-pressure kill is recovered), which means Android would normally relaunch them with a null intent right after the swipe-kill — making the app look like it was never killed. To prevent this, `AppShutdown` stamps `manual_kill_at = now` (SharedPreferences `vrca_remote`, committed synchronously) before killing; each service's `onStartCommand` treats a **null intent** as a sticky restart and, if `AppShutdown.isManualKillFresh()` (within `MANUAL_KILL_WINDOW_MS` = 15s), calls `stopForeground` + `stopSelf`, returns `START_NOT_STICKY`, AND kills its own (freshly-resurrected) process after a 300ms delay — because `stopSelf` alone leaves the recreated process sitting idle as a cached background process (Samsung's "running apps" list still showed it). The delay lets `START_NOT_STICKY` register before the kill so Android does NOT recreate the service yet again. A legitimate reopen always passes a non-null intent (with `EXTRA_DEVICE_HASH`) so it bypasses the guard, and the 15s window expires harmlessly. (Note:
  `NowPlayingListenerService` is a `NotificationListenerService` the system binds independently; it can be rebound by the OS later when notification activity occurs, but that no longer keeps the process perpetually alive after swipe.) **Persistent swipe flag (`swiped_away`)**: the 15s `manual_kill_at` window is NOT enough on its own — the `PipelineWatchdogWorker` (WorkManager, ~15 min) survives the process kill and fires in a fresh process LONG after the window expired, sees the user still logged in, and resurrects the pipeline + keep-alive. That was the "I swiped it away but it starts running again after a while" bug. So `onTaskSwiped` ALSO sets a persistent `AppShutdown.KEY_SWIPED_AWAY=true` boolean (committed synchronously) and best-effort cancels the watchdog (`PipelineWatchdogWorker.cancel`). The watchdog `doWork()` and every service's null-intent sticky-restart guard now back off when `isManualKillFresh() || isSwipedAway()`. The flag is cleared ONLY by a real user reopen (`MainActivity.onCreate` → `AppShutdown.clearSwipedAway()`) or reboot (`BootReceiver` clears it then restarts services).
  An OS/OEM kill never runs `onTaskSwiped`, so the flag stays false there and the watchdog still recovers the process — **a deliberate swipe stays dead, an OEM kill comes back.** **Stale-notification hardening (the "Connected as X doesn't consistently disappear on swipe" fix)**: (1) the kill thread enforces a **minimum 1.2s shutdown floor** (`MIN_SHUTDOWN_DELAY_MS`) before `killProcess` — `stopOtherServices()` only QUEUES the stop requests from `onTaskRemoved` (main thread); the actual `onDestroy`/`ACTION_STOP` handling runs on the main looper after it returns, so a fast (or null-task) offline write let `killProcess` race the stops and all four still-foreground services died abruptly — exactly where OEMs (Samsung) leave the shared notification stale in the shade; (2) right before `killProcess` the thread calls **`AppShutdown.cancelPersistentNotification()`** (`nm.cancel(SHARED_NOTIF_ID = 1001)`, processed in system_server so it survives our death — ignored while a live FGS still owns the id, a cleanup sweep once they've stopped); (3) each sticky-restart guard's delayed kill thread (KeepAlive/Pipeline/Discord) also calls it, because `KeepAliveService.onCreate` re-posts the notification BEFORE the `onStartCommand` guard runs and the `stopForeground(STOP_FOREGROUND_REMOVE)` removal can race the 300ms-delayed kill.

- `lastActiveAt` (timestamp): **Canonical liveness field (hourly model).** Written on cold-open and then once per hour by `VrcaViewModel.startHourlyHeartbeat()` (in-process coroutine — a swiped/OS-killed app stops firing it, so it goes stale and is correctly counted offline; an AlarmManager wakeup is deliberately NOT used because it would resurrect a dead app and make it report online forever). Also refreshed every 10s while an admin is watching this user (real-time ~25s liveness for the watched user). Admin online = `lastActiveAt` within ~65 min (see "Admin online detection" — the admin ignores the `isOnlineInApp` flag entirely and keys on this timestamp's freshness, minus a newer `offlineAt` marker).

- `offlineAt` (timestamp): **Clean-shutdown marker.** Written (alongside `isOnlineInApp=false`) ONLY on a deliberate swipe-away by `AppShutdown.buildOfflineWriteTask` and `VrcaViewModel.onCleared`. The admin's `isUserOnline` forces a row offline the instant `offlineAt` is newer than `(lastActiveAt ?? lastSeenAt)`, giving instant swipe→offline; a live heartbeat advances `lastActiveAt` past it so it can never false-flag a running app. If the swipe write never lands, the ~65-min staleness window still flips the user offline. **Both offline writes deliberately do NOT bump `lastSeenAt`** — refreshing the liveness mirror on shutdown would let `offlineAt > (lastActiveAt ?? lastSeenAt)` TIE (both the same serverTimestamp) for any user whose `lastActiveAt` is somehow absent, keeping a swiped app falsely "online" until the 65-min decay; `offlineAt` is the sole shutdown marker. In `selfMutableKeys()`.

- `lastSeenAt` (timestamp): **Legacy mirror of `lastActiveAt`** — written with the same server timestamp on every liveness write so older admin builds that read `lastSeenAt` keep working (additive migration; nothing removed). New admin code should read `lastActiveAt`.

- `afkEnabled`, `cycleEnabled`, `spotifyEnabled`, `timeEnabled`: Feature toggles (admin-editable)

- `warned`, `banned`, `warnReason`, `banReason`: Moderation flags (read by public app via snapshot listener)

- `targetedUpdateUrl` / `targetedUpdateNotes` (strings): **Legacy** — kept for backwards compat with old app versions. New directed releases use `releases/{deviceHash}` instead (see below).

- `watcherActiveAt` (timestamp): **Admin-only write.** Refreshed every ~30s while an admin has this user's detail page open. User app reads it from snapshots and feeds into `AdminWatchState.updateFromTimestampMs` — if within 60s, live-mode loops start.

- `killSignal` (timestamp): **Admin-only write.** Written by admin kill switch button. User app reads it from moderation snapshot listener — if fresh (within 60s), kills the app process.

- VRChat presence fields (`vrchatUserId`, `vrchatDisplayName`, `vrchatState`, `vrchatLocation`, etc.): Written every 10s while watched (real-time), AND refreshed by the **hourly delta** (`captureStateForSync` reads `VrchatPipelineState.presence`, null-safe — keys omitted entirely when not logged into VRChat so stale doc values are never clobbered with blanks). So an unwatched user's directory row shows location at hourly freshness. **Instance player count freshness (`refreshInstanceCountBeforeSync`)**: `vrchatInstancePlayerCount`/`vrchatInstanceCapacity` ride the hourly delta but were going STALE for unwatched users (frozen at the last successful heavy `fetchPresence` chain — often `0/N` when the location was patched from a `user-location` WebSocket event, which carries no count, and no later `fetchPresence`/`fetchInstanceCount` succeeded).
  `startHourlyHeartbeat()` now calls `refreshInstanceCountBeforeSync()` immediately before each `performSelfSync()` — a single lightweight `GET /instances/{loc}` (`VrchatAuthManager.fetchInstanceCount`, the same call the watched fallback + website tab-refresh use) that patches the live count into `VrchatPipelineState.presence` so the hourly write carries an accurate number. **Zero extra Firestore cost**: the hourly write already fires unconditionally (liveness) and already carried these two fields — the count was just stale; this only adds ONE VRChat REST call per hour per online user (not a Firestore read/write).

- NowPlaying / preview fields (`nowPlayingTitle`, `nowPlayingArtist`, `combinedPreviewText`, `activePackage`): **Volatile** — these change constantly during music playback. Real-time (10s) only while watched via the watcher-gated live-sync loop; never written on raw NowPlaying state emissions (that caused a write storm with no admin present). **They also ride the hourly delta + any debounced edit write** — `captureStateForSync()` includes them, so they're swept up whenever a write fires anyway (Firestore bills per doc write, not per field — zero extra writes; the 30s edit debounce is still only SCHEDULED by genuine content edits, never by NowPlaying ticks). History: these fields were in `buildUserSnapshot` (with a comment claiming "included in every self-sync write") but were silently dropped when the delta-write model introduced `captureStateForSync()` without them — `buildUserSnapshot` only fires on first install / uid change, so unwatched users' previews froze at their last watch session ("hourly write doesn't update preview/presence" bug). `VOLATILE_SYNC_KEYS` excludes them from `captureContentForOfflineWrite` (the swipe write deliberately omits volatile preview; the service's offline write already carries final presence).

- `lastReportedTime`, `cycleTrimWarning`, `lastTimeUpdateAt`: Only written while watched (live-mode loop).

**Friends are no longer in Firestore** — `savedFriendIds`/`savedFriendNames` are deleted via `FieldValue.delete()` on offline write. They live in local SharedPreferences only.

**Volatile subdoc `users/{deviceHash}/live/state`** (Phase 2 infrastructure — rules deployed, write migration deferred): Firestore rules allow the subcollection `users/{deviceHash}/live/{doc}`. It was intended to hold high-frequency volatile data (nowPlaying, VRChat presence, preview text) to keep them off the main doc. After the Phase 3 read-model change the admin detail view polls the **main doc** every 10s (no admin-side collection listener at all), so volatile fields stay on the main doc for now — splitting them out would require the admin detail poll to read two docs for no current benefit. The rules remain in place as future-proofing; revisit only if the user's own self-doc listener firing on watched-user volatile writes (echo-suppressed today) becomes a measured cost.

### Firestore Sync Architecture

The sync model is intentionally minimal — Firestore costs money and we only push to it when we have to. Three classes of writes:

1. **App-open / cold-open write (one)**: After `initialDataLoaded` flips, `applyRemoteContentBeforeSync()` reads the Firestore doc to pick up any admin edits made while the user was offline (messages, presets, intervals — not toggles, which always start OFF), then `performSelfSync(coldOpen = true)` runs once with the merged state (`isOnlineInApp=true`, `lastActiveAt`). On first install or when `lastSyncedValues` is empty, this is a full ~40-field snapshot write (handles doc creation). On subsequent cold-opens with a persisted baseline, this is a **delta write**: only liveness fields + any content that changed since the previous session are written — unchanged presets/chatbox stay untouched.
  **Cold-open liveness throttle (`COLD_OPEN_LIVENESS_THROTTLE_MS` = 20 min)**: the background-survival stack (`START_STICKY`, the ~15-min `PipelineWatchdogWorker`, `BootReceiver`, OEM killers) resurrects the process repeatedly, and EACH resurrection re-ran this cold-open delta write (4 liveness fields) plus a self-listener echo read — that per-restart cost × frequent kills was the dominant *"steady Firestore reads/writes even with no admin browsing"* source (each cold start also re-attaches ~4-6 snapshot listeners, whose initial reads stack into the periodic read spikes). The cold-open write is now SKIPPED when (a) it's `coldOpen`, (b) the delta is liveness-ONLY (no content changed — gated on `LIVENESS_KEYS`), and (c) the last *actual* write (`PREF_LAST_SELF_SYNC_MS`, persisted via `markSelfSyncWritten()`) was within the throttle window. The still-fresh `lastActiveAt` already proves online, so status is unaffected; the **hourly heartbeat is anchored to the last real write** (first tick delay = `HOURLY - sinceLastWrite`, floored 60s) so a liveness write still lands within the 65-min staleness window even when the cold-open is skipped.
  A 15-min churn cadence drops from ~4 writes/hr to ~2/hr; a pathological fast (<20 min) restart loop writes at most once per ~20-40 min instead of once per restart. The first-ever sync and any content delta are NEVER throttled. **`clearSwipedAway` (called from `MainActivity.onCreate` on a real user reopen) also clears `PREF_LAST_SELF_SYNC_MS`** so the throttle can never suppress the cold-open write after a swipe — the stale `offlineAt` on the doc MUST be overridden by a fresh `lastActiveAt` or the user stays offline in the directory.

2. **Hourly liveness + delta write (periodic, the ONLY steady-state periodic write)**: `VrcaViewModel.startHourlyHeartbeat()` fires once per hour after the cold-open write. Each tick calls `performSelfSync()` which always writes liveness (`lastActiveAt`, `isOnlineInApp`, `lastSeenAt`, `updatedAt`) and includes only content fields that changed since the last write (field-by-field delta comparison against `lastSyncedValues`). **The delta map (`captureStateForSync`) also carries the volatile preview/nowPlaying fields and the VRChat presence snapshot** (see schema notes above), so an unwatched user's directory row (preview text, current track, VRChat location) refreshes at hourly granularity for free — same single write, more fields. If nothing changed, only the 4 liveness fields are written — a single minimal merge. It is an **in-process coroutine**, NOT an AlarmManager wakeup: a swiped/OS-killed app stops firing it → goes stale → correctly counted offline.

3. **App-close write (one)**: `VrchatPipelineService.onTaskRemoved` / `AppShutdown` writes `isOnlineInApp=false, offlineAt, lastSeenAt` plus current VRChat presence fields if available. `VrcaViewModel.onCleared` writes `isOnlineInApp=false, offlineAt, lastSeenAt` via `GlobalScope` as a fallback for cases where the foreground service isn't running. The `offlineAt` server timestamp is the authoritative clean-shutdown marker the admin reads for instant swipe→offline (see "Admin online detection").

4. **Edits use a 30s idle-debounce write**: changing a toggle/message/preset persists to local DataStore immediately (as always) AND schedules ONE delta write 30s after the last edit via `startSelfSyncLoopIfNeeded()` (`SELF_SYNC_DEBOUNCE_MS = 30_000`). Each edit cancels+reschedules, so a burst of edits flushes exactly once. (This was briefly a true no-op during the Phase-1 cost reduction, but that made "edit a preset then close the app" revert on reopen — the app-open read overwrote the not-yet-synced edit — so the debounced write was restored in commit `e21103e`. `performSelfSync` writes only changed content + liveness, so an idle user who isn't editing schedules nothing. The call sites fire ONLY on genuine content/toggle changes, never on NowPlaying ticks or preview rebuilds.) Still pushed on the next hourly tick too (or instantly via the 10s live loop if an admin is watching). **Note: this means an actively-editing user, or a content change pulled in by cross-device sync, costs one write per 30s-quiet-period — it is NOT zero per-edit.**

**Hourly liveness model (Phase 1)**: Liveness is determined by `lastActiveAt`, written once per hour by `VrcaViewModel.startHourlyHeartbeat()` (anchored to cold-open) and every 10s while an admin watches this user. Admin online = `lastActiveAt` within ~65 min (or ~25s for a watched user). `lastSeenAt` is written as a legacy mirror (same timestamp) so older admin builds keep working. **Removed in Phase 1**: the 30s browse-gated heartbeat, the 5-min always-on heartbeat, the per-edit debounced self-sync, and the browse-volatile 30s loop — none of these write to Firestore anymore. An admin merely browsing the directory causes **zero** per-user writes; only opening a specific user's detail (which flips `AdminWatchState.isWatched`) starts that one user's 10s live loop.

**Browse heartbeat (FULLY REMOVED)**: Previously, when an admin was on the Dashboard/Users tab the admin app wrote `config/adminPresence.browsingAt` every 30s and public apps ran a 30s `lastSeenAt` heartbeat while that was fresh. Phase 1 made the public-side write a no-op but the admin still WROTE `browsingAt` and every public app still held a `config/adminPresence` snapshot listener feeding `AdminBrowsingState`. That listener was the single biggest admin-side read cost: every 30s `browsingAt` write fanned a billed read out to EVERY online user's listener (~120k reads/hour at 1k users) for ZERO benefit (nothing reads `AdminBrowsingState` to drive a write under the hourly model — `startBrowseVolatileSyncWatcher` is empty). Now **both sides are gone**: `AdminRuntime` no longer writes `browsingAt` (its loop only runs the local force-kill staleness sweep), and `VrchatPipelineService` no longer attaches the `config/adminPresence` listener. (`AdminBrowsingState` remains as dead code, unfed.)

**Slow always-on lastSeenAt heartbeat (REMOVED in Phase 1 — historical)**: The service used to write `lastSeenAt` every 5 minutes (`LASTSEEN_HEARTBEAT_MS`) while alive (~288 writes/user/day). This is replaced by the once-per-hour `lastActiveAt` write (~24 writes/user/day) owned by the ViewModel. The constant and `writeHeartbeat()` are deleted.

**Live-mode (watcher-gated)**: When an admin opens a specific user's detail page in the admin panel, the admin app refreshes `watcherActiveAt` every ~30s on that user's doc. The user app's snapshot listener feeds the timestamp into `AdminWatchState`; if fresh (within 60s), `isWatched` flips to true and two side-effects start:

- `VrcaViewModel.startLiveSyncWatcher` writes `buildLivePayload` (nowPlaying, preview, the feature toggles `afkEnabled`/`cycleEnabled`/`spotifyEnabled`/`timeEnabled`, `lastReportedTime`, `lastActiveAt`, `lastSeenAt`) every 10s (`LIVE_SYNC_INTERVAL_MS`). **`lastActiveAt` is included** so a watched user's liveness stays fresh in the admin directory (not just the detail view) — previously only `lastSeenAt` was written, and since `isUserOnline` only falls back to `lastSeenAt` when `lastActiveAt` is null, the directory could show a watched user as offline. **The toggles stream here so the admin detail's Pinned/Cycle/Music/Time button states reflect a user's own toggle change within 10s while watching** (they also persist via the hourly delta + the 30s edit debounce — `captureStateForSync` carries them — so an unwatched toggle surfaces on the next hourly write)

- `VrchatPipelineService.startPresenceRefreshLoop` writes VRChat presence every 10s

`VrcaViewModel.startBrowseVolatileSyncWatcher` is now a **no-op** (Phase 1): an admin merely browsing the directory no longer causes this user to emit any writes. The directory is populated from the admin's own one-shot fetch; only opening this user's detail (which flips `isWatched`) starts the 10s live loop.

The live loop stops instantly when `isWatched` flips back to false (`collectLatest` cancels the inner loop). When nobody is watching, neither loop touches Firestore — the only periodic write is the hourly `lastActiveAt`.

**Force-kill detection (hourly model)**: If the user's app is force-killed, neither `onTaskRemoved` nor `onCleared` fires, so `isOnlineInApp` stays `true` in Firestore — but the in-process hourly loop stops, so `lastActiveAt` goes stale. The admin determines offline by `lastActiveAt` age (>~65 min, or ~25s for a currently-watched user whose 10s loop stopped). The admin-side staleness sweep (`AdminRuntime`) keys on `lastActiveMs` (canonical `lastActiveAt`, falling back to `lastSeenAt`) with `ONLINE_STALENESS_WINDOW_MS = 65 min` — past the 60-min hourly heartbeat with 5 min of grace, so a live unwatched user is never false-flagged. When an admin is browsing and a user's `lastActiveAt` exceeds the window, the sweep writes `isOnlineInApp=false` to that user's doc.

**Admin watcher heartbeat**: When an admin selects a user in the admin panel's detail view, a `LaunchedEffect` writes `watcherActiveAt = serverTimestamp()` to that user's doc every 30 seconds. When the admin navigates away or selects a different user, the coroutine is cancelled automatically. The user app reads `watcherActiveAt` from its snapshot listener and feeds it into `AdminWatchState.updateFromTimestampMs()` — if within 60s, live-mode starts.

**Echo suppression** (per-field `lastSyncedValues` map): Every field (toggle or content) compares its incoming snapshot value against `lastSyncedValues` — what we last knew was on the Firestore doc. If `remote == lastSyncedValues`, the snapshot is an echo (from self-sync, watcher heartbeat, or live-mode write) and we skip. If `remote != lastSyncedValues`, an admin actually changed it and we apply. Comparing against current local state would break this: during admin watch, the heartbeat fires snapshots with the OLD field values (Firestore hasn't received the user's pending local toggle yet), so a `remote != local` test would revert whatever the user just toggled. Content fields fall back to current local state when no baseline exists yet. Both branches update `lastSyncedValues` immediately on every snapshot (whether applied or skipped), so subsequent self-sync echoes are correctly suppressed. The map is also bulk-updated after each successful `performSelfSync` write via `captureStateForSync()`. The first snapshot seeds the baseline via `seedLastSyncedFromSnapshot`. **`lastSyncedValues` is persisted to SharedPreferences** (`vrca_remote/last_synced_values_json`) as a JSON object after each successful sync so the delta writer has a baseline across cold starts — without this, every app restart would fall back to a full snapshot write.

**Initial-data gate** (`initialDataLoaded`): `performSelfSync` returns early until a loader coroutine has read every user-content DataStore field into ViewModel state. Prevents cold-start sync from writing empty defaults.

**First-snapshot skip** (`initialSnapshotProcessed`): The very first Firestore snapshot after listener attach is dropped — DataStore is the source of truth on cold start.

**Cross-device content sync (multi-phone, same VRChat account)**: When the same VRChat user logs in on two phones, the installs have DISTINCT `deviceHash`es → two separate `users/{deviceHash}` docs. To keep presets/messages/intervals consistent without merging the docs, `VrcaViewModel.applyCrossDeviceSync()` (public build only, launched from `init`) waits for the pipeline to surface the user's `vrchatUserId` (`VrchatPipelineState.presenceFlow.first { it != null }`, 120s timeout), then queries `users` for sibling docs `whereEqualTo("vrchatUserId", myVrchatId)`. It picks the sibling with the freshest `updatedAt`; if that is newer than this device's own `updatedAt`, it pulls the sibling's content into local DataStore + ViewModel state via the shared `applyContentFromSnapshot(snap)` helper (extracted from `applyRemoteContentBeforeSync()` — applies afkMessage, cycleIntervalSeconds, cycleLinesText, afkPreset1-3, cyclePreset1-5, spotifyPreset, each guarded by a value-changed check) and rebuilds the preview. So editing presets on phone A surfaces on phone B's next app open. The query keys on the already-written `vrchatUserId` field (a single-field index Firestore auto-provides).
  The content pull is read-only against siblings — no cross-device content WRITE — so the only authority over a device's own doc remains that device + the admin. **The query returns the device's OWN doc too (same `vrchatUserId`), so its `updatedAt` is read from the result set inline — no separate own-doc `get()`.** **Two throttles now**: the sibling QUERY runs at most once per 60s (`ACCOUNT_QUERY_THROTTLE_MS`, persisted `last_account_query_ms`) — short, because it ALSO drives the single-session claim and so must run on a genuine reopen (not be suppressed for 30 min) while still bounding OS-kill relaunch storms — and the expensive CONTENT pull keeps its own 30-min window (`CROSS_DEVICE_SYNC_THROTTLE_MS`, persisted `last_cross_device_sync_ms`). A genuine reopen after editing on the other phone is almost always >30 min from the last sync, so the content feature is intact.

**Offline editing**: User-content edits land in DataStore immediately and survive process death. On reconnect, the next debounced write or app-close write pushes them to Firestore. Admin-content edits are preserved across user restarts via `applyRemoteContentBeforeSync()` (read-before-write on app-open). If both the user and admin edited the same field while the user was offline, the Firestore version (admin's) wins because it's applied before the app-open write.

**Admin edits to OFFLINE users (cold-open apply path + moderation-listener backstop — toggles AND content)**: There are now TWO cooperating paths that both apply admin edits made while the user was offline, both keyed on the PERSISTED baseline (`lastSyncedValues`, loaded from prefs in `init`):

1. **`applyRemoteContentBeforeSync()`** (runs once on cold-open BEFORE `performSelfSync`, wrapped in a 12s `withTimeoutOrNull`): (a) `ensureAnonAuth()`; (b) reads the user doc **from `Source.SERVER`** — NOT the default `get()`, which returns Firestore's LOCAL CACHE holding this device's OLD pre-edit values, so an admin edit made while the app was closed would be invisible (old-vs-old → nothing applied; this stale-cache read was a primary cause of "admin content/preset edits don't apply when the user reopens"); (c) if the doc exists it sets `remoteDocConfirmedExists=true` (see liveness-only gate below); (d) `applyContentFromSnapshot(snap)` + `applyOfflineToggleEdits(snap)` apply admin-edited content/toggles. **There is NO blanket snapshot-seed of the baseline** — the old `seedLastSyncedFromSnapshot` was DELETED because it POISONED the listener: it set the baseline to the server value for EVERY field (even ones the apply skipped), so (i) the moderation listener then saw `remote == baseline` and echo-SUPPRESSED un-applied admin edits, and (ii) combined with a stale local value it made the cold-open delta write the local value BACK, overwriting the admin's edit. Instead, `applyContentFromSnapshot`/`applyOfflineToggleEdits` update `lastSyncedValues[key]` **only for the specific field they actually apply**, leaving every other key on its prefs baseline.

2. **The moderation snapshot listener (`applyRemoteConfig`)** is the **backstop** and is now ALSO the path that catches the common case where the admin's offline edit arrives as the FIRST (and on a fresh device the ONLY) server snapshot. **The first-snapshot drop was REMOVED** (`initialSnapshotProcessed` deleted): dropping it silently lost every admin edit that arrived as the first snapshot — the core "nothing applies on reopen" bug. All snapshots now run through `applyRemoteConfig`'s baseline-vs-`lastSyncedValues` echo-suppression.

**Cold-open write is LIVENESS-ONLY for an existing doc (`remoteDocConfirmedExists`)**: this is the structural guarantee that the cold-open `performSelfSync` can NEVER clobber an admin offline edit. When the `Source.SERVER` read confirmed the doc exists, the cold-open delta SKIPS all content+toggle keys and writes only liveness (and, crucially, does NOT rebaseline `lastSyncedValues` to local afterward — that would drop the prefs baseline the listener needs and let a later write clobber a user's own offline edit). The admin's edits live on the server doc; the apply path + listener pull them into local; a later debounced/hourly write (non-coldOpen) pushes any genuine user offline edit up. The full-write branch now fires only when `isFirstSync && !remoteDocConfirmedExists` (true first install, doc absent) or `uidChanged` (rules require `uid`/`authUid` to match the new auth, so a delta omitting them is denied).

**Content vs toggles differ on the null-baseline fallback (the OS-kill revival safety):** `applyContentFromSnapshot` falls back to comparing against current LOCAL when a field has no persisted baseline (so admin content still wins on first sync). `applyOfflineToggleEdits` does NOT — it SKIPS on a null baseline. This is deliberate: `restoreFeatureSession()` runs first on an OS-kill revival and may have just resumed OSC sending with toggles ON; a null-baseline local fallback could flip a just-restored toggle off and STOP the revived user's OSC. So a toggle is only changed when a REAL baseline shows the admin genuinely changed it (`remote != baseline`) — admin DISABLE while OEM-killed is respected (sender stops), while an untouched toggle (`remote == baseline`) leaves the restored toggle and its OSC alone. With a real baseline the apply preserves the user's OWN offline content edits too: `remote == baseline` means the admin didn't touch it, so the user's local edit survives and the debounced write pushes it up; both edited → `remote != baseline` → admin wins (documented intent). (The earlier compare-vs-LOCAL design clobbered the user's offline edits whenever the cache read returned the stale server value.)

**Cold-open `performSelfSync` write rules (`TOGGLE_KEYS = afkEnabled/cycleEnabled/spotifyEnabled/spotifyDemoEnabled/timeEnabled`):** for an existing doc (`remoteDocConfirmedExists`) the cold-open delta is LIVENESS-ONLY — all content+toggle keys are skipped and the baseline is NOT rebaselined to local (see above), so it can't clobber. For a first-install cold open (doc absent) toggle keys are still skipped (they start OFF; writing OFF back would race an admin's enabled toggle) while content is written into the creating snapshot. The hourly/debounced (non-coldOpen) writes are full deltas and push genuine user edits. (True first-install with no doc: `applyRemoteContentBeforeSync` early-returns on `!snap.exists()` leaving `remoteDocConfirmedExists=false` and `lastSyncedValues` empty → `isFirstSync && !remoteDocConfirmedExists` full write creates the doc — toggles default OFF, nothing to apply.)

**Admin online detection (liveness-driven, NOT the `isOnlineInApp` flag)**: `isUserOnline(u, nowMs)` in `UsersTab.kt` is driven by **`lastActiveAt` freshness**, deliberately IGNORING the `isOnlineInApp` boolean. A user is online ⟺ `(lastActiveAt ?? lastSeenAt)` is within `ONLINE_STALENESS_WINDOW_MS` (~65 min) **AND** there is no clean-shutdown `offlineAt` marker newer than `lastActiveAt`. **Why the flag was dropped**: pre-app-scoped-VM public builds wrote `isOnlineInApp=false` from `VrcaViewModel.onCleared()` on EVERY Activity destruction (normal under memory pressure / "Don't keep activities") **without advancing `lastActiveAt`**, so a perfectly-live user showed offline with a fresh 28-min-old timestamp — the "Cherubic shows offline while her chatbox is clearly updating" bug. `lastActiveAt` is the ground truth because the hourly heartbeat (every 10s while watched) only fires while the process is alive. Under the hourly model an unwatched user writes `lastActiveAt` once per hour, so the window is ~65 min (5 min grace past the 60-min heartbeat); a watched user (10s loop) shows online within ~25s.
  **Instant-offline on swipe via `offlineAt`**: a clean swipe-away (`AppShutdown.buildOfflineWriteTask` + `VrcaViewModel.onCleared`) stamps `offlineAt = serverTimestamp()`. When `offlineAt > lastActiveAt` the row is forced offline INSTANTLY (no 65-min wait). This can never false-flag a live app — the next heartbeat advances `lastActiveAt` past `offlineAt` (self-healing, no clear needed). If the swipe-time write races the 5s kill timeout and never lands (the long-standing "swipe doesn't consistently go offline"), the staleness window still flips the user offline within ~65 min — instant when the write succeeds, eventually-consistent when it doesn't. VRChat session state is irrelevant to all of this: the liveness write uses Firebase anon auth + device hash and is fully decoupled from VRChat auth (a VRChat un-auth never blocks or triggers an online/offline write; VRChat presence fields are only additively merged when present). **The Dashboard counter uses the SAME `isUserOnline` predicate** (`DashboardTab.kt`) so the count and the directory rows stay consistent.
  The admin-side staleness sweep (`AdminRuntime`) still flips `isOnlineInApp=false` for genuinely-stale users — now only to keep the raw flag roughly accurate for any OLD admin builds that still read it directly; the current build never reads it for the online decision. `UserRow`/`UserDetail`/`parseUserRow`/`UsersDirectoryCache` all carry the new `offlineAt` timestamp; `firestore.rules` `selfMutableKeys()` includes `offlineAt`. The shared user-list state is `mutableStateOf<List<UserRow>>` (whole-value assignment) populated by the one-shot directory fetch.

### Remote Config (Admin Edits)

The public app's moderation snapshot listener on `users/{deviceHash}` also picks up admin-editable fields (feature toggles, messages, intervals, presets) and applies them in real-time. Each incoming snapshot is filtered by:

1. `initialSnapshotProcessed` — drop the very first snapshot (DataStore wins cold start)

2. Per-field `lastSyncedValues` comparison — if the remote value matches what we last wrote, it's our own echo and is skipped; if it differs, an admin changed it and it's applied

After those filters, the snapshot's content fields (afkMessage, cycleLines, presets) are written to DataStore so existing flow collectors propagate them into ViewModel state. Toggles are set directly on the ViewModel (they don't persist — see below).
