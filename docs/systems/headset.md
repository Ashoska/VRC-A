# Headset (Meta Quest) build

_Scope: The third build flavor: manifest, monitor-shape framing, 3-column Home, OSC-in (OSCQuery) tokens, headset OSC send target._

- **Headset (Meta Quest) build variant (M1 scaffold shipped)**: a third product flavor `headsetApp` (applicationId **`com.gremlin.inc.headset`**, `BuildConfig.IS_HEADSET_BUILD=true`; `IS_HEADSET_BUILD=false` on public/admin) alongside `publicApp`/`adminApp`. Its own Firebase app (`app/src/headsetApp/google-services.json`, same `vrc-a-b592e` project) + a headset-only `VideoTranscode.kt` stub (mirrors publicApp; the transcoder is admin-only) + a headset manifest overlay (`app/src/headsetApp/AndroidManifest.xml`) that merges `android:screenOrientation="sensorLandscape"` onto `MainActivity` so the app opens in Quest's 16:10 **1024×640 dp default panel** ("monitor" shape) instead of a tall phone. **Monitor-shape framing is width-responsive, NOT flavor-gated**: `VrcaScreen`'s Scaffold content is wrapped in a `BoxWithConstraints` that centers page content at `HEADSET_MAX_CONTENT_WIDTH` (720.dp) once available width ≥ `HEADSET_WIDE_THRESHOLD` (640.dp) — the Quest panel (1024 dp) is well above it so content reads as a centered monitor window; a phone (portrait ~360–420 dp) stays below it so it's untouched (also helps tablets/foldables).
  Top/bottom bars keep full panel width as the window chrome; only the content centers. Build: `./gradlew assembleHeadsetAppDebug`. Distribution target is the **Meta Horizon Store / App Lab** (dev/testing via sideload/MQDH). **Fixed panel (no user resize — best-effort)**: the headset manifest sets `android:resizeableActivity="false"` on BOTH `<application>` and `MainActivity`, PLUS `android:minAspectRatio="1.6"`+`android:maxAspectRatio="1.6"` on `MainActivity` to pin the 16:10 shape. **Honest limit (device-confirmed): Horizon OS still lets the user resize a 2D panel regardless** — Android has no hard "no resize" for VR panels. The real safeguard is the width-responsive framing + the Home **3/2/1-column thresholds** (below), which degrade gracefully at any size, so resizing is harmless even when it can't be prevented. **Headset Home = THREE columns** (`HomePage.kt`, `HOME_THREE_COL_THRESHOLD`=820.dp, cleared by the 1024dp panel; drops to 2-col ≥560dp then 1-col): **left** = skinny preview, **middle** = Line Toggles + Manual Send (they fit together), **right** = the instance roster pinned far-right.
  Each column scrolls internally; the Manual Send card hosts a hoisted `expandedState` + a `BringIntoViewRequester` so expanding it scrolls the middle column down to reveal the full editor. Headset top-bar notification badge is `offset(x=-2,y=4)` so it sits ON the bell instead of clipping past the bar's top edge; the Home NAV setup badge (`setupNeedsAttention`) is suppressed on the headset build (redundant — the same items already show in the top-bar notification button).

- **OSC-in tokens (headset — `com.vrca.osc.VrcaOscQuery` + `VrcaOscReceiver` → `VrcaOscState`)**: the chatbox reads the local player's live avatar params for **`{mute}`** (MuteSelf→"Muted"/""), **`{afk}`** (AFK→"AFK"/""), **`{movement}`** (VelocityX/Y/Z magnitude→"Moving"/"Still"), **`{scale}`** (avatar size — `EyeHeightAsMeters` "1.65m", else `ScaleFactor` as "%"), **`{param:Name}`** (ANY avatar param). `TokensHint` shows these only on the headset build; `VrcaOscState.isLive` (updated within 8s) is a "VRChat OSC live" signal. **The delivery mechanism is OSCQuery PULL, not a UDP push — this was the whole battle.** VRChat on **Quest standalone does NOT push avatar-param OSC output** over UDP 9001 (confirmed on-device: `rxPackets=0` even while unmuting/moving; and via VRChat's own tracker — vrchat-community/osc #129 — "only `/avatar/change` is sent to localhost:9001, all other params dropped"). BUT VRChat on Android **serves every param's live value over its OSCQuery HTTP server** (VRChat's OSCQuery wiki: Android is not same-machine-limited like Windows). So **`VrcaOscQuery` (headset-started in `VrcaApplication.onCreate`)**: (1)
  **mDNS-discovers** VRChat's `_oscjson._tcp` service via `NsdManager` (filters to a `VRChat`-prefixed service name), resolving `host:port` (e.g. `VRChat-Client-XXXX @ 192.168.0.89:45631`); (2) **polls `GET http://host:port/avatar/parameters` every 1s** — ONE request returns the whole avatar-param subtree WITH current values (`CONTENTS.<Name> = {FULL_PATH, TYPE, VALUE:[...]}`; TYPE `T`/`F`=bool, `i`=int, `f`=float; `extractValue` reads `VALUE[0]`); (3) folds each into `VrcaOscState.onParam` so the tokens resolve. On a poll HTTP failure it drops `host` and waits for re-discovery (VRChat restart / new session port); `onServiceLost` clears it too. **Requires cleartext HTTP** (OSCQuery is plain `http://` on the LAN — Android blocks cleartext by default): `usesCleartextTraffic="true"` is set on the **headset manifest ONLY** (public/admin stay cleartext-blocked; it does not downgrade any `https://` call, only permits `http` where we explicitly use it). **`VrcaOscReceiver` (UDP 9001 listener) is kept as a no-cost fallback** for the `/avatar/change` event VRChat DOES push and for PC-push setups, but on Quest it receives nothing — OSCQuery is the working path.
  A **Settings → Debug (headset) "OSCQuery probe / OSC-in"** diagnostic (`VrcaOscState.diagString()`/`oscQueryDiag`) shows bind/rx state + the discovered service + a live `MuteSelf` read, which is how this was root-caused. **`{scale}`/`EyeHeightAsMeters` also drives the avatar-size READ**; the avatar-size WRITE (`/avatar/eyeheight`, VrcaOsc) works independently (OSC INPUT is the half Quest supports). **HEADSET OSC SEND TARGET = the reachable OSCQuery host, NOT loopback (proven fix for "chatbox/avatar-size randomly stops, reopen fixes it")**: sending to hardcoded `127.0.0.1:9000` was PROVEN undelivered on-device — the **eyeheight delivery canary** (`VrcaOscState.recordEyeHeightSend`/`deliveryDiag`, surfaced in the send-health diag: send `/avatar/eyeheight` → confirm VRChat received it ONLY if the `EyeHeightAsMeters` OSCQuery readback MOVES; `udp ok` is a LIE for UDP — it only means the OS accepted the datagram) read **`size probe: NOT DELIVERED (readback never moved)` for minutes while `udp ok=0s`/`failStreak=0`**, at the same moment OSCQuery HTTP to VRChat's discovered host was fully live (96 params).
  So on Quest it's specifically **outbound UDP to loopback that dies**, not the reachable host. Fix: `VrcaOscQuery.oscSendTargetFlow` publishes `(host, oscInPort)` — the SAME mDNS-resolved host our polls reach VRChat at (the device LAN IP, e.g. `192.168.0.89`) + VRChat's advertised OSC-in port from HOST_INFO (`/?HOST_INFO` → `OSC_PORT`, falls back to 9000). The **headset** VM (`VrcaViewModel` init, `IS_HEADSET_BUILD` branch) collects it and re-points `remoteVrcaOsc` (ip+port), falling back to `127.0.0.1:9000` only until discovery resolves; re-points only on a genuine host/port change (no socket thrash). **Mobile is unchanged** (targets the manually-entered LAN IP; never runs OSCQuery discovery). The send-health diag's `target=` line shows the LAN IP once rerouted and the canary confirms `DELIVERED` — a built-in verdict. `VrcaOsc` sends a FRESH `OSCPortOut` per send on a dedicated `vrca-osc-send` thread (a persistent reused socket was tried + reverted: over loopback `send()` never throws even after VRChat rebinds, so it wedged "successfully" until process restart).
