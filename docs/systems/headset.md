# Headset (Meta Quest) build

_Scope: The third build flavor: manifest, monitor-shape framing, 3-column Home, OSC-in (OSCQuery) tokens, headset OSC send target._

- **Headset (Meta Quest) build variant (M1 scaffold shipped)**: a third product flavor `headsetApp` (applicationId **`com.gremlin.inc.headset`**, `BuildConfig.IS_HEADSET_BUILD=true`; `IS_HEADSET_BUILD=false` on public/admin) alongside `publicApp`/`adminApp`. Its own Firebase app (`app/src/headsetApp/google-services.json`, same `vrc-a-b592e` project) + a headset-only `VideoTranscode.kt` stub (mirrors publicApp; the transcoder is admin-only) + a headset manifest overlay (`app/src/headsetApp/AndroidManifest.xml`) that merges `android:screenOrientation="sensorLandscape"` onto `MainActivity` so the app opens in Quest's 16:10 **1024×640 dp default panel** ("monitor" shape) instead of a tall phone. **Monitor-shape framing is width-responsive, NOT flavor-gated**: `VrcaScreen`'s Scaffold content is wrapped in a `BoxWithConstraints` that centers page content at `HEADSET_MAX_CONTENT_WIDTH` (720.dp) once available width ≥ `HEADSET_WIDE_THRESHOLD` (640.dp) — the Quest panel (1024 dp) is well above it so content reads as a centered monitor window; a phone (portrait ~360–420 dp) stays below it so it's untouched (also helps tablets/foldables).
  Top/bottom bars keep full panel width as the window chrome; only the content centers. Build: `./gradlew assembleHeadsetAppDebug`. Distribution target is the **Meta Horizon Store / App Lab** (dev/testing via sideload/MQDH). **Fixed panel**: next line. **Headset Home = THREE columns** (`HomePage.kt`, `HOME_THREE_COL_THRESHOLD`=820.dp, cleared by the 1024dp panel; drops to 2-col ≥560dp then 1-col): **left** = skinny preview, **middle** = Line Toggles + Manual Send (they fit together), **right** = the instance roster pinned far-right.
  **Fixed panel (user request: not resizable; `PanelScale.kt`)**: Horizon OS lets users resize any Android panel (Meta's docs: the resize handles are the system's) and `resizeableActivity="false"` + min/maxAspectRatio only letterboxed the app in grey when enlarged (device-confirmed), so resizeableActivity stays true and: (1) the headset manifest gives MainActivity Meta's `<layout>` default 1024x640dp, which is also the MINIMUM (`minWidth`/`minHeight`), so the panel can only be made bigger, never smaller than the default, plus the Horizon shell flags `com.oculus.vrshell.supports_free_resizing=false` and `free_resizing_lock_aspect_ratio=true` (NOT in Meta's public docs: Meta forum answers, apps' manifests). Device-tested 2026-10-16: Horizon ignores `supports_free_resizing=false` (the panel still resized; the app zoomed as designed); kept in case a later Horizon honours it. Meta's own agent docs (github.com/meta-quest/agentic-tools, panel-layout.md): users can resize panels freely, no lock; an app also has no API to resize its own panel;
  (2) whatever size Horizon still gives, `FixedPanel` (in `GremlinTheme`, headset only) lays the app out at exactly 1024x640dp and scales it to fit (LocalDensity x min(w/1024, h/640); another shape gets the app background around it): a resize zooms instead of reflowing, and the Home column thresholds always see 1024dp (3 columns). Each dialog is its own window that sets LocalDensity again, so the app's dialogs use `PanelDialog` (Dialog + `PanelScaled` via `LocalPanelDensity`); Material DropdownMenus stay at real size (M3 lays out their frame inside its popup). UI Lab-checked: default size pixel-identical to before, 1440x900 = the same layout x1.41, 1280x1000 = fit to width with bars, dialogs scale, real touches hit.
  Each column scrolls internally; the Manual Send card hosts a hoisted `expandedState` + a `BringIntoViewRequester` so expanding it scrolls the middle column down to reveal the full editor. Headset top bar shows the VRC-A logo (`drawable/vrca_logo_vector`: a vector traced by `tools/symbol-lab/logo_trace.py` from the logo cropped to its drawing, so it stays sharp at any panel zoom; 56dp tall in the 64dp bar; the boot screen uses the same drawing and flies into this exact spot) instead of the "VRC-A" words; public/admin keep the text. Headset top-bar notification badge is `offset(x=-2,y=4)` so it sits ON the bell instead of clipping past the bar's top edge; the Home NAV setup badge (`setupNeedsAttention`) is suppressed on the headset build (redundant — the same items already show in the top-bar notification button).

- **OSC-in tokens (headset — `com.vrca.osc.VrcaOscQuery` + `VrcaOscReceiver` → `VrcaOscState`)**: the chatbox reads the local player's live avatar params for **`{mute}`** (MuteSelf→"Muted"/""), **`{afk}`** (AFK→"AFK"/""), **`{movement}`** (VelocityX/Y/Z magnitude→"Moving"/"Still"), **`{scale}`** (avatar size — `EyeHeightAsMeters` "1.65m", else `ScaleFactor` as "%"), **`{param:Name}`** (ANY avatar param). Also the dictation **Listen trigger** (voice-to-text.md): `VrcaOscState.boolParams()`/`freshBool()` read on/off params only if reported within 3 s (`seenMs`), since a param missing from the current avatar keeps its old value in the map. `TokensHint` shows these only on the headset build; `VrcaOscState.isLive` (updated within 8s) is a "VRChat OSC live" signal. **The delivery mechanism is OSCQuery PULL, not a UDP push — this was the whole battle.** VRChat on **Quest standalone does NOT push avatar-param OSC output** over UDP 9001 (confirmed on-device: `rxPackets=0` even while unmuting/moving; and via VRChat's own tracker — vrchat-community/osc #129 — "only `/avatar/change` is sent to localhost:9001, all other params dropped"). BUT VRChat on Android **serves every param's live value over its OSCQuery HTTP server** (VRChat's OSCQuery wiki: Android is not same-machine-limited like Windows). So **`VrcaOscQuery` (headset-started in `VrcaApplication.onCreate`)**: (1)
  **mDNS-discovers** VRChat's `_oscjson._tcp` service via `NsdManager` (filters to a `VRChat`-prefixed service name), resolving `host:port` (e.g. `VRChat-Client-XXXX @ 192.168.0.89:45631`); (2) **polls `GET http://host:port/avatar/parameters` every 250 ms** (`POLL_MS`) — ONE request returns the whole avatar-param subtree WITH current values (`CONTENTS.<Name> = {FULL_PATH, TYPE, VALUE:[...]}`; TYPE `T`/`F`=bool, `i`=int, `f`=float; `extractValue` reads `VALUE[0]`); (3) folds each into `VrcaOscState.onParam` so the tokens resolve. On a poll HTTP failure it drops `host` and waits for re-discovery (VRChat restart / new session port); `onServiceLost` clears it too. **Requires cleartext HTTP** (OSCQuery is plain `http://` on the LAN — Android blocks cleartext by default): `usesCleartextTraffic="true"` is set on the **headset manifest ONLY** (public/admin stay cleartext-blocked; it does not downgrade any `https://` call, only permits `http` where we explicitly use it). **`VrcaOscReceiver` (UDP 9001 listener) is kept as a no-cost fallback** for the `/avatar/change` event VRChat DOES push and for PC-push setups, but on Quest it receives nothing — OSCQuery is the working path.
  A **Settings → Debug (headset) "OSCQuery probe / OSC-in"** diagnostic (`VrcaOscState.diagString()`/`oscQueryDiag`) shows bind/rx state + the discovered service + a live `MuteSelf` read, which is how this was root-caused. **`{scale}`/`EyeHeightAsMeters` also drives the avatar-size READ**; the avatar-size WRITE (`/avatar/eyeheight`, VrcaOsc) works independently (OSC INPUT is the half Quest supports). **HEADSET OSC SEND TARGET = the reachable OSCQuery host, NOT loopback (proven fix for "chatbox/avatar-size randomly stops, reopen fixes it")**: sending to hardcoded `127.0.0.1:9000` was PROVEN undelivered on-device — the **eyeheight delivery canary** (`VrcaOscState.recordEyeHeightSend`/`deliveryDiag`, surfaced in the send-health diag: send `/avatar/eyeheight` → confirm VRChat received it ONLY if the `EyeHeightAsMeters` OSCQuery readback MOVES; `udp ok` is a LIE for UDP — it only means the OS accepted the datagram) read **`size probe: NOT DELIVERED (readback never moved)` for minutes while `udp ok=0s`/`failStreak=0`**, at the same moment OSCQuery HTTP to VRChat's discovered host was fully live (96 params).
  **"OSCQuery full endpoint list"** (same Debug section, `VrcaOscQuery.dumpTree()`, button "Dump all endpoints"): GETs `/?HOST_INFO` + the WHOLE OSCQuery tree `/` once (off the main thread) and lists every endpoint VRChat advertises with TYPE, access (r/w/rw), current VALUE and DESCRIPTION; `/avatar/parameters` children are only counted. Purpose: find undocumented endpoints on Quest VRChat (head/wrist tracking output, anything play-space/floor) for the planned hand-drag locomotion. Research so far: OSC has no vertical input; the Quest system floor height DOES move the player live in VRChat (user-tested: floor below feet = float, above = crouch) but no public API sets it. **"Floor / boundary values"** (same Debug section, `FloorProbe.dump()`, button "Read floor values"): READ-ONLY list of every `Settings.System`/`Secure`/`Global` key and `getprop` system property whose name mentions floor/guardian/boundary/tracking/space/height/stage/recenter (a settings table the app may not read prints "not readable"). Purpose: find where Quest stores the floor height VRChat follows live, and whether a normal app can see it. **"Announce to VRChat (receive test)"** (`OscAnnouncer`, button "Start / stop announcing"): registers VRC-A over mDNS as an OSCQuery app (`_oscjson._tcp` + `_osc._udp`), serves HOST_INFO (OSC_IP = the device LAN IPv4) and a tree listing `/avatar/change` + `/tracking/vrsystem/{head,leftwrist,rightwrist}/pose`; VRChat then PUSHES those poses and every avatar param to our UDP port (device-proven). Name + both ports are saved per install (`osc_announce` prefs) and re-bound on every start: a new name/ports after stop/start left VRChat sending to the old address (0 packets until VRChat restarted). **"Hand drag (prototype)"** (`HandDrag`, on/off + Strength slider 0.25-4): fist (`GestureRight`/`GestureLeft` == 1) + wrist movement → flipped, rotated by head yaw → `/input/Vertical` + `/input/Horizontal` (stick = hand speed x strength / 4 m/s, low-passed, deadzone 0.04, ~60 Hz; open hand sends 0); readout shows hand speed, sticks and VRChat VelocityX/Z. Horizontal only. Findings + ideas: `docs/osc-endpoints.md`. **"Save all findings to Downloads"** (`FindingsExport`): writes the OSCQuery probe, announce + hand-drag status, the full endpoint dump and the floor probe to one `Downloads/vrca-findings-<time>.txt` (MediaStore, no permission) so the user can hand it over instead of screenshotting.
  So on Quest it's specifically **outbound UDP to loopback that dies**, not the reachable host. Fix: `VrcaOscQuery.oscSendTargetFlow` publishes `(host, oscInPort)` — the SAME mDNS-resolved host our polls reach VRChat at (the device LAN IP, e.g. `192.168.0.89`) + VRChat's advertised OSC-in port from HOST_INFO (`/?HOST_INFO` → `OSC_PORT`, falls back to 9000). The **headset** VM (`VrcaViewModel` init, `IS_HEADSET_BUILD` branch) collects it and re-points `remoteVrcaOsc` (ip+port), falling back to `127.0.0.1:9000` only until discovery resolves; re-points only on a genuine host/port change (no socket thrash). **Mobile is unchanged** (targets the manually-entered LAN IP; never runs OSCQuery discovery). The send-health diag's `target=` line shows the LAN IP once rerouted and the canary confirms `DELIVERED` — a built-in verdict. `VrcaOsc` sends a FRESH `OSCPortOut` per send on a dedicated `vrca-osc-send` thread (a persistent reused socket was tried + reverted: over loopback `send()` never throws even after VRChat rebinds, so it wedged "successfully" until process restart).
