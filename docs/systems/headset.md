# Headset (Meta Quest) build

_Scope: The third build flavor: manifest, monitor-shape framing, 3-column Home, OSC-in (OSCQuery) tokens, headset OSC send target._

- **Headset (Meta Quest) build variant (M1 scaffold shipped)**: a third product flavor `headsetApp` (applicationId **`com.gremlin.inc.headset`**, `BuildConfig.IS_HEADSET_BUILD=true`; `IS_HEADSET_BUILD=false` on public/admin) alongside `publicApp`/`adminApp`. Its own Firebase app (`app/src/headsetApp/google-services.json`, same `vrc-a-b592e` project) + a headset-only `VideoTranscode.kt` stub (mirrors publicApp; the transcoder is admin-only) + a headset manifest overlay (`app/src/headsetApp/AndroidManifest.xml`) that merges `android:screenOrientation="sensorLandscape"` onto `MainActivity` so the app opens in Quest's 16:10 **1024×640 dp default panel** ("monitor" shape) instead of a tall phone. **Monitor-shape framing is width-responsive, NOT flavor-gated**: `VrcaScreen`'s Scaffold content is wrapped in a `BoxWithConstraints` that centers page content at `HEADSET_MAX_CONTENT_WIDTH` (720.dp) once available width ≥ `HEADSET_WIDE_THRESHOLD` (640.dp) — the Quest panel (1024 dp) is well above it so content reads as a centered monitor window; a phone (portrait ~360–420 dp) stays below it so it's untouched (also helps tablets/foldables).
  Top/bottom bars keep full panel width as the window chrome; only the content centers. Build: `./gradlew assembleHeadsetAppDebug`. Distribution target is the **Meta Horizon Store / App Lab** (dev/testing via sideload/MQDH). **Fixed panel**: next line. **Headset Home = THREE columns** (`HomePage.kt`, `HOME_THREE_COL_THRESHOLD`=820.dp, cleared by the 1024dp panel; drops to 2-col ≥560dp then 1-col): **left** = skinny preview, **middle** = Line Toggles + Manual Send (they fit together), **right** = the instance roster pinned far-right.
  **Fixed panel (user request: not resizable; `PanelScale.kt`)**: Horizon OS lets users resize any Android panel (Meta's docs: the resize handles are the system's) and `resizeableActivity="false"` + min/maxAspectRatio only letterboxed the app in grey when enlarged (device-confirmed), so resizeableActivity stays true and: (1) the headset manifest gives MainActivity Meta's `<layout>` default 1024x640dp, which is also the MINIMUM (`minWidth`/`minHeight`), so the panel can only be made bigger, never smaller than the default, plus the Horizon shell flags `com.oculus.vrshell.supports_free_resizing=false` and `free_resizing_lock_aspect_ratio=true` (NOT in Meta's public docs: Meta forum answers, apps' manifests). Device-tested 2026-10-16: Horizon ignores `supports_free_resizing=false` (the panel still resized; the app zoomed as designed); kept in case a later Horizon honours it. Meta's own agent docs (github.com/meta-quest/agentic-tools, panel-layout.md): users can resize panels freely, no lock; an app also has no API to resize its own panel;
  (2) whatever size Horizon still gives, `FixedPanel` (in `GremlinTheme`, headset only) lays the app out at exactly 1024x640dp and scales it to fit (LocalDensity x min(w/1024, h/640); another shape gets the app background around it): a resize zooms instead of reflowing, and the Home column thresholds always see 1024dp (3 columns). Each dialog is its own window that sets LocalDensity again, so the app's dialogs use `PanelDialog` (Dialog + `PanelScaled` via `LocalPanelDensity`); Material DropdownMenus stay at real size (M3 lays out their frame inside its popup). UI Lab-checked: default size pixel-identical to before, 1440x900 = the same layout x1.41, 1280x1000 = fit to width with bars, dialogs scale, real touches hit.
  Each column scrolls internally; the Manual Send card hosts a hoisted `expandedState` + a `BringIntoViewRequester` so expanding it scrolls the middle column down to reveal the full editor. Headset top bar shows the VRC-A logo (`drawable/vrca_logo_vector`: a vector traced by `tools/symbol-lab/logo_trace.py` from the logo cropped to its drawing, so it stays sharp at any panel zoom; 56dp tall in the 64dp bar; the boot screen uses the same drawing and flies into this exact spot) instead of the "VRC-A" words; public/admin keep the text. Headset top-bar notification badge is `offset(x=-2,y=4)` so it sits ON the bell instead of clipping past the bar's top edge; the Home NAV setup badge (`setupNeedsAttention`) is suppressed on the headset build (redundant — the same items already show in the top-bar notification button).

- **OSC-in tokens (headset — `com.vrca.osc.VrcaOscQuery` + `VrcaOscReceiver` → `VrcaOscState`)**: the chatbox reads the local player's live avatar params for **`{mute}`** (MuteSelf→"Muted"/""), **`{afk}`** (AFK→"AFK"/""), **`{movement}`** (VelocityX/Y/Z magnitude→"Moving"/"Still"), **`{scale}`** (avatar size — `EyeHeightAsMeters` "1.65m", else `ScaleFactor` as "%"), **`{param:Name}`** (ANY avatar param), **`{avatar}`** (own avatar name, `VrcaOscState.avatarNameFlow` from `/avatar/name`; empty until known). Also the dictation **Listen trigger** (voice-to-text.md): `VrcaOscState.boolParams()`/`freshBool()` read on/off params only if reported within 3 s (`seenMs`), since a param missing from the current avatar keeps its old value in the map. `TokensHint` shows these only on the headset build; `VrcaOscState.isLive` (updated within 8s) is a "VRChat OSC live" signal. **The delivery mechanism is OSCQuery PULL, not a UDP push — this was the whole battle.** VRChat on **Quest standalone does NOT push avatar-param OSC output** over UDP 9001 (confirmed on-device: `rxPackets=0` even while unmuting/moving; and via VRChat's own tracker — vrchat-community/osc #129 — "only `/avatar/change` is sent to localhost:9001, all other params dropped"). BUT VRChat on Android **serves every param's live value over its OSCQuery HTTP server** (VRChat's OSCQuery wiki: Android is not same-machine-limited like Windows). So **`VrcaOscQuery` (headset-started in `VrcaApplication.onCreate`)**: (1)
  **Stale values (2026-10-29, tester: "Muted" stuck after unmuting)**: `{mute}` `{afk}` `{movement}` `{scale}` `{param:Name}` read `VrcaOscState.live()`: a value seen within 3 s (`PRESENT_MS`; the poll refreshes every value each 0.25-1 s) or while `OscAnnouncer.pushLive` (VRChat pushes only on change, so its last value holds); otherwise the token is blank. When the bridge link drops, `OscAnnouncer` forgets `pushVrchat`, params and poses (a fist released during the gap would otherwise restart a drag after relink); `OscAnnouncer.param` falls back to the poll's fresh value (`VrcaOscState.freshFloat`) until VRChat pushes again. A different `/avatar/change` id clears the old avatar's params. `tickLiveness` clears avatar name, eye height and world size limits once VRChat is quiet (not live, no push), so `{avatar}` and the size control don't show the last session.
  **mDNS-discovers** VRChat's `_oscjson._tcp` service via `NsdManager` (filters to a `VRChat`-prefixed service name), resolving `host:port` (e.g. `VRChat-Client-XXXX @ 192.168.0.89:45631`); (2) **polls `GET http://host:port/avatar` every 250 ms** (`POLL_MS`; **1 s** `POLL_MS_PUSH_LIVE` while `OscAnnouncer.pushLive`, i.e. the running VRChat is pushing to the announced app) — ONE request returns the avatar-param subtree (`CONTENTS.parameters.CONTENTS`) WITH current values plus the avatar nodes, which go to `VrcaOscState.onAvatarInfo` (name, id, eye height, the world's recommended min/max, scaling allowed); falls back to `/avatar/parameters` if there is no parameters node (`CONTENTS.<Name> = {FULL_PATH, TYPE, VALUE:[...]}`; TYPE `T`/`F`=bool, `i`=int, `f`=float; `extractValue` reads `VALUE[0]`); (3) folds each into `VrcaOscState.onParam` so the tokens resolve. On a poll HTTP failure it drops `host` and waits for re-discovery (VRChat restart / new session port); `onServiceLost` clears it too. **Requires cleartext HTTP** (OSCQuery is plain `http://` on the LAN — Android blocks cleartext by default): `usesCleartextTraffic="true"` is set on the **headset manifest ONLY** (public/admin stay cleartext-blocked; it does not downgrade any `https://` call, only permits `http` where we explicitly use it). **`VrcaOscReceiver` (UDP 9001 listener) is kept as a no-cost fallback** for the `/avatar/change` event VRChat DOES push and for PC-push setups, but on Quest it receives nothing — OSCQuery is the working path.
  A **Settings → Debug (headset) "OSCQuery probe / OSC-in"** diagnostic (`VrcaOscState.diagString()`/`oscQueryDiag`) shows bind/rx state + the discovered service + a live `MuteSelf` read, which is how this was root-caused. **`{scale}`/`EyeHeightAsMeters` also drives the avatar-size READ**; the avatar-size WRITE (`/avatar/eyeheight`, VrcaOsc) works independently (OSC INPUT is the half Quest supports). **HEADSET OSC SEND TARGET = the reachable OSCQuery host, NOT loopback (proven fix for "chatbox/avatar-size randomly stops, reopen fixes it")**: sending to hardcoded `127.0.0.1:9000` was PROVEN undelivered on-device — the **eyeheight delivery canary** (`VrcaOscState.recordEyeHeightSend`/`deliveryDiag`, surfaced in the send-health diag: send `/avatar/eyeheight` → confirm VRChat received it ONLY if the `EyeHeightAsMeters` OSCQuery readback MOVES; `udp ok` is a LIE for UDP — it only means the OS accepted the datagram) read **`size probe: NOT DELIVERED (readback never moved)` for minutes while `udp ok=0s`/`failStreak=0`**, at the same moment OSCQuery HTTP to VRChat's discovered host was fully live (96 params).
  **"OSCQuery full endpoint list"** (same Debug section, `VrcaOscQuery.dumpTree()`, button "Dump all endpoints"): GETs `/?HOST_INFO` + the WHOLE OSCQuery tree `/` once (off the main thread) and lists every endpoint VRChat advertises with TYPE, access (r/w/rw), current VALUE and DESCRIPTION; `/avatar/parameters` children are only counted. Purpose: find undocumented endpoints on Quest VRChat (head/wrist tracking output, anything play-space/floor) for the planned hand-drag locomotion. Research so far: OSC has no vertical input; the Quest system floor height DOES move the player live in VRChat (user-tested: floor below feet = float, above = crouch) but no public API sets it. **"Floor / boundary values"** (same Debug section, `FloorProbe.dump()`, button "Read floor values"): READ-ONLY list of every `Settings.System`/`Secure`/`Global` key and `getprop` system property whose name mentions floor/guardian/boundary/tracking/space/height/stage/recenter (a settings table the app may not read prints "not readable"). Purpose: find where Quest stores the floor height VRChat follows live, and whether a normal app can see it. **Pushed values feed the app:** `OscAnnouncer` folds every pushed avatar param into `VrcaOscState.onParam` (typed like the poll) and every other `/avatar/*` node into `onAvatarInfo`, so tokens, the dictation Listen trigger and the size readout update the instant VRChat changes them; the poll keeps "present" params fresh (3 s window) as the safety net. **How VRChat discovers us, and keeping it** (vrc-oscquery-lib `MeaModDiscovery` + MeaMod.DNS `MulticastService`, device tests 2026-10-25/26): VRChat searches only at its own start and when a network adapter appears; otherwise it reacts to announcements, and it connects to the first VRC-A per VRChat session whichever opens first. **Once VRC-A's receive socket closes, even for 3 s with the same port re-bound, no goodbye, and VRChat sending to a multicast group so no "port unreachable" (a self-test proved the re-opened socket received), VRChat stops sending until VRChat restarts.** Tried and ruled out: fresh names + re-announce watchdog, stable name without goodbye, multicast destination. So the socket must outlive the main app: **`:oscbridge` process** (`OscBridgeService`, headset manifest only, `android:process=":oscbridge"`, FGS `dataSync`, own `osc_bridge` notification "Connected to VRChat"/"Waiting for VRChat" with a Stop action; `VrcaApplication.onCreate` returns right after `instance = this` in that process so none of the app startup runs there). **`OscBridge`** (bridge process) holds the UDP receive socket, the OSCQuery HTTP server (HOST_INFO `OSC_IP` = device LAN IPv4 re-read per request, `OSC_PORT` = our port; tree lists `/avatar/change` + the three tracking poses) and **`MdnsAnnouncer`** (own mDNS responses instead of NsdManager, which says goodbye when its process ends: PTR `_oscjson._tcp.local` + `_osc._udp.local`, SRV, empty TXT, A, TTL 4500, burst of 3 at 1 s then every 5 s, answers `_osc*` queries when it binds 5353 with reuse, `MulticastLock` + `CHANGE_WIFI_MULTICAST_STATE`) under a stable name + ports (`osc_announce` prefs `name`, `udp`, `http`). **Address (user report 2026-10-26)**: a bridge started before Wi-Fi was up (power-on launch) fell back to `127.0.0.1`, kept it (the address was only re-read on an HTTP request, which VRChat never made) and VRChat never read our tree (0 requests, 0 packets). Now `localIpv4()` prefers `wlan*`, then any non-`tun`/`dummy` interface, skipping link-local; `ownIp` starts empty, the status loop re-reads it every 5 s and on a change calls `MdnsAnnouncer.onIpChanged()`, which reopens the multicast socket on the new interface and announces in a fresh burst; `announce()` never advertises `127.0.0.1` or no address. The readout shows `address changes`. It relays every datagram raw to the main process over a `LocalServerSocket` (`<package>.oscbridge`, peer uid must be ours; frames `[type:1][len:4][payload]`, 0 = datagram, 1 = status JSON each second). It is not stopped by a swipe (`AppShutdown` only stops its own services and kills the main pid); it stops itself when no main process is connected and VRChat has been silent 10 min (`IDLE_STOP_MS`), or via the notification's Stop. An app update ends all processes, so after one VRChat needs one restart. **`OscAnnouncer`** (main process, started once from `VrcaApplication`) starts the service (`OscBridgeService.start`, refused in the background → poll fallback), keeps a `LocalSocket` link (reconnects each 1 s, restarts the service every 5th failure), parses the relayed datagrams (poses, params, avatar info) and computes `pushLive`. Memory: nothing is queued (the bridge writes each datagram straight to the link; a stalled reader backs up into the kernel UDP buffer, which drops), only latest values are kept: pushed params are cleared on `/avatar/change`, `others`/`counts` are capped at 64 paths, and `VrcaOscState` drops param names unseen for 10 min (`pruneStale`, at most once a minute). Debug: "Start / pause announcing" (pause only), "Self-test" (`selfTest`: sends `/vrca/selftest` to the bridge's port and reports whether it came back through the relay). Diagnostics: `mDNS heard` / `mDNS last query from` / `Android mDNS sees` (`VrcaOscQuery.seenServices`). The readout also lists every other value VRChat pushes (avatar id/name, eye height + world min/max/scaling allowed) and key params (Gesture*, Velocity*, Grounded, AFK, MuteSelf). **"Hand drag (prototype)"** (`HandDrag`, on/off + Strength slider 0.25-4): fist (`GestureRight`/`GestureLeft` == 1) + wrist movement → flipped, rotated by head yaw → `/input/Vertical` + `/input/Horizontal` (stick = hand speed x strength / 4 m/s, low-passed, deadzone 0.04, ~60 Hz; open hand sends 0); readout shows hand speed, sticks and VRChat VelocityX/Z. Horizontal only. The axes are sticky in VRChat (held until 0 is sent), so a VRC-A crash mid-drag kept the player moving (user-reported): each grab start/end goes to the bridge as relay frame type 2 (`OscAnnouncer.reportDrag`: host, port, moving), and when the main process's link hits EOF while moving the bridge sends the zeros (`OscBridge.stopDrag`, counted as `dragStops` in the readout); `hand_drag` prefs `moving` also makes the next main-process start send them (`HandDrag.clearStale`) in case the bridge wasn't running. Findings + ideas: `docs/osc-endpoints.md`. **"Vertical input tests"** (`VerticalTests`): Sit/stand as int 0/1/0 or bool F/T/F (`/input/ToggleSitStand`), Look up/down holds `/input/LookVertical` ±1 for 1 s, all at the headset send target. **"Save all findings to Downloads"** (`FindingsExport`): writes the OSCQuery probe, announce + hand-drag status, the full endpoint dump, the floor probe and the last ADB shell test report (`AdbProbes.lastReport`) to one `Downloads/vrca-findings-<time>.txt` (MediaStore, no permission) so the user can hand it over instead of screenshotting.
  **"ADB shell tests"** (headset only, `AdbShell` in `src/headsetApp`, stubs with `SUPPORTED = false` in public/admin; read-only probes `AdbProbes` in main): an ADB client (libadb-android 3.1.1 + Conscrypt for TLS 1.3 pairing + BouncyCastle for the self-signed cert, all `headsetAppImplementation`, JitPack groups filtered in `settings.gradle`, R8 keeps in `proguard-rules.pro`) that pairs with the Quest's OWN Wireless debugging (Pair code + optional Port; empty port = found over mDNS `_adb-tls-pairing._tcp` / `_adb-tls-connect._tcp`, connect falls back to 5555) at 127.0.0.1. Key + cert persist in `files/adb/` so pairing is once per install. "Run all probes": `id`/fingerprint, `service list`, `dumpsys -l`, `cmd -l`, `getprop`, `settings list system|secure|global`, `ps -A`, `pm list packages`, the full `dumpsys` of up to 12 matching services, and logcat, each filtered to floor/guardian/boundary/tracking/space/height/stage/recenter/playarea/anchor/origin words. "Floor test: Before" / "After" snapshot every probe around a floor change in Quick Settings and show only lines that appeared (+) or vanished (-), plus matching logcat since Before. "Shell command" runs one typed command. Output in the panel is cut at 6,000 chars (full text in Save all findings); each command is stopped after 15 s (dumpsys 10 s) and capped at 256 KB.
  So on Quest it's specifically **outbound UDP to loopback that dies**, not the reachable host. Fix: `VrcaOscQuery.oscSendTargetFlow` publishes `(host, oscInPort)` — the SAME mDNS-resolved host our polls reach VRChat at (the device LAN IP, e.g. `192.168.0.89`) + VRChat's advertised OSC-in port from HOST_INFO (`/?HOST_INFO` → `OSC_PORT`, falls back to 9000). The **headset** VM (`VrcaViewModel` init, `IS_HEADSET_BUILD` branch) collects it and re-points `remoteVrcaOsc` (ip+port), falling back to `127.0.0.1:9000` only until discovery resolves; re-points only on a genuine host/port change (no socket thrash). **Mobile is unchanged** (targets the manually-entered LAN IP; never runs OSCQuery discovery). The send-health diag's `target=` line shows the LAN IP once rerouted and the canary confirms `DELIVERED` — a built-in verdict. `VrcaOsc` sends a FRESH `OSCPortOut` per send on a dedicated `vrca-osc-send` thread (a persistent reused socket was tried + reverted: over loopback `send()` never throws even after VRChat rebinds, so it wedged "successfully" until process restart).
