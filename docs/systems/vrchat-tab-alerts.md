# VRChat tab: in-app alerts, events, instance picker

_Scope: In-app alert groups/cards, rich event + announcement cards, signed-up/pinned sections, series/Repeats dialog, GroupAlertEnricher, AlertImageStore, InstanceListDialog + 24h instance history._

  - **In-app action symbols + instance picker (`VrchatPage.kt`)**: per-event full-width action buttons were REPLACED by **compact circular symbol buttons in the card header**, sitting next to the collapse (chevron) and dismiss (X) affordances and matching their style (`HeaderActionSymbol`, 34dp tinted `Surface`). Per group the header shows: an **invite symbol** (↪ `Login` for invite-me / ＋ `PersonAdd` for invite-them) when the group has invite actions, and **one** "Open in VRChat" symbol (⧉ `OpenInNew`) for the single url shared by all events. **Open dedup**: friend-request+new-friend and bio/name/rank history all point at the same profile url, so they show ONE header open symbol instead of repeating it per event; groups with DISTINCT per-event urls (separate group posts/events) keep per-event "Open in VRChat" buttons in the body via `showPerEventOpen` (`= sharedOpenUrl == null`). **Invite symbol tap behavior**: invite-request (single) → instant `inviteUserToInstance`; world-invite with ONE distinct instance → instant `inviteSelfToInstance`; world-invite with MULTIPLE distinct instances (same person invited you to several) → opens **`InstanceListDialog`** (the instance picker).
    `CompactAlertButton` (38dp full-width tonal) remains for the body per-event opens and the dialog rows. `AlertActionButtons` was deleted. `InAppAlertEvent` carries `actionType`/`actionData` (persisted in the alerts JSON).
  - **`InstanceListDialog` + 24h instance history (`VrchatPage.kt`, all LOCAL — zero Firestore)**: a reusable app-styled picker listing instances with world image (Coil via `VrchatImageLoader`, session-authed), live occupancy, and a joinability status chip, plus a per-row **Invite** button (`inviteSelfToInstance`). Instance info is fetched FRESH every time the dialog opens (`VrchatAuthManager.fetchInstanceInfo(loc)` → `InstanceInfo(worldName, worldImageUrl, players, capacity, status)`; `InstanceStatus` from the HTTP code: 200=OPEN, 404=CLOSED/dead, 403=INACCESSIBLE), so counts/closed status are never stale. Used by (a) the world-invite multi-instance picker above, and (b) the **Instance History** chip in the VRChat-tab identity header: `InstanceHistoryStore` (`com.vrca.vrchat`, SharedPreferences `vrca_instance_history`) records every instance the user enters (full location WITH the `~nonce` access token, captured from the self `user-location` event in `applySelfLocationEvent`) along with **join/left times** (`joinedMs`/`leftMs`; `leftMs==0` = still in it;
    `markCurrentLeft()` closes it out when leaving) so the user can re-invite themselves to anywhere they've been in the past 24h and cross-reference what they played and when. **"Still here" is derived from the LIVE `VrchatPipelineState.presence` (the SAME signal the Discord RPC reads), NOT from the stored `leftMs` flag**: the dialog labels the newest open session "Still here" only while `presence.location == entry.location` (keyed on the live location so it recomputes reactively) — the instant presence leaves that world (offline / traveling / hopped) the label drops, regardless of whether `markCurrentLeft` fired. This was the "Still here never changes when I get off VRChat" fix — the old code trusted only `leftMs`, which depended on a `markCurrentLeft` signal that didn't always land. `markCurrentLeft` is ALSO now broadened on the service side: both `applySelfLocationEvent` and `syncPresenceToFirestore` close the open session on ANY world→non-world transition (offline / traveling / blank, excluding the redacted "private" which means still-in-instance), not just `location=="offline"`, so the stored "Left HH:MM" time is accurate too.
    Entries left >24h ago self-prune on every read/write; an instance still occupied never prunes. The nonce lives ONLY on-device (never synced to Firestore — like the user's own cookie). All of this costs **zero Firestore reads/writes**; the only network cost is VRChat REST (instance-info on dialog open, invite on tap), on the user's own session. **Pre-stored thumbnail + type at ENTRY time (so a cold history open never looks bad)**: `Entry` carries `imageUrl` + `instanceType`, grabbed the MOMENT the user enters an instance — the single `GET /instances/{loc}` that already fires on every self world-hop in `applySelfLocationEvent` (for the occupancy count) now uses `VrchatAuthManager.fetchInstanceInfo` (the SAME one request + `extractInstanceUserCount` count logic, just a richer parse) instead of `fetchInstanceCount`, so that ONE already-made call ALSO reads the world thumbnail + API instance `type` and writes them onto the history entry via `InstanceHistoryStore.updateInfo(...)`, and caches the image bytes via `AlertImageStore.ensureCached`.
    **Zero extra network cost** — it's the same call returning more of the response (only patches presence count when `status==OPEN`; only stores non-blank image/type so a CLOSED/INACCESSIBLE reply never wipes a prior value). Opening Instance History later renders the image + type chip INSTANTLY from the stored entry (`InstanceTarget.imageUrl`/`instanceType`, the latter fed into `parseInstanceType` as `apiType` with the location-string derivation as fallback) instead of fetching everything on the spot; the picker still live-refreshes occupancy and re-persists the freshest world-name/image/type via `updateInfo`. `updateImage` is now a thin wrapper over `updateInfo`. When the entry ages out of the 24h window and is pruned, `AlertImageStore.gc()` sees its `imageUrl` reference vanish and deletes the cached file — so the image clears with the entry.
  - **Rich event/announcement alerts (`AlertEventBody` in `VrchatPage.kt` + `AlertRichMeta`/rich fields on `InAppAlertEvent`)**: group-event and announcement alert cards render structured content instead of a text blob. Events show: a full-width **banner at the image's OWN intrinsic ratio** (`ContentScale.FillWidth` + wrapped height — creators upload arbitrary ratios, so ANY fixed-ratio Crop box cut edges; tester confirmed cropping twice, first at 21:9 then at 1200:630 — do NOT reintroduce a fixed-ratio crop). **Overlays ride the banner, identity-header style**: **language chips top-right in a right-aligned STACK** (`LanguageChip`; a horizontal row overflowed on long native sign names; native names via `vrcLanguageNames`/`nativeLanguageName()` — "日本語, English, 日本手話" EXACTLY as VRChat's site renders them;
    **tapping a chip shows the device-language translation (`deviceLanguageName()` — "Japanese Sign Language" on an English phone, VRChat's in-client localization style) in place for 5s then reverts** (`LanguageChip` is CONTROLLED — `AlertEventBody` hoists a single `translatedLang` + `langTapTick`, so only ONE chip is translated at a time and tapping another instantly reverts the previous even mid-window; re-tap restarts the 5s; sign languages translate to English names since Locale can't resolve them); the earlier `Locale.displayLanguage` localized names to the DEVICE language so "English" showed as 英語 on a Japanese-locale phone, and sign tags were wrongly shortened to "JSL" — VRChat's real names are `jsl`→日本手話, `ase`→American Sign Language, `kvk`→한국수어 etc.; map first, then native-Locale resolution, then uppercased code) and a **bottom scrim row** (black vertical-gradient) carrying the status/category/access chips (dark `solid` `EventMetaChip` variant) + **platform SYMBOLS** (`PlatformSymbols`: circular tinted BRAND glyphs matching VRChat's badges — Windows flag blue (`ic_platform_windows.xml`) / Android robot green (`Icons.Filled.Android`) / Apple mark light (`ic_platform_apple.xml`); a monitor/phone glyph read as wrong per user reference).
    **All chips (`EventMetaChip`/`LanguageChip`) are a FIXED 22dp height with centered single-line text** — CJK glyphs are taller than Latin, so padding-based chips rendered at different sizes and looked ragged in mixed-language rows. **Tappable chips (access chip's group link, language chips) use `Surface` + `Modifier.clickable`, NOT `Surface(onClick=...)`** — a clickable Surface enforces Material3's 48dp minimum interactive size, which padded each tappable chip to 48dp tall and blew a huge invisible vertical gap between the chip rows (tester-reported "big gap that looks weird"); `clickable` keeps the chip its true height. No banner → **TWO tight rows in a `Column(spacedBy(6.dp))`**: (1) a `FlowRow` with the status/category/access chips (wrapped in ONE inner `Row` so they're inseparable — as bare FlowRow children it split them, wrapping "Group" off on its own) + platform symbols on the same line; (2) a `FlowRow` of language chips directly below. Languages in their OWN row (not the same FlowRow as the chips) is what removed the big vertical gap the single-FlowRow wrap left. A thin `Divider` separates the meta block from the description.
    `richChips(solid)` is the single shared chip definition; `ExperimentalLayoutApi` for `FlowRow`. Chips: **status** ("Starts in 2h" primary / amber when <2h → "**Live now**" green while `startsAtMs ≤ now ≤ endsAtMs` → "**Ended**"; no `endsAt` = live for 4h after start, via `eventPhase()`), **category** (`prettyEventCategory`: `film_media` → "Film & Media", generic underscore→Title Case fallback), a **recurring indicator** (`InAppAlertEvent.recurring`, best-effort from `GroupAlertEnricher.extractRecurring`) — placed on the banner's empty **top-left** corner when there's a thumbnail, else appended to the muted meta line ("... · ↻ Repeats"); deliberately NOT a status-row chip (it crowded that row). **Recurring-flood collapse**: VRChat writes EVERY day of a repeating event as its own calendar event (a daily repeat = up to 50 alerts in one `event_$groupId` group). `collapseRecurring()` folds same-title events in a group down to the **nearest UPCOMING occurrence** (or most-recent past if none upcoming) at DISPLAY time in `AlertGroupCard` — so the card shows ONE, the "(N)" count is the collapsed count, and the header preview uses the SOONEST event (not the farthest, which read "in 48d").
    It's retroactive (fixes cards that already flooded) and self-advancing (as an occurrence passes, the collapse picks the next from the stored occurrences). The Android notification was already one per group (`setOnlyAlertOnce` on the shared `alertGroupKey` id), **access chip** (Public green 0xFF4CAF50, Group purple 0xFFAB47BC) which **IS the tap target that opens the hosting group's web page** (per user feedback: the CHIP opens the group, NOT the card title — a title-click attempt was reverted). Below the meta line, a **"Hosted by <name>"** one-liner where the name is primary-tinted and clickable → the organizer's VRChat profile (`organizerId`/`organizerName`; `extractOrganizerId` probes owner/author/creator fields, name resolved once via `VrchatAuthManager.fetchUserDisplayName` and cached in the enricher). Below: description in `bodySmall`, a compact **one-line timing row** (Schedule icon + "Jul 5 · 3:05 PM → Jul 8 · 5:05 PM", `eventDateTime` has NO year), a **muted meta line** ("1 interested · Posted Jul 4, 2026" — `eventDate` keeps the year), NO relative-time footer on rich events (the chip + timing line already say when; plain alerts keep it), and **phase-appropriate actions**:
    UPCOMING → **Add to Calendar / Remove from Calendar** (`VrchatAuthManager.setCalendarEventFollowing` → `POST /calendar/{groupId}/{eventId}/follow` `{"isFollowing":bool}` — community-documented endpoint, failures surface VRChat's own error; success optimistically updates `following` via `InAppAlertState.enrichEvents`, AND schedules a **local reminder** (`EventReminderScheduler` — an inexact `AlarmManager.setAndAllowWhileIdle` alarm ~10 min before `startsAt`, no exact-alarm permission; `EventReminderReceiver` posts the "Event starting soon" notification; persisted to `vrca_event_reminders` prefs and re-armed on reboot via `BootReceiver.rescheduleAll`; Remove-from-Calendar cancels it). **Signed-up events (following==true) golden-pin to the top**: `VrchatStatusPage.inAppAlertSection` partitions the alert groups into a "★ Signed up Events" section (gold sub-header, `AlertGroupCard(signedUp=true)` → gold accent bar + gold border + faint gold container tint + a "★ Going" pill by the title) pinned above an "Other notifications" section;
    **Splitting is at the EVENT level, not the group, but COLLAPSED per SERIES**: a group can have some events the user signed up for and some they didn't, so the FOLLOWED events become cards in "Signed up Events" while the remaining unfollowed events stay grouped in Pinned (if the group is manually pinned) or Other. **Followed events are grouped by SERIES (normalized title) into ONE card per series** (`bySeries` map → `su_<groupId>_<seriesKey>`, the card's own `collapseRecurring` picks the nearest upcoming occurrence + shows the count) — a recurring event the user signed up for has ~50 occurrences each independently `following==true`, which without this collapse spawned ~50 identical "Going" cards (tester-found flood). Un-following an event drops it back into the remainder group; dismissing a remainder card uses `dismissEvents` (removes only its unfollowed events, so the followed ones shown separately survive).
    **SHORT-WINDOW per-series follow override (`followSeriesKey`/`recordFollowToggle`/`followOverride`, in `InAppAlertState`, in-memory)**: tapping Add/Remove records the user's decision keyed by SERIES (normalized title, or `id:<evId>` when titleless); the enricher's `following` read consults `followOverride(followSeriesKey(...))` FIRST, but the override lasts only `FOLLOW_OVERRIDE_MS` = **30s** — just long enough to cover VRChat's follow-propagation delay so an in-flight enrich can't flip a just-toggled event back. **After the window the SERVER's `userInterest.isFollowing` is authoritative**, so a follow/unfollow made on the **WEBSITE or in the VRChat CLIENT** is picked up by the 10s expanded poll / 60s tab loop. (The override was briefly made PERMANENT+persisted as a workaround for the old `extractEventFollowing` bug that reported EVERY event as followed — but permanence blocked external follow changes from ever showing, and with the follow field now read correctly (`userInterest.isFollowing`) there's no flip-back to guard against beyond the propagation window.)
    The optimistic UI update (`applyFollowToSeries`) covers every occurrence of the series at once, and a failed API call reverts both the override and the display. **Signed-up cards are NOT dismissable** — the per-card X is hidden and `InAppAlertState.dismissAll` preserves them (Remove-from-Calendar un-pins → the X returns), so a user can't accidentally delete an event they're going to. **Manual "📌 Pinned" section (universal, any alert type)**: below "★ Signed up Events" sits a **collapsible** "📌 Pinned (N)" section for groups the user manually pinned (`InAppAlertGroup.pinned`, persisted). A **tiny pin toggle** sits next to the "ago" row in EVERY card (both collapsed and expanded states) — filled gold when pinned, outline otherwise — **EXCEPT signed-up (Added-to-Calendar) cards, where the pin is hidden** (they auto-sort into "Going", so a manual pin fought the auto-sort; **Add-to-Calendar also auto-unpins** via `setPinned(false)`). `InAppAlertState.setPinned` caps manual pins at **`MAX_PINNED` = 10** (over-cap → a toast, no-op).
    **Per-event dismiss**: a multi-event card shows a small X per event (title row / "Change N" row) → `InAppAlertState.dismissEvent` removes just that event (a recurring series' X clears the whole series; emptying the group removes it). The AnimatedVisibility event list is wrapped in `key(displayEvents ids)` so a SECOND event fusing into a group actually repaints (the content lambda otherwise skips — same cycle-mute class). Pinned groups get the SAME gold treatment + a "📌 Pinned" pill, are NOT dismissable (X hidden + `dismissAll` preserves `pinned || following`), and un-pinning (tap the pin again) drops them back to "Other notifications". The Pinned section's collapse state is `PinnedSectionState.expanded` — the SAME process-scoped model as `AlertSectionState` (survives tab switches, resets to expanded on a cold process start). The three partitions (signed-up / pinned-not-signed-up / rest) are disjoint (signed-up wins) so a group renders once; keys stay the plain groupId so expand state survives partition moves.
    `following` is read from the calendar object via `extractEventFollowing` (probes `isFollowing`/`isInterested`/`isAttending`/... booleans + `userInterest`) so an event added IN-GAME shows as signed-up and its button reads "Remove from Calendar" instead of wrongly offering "Add" — best-effort pending confirmation of VRChat's exact field name); LIVE → **Join event** (fetches `VrchatAuthManager.fetchGroupInstances` = `GET /groups/{id}/instances` — VRChat doesn't link events to instances, so ALL the hosting group's open instances are listed in the SAME `InstanceListDialog` the multi-invite picker uses, with an `emptyText` explaining when the group has none open); ENDED → no action. Announcements get the banner (group-post `imageUrl`), **"Visit <host>" link buttons** for URLs in the body (`extractBodyUrls`, max 3), and **read-more** collapse past 320 chars. **Announcements from a group that currently has an OPEN instance also get a "See active instances" button** (same `InstanceListDialog`/`fetchGroupInstances` picker as a LIVE event's "Join event", shared `onJoinEvent`/`openJoinPicker`, dialog title neutralised to "Active instances · <group>").
    The button shows ONLY when the group has ≥1 open instance — `AlertEventBody` fires ONE `fetchGroupInstances` check on expand (this body only renders while the card is expanded, so it's one lightweight GET per opened announcement, not per row) and stores `announcementInstanceCount`. Per-event `remember` state is wrapped in `key(event.id)`. **The shared alert-card header title (`AlertGroupCard` `displayTitle`) is `maxLines = 2`** (was 1) — long notification titles ("Announcement from <long group name>", etc.) were ellipsis-cut on EVERY alert type since the header is shared; two lines before ellipsizing handles it.
  - **Event identity = `seriesId`, not title (`InAppAlertEvent.seriesId`); re-surface dismissed follows; "Removed" state**: three coupled fixes to event alerts. (1) **Stable series identity** — `InAppAlertEvent` gained `seriesId` (VRChat's per-series id; every occurrence of a repeat shares it, a one-off has its own), populated at the fire paths (`fireGroupCalendarEvent`/`fireDetailedCalendarEvent` via `AlertRichMeta.seriesId` = `GroupAlertEnricher.extractSeriesId`) and by the enricher, and persisted. The **display collapse** (`collapseRecurring`), the **signed-up `bySeries` partition**, and the **enricher match/transform** now key on `seriesId` FIRST (title only as a fallback for cards with no seriesId yet). This fixes "two DIFFERENT repeating events override/mix each other's thumbnail/languages/description/title and the card flip-flops between them" — title is not a unique identity (distinct series collided, edits changed it, the enricher's title clause cross-wrote one series' fields onto another).
    The thin v2 fire paths ALSO try to pull `seriesId` from the push (`content`/`data`/`details`, same as `startsAt`) so a series-carrying push groups correctly on first fire; when the trimmed payload omits it, seriesId is null and the targeted enrich sweep fills it within seconds. (2) **Re-surface a swiped followed event — POST-FIRE ONLY** — the signed-up section derives purely from `following==true` events in `_groups`, so an event dismissed from the in-app list (while `following` was still null, before enrichment confirmed it) vanished from "Going" (the enricher only UPDATES existing cards). When the enricher's server follow-read (`userInterest.isFollowing`, which reflects website/PC/headset subscribes) says `following==true` and `InAppAlertState.hasSeriesCard(...)` is false, it silently re-adds the card (`readdFollowedEventIfMissing`, no Android notification).
    **CRITICAL: this only runs on the POST-FIRE targeted sweep (`enrich(..., allowResurface=true)` from `scheduleTargetedGroupSweep`), NOT the routine periodic tab-loop/expanded sweeps (`allowResurface=false`, the default).** VRChat reports the user's OWN created events as `following==true` FOREVER, so a periodic re-surface resurrected every dismissed self-created event on every VRChat-tab open (tester-found "old dismissed events keep reappearing in Going"). Gating to the post-fire window keeps the genuine "you subscribed/created and swiped it away too fast" case while never fighting a deliberate dismissal of an old event. Remove-from-Calendar sets `following=false` so an intentional un-follow is also never fought; repeatable and per-series. (3) **Deletion → "Removed"; ENDED → pruned** — two cleanup mechanisms. **Ended prune** (`InAppAlertState.pruneEndedEvents(ctx, now)`, timestamp-only, no network): removes events whose end has passed (`eventEnded` = past `endsAtMs`, or >4h past `startsAtMs` with no end) so concluded events stop cluttering "Going"/the notifications area (a recurring series sheds past occurrences, keeps upcoming ones;
    `removed` red cards are KEPT; non-event alerts untouched). Run on VRChat-tab entry + every 60s in the tab loop. **Deletion → red "Removed" card** (`InAppAlertEvent.removed`, persisted): the enricher's `detectRemovedEvents` trusts the AUTHORITATIVE group calendar LIST. **`fetchGroupCalendarEvents` now returns `[]` (not null) for an emptied group** — the canonical `/calendar/{groupId}` endpoint's 200-with-`results:[]` is returned as an empty array instead of falling through to the legacy 404 endpoints and returning null, so "group has zero events" is finally distinguishable from "fetch failed" (null). Detection runs ONLY when the list is non-null (a null list = network error → skip, so a blip can't false-flag). Detection asks VRChat **DIRECTLY per event id** (`fetchCalendarEventResult` = `GET /calendar/{g}/{eventId}` → **404/410 = deleted**, 200 = alive) for every not-yet-removed, non-ended, signed-up-or-upcoming card — the PRIMARY signal, NOT gated on list-presence.
    Gating on list-absence (a first attempt) was the "second-deleted event never flags" bug: if VRChat's group calendar LIST lags and still shows the just-deleted event, that event was marked "present" and never even 404-checked. Going straight off the event's own 404 sidesteps the list entirely. Blip protection: a network/429/5xx reply is UNKNOWN and does NOT flag on its own; only when the direct check is inconclusive does it FALL BACK to the list — absent there for **`ABSENT_STRIKES_TO_REMOVE` = 2 consecutive sweeps** (`absentStrikes` in-memory counter) also flags, while a definitive 200 or list-presence resets the strike. The direct checks are bounded (≤10/sweep). List fetched at n=100 (fallback only). `markSeriesRemoved` sets `removed=true`+`following=false`. ENDED events are skipped (pruned, not flagged — the red state is for a cancelled event you might still attend). (`fetchGroupCalendarEvents` still returns `[]` not null for an emptied group so the list fallback can distinguish "zero events" from "fetch failed".)
    A removed event drops out of "Going", becomes its own **red** card (`rm_<groupId>_<series>`, `AlertGroupCard(removed=true)` → red accent bar/border/tint + "Removed" pill) in the normal area, body shows "This event was removed from VRChat" instead of Add/Join/Remove, and it's **dismissable**. **`removed` is STICKY** — the enricher deliberately does NOT clear it on a live-representative match (a title-fallback match could otherwise un-remove a deleted same-title sibling series); a genuinely recreated event gets a fresh id → new card. Won't be re-surfaced by (2) since `following` is cleared AND re-surface is post-fire-only.
  - **Repeats dialog — per-occurrence subscribe (`EventOccurrencesDialog` + `EventSeriesStore`)**: tapping the **"↻ Repeats"** indicator on a recurring event card (clickable when `recurring && seriesId != null && groupRefId != null`) opens a picker (styled like `InstanceListDialog`) listing **every occurrence** of the series with its start date/time + a per-occurrence **Subscribe/Going toggle** — VRChat tracks follow **per occurrence** (`cal_` id), so this matches the real model (`setCalendarEventFollowing(groupId, occurrenceId, following)`). **`EventSeriesStore` (`com.vrca.vrchat`, SharedPreferences `vrca_event_series`)** persists every occurrence per `groupId|seriesId` (`{id, startsAt, endsAt, following, deleted}`) until it ENDS (pruned) or is DELETED (flagged red "Removed", kept 24h, then pruned).
    **Cost model**: occurrence existence + timing + the **deletion diff** come FREE from the group calendar list the enricher already fetches (`reconcileOccurrenceStore` in `GroupAlertEnricher.enrichLocked` — groups the raw list by seriesId, reconciles the store, flags stored-but-absent occurrences deleted **only within the n=100 window** via `maxLiveStart` so a far-future occurrence isn't false-flagged). Only per-occurrence FOLLOW state costs a call (the list omits it), so `following` starts null and is filled **lazily**: the representative's follow is written free by the enricher (already fetched); the dialog fetches the rest **on open**, paced (300ms), nearest-first, capped 20, skipping any the user is actively toggling. In-app subscribes write the store instantly + fire the API optimistically (revert on failure). **Card aggregate "Going"**: a recurring card golden-pins when `ev.following == true` OR `EventSeriesStore.anySubscribed(...)` (subscribed to ≥1 live occurrence) — the partition's `isGoing()` in `VrchatStatusPage.inAppAlertSection` — so subscribing to any occurrence in the dialog lights the one series card in "Signed up Events".
    **Roll-forward when the shown occurrence ends (`pruneEndedEvents` → `advanceRecurringEvent`)**: the alert stores only ONE fired occurrence per series, and the ended-event prune ran BEFORE the enricher could re-point it, so a recurring card used to VANISH when its shown occurrence ended instead of switching to the next date. Now the prune, on finding a recurring event whose occurrence ended, re-points the card to the series' **next upcoming occurrence** from `EventSeriesStore.nextUpcoming(...)` (updates `eventRefId`/`startsAt`/`endsAt`/`timestamp`/`following`, preserving title/banner) instead of removing it; only a CONCLUDED series (no upcoming occurrence in the store) or a non-recurring event drops. The store is populated by the enricher over the card's lifetime, so by the time an occurrence ends it's virtually always present; if it somehow isn't, the fallback is the old behavior (drop) — no regression.
    **DELETION of the shown occurrence also rolls forward, not just ENDING** (`GroupAlertEnricher.removeOrAdvance`): when `detectRemovedEvents` confirms the card's occurrence is deleted (404), for a RECURRING series it marks that occurrence deleted in the store, then `InAppAlertState.advanceSeriesIfUpcoming` re-points the card to the next upcoming occurrence (clearing `removed`) — only a one-off, or a series with NO upcoming occurrence left, falls through to `markSeriesRemoved` (the red card). `reconcileOccurrenceStore` runs BEFORE `detectRemovedEvents` in `enrichLocked` so `nextUpcoming` already excludes the just-deleted occurrence. This also stops the card from collapsing on the delete (it stays in its section instead of moving to "Removed", so its `key` — and expand state — survive). **Dialog survives enrichment (`occurrencesFor` hoisted to `AlertGroupCard`)**: the Repeats dialog's open-state used to live inside `AlertEventBody`, which is wrapped in `key(event.id, event)` — so every enrichment tick that changed the event data disposed+recreated the body and slammed the dialog shut.
    It now lives in `AlertGroupCard` (card scope, keyed by the stable `groupId`) and `AlertEventBody` opens it via an `onShowOccurrences` callback, so an enrich sweep no longer closes it. A fully-deleted series shows a "removed from VRChat" notice. **Instance history reuse**: `InstanceListDialog` gained a `liveRefresh` param — the invite/join pickers keep the 15s occupancy re-fetch loop, but Instance History passes `liveRefresh=false` for a ONE-TIME grab (no continuous re-fetch), cutting its calls to a single pass.
  - **Thin-payload enrichment + live refresh (`GroupAlertEnricher`, `com.vrca.vrchat`)**: notification-v2 pushes carry far less than the calendar object (no banner, often no timing) AND an alert used to freeze at fire-time data (interested count never moved, event edits never appeared). `GroupAlertEnricher.enrich(ctx, groupId)` is the shared ONE-GROUP REST sweep (calendar events + posts, 2 calls, debounced 60s per group inside the enricher) that **merges fresh values into the fired alerts in place** via `InAppAlertState.enrichEvents` (events matched by `cal_` id, announcements by normalized-body == the content-fingerprint normalization): banner, start/end, created, interested count, category/platforms/access/**languages**, `following`, the event's REAL title (**strips VRChat's "New event by X:" v2 boilerplate via `cleanEventTitle`**, also applied at v2 fire time), display timestamp → `startsAt`, body → clean description.
    **Every post-creation-editable event field (title, start/end, category, description, visibility, thumbnail, platform, languages) refreshes through this merge** — fresh non-blank values overwrite; languages is the one field an edit can EMPTY, so it's keyed on `ev.has("languages")` (present-but-empty CLEARS the stale value instead of keeping it). **In-game follow detection + representative collapse**: the group calendar LIST omits the user's per-event follow state, so an event added to the calendar IN-GAME wasn't detected. The enricher collapses the fetched events to ONE representative per series (`collapseEventsByTitle`, nearest-upcoming — bounds the per-event work), then does a **single-event fetch** (`VrchatAuthManager.fetchCalendarEvent` = `GET /calendar/{groupId}/{eventId}`) which carries the follow state + richer organizer/recurrence, and applies `following` from it **UNLESS the user set a persistent in-app override** (`InAppAlertState.followOverride(followSeriesKey(...))`, checked first — a user's own Add/Remove always wins over the server, which reports the creator's own events as perpetually followed).
    A recurring representative's enrich MATCHES ALL stored occurrences of its series (by normalized title) so following/interested propagate to every one. **CONFIRMED VRChat calendar-event field names (from an on-device raw-JSON capture via the Settings→Debug diagnostics, `VrcaEventDiag`)**: follow state is the NESTED `userInterest.isFollowing` boolean (`extractEventFollowing` reads it — the old "`userInterest` present ⇒ following" test reported EVERY event as signed-up, since `userInterest` is always a non-null object); recurrence is `seriesId` (non-null) + `occurrenceKind=="occurrence"` (a one-off is `"single"`); interested count is `interestedUserCount`; banner is `imageUrl`. **Events have NO individual creator** — `ownerId` is the owning GROUP (`grp_`), not a person, so events show no "Hosted by" line (the group is already the access chip). **Posts/announcements DO carry `authorId` (a `usr_`)** — the announcement enrich path resolves it via `fetchUserDisplayName` (cached) and shows **"Posted by <name>"** (label is "Hosted by" for events / "Posted by" for announcements, keyed on `isRichEvent`).
    **`collapseEventsByTitle` keys on `seriesId ?: normalizedTitle`** (every occurrence of a repeat shares both), so a flooded recurring series collapses to ONE representative → ONE single-event fetch (fixes "repeat events take ages to load their info because the app grabs them all"). **It must NOT be keyed on `occurrenceKind`**: the calendar LIST endpoint reports that field unreliably (the confirmed value is only on the single-event fetch), and a brief attempt to give `occurrenceKind=="single"` list items their OWN bucket REGRESSED the collapse — every occurrence became unique, so the whole series flooded the fire path again AND the enricher went back to ~50 single-event fetches. The one-off-falsely-flagged-recurring concern lives in `extractRecurring` (the chip), not the collapse. Three callers: (1) `VrchatPipelineService.scheduleTargetedGroupSweep` (retries at 2.5s/8.5s/23s with `minIntervalMs=0` so a genuine new event enriches even before VRChat has indexed it, and a second event right after a first isn't debounced away); (2)
    **`VrchatStatusPage` runs a refresh loop while the tab is composed** (first pass 5s after entry, then every 60s, capped at 6 distinct `groupRefId`s from visible `event_grp_`/`announcement_grp_` alert groups) so interested counts and event edits UPDATE while the notification is on screen; (3) **while an event/announcement card stays EXPANDED it re-enriches every 10s** (`LaunchedEffect(expanded)` in `AlertGroupCard` LOOPS with `delay(10_000)` + `minIntervalMs = 9_000` — the ~9s per-group min lets each 10s tick through while the 55s tab loop mostly no-ops for that group; the effect is cancelled the instant it collapses, so the loop stops with it). This keeps the interested count / timing / banner / follow state / edits live on-screen (fixes "the interested counter is inconsistent with updating").
    **Rate-limit guards, two layers**: the per-group debounce (atomic check+stamp via `compute`) caps each group to one sweep per window, AND a **global `sweepMutex` + 2.5s spacing** serializes sweeps ACROSS groups — spamming expand across cards from several different groups queues one 2-call sweep per 2.5s max instead of firing an unspaced burst (the 250ms intra-sweep pacing matches the backfill's). A multi-event card needs only ONE sweep: all its events share the group, and the single calendar response enriches each by its `cal_` id. **Repaint requirement: `AlertEventBody` is wrapped in `key(event.id, event)` — keyed on the FULL event data.** The card body sits inside `AnimatedVisibility`, which (proven on-device, same class as the cycle-mute saga) can skip repainting children whose params changed — keyed on id alone, enrichment updated the state but the expanded card never visually changed ("re-expanding doesn't update"). Do not reduce the key back to just the id. Enrichment NEVER fires a notification — display-state only.
    The rich fields ride `fireEventNotification(alertRich = AlertRichMeta(...))` from the REST calendar sweep (full meta at fire time, helpers now on `GroupAlertEnricher`) and the v2 paths. **Instant-detail live event fire (the "event notification shows a thin title-only card, then ~1 min later a SECOND full card appears in Signed up" fix)**: the live notification-v2 EVENT push used to fire a THIN card (no banner, no `following`) because a freshly-created event's push often carries no `cal_` id — so (a) the enricher couldn't match it and (b) the REST poll fired a separate full card that, being `following==true` for the creator, golden-pinned to Signed up while the thin one lingered. The v2 event branch now **fetches the full calendar object BEFORE firing** (`VrchatPipelineService.resolveFullCalendarEvent` → `fireDetailedCalendarEvent`) so its FIRST card is already detailed (banner/timing/interested/`following`, instantly pinning a self-created event to Signed up).
    `resolveFullCalendarEvent` prefers the single-event fetch (`fetchCalendarEvent` by `cal_` id — carries `userInterest.isFollowing`), else matches the group calendar by normalized title (nearest-upcoming occurrence for a recurring series) then upgrades to the single event, with one 1.2s retry for VRChat backend indexing lag; on total failure it falls back to the OLD thin fire + `scheduleTargetedGroupSweep` (the sweep then upgrades that thin card in place). This runs on `pipelineDispatcher` but its REST calls `withContext(Dispatchers.IO)`, so it yields the dispatcher thread (doesn't block other WS handlers) and touches no `friendsCache` across the suspension. **Cross-path DUPLICATE prevention is keyed on TITLE as well as the `cal_` id** (`InAppAlertState.hasEventFor(groupKey, eventId, normalizedTitle)`): both fire paths (the v2 push AND `fireGroupCalendarEvent`) skip + record the fingerprint when a card already exists for the event by id OR title, and the enricher ADOPTS a still-thin card by title (`eventRefId==null && title match`, transform sets its `eventRefId`) — so whichever path fires SECOND never spawns a duplicate even when only one of them knew the id. (Tradeoff: two genuinely-distinct undismissed events in the same group sharing an EXACT title collapse to one — rare, and it aligns with the recurring "one card per series" behavior.)
  - **`AlertImageStore` (`com.vrca.vrchat`, files at `filesDir/alert_images/<sha1(url)>.img`)**: dismissal-scoped persistent image cache fixing "thumbnails reload every time you open the menu". One file per unique image URL, downloaded ONCE (`ensureCached`, session cookie attached for vrchat hosts) when the notification fires / info first resolves; UI loads via `AlertImageStore.resolve(ctx, url) ?: url` (disk file first, Coil network fallback). **Lifecycle = references**: a file lives until NOTHING references its URL — alert dismissal (`InAppAlertState.dismiss`/`dismissAll`) and the instance-history 24h prune drop references, then `gc()` (also run at `load()`) deletes orphans. References tracked from: alert events' `imageUrl` (event/announcement banners; invite targets get theirs recorded via `setInviteTargetImage` when the picker first resolves info) + `InstanceHistoryStore.Entry.imageUrl` (recorded via `updateImage` at the same moment). `InstanceTarget.imageUrl` feeds the stored thumb into `InstanceRow` so history/invite rows render instantly while live info is in flight. Deliberately NO size cap (thumbnails are ~50-150 KB; even hundreds of undismissed alerts is single-digit MB).
  - **In-app alerts (grouped)**: Notifications create persistent in-app alert groups displayed as dismissible cards at the top of the VRChat tab. The notification section starts **collapsed** by default and is expandable via a "Notifications (N)" header. Groups are keyed by `userId + notificationType` (e.g., `bio_usr_xxx`, `name_usr_xxx`) or by notification category (e.g., `announcement_$groupId`, `event_$groupId`). When the same event type fires multiple times for the same user/group, events are appended to the existing group — never overwritten. `InAppAlertState` singleton manages `MutableStateFlow<List<InAppAlertGroup>>`. Each `InAppAlertGroup` contains a list of `InAppAlertEvent` objects (max 50 per group), with `firstSeenMs`, `lastUpdatedMs` timestamps, and optional `eventTitle` per event. The UI shows "Title (N)" when a group has multiple events. Expanding a group shows all events in chronological order, each with its own before/after diff (`wordDiff()` in `VrchatPage.kt`) and optional per-event title and relative timestamp.
    **The diff is LINE-level, not word-level.** Bios are usually multi-line lists; a word-level LCS matched common words ("the", "my", "get") across DIFFERENT lines and painted an inconsistent red/green/purple mess (the user reported this). Whole lines are far more unique, so the algorithm runs LCS over lines: each line is unchanged (neutral grey), removed (red), added (green), or **moved (purple `0xFFB388FF`)**. **Line move detection** matches a removed line's exact trimmed content against added lines — whole-line matching is unambiguous, so no blocklist is needed (the prior word-level move detection needed a blocklist to stop short words like "my"/"I" turning purple everywhere). **Single-line refinement**: each remaining real-removed line is paired with the most similar real-added line (token Jaccard > 0.3); paired lines get a word-level red/green diff (`lineWordDiff()`) so editing one word in a line highlights just that word instead of reddening the whole line. Single-line bios fall through this pairing and show word-level diffs too. Newlines are preserved so multi-line layout stays intact.
    Each rendered card is wrapped in `key(group.groupId)` so Compose tracks its expanded/collapsed state by group identity, not list position — without this, a new alert prepended to the list shifted every card's remembered state up one slot, so the card the user was reading collapsed and the new top card appeared expanded. Bio diff cards show bold **BEFORE** (red) and **AFTER** (green) headers above each half so users aren't confused about which side is the old/new bio. The collapse/expand chevron and the dismiss (X) button each sit in a tinted circular `Surface` (primary-tint for the chevron, error-tint for dismiss) so they stand out instead of blending into the card. Groups are capped at 20 (FIFO). Only 3 groups visible at once; "+N more" button reveals the rest. Dismissing removes the entire group, all its events, AND cancels the linked Android notification (using `groupId.hashCode()` as the stable notification ID). Backward-compatible: `addAlert()` wraps single events into single-event groups. Old flat alerts are auto-migrated to the group format on first load.
    `fireEventNotification` accepts `alertGroupKey` and `alertEventTitle` parameters — when provided, the event is added to the named group with its own title instead of creating a standalone alert. For grouped Android notifications, uses stable notification ID per `alertGroupKey.hashCode()` with `setOnlyAlertOnce(true)` so subsequent events update the notification silently (no re-alert). Bio change notifications no longer have a per-friend cooldown — the grouping model replaces cooldown-based spam prevention.
