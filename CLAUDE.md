# VRC-A — Claude Code Instructions

## Project Overview
Android app called VRC-A (VRChat Assistant).
Built with Kotlin, Jetpack Compose, Firebase Firestore, and GitHub Actions CI.
There are two build variants: a public user-facing APK and a separate admin APK.
Display name embedded in UI strings: "Ashoska Mitsu Sisko".

## Repository Structure
- Main app source: `app/src/main/kotlin/com/vrca/`
- Kotlin package: `com.vrca` (applicationId stays `com.scrapw.chatbox` for install continuity)
- Subpackages: `admin/`, `app/`, `data/`, `discord/`, `keepalive/`, `nowplaying/`, `osc/`, `overlay/`, `sync/`, `ui/` (with `common/`, `conversation/`, `screen/`, `settings/`, `theme/`, `viewmodel/`), `update/`, `vrchat/`

## Architecture & Stack
- Language: Kotlin
- UI: Jetpack Compose
- Backend: Firebase Firestore
- Auth/device management: Firestore `bannedDevices` collection
- NowPlaying: pause detection logic (check for edge cases when modifying)
- Admin UI: Users tab, Releases tab, tab bar navigation
- APK distribution: GitHub Releases. `githubUploadAsset()` and `githubCreateRelease()` in `ReleasesTab.kt` use OkHttp. `githubUploadAsset` (shared by the Releases tab AND the admin targeted/directed-release upload in `UsersTab.kt`) **manually follows 301/302/307/308 redirects** from `uploads.github.com`: OkHttp does NOT auto-replay a streamed POST body to a redirect target, so it surfaced GitHub's redirect as a `GitHub upload failed (307)` error. The fix reads the `Location` header and re-issues the POST (the file-backed `RequestBody` is repeatable) for up to 3 hops, preserving the POST method. Both functions retry up to 5 times with exponential backoff on failure.

### VRChat Integration
- **VrchatAuthManager**: Singleton handling VRChat API auth (Basic auth + 2FA), cookie storage via EncryptedSharedPreferences, presence fetching, and friends list retrieval. Also saves credentials to EncryptedSharedPreferences for auto-relogin when sessions expire. Credentials are saved BEFORE the login HTTP request so they survive app kills during response processing; cleared only on HTTP 401 (wrong password) via `clearCredentials()`. On re-login after auth-cookie expiry, the Basic-auth request sends ONLY the persisted `twoFactorAuth` cookie via `getTwoFaOnlyCookieHeader()` — never the expired `auth=` cookie, which can cause VRChat to reject the request as a session conflict. VRChat recognizes the trusted device and skips the 2FA prompt — works for up to 30 days from the last successful 2FA verification (`KEY_2FA_COOKIE_STORED_AT` tracks the age; expired cookies are dropped before sending; timestamp of 0 triggers one-time migration to current time instead of being treated as valid forever). On successful Basic-auth login, only the auth cookie + user info are written via a direct prefs edit; the existing 2FA trusted-device cookie and its original stored-at timestamp are preserved (without this preservation, the 2FA cookie would get wiped on every successful relogin and the SECOND auth-cookie expiry would always force manual 2FA). `getPrefs()` has a recovery fallback: if EncryptedSharedPreferences init fails (MasterKey corruption), it deletes the corrupted prefs file and retries. `diagnoseAuthState()` logs the presence/age of all auth-related preferences for debugging. `VrchatPipelineService` runs a 6-hour `startAuthRefreshLoop()` that proactively calls `shouldRefreshCookies()` → `autoRelogin()` before the session expires. Also provides REST helpers for offline notification backfill: `fetchPendingNotifications()`, `fetchPendingNotificationsV2()`, `fetchUserGroups()`, `fetchGroupAnnouncement(groupId)`. Trust rank extraction (`extractTrustRankFromTags`) reads the highest `system_trust_*` tag from VRChat's tags array. All REST `get()` calls set `useCaches = false` + `Cache-Control: no-cache` so Android's HttpURLConnection never serves a stale cached response — this fixes the instance player count (`/instances/$location` → `n_users`) showing minutes-old values in both the app and Discord RPC.
- **VrchatPipelineService**: Foreground service with OkHttp WebSocket to `wss://pipeline.vrchat.cloud`. Handles real-time events (friend online/offline/active/location, friend-update, unfriend, invites, group events) and manages friends cache. Writes VRChat presence to Firestore **only while an admin is watching** this user (gated by `AdminWatchState.isWatched`); when unwatched, in-app presence still updates locally via WebSocket events but no traffic hits Firestore. The `syncPresenceToFirestore()` function gates the VRChat API fetch call itself behind `AdminWatchState.isWatched` (not just the Firestore write), so no unnecessary HTTP calls are made when unwatched. Reactive event handlers (`user-update`, `friend-location` for self) also check `isWatched` before calling sync. When watched, presence polls every 10s. A slow 10s loop runs when unwatched with `forceLocalUpdate=true` to keep local presence state current without triggering Firestore writes or VRChat API calls. Also runs a 30s `lastSeenAt` heartbeat gated by `AdminBrowsingState.isBrowsing` (admin on Dashboard/Users tab) plus a slow 5-min always-on `lastSeenAt` heartbeat (see "Slow always-on lastSeenAt heartbeat" below). Connect/disconnect transitions fire connection-status notifications (gated by `notif_connection` pref).
- **Friends cache**: Persisted **locally** in SharedPreferences (`vrca_friends_cache` / `friends_json`) via `FriendsCacheStore`. No Firestore involvement — friends data is only used by the user's own app for unfriend notifications and is meaningless to admins. Old `savedFriendIds`/`savedFriendNames` fields in user docs are removed via `FieldValue.delete()` on every offline write so legacy data doesn't linger.
- **Unfriend notification logic**: Two sources cooperate via a `notifiedUnfriendIds` dedup set. (1) Real-time `friend-delete` from the WebSocket fires immediately for unfriends during an active session — but is **skipped if the userId isn't in the cache** (queued event for an offline unfriend that loadFriendsCache already removed). (2) Offline diff uses **two-fetch confirmation** to eliminate API pagination flaps: after the first API fetch on connect, removed IDs are captured into `candidateRemovals` but NOT notified. After the second fetch (60s later), only IDs still missing in BOTH fetches (`candidateRemovals ∩ stillMissing`) advance to verification. **Final verification gate**: both paths call `VrchatAuthManager.verifyStillFriend(userId)` which hits `GET /users/{id}` and reads the `isFriend` field. If true → suppress notification and re-add to cache (false positive); if false or 404 → fire notification; if null (network error / 429 / expired session) → fall back to firing the notification so we don't silently drop real unfriends. The dedup set ensures at most one notification per userId per session. The notification text is neutral — "Friend removed" / "$name is no longer on your friends list" — since the app can't know who initiated the removal.

- **Notification system**: Seven Android notification channels — `vrca_pipeline` (background service, MIN), `vrca_friends_activity` (online/offline/world/status/avatar/rank), `vrca_friend_requests` (incoming requests + new friends + messages), `vrca_friend_removals` (unfriends), `vrca_invites` (world + group invites), `vrca_groups` (announcements/queue/role/etc.), `vrca_connection` (pipeline disconnect + sign-in alerts + server alerts). Legacy `vrca_vrchat_events` is deleted on upgrade. The "VRChat connected / Monitoring VRChat events" notification is intentionally NOT fired — the persistent foreground service notification already conveys that state, and the duplicate notification was redundant. `fireConnectionNotification(true)` only cancels any leftover disconnect notification from a previous cycle. Notifications use `setGroup()` keys (`vrca_group_friends`, `vrca_group_social`, `vrca_group_invites`, `vrca_group_groups`) so multiple events stack in the shade with summary notifications; summary notifications use `GROUP_ALERT_CHILDREN` to prevent double notification sounds. Per-friend cooldowns (60s) on chatty events (location, status, avatar). Bio uses the grouped notification model instead of cooldowns — every bio change is captured as a separate event in the in-app alert group. **Bio change detection fires on edit, clear (text→empty), AND add (empty→text)** — the prior code required both old and new bio non-blank, so clearing a bio or adding one to an empty bio never fired. The live `handleFriendUpdate` path gates on `user.has("bio")` so partial location/status payloads (which omit the field) don't false-fire; empty sides render as `(empty)` in the diff. Notification titles reflect the action ("cleared their bio" / "added a bio" / "updated bio"). All 27 toggles live in `VrchatNotificationPrefs` keys + `UserPreferencesRepository` flows. The UI lives in `LegacyPagesAndSettingsPage.kt`'s `NotificationToggleSection` (public, called from `VrcaScreen.kt`). Each `ToggleRow` has an optional `description` parameter showing muted `bodySmall` text explaining what the toggle does. Organized into 5 collapsible sections with sub-section labels for visual grouping: Friend list (4 toggles), Friends activity (10 toggles, sub-grouped into Presence / Profile changes / Alerts), Invites (3 toggles: world invites / invite requests / group invites), Groups (6 toggles, sub-grouped into Updates / Management), App and connection (6 toggles, sub-grouped into App / VRChat). Each section is expandable/collapsible via `AnimatedVisibility` with fade+slide animation. The `SubSectionLabel` composable renders muted-color `labelMedium` text between toggle groups. The `KEY_NOTIF_INVITE_REQUEST` flow falls back to `KEY_NOTIF_INVITE` until the user explicitly toggles it, so existing users who had the combined invite preference enabled keep getting invite-request notifications.
  - **Offline notification backfill**: On every successful pipeline connect, `backfillOfflineNotifications()` runs a REST sweep across VRChat endpoints (`/auth/user/notifications`, `/auth/user/notifications/v2`, `/users/{id}/groups` + per-group `/groups/{id}/posts` and group events). The posts sweep is the sole announcement source — `fetchGroupAnnouncement()` (the single pinned announcement) was removed from both backfill and poll loop because the posts endpoint already returns the pinned announcement as one of its posts, and having both caused duplicate notifications (`ga_` vs `gp_` dedup IDs for the same content). **`fetchGroupPosts` parses VRChat's wrapped response** (`{"posts":[...],"total":N}`) as well as a bare array. **`fetchGroupCalendarEvents`** tries three endpoint paths in order (`/groups/{id}/events`, `/scheduledEvents`, `/calendar`) with fallback on 404, parsing multiple response shapes (`results`, `events`, `calendarEvents`, `scheduledEvents` array keys). `fireGroupCalendarEvent()` is the shared helper (backfill + poll loop) that fires each new event (dedup `${groupId}_event_$eventId`, seen-marker = `startsAt`) into the `event_$groupId` in-app alert group with URL `/home/group/$groupId/calendar/$eventId`. `seedBackfillBaseline()` seeds recent post IDs and calendar event IDs so the first run doesn't flood pre-existing items. A one-time migration (`posts_events_baseline_v2` DataStore flag) re-seeds posts/events into the existing seenMap for users who installed before `fetchGroupPosts` was fixed — `seedPostsAndEventsIntoExistingMap()` merges without overwriting. It seeds ALL posts but **only PAST calendar events** (startsAt already elapsed); upcoming events are intentionally NOT seeded so the backfill sweep fires them once and users see events they missed while closed (per-event dedup stops re-fires). **Cross-dedup, two flavors**: (1) announcements/posts use a CONTENT fingerprint (`announcementContentFingerprint(groupId, title, text)`) added to `seenNotifIds` when fired from any path, checked by the other paths — correct because the same announcement has identical content everywhere. (2) **EVENTS use an ID-keyed fingerprint** (`eventFingerprint(groupId, eventId)` → `evt_fp_<groupId>_<eventId>`) shared across the WebSocket live handler, `processV2Notification`, and `fireGroupCalendarEvent` (the REST sweep). The content fingerprint was WRONG for events: distinct events frequently share a generic title ("Event starting") and the same 80-char text prefix, so a content key collided and suppressed all but the first event — the cause of "only one event shows even when the group made several". The eventId-keyed fingerprint dedups the SAME event across the three paths (all extract the same `cal_xxx` id) without colliding sibling events. Fires missed notifications through the same `fireEventNotification` flow with dedup IDs. **Staleness filters**: only *transient* notifications older than 24h are skipped via `parseVrcTimestampMs()` on the `created_at` field — V1 invites/requestInvite/votetokick/message, and V2 invite/queue/join-request/instance. **Catch-up types are exempt from the age cutoff** and fire regardless of age: V1 `friendRequest` (pending state until accepted/declined), V2 announcement/post/event/calendar and role/transfer, and group announcements/posts (backfill + poll loop). This is safe because the per-item dedup (`seenNotifIds` for V1/V2, the `notif_group_announcement_seen` per-group timestamp map for group REST) already guarantees each one fires exactly once. A user offline for a week still receives the friend requests, role changes, and group announcements/events they missed, while already-seen items never resurface. The first-run baseline guard (below) prevents a flood on fresh install. Announcements from the same group are grouped together via `alertGroupKey = "announcement_$groupId"`. **Group name resolution**: a `groupNameCache` (groupId → name) is populated whenever `fetchUserGroups()` runs; `resolveGroupName(groupId, sender)` looks up the cache first, falls back to the sanitized sender username (rejecting `null`/blank/`someone`), then `"a group"` — so notifications never render "Announcement from null". `resolveGroupNameAsync()` is the suspend variant used by live + backfill group announcement/event paths: when the groupId isn't cached and the sender name is missing, it fetches the group's real name once via `VrchatAuthManager.fetchGroupName(groupId)` (`GET /groups/{id}` → `name`) and caches it — this fixes group **events** rendering "Event from a group" because event payloads frequently omit `senderUsername`. **Event/announcement timestamps**: `fireEventNotification` accepts `eventTimestampMs`; the V2 backfill/live handlers and group-announcement paths pass the parsed `created_at`/`createdAt` so the in-app alert shows when the announcement/event was actually posted on the website, not when the notification reached the phone. **Periodic group polling**: `startGroupAnnouncementPollLoop()` polls every 5 minutes independently of the WebSocket — fetches recent posts via `fetchGroupPosts()` and calendar events, AND re-sweeps pending `notification-v2` (events/announcements/role changes) via `processV2Notification()`. Its first poll runs ~45s after start (not a full 5 min) so catch-up surfaces quickly on reopen. **This is the retry path** for the one-shot connect backfill: that backfill makes 50+ REST calls rapidly and can miss items on a transient 429/timeout or a cold-start race, with no built-in retry — the poll loop re-attempts the V2 sweep every cycle so nothing made while the app was closed is lost. `processV2Notification(obj)` is the shared per-notification handler used by both the connect backfill and this retry sweep; `seenNotifIds` dedup makes re-processing safe (each fires at most once). The V2 sweep is skipped until `notif_backfill_initialized` is set (first-run baseline). This catches announcements that the WebSocket missed or delayed. Notification-v2 handler explicitly matches `post` types as announcements and `event`/`calendar` types as group events, with proper URLs (`/posts` for announcements, group page for events). Per-group announcement timestamps are persisted in DataStore (`notif_group_announcement_seen`) to avoid re-firing on reconnect. `seenNotifIds` set (capped at 500 entries, FIFO eviction) deduplicates between REST backfill and websocket replay — **persisted to SharedPreferences** (`vrca_seen_notifs/ids`) so IDs survive service restarts and prevent repeat notifications. **Ordering matters**: `fireEventNotification` checks the per-type toggle (`enabled`) BEFORE adding the dedup id to `seenNotifIds`. Adding it first would permanently poison the id if `enabled` read false transiently (e.g. DataStore not fully loaded during the cold-start connect/backfill race) — the notification would be dropped AND marked seen, so it could never fire on any later path. This was a cause of group announcements/events inconsistently never appearing on app open. REST calls are paced with 250-300ms delays; groups capped at 50 to stay under VRChat rate limits. Group announcement notifications include the group name in the title ("Announcement from GROUP_NAME"). Event notifications use calendar URLs (`/home/group/$groupId/calendar/$eventId`) when available. The `groupId` is extracted from `relatedGroupId`, `groupId`, `data.groupId`, `details.groupId`, or `senderUserId` (if `grp_` prefix), and the `eventId` from `eventId`, `data.eventId`, `details.eventId`, or `id` (if `cal_` prefix). As a final fallback BOTH fall back to `findIdWithPrefix(payload, "grp_"/"cal_")` — a recursive scanner that walks the entire notification-v2 JSON (including nested `data`/`details` blobs and embedded URLs) for the first value with that prefix. This is what makes event notifications reliably link to the calendar URL (`/home/group/grp_xxx/calendar/cal_xxx`) instead of falling back to `/home/notifications`. The notification-v2 `when` block has an **`else` catch-all** that logs the unmatched `type` string at INFO and still fires a generic group notification (gated by `KEY_NOTIF_GROUP_EVENT`) — so no notification-v2 is ever silently dropped just because VRChat used an unexpected type string. All handlers (WebSocket, poll loop, backfill) share `seenNotifIds` for dedup — WebSocket events now pass `dedupId = notifId` to prevent duplicates between real-time and polling. Each endpoint is wrapped in try/catch — failures are logged and skipped for this connect cycle. Bio/name change detection also runs on reconnect by diffing the old `friendsCache` against fresh API data before the cache is overwritten.
  - **First-run baseline guard**: A `notif_backfill_initialized` DataStore boolean blocks the first-ever backfill from firing anything. On the first pipeline connect, `seedBackfillBaseline()` walks user groups and silently records recent post IDs and calendar event IDs into `notif_group_announcement_seen`, then pre-seeds `seenNotifIds` with all V1 and V2 notification IDs (without firing), then sets both `notif_backfill_initialized` and `posts_events_baseline_v2`. This prevents both historical group announcements and pending friend requests/invites from firing on first install. From the second connect onward, the regular backfill flow runs and fires only events that arrived after setup.

  - **Notification click actions**: Invite, group, and friend offline notifications open relevant VRChat web pages (`vrchat.com/home/notifications`, `/home/group/$groupId`, `/home/user/$userId`) instead of just opening the app. Group v2 notifications fall back to `vrchat.com/home/notifications` when `groupId` is missing from the payload.
  - **In-app alerts (grouped)**: Notifications create persistent in-app alert groups displayed as dismissible cards at the top of the VRChat tab. The notification section starts **collapsed** by default and is expandable via a "Notifications (N)" header. Groups are keyed by `userId + notificationType` (e.g., `bio_usr_xxx`, `name_usr_xxx`) or by notification category (e.g., `announcement_$groupId`, `event_$groupId`). When the same event type fires multiple times for the same user/group, events are appended to the existing group — never overwritten. `InAppAlertState` singleton manages `MutableStateFlow<List<InAppAlertGroup>>`. Each `InAppAlertGroup` contains a list of `InAppAlertEvent` objects (max 50 per group), with `firstSeenMs`, `lastUpdatedMs` timestamps, and optional `eventTitle` per event. The UI shows "Title (N)" when a group has multiple events. Expanding a group shows all events in chronological order, each with its own before/after diff (LCS word-level algorithm highlights only actually changed words — red for removed, green for added, **purple for moved**; the tokenizer keeps whitespace/newline runs as their own tokens via `Regex("\\s+|\\S+")` so multi-line bios diff correctly and preserve layout instead of gluing newlines onto adjacent words) and optional per-event title and relative timestamp. **Move detection**: after the LCS pass, any token that appears as BOTH a removal (in before) and an addition (in after) — multiset-matched so counts balance — is recolored purple (`0xFFB388FF`) on both sides instead of red/green, so reordering text in a bio reads as "moved" rather than deleted+added. **Only meaningful tokens (trimmed length >= 4) are move-eligible** (`moveEligible()`): common short words/punctuation ("my", "I", "<3", "|", "a", "to") recur all over a bio, so matching them as "moved" painted them purple everywhere even when nothing actually moved — short tokens now fall back to normal red/green add/remove. Groups are capped at 20 (FIFO). Only 3 groups visible at once; "+N more" button reveals the rest. Dismissing removes the entire group, all its events, AND cancels the linked Android notification (using `groupId.hashCode()` as the stable notification ID). Backward-compatible: `addAlert()` wraps single events into single-event groups. Old flat alerts are auto-migrated to the group format on first load. `fireEventNotification` accepts `alertGroupKey` and `alertEventTitle` parameters — when provided, the event is added to the named group with its own title instead of creating a standalone alert. For grouped Android notifications, uses stable notification ID per `alertGroupKey.hashCode()` with `setOnlyAlertOnce(true)` so subsequent events update the notification silently (no re-alert). Bio change notifications no longer have a per-friend cooldown — the grouping model replaces cooldown-based spam prevention.
  - **Avatar change suppression**: Avatar change notifications are suppressed when the friend's location changed in the same `friend-update` payload OR when a `friend-location` event fired for the same friend within the last 15 seconds (`recentlyRelocated` map). This two-layer guard handles both same-payload location changes and the common race condition where `friend-location` updates the cache before `friend-update` arrives.
  - **Status change suppression during world hop**: `maybeFireStatusChange` is only called in `handleFriendUpdate` when the location did NOT change. VRChat sends status data redundantly with location changes, so firing both a "Friend moved" and "Friend changed presence" notification for the same event is noise.
  - **Warmup suppression**: For 30 seconds after pipeline connect (`WARMUP_MS`), all friend activity notifications (online, active, location, and handleFriendUpdate changes) are suppressed. This prevents the initial burst of WebSocket events from firing stale notifications for friends' existing state. Cache updates still happen during warmup so subsequent real changes are correctly diffed. Does NOT suppress friend-add, friend-delete, notification/notification-v2, or show-alert events.
  - **Gift notifications**: `gift`, `giftCredits`, and `giftBundle` notification types are handled in `handleNotificationEvent` and fire via `KEY_NOTIF_GIFT_RECEIVED`.
  - **Invite response notifications**: `requestInviteResponse` (someone accepted your invite request) and `inviteResponse` (someone accepted your invite) are handled and fire through the invite channel.
  - **Unknown event logging**: Unhandled pipeline event types are logged at DEBUG level for discovery. Known non-notification events (`user-location`, `see-notification`, `hide-notification`, `clear-notification`, `response-notification`, `content-refresh`) have explicit no-op branches.
  - **Reconnection notification fix**: `scheduleReconnect()` now calls `startPipeline()` (which handles session recovery and proper notification updates) when the user isn't logged in, instead of silently falling through with stale "Reconnecting in Xs..." text. Also updates to "Connecting..." before calling `connectWebSocket()`. If `connectWebSocket()` finds no cookie/auth token, it falls back to `startPipeline()` instead of silently returning.
  - **Persistent notification resilience**: A 10s loop re-posts the foreground notification if it gets swiped away. The notification channel uses `setSound(null, null)` and the builder uses `setSound(null)` + `setVibrate(null)` to ensure silence. The notification also refreshes automatically when Discord RPC status changes.

  - **App update notifications**: `startAppUpdateCheckLoop()` runs on service creation (public build only), checks `checkFirestoreRelease()` immediately and every 6 hours. Fires via `fireAppUpdateNotification()` with `KEY_NOTIF_APP_UPDATE` (defaults to enabled). Uses stable notification ID `NOTIF_ID_APP_UPDATE` so repeated checks update in place. Shows version name and release notes in expandable notification.

- **VrchatPipelineState**: Shared in-memory singleton using `MutableStateFlow` for reactive cross-component state (connection status, presence data, VRChat status page). Compose UI observes via `collectAsState()`. `statusPageFlow` exposes `VrchatStatusPageData?` for the status banner.
- **DiscordRpcService**: Foreground service running a hidden WebView that loads `discord.com`. Discord's own JavaScript handles the gateway connection (intents, capabilities, X-Super-Properties, TLS, /science telemetry) — all traffic looks like a real Discord web session, making detection effectively impossible. After page load, a JS shim hooks `WebSocket.prototype.send` to capture the gateway WebSocket reference, then exposes `window.VRCA_setActivity(json)` / `window.VRCA_clearActivity()` which send OP 3 (Presence Update) directly on the captured gateway connection. The Flux dispatcher approach was abandoned after Discord fully obfuscated all internal module names. The native side pushes activity updates via `evaluateJavascript` whenever `VrchatPipelineState.presenceFlow` emits (1.5s debounce) or every 10s as keep-alive. World thumbnails are squash-proxied via `images.weserv.nl` (`fit=fill`); the default VRChat image (`DEFAULT_VRCHAT_IMAGE_URL`) skips squashing. Image URLs are resolved to `mp:external/...` format via Discord's `POST /api/v9/applications/{app_id}/external-assets` endpoint (called from within the WebView JS using the session token read from `localStorage.token` or captured from Discord's own fetch calls — the token never leaves the JS context and is never sent to native code). Resolved URLs are cached in `window._vrca_asset_cache`. The user token is never extracted or stored natively — `DiscordLoginWebView` just seeds the `CookieManager` session. Auto-starts when VRChat pipeline connects if `discord_rpc_enabled` and `discord_session_seeded` are both true.
  - **OP 3 interception**: The `WebSocket.prototype.send` hook intercepts all outgoing OP 3 messages from Discord's own code. When our activity is set (`window._vrca_activity`), it's injected into the `activities[]` array of every Discord-originated OP 3. This ensures our RPC persists through Discord's own status changes, idle detection, and gateway reconnects — Discord can't overwrite our activity because it's included in every outgoing presence update. The hook also captures the user's current status (`online`/`dnd`/`invisible`) from each OP 3 so our direct sends use the correct status rather than hardcoding `'online'`.
  - **Anti-idle**: On mobile, Discord auto-sends OP 3 with `status: 'idle'` when the user backgrounds the app. The hook tracks the user's "intended" status (last non-idle status they set). When Discord tries to send `status: 'idle'` but the intended status is `'online'`, the hook overrides it back to `'online'` with `since: 0`. This keeps the user's Discord status online while VRC-A's foreground service is running. DND and invisible are respected (never overridden).
  - **Safety system (7 features):**
    1. **Risk gating UI**: First-time enable shows a consent dialog with checkbox acknowledgment + 4-second delay before the Continue button activates. Consent persisted in `discord_risk_accepted` DataStore key — only shown once. Bullet list explicitly warns that disconnecting may cause Discord to invalidate sessions on other devices, logging the user out everywhere.
    2. **Session state monitoring**: A 30s background loop checks `window._vrca_gatewayWs.readyState === 1` via `evaluateJavascript`. If the gateway WebSocket is dead, triggers shim re-injection. WebViewClient detects login-page redirects (both `onPageFinished` and `shouldOverrideUrlLoading`) for session expiry.
    3. **Failure detection + response**: Non-silent — failures update `DiscordRpcState.status` (shared `MutableStateFlow`) and the notification. Session expiry shows a red "Sign in again" button in the UI. Module finder failure shows "needs update" status. UI status messages are user-friendly ("Setting up Discord connection...", "Reconnecting to Discord...", "Discord connection setup failed") rather than technical injection terminology.
    4. **Auto recovery**: On session expiry, up to 3 auto-recovery attempts with linear backoff (2s, 4s, 6s) reload the WebView page. On dispatcher loss, shim re-injection with exponential backoff (3s, 6s, 9s, 12s, 15s). On consecutive push failures (5), shim re-injection. All counters reset on successful reconnection.
    5. **Per-user failure isolation**: All state is service-scoped — failures only pause the Discord RPC service, never affect VRChat pipeline, Firestore sync, or any other system.
    6. **User feedback/transparency**: `DiscordRpcState` singleton exposes `statusFlow` (enum: IDLE/CONNECTING/CONNECTED/RECONNECTING/SESSION_EXPIRED/FAILED) and `failureMessageFlow`. UI shows a colored status dot + label (green=Connected, yellow=Connecting/Reconnecting, red=Expired/Failed) with detail message.
    7. **Safety guards**: Max 5 shim retries with backoff, max 3 session recovery attempts, max 5 consecutive push failures before re-inject, 1.5s minimum interval between JS evaluations (double-guarded: both delay and timestamp check), all counters capped.
  - **RPC counter persistence**: `onlineStartEpochMs` (the Discord activity `timestamps.start`, always milliseconds) is persisted to SharedPreferences (`rpcPrefs / online_start_epoch`). **The grace-window restore is keyed on a `last_online_seen` heartbeat** (refreshed in `buildActivityJson()` on every confirmed-online tick), NOT on `offline_at`: when the user returns online and `onlineStartEpochMs` is 0, the saved start epoch is restored only if `now - last_online_seen < 10 min`. Because `last_online_seen` freezes the moment the app stops tracking (process death, swipe), a long untracked gap correctly resets the counter to a fresh start instead of bridging into a bogus multi-hour timer. **Critically, `onStartCommand` sets `onlineStartEpochMs = 0L` (it does NOT preload the persisted epoch)** so `buildActivityJson()`'s grace check always runs — preloading the stale epoch directly was the bug that shipped a day-old start to Discord as a "25 hours online" timer after a normal cold start (the grace block only runs when the in-memory value is 0). After 10 minutes untracked, a fresh counter starts.
- **DiscordRpcState**: Shared in-memory singleton using `MutableStateFlow` for Discord RPC status reporting. Compose UI in the settings page observes `statusFlow` and `failureMessageFlow` via `collectAsState()` to show real-time connection status.
- **DiscordLoginWebView**: WebView-based Discord login flow. User logs into discord.com; login completion uses a 3-layer verification: (1) URL must contain `discord.com/channels` OR `discord.com/app` (Discord may redirect to either after login), (2) 2-second dwell timer ensures the URL is stable (cancelled if page navigates away), (3) JS authentication probe checks `#app-mount` has rendered children AND no login form (`input[type="password"]`, `input[type="email"]`) is visible — uses stable DOM structure rather than webpack chunk variable names which Discord may rename. The probe retries up to 4 times at 1.5s intervals when it returns false, since Discord's SPA can take a few seconds to hydrate after the auto-redirect from `/login` for users with valid cached cookies. All retry runnables are tracked and cancelled in `onPageStarted` so a navigation away cannot trigger a stale `onLoginComplete`. Only after all 3 layers pass does `onLoginComplete` fire and `discord_session_seeded` is set.
- **IpField**: Multi-slot IP field component with 3 named slots (Home/Hotspot/Other). Uses local state tracking (not async DataStore) for immediate slot switching without cross-contamination. Supports per-slot editing and auto-migration from legacy single IP key. The Apply button and the slot-1 migration LaunchedEffect call `repo.saveIpSlotAddress(slot, address)` rather than `saveIpSlot(slot, name, address)` — only the auto-save debounce in the expanded slot editor is allowed to write the slot name. This prevents the placeholder defaults from `collectAsState(initial = "Home"|"Hotspot"|"Other")` from overwriting the user's saved name when DataStore hasn't yet emitted its real value.

### Firestore Schema (users/{deviceHash})
Key fields written by the app:
- `isOnlineInApp` (bool): Set to `true` by the app-open write, `false` by `VrchatPipelineService.onTaskRemoved` and `VrcaViewModel.onCleared` (GlobalScope fallback). On swipe-away, `onTaskRemoved` stops Discord RPC, then on a background thread **awaits the offline Firestore write (5s timeout) and immediately hard-kills the process** (`Process.killProcess` + `exitProcess`) — so nothing lingers in the background after the app is swiped (users were confused seeing it still alive). The await ensures the going-offline write has a chance to reach Firestore before the kill; if it times out, the admin-side staleness sweep still flips the user offline within ~75s. (Previously it waited a fixed 10s before killing, leaving the app running in the background that whole time.)
- `lastSeenAt` (timestamp): Refreshed on app-open, app-close, content edits, and live-mode writes (when watched)
- `afkEnabled`, `cycleEnabled`, `spotifyEnabled`, `timeEnabled`: Feature toggles (admin-editable)
- `warned`, `banned`, `warnReason`, `banReason`: Moderation flags (read by public app via snapshot listener)
- `targetedUpdateUrl` / `targetedUpdateNotes` (strings): Admin-pushed targeted APK update for specific user. **Real-time detection**: The moderation snapshot listener on `users/{deviceHash}` reads these fields on every change and updates `VrcaViewModel.targetedUpdateUrl/Notes`. `VrcaApp` observes these via `LaunchedEffect(liveTargetedUrl)` and immediately shows the update dialog when the admin pushes a targeted update — no need to wait for app restart or 6-hour poll. The download uses Android's `DownloadManager` for in-app APK download, then triggers the system package installer.
- `watcherActiveAt` (timestamp): **Admin-only write.** Refreshed every ~30s while an admin has this user's detail page open. User app reads it from snapshots and feeds into `AdminWatchState.updateFromTimestampMs` — if within 60s, live-mode loops start.
- `killSignal` (timestamp): **Admin-only write.** Written by admin kill switch button. User app reads it from moderation snapshot listener — if fresh (within 60s), kills the app process.
- VRChat presence fields (`vrchatUserId`, `vrchatDisplayName`, `vrchatState`, `vrchatLocation`, etc.): Only written while watched.
- NowPlaying / preview fields (`nowPlayingTitle`, `nowPlayingArtist`, `combinedPreviewText`, `activePackage`): **Volatile** — these change constantly during music playback. They are written to Firestore **only when an admin is present**, via two gated loops (never on the raw NowPlaying state emission, which previously caused a write storm even with no admin present): (1) the watcher-gated live-sync loop writes them every 10s while watched; (2) the browse-gated volatile loop (`startBrowseVolatileSyncWatcher`) writes them every 30s while an admin is on the dashboard/users list but not actively watching. With no admin present, NowPlaying changes update only local UI state — zero Firestore traffic. The `buildUserSnapshot` self-sync still carries the current preview values, but self-sync only fires on genuine content edits/toggles now, not on NowPlaying ticks.
- `lastReportedTime`, `cycleTrimWarning`, `lastTimeUpdateAt`: Only written while watched (live-mode loop).

**Friends are no longer in Firestore** — `savedFriendIds`/`savedFriendNames` are deleted via `FieldValue.delete()` on offline write. They live in local SharedPreferences only.

### Firestore Sync Architecture
The sync model is intentionally minimal — Firestore costs money and we only push to it when we have to. Three classes of writes:

1. **App-open write (one)**: After `initialDataLoaded` flips, `applyRemoteContentBeforeSync()` reads the Firestore doc to pick up any admin edits made while the user was offline (messages, presets, intervals — not toggles, which always start OFF), then `performSelfSync` runs once with the merged state. This is the only write tied to startup.
2. **App-close write (one)**: `VrchatPipelineService.onTaskRemoved` writes `isOnlineInApp=false, lastSeenAt` plus current VRChat presence fields (`vrchatState`, `vrchatLocation`, `vrchatWorldName`, `vrchatDisplayName`) if available. `VrcaViewModel.onCleared` writes `isOnlineInApp=false, lastSeenAt` via `GlobalScope` as a fallback for cases where the foreground service isn't running.
3. **Event-driven content writes (debounced 500ms)**: Whenever the user changes a toggle, types in a message, edits a preset, etc., a debounced trigger writes the current content snapshot. No safety net periodic loop — if a write fails, the next user edit picks it up.

**Browse-gated heartbeat**: When an admin is on the Dashboard or Users tab in the admin panel, the admin app writes `config/adminPresence.browsingAt = serverTimestamp()` every 30s. Public user apps subscribe to that single doc via a snapshot listener inside `VrchatPipelineService`. If `browsingAt` is fresh (within 75s — `AdminBrowsingState.FRESHNESS_WINDOW_MS`), `AdminBrowsingState.isBrowsing` flips true and the service runs a 30s `lastSeenAt` heartbeat on the user's own doc. When admin closes both tabs, the doc goes stale and the 30s heartbeat stops. Force-killed users can't heartbeat, so their `lastSeenAt` immediately starts going stale, which the admin's 75s staleness filter detects (see Admin online detection below).

**Slow always-on lastSeenAt heartbeat**: Independently of admin presence, the service writes `lastSeenAt` every 5 minutes (`LASTSEEN_HEARTBEAT_MS`) while the app is alive. This is the ONE intentionally ungated periodic write — it exists so admins can see accurate "last on the app" times even when the admin's own app was closed the whole time (without it, a user who keeps the app open with no edits would show a `lastSeenAt` frozen at app-open time). One field + server timestamp every 5 min ≈ 288 cheap writes/user/day. The faster 30s browse-gated heartbeat layers on top of this only while an admin is actively browsing, for sub-75s online detection.

**Live-mode (watcher-gated)**: When an admin opens a specific user's detail page in the admin panel, the admin app refreshes `watcherActiveAt` every ~30s on that user's doc. The user app's snapshot listener feeds the timestamp into `AdminWatchState`; if fresh (within 60s), `isWatched` flips to true and two side-effects start:
- `VrcaViewModel.startLiveSyncWatcher` writes `buildLivePayload` (nowPlaying, preview, `lastReportedTime`, `lastSeenAt`) every 10s (`LIVE_SYNC_INTERVAL_MS`)
- `VrchatPipelineService.startPresenceRefreshLoop` writes VRChat presence every 10s

`VrcaViewModel.startBrowseVolatileSyncWatcher` covers the browse-only case: when `AdminBrowsingState.isBrowsing` is true but `AdminWatchState.isWatched` is false, it writes `buildLivePayload` every 30s (`BROWSE_VOLATILE_SYNC_INTERVAL_MS`) so a browsing admin sees current preview/nowPlaying without the cost of the 10s watched loop. It skips entirely when watched (the 10s loop covers it) and when no admin is browsing (zero writes).

Both stop instantly when `isWatched` flips back to false (`collectLatest` cancels the inner loop). When nobody is watching, neither loop touches Firestore.

**Force-kill detection**: If the user's app is force-killed, neither `onTaskRemoved` nor `onCleared` fires, so `isOnlineInApp` stays `true` in Firestore. The browse-gated 30s heartbeat (above) keeps `lastSeenAt` fresh while the user app is alive AND an admin is browsing; if the user app is dead, the heartbeat doesn't fire and `lastSeenAt` goes stale within ~75s. After a 90s grace period (to let user heartbeats start), the admin's browsing heartbeat loop sweeps for stale users (`isOnlineInApp == true` but `lastSeenAt` older than 75s) and force-writes `isOnlineInApp = false` on their docs. This ensures force-killed users get cleaned up automatically.

**Admin kill switch**: Admin can force-quit a user's app via the "Kill App" button in UsersTab. Writes `killSignal = serverTimestamp()` to the user's doc. The user's `VrcaViewModel` moderation snapshot listener reads `killSignal` — if fresh (within 60s), calls `Process.killProcess(myPid())`. Handled at most once per session via `killSignalHandled` flag.

**Admin watcher heartbeat**: When an admin selects a user in the admin panel's detail view, a `LaunchedEffect` writes `watcherActiveAt = serverTimestamp()` to that user's doc every 30 seconds. When the admin navigates away or selects a different user, the coroutine is cancelled automatically. The user app reads `watcherActiveAt` from its snapshot listener and feeds it into `AdminWatchState.updateFromTimestampMs()` — if within 60s, live-mode starts.

**Echo suppression** (per-field `lastSyncedValues` map): Every field (toggle or content) compares its incoming snapshot value against `lastSyncedValues` — what we last knew was on the Firestore doc. If `remote == lastSyncedValues`, the snapshot is an echo (from self-sync, watcher heartbeat, or live-mode write) and we skip. If `remote != lastSyncedValues`, an admin actually changed it and we apply. Comparing against current local state would break this: during admin watch, the heartbeat fires snapshots with the OLD field values (Firestore hasn't received the user's pending local toggle yet), so a `remote != local` test would revert whatever the user just toggled. Content fields fall back to current local state when no baseline exists yet. Both branches update `lastSyncedValues` immediately on every snapshot (whether applied or skipped), so subsequent self-sync echoes are correctly suppressed. The map is also bulk-updated after each successful `performSelfSync` write via `captureStateForSync()`. The first snapshot seeds the baseline via `seedLastSyncedFromSnapshot`.

**Admin polling (admin-side only)**: Dashboard stats poll every 30s via `get(Source.SERVER)`. User directory polls every 30s. Selected user detail polls every 5s (online users) or 10s (offline users), based on `isUserOnline()` check. All reads use `Source.SERVER` to bypass Firestore cache. The `watcherActiveAt` heartbeat writes every 30s (time-based) while a user is selected. No periodic writes from the user app — only the admin reads.

**Initial-data gate** (`initialDataLoaded`): `performSelfSync` returns early until a loader coroutine has read every user-content DataStore field into ViewModel state. Prevents cold-start sync from writing empty defaults.

**First-snapshot skip** (`initialSnapshotProcessed`): The very first Firestore snapshot after listener attach is dropped — DataStore is the source of truth on cold start.

**Offline editing**: User-content edits land in DataStore immediately and survive process death. On reconnect, the next debounced write or app-close write pushes them to Firestore. Admin-content edits are preserved across user restarts via `applyRemoteContentBeforeSync()` (read-before-write on app-open). If both the user and admin edited the same field while the user was offline, the Firestore version (admin's) wins because it's applied before the app-open write.

**Admin online detection**: `isUserOnline(u, nowMs)` in `UsersTab.kt` checks `isOnlineInApp == true && lastSeenAt within 75s` — used by the Users-tab row badge for strict force-kill detection. The Dashboard counter uses a simpler `isOnlineInApp` check directly (no staleness requirement) so it shows online users immediately when the admin opens the app, without waiting for user heartbeats to arrive. The admin-side staleness sweep (above) handles cleanup of genuinely dead users. The shared user-list state is stored as `mutableStateOf<List<UserRow>>` (whole-value assignment) rather than `SnapshotStateList` so downstream consumers reliably recompose on update.

### Remote Config (Admin Edits)
The public app's moderation snapshot listener on `users/{deviceHash}` also picks up admin-editable fields (feature toggles, messages, intervals, presets) and applies them in real-time. Each incoming snapshot is filtered by:
1. `metadata.hasPendingWrites()` — skip if it reflects our own pending local write
2. `initialSnapshotProcessed` — drop the very first snapshot (DataStore wins cold start)
3. Fingerprint match against `lastSelfSyncFingerprint` — skip our own confirmed echo

After those filters, the snapshot's content fields (afkMessage, cycleLines, presets) are written to DataStore so existing flow collectors propagate them into ViewModel state. Toggles are set directly on the ViewModel (they don't persist — see below).

### Toggle Persistence
Feature toggles (`afkEnabled`, `spotifyEnabled`, `cycleEnabled`, `timeEnabled`) **do not** persist across full app restarts — they always start OFF when the user opens the app from scratch. However, they DO survive Android process death (when the system kills the app in the background to reclaim memory) via `SavedStateHandle`. This prevents the "toggles revert when tabbing out" issue while still keeping the intentional start-OFF behavior on fresh launch. The DataStore keys, collectors, and `saveX` calls were intentionally removed from the toggle setters. Content (messages, intervals, presets) DOES persist via DataStore as normal. Admin can still flip toggles in real-time via the Firestore snapshot listener, which writes directly to ViewModel state (and SavedStateHandle) without touching DataStore. **Toggle-on auto-starts sender jobs**: Enabling a toggle automatically starts the corresponding sender loop (`startAfkSender()`, `startCycle()`, `startNowPlayingSender()`) — the user does NOT need to press Start separately after toggling. The `killStopAndClear()` function disables all four toggles and cancels the keepalive job before clearing the chatbox, so a single Kill press fully stops everything.
