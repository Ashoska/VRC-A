# VRC-A — Claude Code Instructions

## Project Overview
Android app called VRC-A (VRChat Assistant).
Built with Kotlin, Jetpack Compose, Firebase Firestore, and GitHub Actions CI.
There are two build variants: a public user-facing APK and a separate admin APK.
Display name embedded in UI strings: "Ashoska Mitsu Sisko".

## Repository Structure
- Main app source: `app/src/main/kotlin/com/vrca/`
- Kotlin package: `com.vrca` (applicationId stays `com.scrapw.chatbox` for install continuity)
- Subpackages: `admin/`, `app/`, `data/`, `discord/`, `keepalive/`, `nowplaying/`, `osc/`, `overlay/`, `sync/`, `ui/` (with `common/`, `conversation/`, `screen/`, `settings/`, `theme/`, `viewmodel/`), `update/`, `vrchat/`
- Admin vs public build separation: `BuildConfig.IS_ADMIN_BUILD`
- **Device hash per build variant**: `MainActivity.ensureDeviceHash()` derives the `users/{deviceHash}` doc id from `computeBaseDeviceHash()` (`sha256("v2:$androidId:$signingCert")`, with a stored random fallback for blank ANDROID_ID). The **admin build** namespaces this as `sha256("admin:" + base)` so it resolves to a DISTINCT doc from the public build on the same phone — without this, both installs share one ANDROID_ID + signing key → one doc, so their presets/content overwrote each other AND the admin user-list self-filter (`it.id != myDeviceHash` in `AdminScreen`) hid the public install. With the distinct admin hash: (1) the two installs no longer sync (the admin build's moderation listener watches its own empty doc, not the public one); (2) the public install now appears in the admin Users tab / Dashboard so directed releases can be tested against it. The admin build never writes a user doc — `performSelfSync()`, `applyRemoteContentBeforeSync()`, and `applyRemoteConfig()` all early-return on `IS_ADMIN_BUILD`, so no orphan doc is created under the admin hash AND the admin's chatbox presets/messages live purely in local DataStore. (This gating was missing before: the admin build was reading its own `users/{adminHash}` doc back into DataStore on every launch via `applyRemoteContentBeforeSync`/`applyRemoteConfig`, which overwrote fresh local presets with a stale earlier snapshot — the "admin reverts to a past synced state on reopen" bug. With the three gates in place, DataStore is the sole source of truth for the admin build's content.) The admin hash is force-normalised on launch (overwrites any previously-cached public-equal hash). Public-only users are unaffected — their seed/hash is unchanged.
- CI workflow: `.github/workflows/android.yml`
- Firebase config: `google-services.json`
- Firestore rules: `firestore.rules` (uses `isOwner()` via `config/app.ownerUid`, NOT `sign_in_provider`). **Hardening (Phase 7)**: `selfMutableKeys()` includes `lastActiveAt` (hourly heartbeat write); `ownerOnlyUserKeys()` explicitly includes `killSignal` (defensive — self-update already can't touch it since it isn't in `selfMutableKeys()`). `announcements` read is `isOwner() || (signedIn() && resource.data.active == true)` — drafts (active==false) are owner-only and unauthenticated scraping is blocked; both client listeners already filter `active==true` so list queries pass per-doc. `users/{deviceHash}/live/{doc}` subcollection is readable by the owner or the device-doc owner, writable by the device-doc owner or admin. `bannedIdentifiers` `get` stays `signedIn()` (the client ban check reads its own vrchatId, unverifiable in rules) but `list` is owner-only so the collection can't be enumerated.

## Architecture & Stack
- Language: Kotlin
- UI: Jetpack Compose
- Backend: Firebase Firestore
- Auth/device management: Firestore `bannedDevices` collection
- NowPlaying: pause detection logic (check for edge cases when modifying)
- Admin UI: Users tab, Releases tab, tab bar navigation
- APK distribution: GitHub Releases. `githubUploadAsset()` and `githubCreateRelease()` in `ReleasesTab.kt` use OkHttp. **`githubUploadAsset` uploads to the canonical `upload_url` template returned by `githubCreateRelease`** (e.g. `https://uploads.github.com/repos/OWNER/REPO/releases/ID/assets{?name,label}`) — it strips the `{?name,label}` suffix and appends `?name=<encoded>`. It does NOT rebuild the URL from `BuildConfig.GITHUB_OWNER`/`GITHUB_REPO`. This matters because if those are a renamed/old repo, `uploads.github.com` responds with a redirect *early* (before the streamed APK body finishes), which closes the okio sink mid-`writeTo()` and surfaces as `IllegalStateException: closed` on every retry. `githubCreateRelease` already follows the moved-repo redirect during create, so its response `upload_url` is canonical — using it sends the binary straight to the right host with no redirect. The owner/repo for create-release come from `RELEASE_OWNER`/`RELEASE_REPO` GitHub Actions secrets (CI overwrites `keystore.properties` from them at build time; the committed `keystore.properties` is only used for local builds). `githubUploadAsset` still uses `followRedirects(false)` + a manual `Location` redirect loop (fresh `buildBody()` per hop, repeatable file stream) as a fallback. Both functions use `retryOnConnectionFailure(true)` and retry up to 5 times with exponential backoff. Error messages include the exception class name and cause chain for diagnostics.

### VRChat Integration
- **VrchatAuthManager**: Singleton handling VRChat API auth (Basic auth + 2FA), cookie storage via EncryptedSharedPreferences, presence fetching, and friends list retrieval. Also saves credentials to EncryptedSharedPreferences for auto-relogin when sessions expire. Credentials are saved BEFORE the login HTTP request so they survive app kills during response processing. **Basic-auth credentials are URI-encoded (`encodeUriComponent`, an `encodeURIComponent`-equivalent) BEFORE base64** — VRChat's backend URL-decodes them, so a password containing `@ + # : & %` etc. fails with 401 if sent raw. This was a real "permanent 2FA bypass broke" cause: the raw-bytes login 401'd → `clearCredentials()` wiped the saved creds → auto-relogin died → the next launch forced a full manual login *including* the 2FA prompt. **The 401 handler now only calls `clearCredentials()` when the error message actually indicates bad credentials** (`invalid`/`incorrect`/`credential`/`password`/`username`); a transient/session 401 (e.g. IP-invalidated session — VRChat binds the `auth` cookie to the client IP, which changes constantly on mobile) keeps the saved creds so auto-relogin can recover instead of forcing manual 2FA. On re-login after auth-cookie expiry, the Basic-auth request sends ONLY the persisted `twoFactorAuth` cookie via `getTwoFaOnlyCookieHeader()` — never the expired `auth=` cookie, which can cause VRChat to reject the request as a session conflict. VRChat recognizes the trusted device and skips the 2FA prompt. **The `twoFactorAuth` cookie is ALWAYS sent regardless of age — there is NO client-side expiry drop.** The web client keeps a remembered device trusted effectively indefinitely (rolling it forward on use), so any hard client-side cutoff (the old `TWO_FA_COOKIE_MAX_AGE_MS` 30-day guard, now removed) only ever HURTS — it forced an avoidable 2FA prompt that VRChat itself would not have asked for. Sending a stale cookie is harmless: worst case VRChat ignores it and returns `requiresTwoFactorAuth`, which is exactly what dropping it would have produced — so the SERVER is the sole authority on trusted-device validity. `KEY_2FA_COOKIE_STORED_AT` is kept for diagnostics only. On successful Basic-auth login, the auth cookie + user info are written via a direct prefs edit; **if VRChat re-issued a `twoFactorAuth` cookie in that login's `Set-Cookie`, it is captured and its 30-day clock RESET so the trusted window keeps extending**; if it did NOT (the common bypass-login case), the existing 2FA cookie and its original stored-at timestamp are preserved untouched (without this preservation, the 2FA cookie would get wiped on every successful relogin and the SECOND auth-cookie expiry would always force manual 2FA). **Trusted-device cookie roll-forward (`captureRolledCookies`)**: VRChat's web client never re-prompts because the server rolls the `twoFactorAuth` cookie forward on EVERY use — the browser's cookie never reaches its ~30-day Max-Age. The app previously captured that rotation ONLY on the explicit login/verify paths and discarded the `Set-Cookie` on every other authenticated call (`fetchPresence`, `validateSession`, `refreshProfilePic`, …), so the app's stored trusted-device cookie aged out and ~30 days after the last login VRChat demanded a fresh 2FA code even though the website would not. **`captureRolledCookies(context, rawCookies)` now persists any refreshed `auth`/`twoFactorAuth` cookie (resetting its stored-at clock) after every authenticated success** — wired into `fetchPresence` (runs every 10s while watched / on the slow loop, so the cookie stays continuously fresh), `validateSession`, and `refreshProfilePic`. It is strictly additive (only overwrites when a non-blank refreshed cookie is present), so it keeps the app's trusted-device window as fresh as the browser's and stops the spurious "keeps asking for 2FA" re-prompts. (A user whose stored cookie already expired under the old behaviour will be asked once more, then stays trusted.) **`captureRolledCookies` is now wired into EVERY authenticated REST call, not just three** — `fetchFriends`, `fetchPendingNotifications`/`V2`, `fetchUserGroups`, `fetchGroupName`/`Announcement`/`Posts`/`CalendarEvents`, `verifyStillFriend`, the `fetchPresence` `/users/{id}` + `/instances/{location}` sub-calls, and the post-2FA `/auth/user` fetch all roll the cookie forward. This matters for a NORMAL (unwatched) user: `fetchPresence` only hits the VRChat API while an admin is watching (the unwatched slow loop is local-only), so previously the sole roll-forward point for most users was the 6-hour `validateSession`; now the every-connect REST sweep keeps the `twoFactorAuth` cookie continuously rolled forward like the browser's cookie jar. **CRITICAL double-prefix fix**: `extractCookieValue()` already returns the full `name=value` pair (e.g. `twoFactorAuth=VALUE`), but the old `verify2FA()` re-wrapped it as `"twoFactorAuth=$it"` → stored the MALFORMED `twoFactorAuth=twoFactorAuth=VALUE`. VRChat rejected that as an invalid trusted-device cookie, so EVERY VRChat global logout forced a fresh manual 2FA prompt even though the website (whose cookie jar stored the correct value) would not. This was the real "trusted device never sticks" cause. `verify2FA()` now stores `extractCookieValue`'s return verbatim. A read-side self-heal (`normalizeCookie`/`readCookie`, used by `getCookieHeader`/`getTwoFaOnlyCookieHeader`) collapses any historically-stored double prefix in place (persisting the corrected value, so the WebSocket and all paths get the clean cookie) — existing users are migrated automatically on first read. `getPrefs()` has a recovery fallback: if EncryptedSharedPreferences init fails (MasterKey corruption), it deletes the corrupted prefs file and retries. `diagnoseAuthState()` logs the presence/age of all auth-related preferences for debugging. `VrchatPipelineService` runs a 6-hour `startAuthRefreshLoop()` that — because the 12-day age threshold rarely fires before the cookie actually dies — also **actively validates the session each cycle (`validateSession()` → `GET /auth`) and `autoRelogin()`s when it's dead regardless of cookie age**. `scheduleReconnect()` likewise re-validates and re-logins after repeated WebSocket failures (`reconnectAttempt >= 2`) instead of spinning on a present-but-dead cookie — `isLoggedIn()` only checks the cookie is PRESENT, not valid. Also provides REST helpers for offline notification backfill: `fetchPendingNotifications()`, `fetchPendingNotificationsV2()`, `fetchUserGroups()`, `fetchGroupAnnouncement(groupId)`. Trust rank extraction (`extractTrustRankFromTags`) reads the highest `system_trust_*` tag from VRChat's tags array. All REST `get()` calls set `useCaches = false` + `Cache-Control: no-cache` so Android's HttpURLConnection never serves a stale cached response — this fixes the instance player count (`/instances/$location`) showing minutes-old values in both the app and Discord RPC. **Instance headcount source (`extractInstanceUserCount`)**: VRChat's `/instances/{loc}` object exposes THREE candidate counts that disagree by a few users. **`userCount` is the field that matches the in-game client's instance panel** (what the player and everyone in the instance actually see in-headset). `n_users` AND the per-platform breakdown (`platforms`: `standalonewindows` + `android` + `ios`, which sums to the **website / VRCX** number) AGREE with each other but run a few HIGH — they count users mid-join / in-transit / timing-out that the in-game client has already dropped. The helper **prefers `userCount`**, falling back to `n_users` then the platforms-sum (iterating ALL keys so new platforms are future-proof) only when `userCount` is absent. (History: this thrashed before it was settled empirically. Original code preferred `n_users`; the user compared against the *website* and found it "wrong", so it was switched to the platforms-sum; a later screenshot showed the platforms-sum over-counting the *in-game* client (21 vs 18) so it was switched to prefer `n_users` — but `n_users` ALSO over-counted in-game (47 vs 36). A temporary in-app debug overlay logging all three fields finally proved `userCount` == the in-game panel (36) while `n_users`/`platformsSum` both read 47. Ironically `userCount` had been sitting in the code as the never-reached final fallback the entire time.) Both `fetchInstanceCount` and `fetchPresence`'s `/instances/{location}` parse go through this helper. Queue size is deliberately NOT added (irrelevant for normal instances).
- **VrchatPipelineService**: Foreground service with OkHttp WebSocket to `wss://pipeline.vrchat.cloud`. Handles real-time events (friend online/offline/active/location, friend-update, unfriend, invites, group events) and manages friends cache. Writes VRChat presence to Firestore **only while an admin is watching** this user (gated by `AdminWatchState.isWatched`); when unwatched, in-app presence still updates locally via WebSocket events but no traffic hits Firestore. The `syncPresenceToFirestore()` function gates the Firestore WRITE behind `AdminWatchState.isWatched`. When watched, presence polls every 10s. A slow 10s loop runs when unwatched with `forceLocalUpdate=true` to keep local presence state current (it does NOT write Firestore when unwatched, but it DOES call `fetchPresence` — the in-app VRChat tab + Discord RPC read the resulting `VrchatPipelineState.presence`; an earlier note claiming "no VRChat API calls when unwatched" was wrong). **Instant instance player count (`fetchInstanceCount`)**: the in-app/RPC player count (`n_users`) used to lag *minutes* behind the VRChat website. Root cause: the count is the 3rd of `fetchPresence`'s sequential calls (`/auth/user` → `/users/{id}` → `/instances/{location}`), so it only refreshed when the WHOLE chain landed — minutes apart on mobile under cookie IP-invalidation / rate limits — whereas the website hits ONLY `/instances/{loc}` per refresh (1 call, instant). Fix: `VrchatAuthManager.fetchInstanceCount(location)` does that single lightweight call (live `platforms`-sum count via `extractInstanceUserCount` / `capacity`). It is fired (a) **immediately on every self `user-location` world-hop** in `applySelfLocationEvent` (the WS location event carries no count, so the count previously sat at 0/stale until the next full chain — now it's fresh the instant you change instances), and (b) as a **null-fallback inside `syncPresenceToFirestore`** when `fetchPresence` returns null (the heavy chain failed) — it patches just the count on the last-known location so the count tracks reality instead of freezing. (When the cookie is *fully* IP-invalidated even this single call fails; that's the session-recovery path, separate.) **Reactive self-presence from the WebSocket (`applySelfLocationEvent` / `applySelfUserUpdate`)**: the user's OWN `user-location` (world-hop) and `user-update` (status) events now patch `VrchatPipelineState.presence` DIRECTLY from the event payload — no REST call. This fixes "the Discord RPC keeps counting but doesn't match my VRChat state": self presence used to refresh only via the periodic `fetchPresence()` REST poll, which returns null whenever the auth cookie is IP-invalidated (constant on mobile/backgrounded), so `presence` froze while the RPC (whose online timer is independent) kept pushing a stale world. The `user-location` event was previously a no-op for self. Now patching it emits on `presenceFlow` → the RPC's `collectLatest` pushes the real world instantly even when REST is dead. When an admin is watching, `pushSelfPresenceToFirestoreIfWatched()` also writes the patched `vrchatLocation`/`vrchatWorld`/`vrchatState` straight to Firestore (no REST round-trip), so the admin directory's VRChat location updates instantly and resiliently — this fixes "the user's VRChat location not updating on the admin menu". The periodic watched 10s `syncPresenceToFirestore()` REST poll still runs as the authoritative full-field refresh (now more reliable thanks to the cookie roll-forward above). **No periodic `lastSeenAt` heartbeat lives here anymore** — liveness is a single hourly write owned by `VrcaViewModel.startHourlyHeartbeat()` (see "Hourly liveness model" below); the only periodic Firestore write this service makes is the 10s watched-user presence sync (which also refreshes `lastActiveAt`). Connect/disconnect transitions fire connection-status notifications (gated by `notif_connection` pref).
- **Friends cache**: Persisted **locally** in SharedPreferences (`vrca_friends_cache` / `friends_json`) via `FriendsCacheStore`. No Firestore involvement — friends data is only used by the user's own app for unfriend notifications and is meaningless to admins. Old `savedFriendIds`/`savedFriendNames` fields in user docs are removed via `FieldValue.delete()` on every offline write so legacy data doesn't linger.
- **Unfriend notification logic**: Two sources cooperate via a `notifiedUnfriendIds` dedup set. (1) Real-time `friend-delete` from the WebSocket fires immediately for unfriends during an active session — but is **skipped if the userId isn't in the cache** (queued event for an offline unfriend that loadFriendsCache already removed). (2) Offline diff uses **two-fetch confirmation** to eliminate API pagination flaps: after the first API fetch on connect, removed IDs are captured into `candidateRemovals` but NOT notified. After the second fetch (60s later), only IDs still missing in BOTH fetches (`candidateRemovals ∩ stillMissing`) advance to verification. **Final verification gate**: both paths call `VrchatAuthManager.verifyStillFriend(userId)` which hits `GET /users/{id}` and reads the `isFriend` field. If true → suppress notification and re-add to cache (false positive); if false or 404 → fire notification; if null (network error / 429 / expired session) → fall back to firing the notification so we don't silently drop real unfriends. The dedup set ensures at most one notification per userId per session. The notification text is neutral — "Friend removed" / "$name is no longer on your friends list" — since the app can't know who initiated the removal.

- **Notification system**: Seven Android notification channels — `vrca_pipeline` (background service, MIN), `vrca_friends_activity` (online/offline/world/status/avatar/rank), `vrca_friend_requests` (incoming requests + new friends + messages), `vrca_friend_removals` (unfriends), `vrca_invites` (world + group invites), `vrca_groups` (announcements/queue/role/etc.), `vrca_connection` (pipeline disconnect + sign-in alerts + server alerts). Legacy `vrca_vrchat_events` is deleted on upgrade. The "VRChat connected / Monitoring VRChat events" notification is intentionally NOT fired — the persistent foreground service notification already conveys that state, and the duplicate notification was redundant. `fireConnectionNotification(true)` only cancels any leftover disconnect notification from a previous cycle. Notifications use `setGroup()` keys (`vrca_group_friends`, `vrca_group_social`, `vrca_group_invites`, `vrca_group_groups`) so multiple events stack in the shade with summary notifications; summary notifications use `GROUP_ALERT_CHILDREN` to prevent double notification sounds. Per-friend cooldowns (60s) on chatty events (location, status, avatar). Bio uses the grouped notification model instead of cooldowns — every bio change is captured as a separate event in the in-app alert group. **Bio change detection fires on edit, clear (text→empty), AND add (empty→text)** — the prior code required both old and new bio non-blank, so clearing a bio or adding one to an empty bio never fired. The live `handleFriendUpdate` path gates on `user.has("bio")` so partial location/status payloads (which omit the field) don't false-fire; empty sides render as `(empty)` in the diff. Notification titles reflect the action ("cleared their bio" / "added a bio" / "updated bio"). All 27 toggles live in `VrchatNotificationPrefs` keys + `UserPreferencesRepository` flows. The UI lives in `LegacyPagesAndSettingsPage.kt`'s `NotificationToggleSection` (public, called from `VrcaScreen.kt`). Each `ToggleRow` has an optional `description` parameter showing muted `bodySmall` text explaining what the toggle does. Organized into 5 collapsible sections with sub-section labels for visual grouping: Friend list (4 toggles), Friends activity (10 toggles, sub-grouped into Presence / Profile changes / Alerts), Invites (3 toggles: world invites / invite requests / group invites), Groups (6 toggles, sub-grouped into Updates / Management), App and connection (6 toggles, sub-grouped into App / VRChat). Each section is expandable/collapsible via `AnimatedVisibility` with fade+slide animation. The `SubSectionLabel` composable renders muted-color `labelMedium` text between toggle groups. The `KEY_NOTIF_INVITE_REQUEST` flow falls back to `KEY_NOTIF_INVITE` until the user explicitly toggles it, so existing users who had the combined invite preference enabled keep getting invite-request notifications.
  - **Offline notification backfill**: On every successful pipeline connect, `backfillOfflineNotifications()` runs a REST sweep across VRChat endpoints (`/auth/user/notifications`, `/auth/user/notifications/v2`, `/users/{id}/groups` + per-group `/groups/{id}/posts` and group events). The posts sweep is the sole announcement source — `fetchGroupAnnouncement()` (the single pinned announcement) was removed from both backfill and poll loop because the posts endpoint already returns the pinned announcement as one of its posts, and having both caused duplicate notifications (`ga_` vs `gp_` dedup IDs for the same content). **`fetchGroupPosts` parses VRChat's wrapped response** (`{"posts":[...],"total":N}`) as well as a bare array. **`fetchGroupCalendarEvents`** hits the correct VRChat group-calendar endpoint **`GET /calendar/{groupId}?n=N`** first (returns `{"hasNext":bool,"results":[...],"totalCount":N}`), with the legacy `/groups/{id}/events` and `/groups/{id}/calendar` paths kept only as 404 fallbacks. The prior code used `/groups/{id}/events`/`/scheduledEvents`/`/calendar` which all 404'd — so the calendar sweep always returned null and events created while the app was closed never surfaced (the only event source was notification-v2, which VRChat drops from the pending feed once marked seen server-side). Parses `results`, `events`, `calendarEvents`, `scheduledEvents` array keys or a bare array. `fireGroupCalendarEvent()` is the shared helper (backfill + poll loop) that fires each new event (dedup `${groupId}_event_$eventId`, seen-marker = `startsAt`) into the `event_$groupId` in-app alert group with URL `/home/group/$groupId/calendar/$eventId`. `seedBackfillBaseline()` seeds recent post IDs and calendar event IDs so the first run doesn't flood pre-existing items. A one-time migration (`posts_events_baseline_v2` DataStore flag) re-seeds posts/events into the existing seenMap for users who installed before `fetchGroupPosts` was fixed — `seedPostsAndEventsIntoExistingMap()` merges without overwriting. A SECOND one-time migration (`calendar_baseline_v3` flag) runs `seedAllCalendarEventsBaseline()` which seeds **ALL** current calendar events (past AND upcoming) into the seenMap + event fingerprint set without firing — necessary because the old calendar endpoint always 404'd, so no events were ever seeded; without this baseline the first working `GET /calendar/{groupId}` sweep would fire every pre-existing upcoming event at once. After this baseline only events created later surface as new. It seeds ALL posts but **only PAST calendar events** (startsAt already elapsed); upcoming events are intentionally NOT seeded so the backfill sweep fires them once and users see events they missed while closed (per-event dedup stops re-fires). **Cross-dedup, two flavors**: (1) announcements/posts use a CONTENT fingerprint (`announcementContentFingerprint(groupId, title, text)`) added to `seenNotifIds` when fired from any path, checked by the other paths. **The fingerprint is BODY-based** (`ann_fp_<groupId>_<normalized-body.hashCode()>`, body = `text.ifBlank{title}` lowercased + whitespace-collapsed + first 120 chars). The title is intentionally EXCLUDED: the live notification-v2 path keys on the `message` field while the REST group-post path keys on the `text` field and they title the same post differently, so a title-inclusive key produced two different fingerprints for one announcement and the dedup missed. **The 5-min poll posts sweep now calls `isContentFingerprintSeen()` before firing** (it previously only checked its own per-post `notif_group_announcement_seen` timestamp map, never the fingerprint the live path set) — this was the cause of "an announcement fires once when the group posts it, then AGAIN a few minutes later" (the live WS path fired immediately; the poll re-fired because it didn't consult the live fingerprint). Now the poll records the seen timestamp and skips when the body fingerprint is already present. (2) **EVENTS use an ID-keyed fingerprint** (`eventFingerprint(groupId, eventId)` → `evt_fp_<groupId>_<eventId>`) shared across the WebSocket live handler, `processV2Notification`, and `fireGroupCalendarEvent` (the REST sweep). The content fingerprint was WRONG for events: distinct events frequently share a generic title ("Event starting") and the same 80-char text prefix, so a content key collided and suppressed all but the first event — the cause of "only one event shows even when the group made several". The eventId-keyed fingerprint dedups the SAME event across the three paths (all extract the same `cal_xxx` id) without colliding sibling events. Fires missed notifications through the same `fireEventNotification` flow with dedup IDs. **Staleness filters**: only *transient* notifications older than 24h are skipped via `parseVrcTimestampMs()` on the `created_at` field — V1 invites/requestInvite/votetokick/message, and V2 invite/queue/join-request/instance. **Catch-up types are exempt from the age cutoff** and fire regardless of age: V1 `friendRequest` (pending state until accepted/declined), V2 announcement/post/event/calendar and role/transfer, and group announcements/posts (backfill + poll loop). This is safe because the per-item dedup (`seenNotifIds` for V1/V2, the `notif_group_announcement_seen` per-group timestamp map for group REST) already guarantees each one fires exactly once. A user offline for a week still receives the friend requests, role changes, and group announcements/events they missed, while already-seen items never resurface. The first-run baseline guard (below) prevents a flood on fresh install. Announcements from the same group are grouped together via `alertGroupKey = "announcement_$groupId"`. **Group name resolution**: a `groupNameCache` (groupId → name) is populated whenever `fetchUserGroups()` runs; `resolveGroupName(groupId, sender)` looks up the cache first, falls back to the sanitized sender username (rejecting `null`/blank/`someone`), then `"a group"` — so notifications never render "Announcement from null". `resolveGroupNameAsync()` is the suspend variant used by live + backfill group announcement/event paths: when the groupId isn't cached and the sender name is missing, it fetches the group's real name once via `VrchatAuthManager.fetchGroupName(groupId)` (`GET /groups/{id}` → `name`) and caches it — this fixes group **events** rendering "Event from a group" because event payloads frequently omit `senderUsername`. **Event/announcement timestamps**: `fireEventNotification` accepts `eventTimestampMs`; the V2 backfill/live handlers and group-announcement paths pass the parsed `created_at`/`createdAt` so the in-app alert shows when the announcement/event was actually posted on the website, not when the notification reached the phone. **`fireGroupCalendarEvent` (the REST calendar sweep) uses the event's `createdAt` (posted time) for the display timestamp, NOT `startsAt`.** `startsAt` is the event's scheduled start, normally in the FUTURE — feeding it to `formatRelativeTime` (`VrchatPage.kt`) produced a negative `now - startsAt` delta that clamped to a permanent "just now" that never advanced. The change marker (re-fire detection) still tracks `startsAt` then `createdAt` so an edited start time re-fires, but the user-visible "posted Xm ago" now reflects `createdAt`. (The live/V2 event paths already used `created_at` and were correct.) **Periodic group polling**: `startGroupAnnouncementPollLoop()` polls every 5 minutes independently of the WebSocket — fetches recent posts via `fetchGroupPosts()` and calendar events, AND re-sweeps pending `notification-v2` (events/announcements/role changes) via `processV2Notification()`. Its first poll runs ~45s after start (not a full 5 min) so catch-up surfaces quickly on reopen. **This is the retry path** for the one-shot connect backfill: that backfill makes 50+ REST calls rapidly and can miss items on a transient 429/timeout or a cold-start race, with no built-in retry — the poll loop re-attempts the V2 sweep every cycle so nothing made while the app was closed is lost. `processV2Notification(obj)` is the shared per-notification handler used by both the connect backfill and this retry sweep; `seenNotifIds` dedup makes re-processing safe (each fires at most once). The V2 sweep is skipped until `notif_backfill_initialized` is set (first-run baseline). This catches announcements that the WebSocket missed or delayed. Notification-v2 handler explicitly matches `post` types as announcements and `event`/`calendar` types as group events, with proper URLs (`/posts` for announcements, group page for events). Per-group announcement timestamps are persisted in DataStore (`notif_group_announcement_seen`) to avoid re-firing on reconnect. `seenNotifIds` set (capped at 500 entries, FIFO eviction) deduplicates between REST backfill and websocket replay — **persisted to SharedPreferences** (`vrca_seen_notifs/ids`) so IDs survive service restarts and prevent repeat notifications. **Ordering matters**: `fireEventNotification` checks the per-type toggle (`enabled`) BEFORE adding the dedup id to `seenNotifIds`. Adding it first would permanently poison the id if `enabled` read false transiently (e.g. DataStore not fully loaded during the cold-start connect/backfill race) — the notification would be dropped AND marked seen, so it could never fire on any later path. This was a cause of group announcements/events inconsistently never appearing on app open. REST calls are paced with 250-300ms delays; groups capped at 50 to stay under VRChat rate limits. Group announcement notifications include the group name in the title ("Announcement from GROUP_NAME"). Event notifications use calendar URLs (`/home/group/$groupId/calendar/$eventId`) when available. The `groupId` is extracted from `relatedGroupId`, `groupId`, `data.groupId`, `details.groupId`, or `senderUserId` (if `grp_` prefix), and the `eventId` from `eventId`, `data.eventId`, `details.eventId`, or `id` (if `cal_` prefix). As a final fallback BOTH fall back to `findIdWithPrefix(payload, "grp_"/"cal_")` — a recursive scanner that walks the entire notification-v2 JSON (including nested `data`/`details` blobs and embedded URLs) for the first value with that prefix. This is what makes event notifications reliably link to the calendar URL (`/home/group/grp_xxx/calendar/cal_xxx`) instead of falling back to `/home/notifications`. The notification-v2 `when` block has an **`else` catch-all** that logs the unmatched `type` string at INFO and still fires a generic group notification (gated by `KEY_NOTIF_GROUP_EVENT`) — so no notification-v2 is ever silently dropped just because VRChat used an unexpected type string. All handlers (WebSocket, poll loop, backfill) share `seenNotifIds` for dedup — WebSocket events now pass `dedupId = notifId` to prevent duplicates between real-time and polling. Each endpoint is wrapped in try/catch — failures are logged and skipped for this connect cycle. Bio/name change detection also runs on reconnect by diffing the old `friendsCache` against fresh API data before the cache is overwritten.

Worst case now the field is briefly blank (Apply is blocked on blank) and self-corrects once DataStore emits. **The "slot contents clone to slot 1 on tab re-entry" bug** (slot 2's IP overwriting a *populated* slot 1 after editing slot 1 → switching to slot 2 → leaving the tab → returning → switching back to slot 1) was caused by the **expanded-editor auto-save debounce** (`LaunchedEffect(n1,a1)` etc.). ### Firestore Schema (users/{deviceHash})
Key fields written by the app:
- `isOnlineInApp` (bool): Set to `true` by the app-open write, `false` by the swipe-away shutdown and `VrcaViewModel.onCleared` (GlobalScope fallback). **Swipe-away shutdown is centralised in `AppShutdown.onTaskSwiped(context)`** (`com.vrca.app.AppShutdown`), called from the `onTaskRemoved` of EVERY foreground service. This was a real bug: the kill used to live only in `VrchatPipelineService.onTaskRemoved`, but the pipeline isn't always running, and **`KeepAliveService` — which IS always running (started from `MainActivity.onCreate`) and holds a `PARTIAL_WAKE_LOCK` — had no `onTaskRemoved` at all**, so after a swipe the wakelock-holding service kept the whole process alive and nothing ever killed it. Now an `AtomicBoolean` in `AppShutdown` makes the heavy work run exactly once no matter which service fires first: it stamps the `manual_kill_at` flag, stops the other services (`VrchatPipelineService`/Discord/KeepAlive/Overlay, releasing wakelocks AND removing the "Connected as X" persistent notification promptly — without stopping the pipeline service here its notification lingered for up to 5s, the offline-write await, before `killProcess`, which looked like the swiped app was still "running / connected as username"), then on a background thread **awaits the offline Firestore write (5s timeout) and hard-kills the process** (`Process.killProcess` + `exitProcess`). `KeepAliveService.onTaskRemoved` is the reliable entry point since it's always running. The await ensures the going-offline write has a chance to reach Firestore before the kill; if it times out, the admin-side staleness sweep still flips the user offline once `lastActiveAt` ages past the ~65-min window. (Previously it waited a fixed 10s before killing, leaving the app running in the background that whole time.) **Sticky-restart guard**: `VrchatPipelineService`, `DiscordRpcService`, and `KeepAliveService` all return `START_STICKY` (so a memory-pressure kill is recovered), which means Android would normally relaunch them with a null intent right after the swipe-kill — making the app look like it was never killed. To prevent this, `AppShutdown` stamps `manual_kill_at = now` (SharedPreferences `vrca_remote`, committed synchronously) before killing; each service's `onStartCommand` treats a **null intent** as a sticky restart and, if `AppShutdown.isManualKillFresh()` (within `MANUAL_KILL_WINDOW_MS` = 15s), calls `stopForeground` + `stopSelf`, returns `START_NOT_STICKY`, AND kills its own (freshly-resurrected) process after a 300ms delay — because `stopSelf` alone leaves the recreated process sitting idle as a cached background process (Samsung's "running apps" list still showed it). The delay lets `START_NOT_STICKY` register before the kill so Android does NOT recreate the service yet again. A legitimate reopen always passes a non-null intent (with `EXTRA_DEVICE_HASH`) so it bypasses the guard, and the 15s window expires harmlessly. (Note: `NowPlayingListenerService` is a `NotificationListenerService` the system binds independently; it can be rebound by the OS later when notification activity occurs, but that no longer keeps the process perpetually alive after swipe.) **Persistent swipe flag (`swiped_away`)**: the 15s `manual_kill_at` window is NOT enough on its own — the `PipelineWatchdogWorker` (WorkManager, ~15 min) survives the process kill and fires in a fresh process LONG after the window expired, sees the user still logged in, and resurrects the pipeline + keep-alive. That was the "I swiped it away but it starts running again after a while" bug. So `onTaskSwiped` ALSO sets a persistent `AppShutdown.KEY_SWIPED_AWAY=true` boolean (committed synchronously) and best-effort cancels the watchdog (`PipelineWatchdogWorker.cancel`). The watchdog `doWork()` and every service's null-intent sticky-restart guard now back off when `isManualKillFresh() || isSwipedAway()`. The flag is cleared ONLY by a real user reopen (`MainActivity.onCreate` → `AppShutdown.clearSwipedAway()`) or reboot (`BootReceiver` clears it then restarts services). An OS/OEM kill never runs `onTaskSwiped`, so the flag stays false there and the watchdog still recovers the process — **a deliberate swipe stays dead, an OEM kill comes back.**
- `lastActiveAt` (timestamp): **Canonical liveness field (hourly model).** Written on cold-open and then once per hour by `VrcaViewModel.startHourlyHeartbeat()` (in-process coroutine — a swiped/OS-killed app stops firing it, so it goes stale and is correctly counted offline; an AlarmManager wakeup is deliberately NOT used because it would resurrect a dead app and make it report online forever). Also refreshed every 10s while an admin is watching this user (real-time ~25s liveness for the watched user). Admin online = `lastActiveAt` within ~65 min (see "Admin online detection" — the admin ignores the `isOnlineInApp` flag entirely and keys on this timestamp's freshness, minus a newer `offlineAt` marker).
- `offlineAt` (timestamp): **Clean-shutdown marker.** Written (alongside `isOnlineInApp=false`) ONLY on a deliberate swipe-away by `AppShutdown.buildOfflineWriteTask` and `VrcaViewModel.onCleared`. The admin's `isUserOnline` forces a row offline the instant `offlineAt` is newer than `(lastActiveAt ?? lastSeenAt)`, giving instant swipe→offline; a live heartbeat advances `lastActiveAt` past it so it can never false-flag a running app. If the swipe write never lands, the ~65-min staleness window still flips the user offline. **Both offline writes deliberately do NOT bump `lastSeenAt`** — refreshing the liveness mirror on shutdown would let `offlineAt > (lastActiveAt ?? lastSeenAt)` TIE (both the same serverTimestamp) for any user whose `lastActiveAt` is somehow absent, keeping a swiped app falsely "online" until the 65-min decay; `offlineAt` is the sole shutdown marker. In `selfMutableKeys()`.
- `lastSeenAt` (timestamp): **Legacy mirror of `lastActiveAt`** — written with the same server timestamp on every liveness write so older admin builds that read `lastSeenAt` keep working (additive migration; nothing removed). New admin code should read `lastActiveAt`.
- `afkEnabled`, `cycleEnabled`, `spotifyEnabled`, `timeEnabled`: Feature toggles (admin-editable)
- `warned`, `banned`, `warnReason`, `banReason`: Moderation flags (read by public app via snapshot listener)
- `targetedUpdateUrl` / `targetedUpdateNotes` (strings): **Legacy** — kept for backwards compat with old app versions. New directed releases use `releases/{deviceHash}` instead (see below).
- **Directed releases via `releases/{deviceHash}`**: Admin writes a per-device release doc to `releases/{deviceHash}` using the same schema as the global `releases/latest` doc (versionCode, versionName, downloadUrl, requiredMinCode, notes, publishedAt, publishedByDevice). The client's `checkFirestoreRelease()` checks `releases/{deviceHash}` first, then falls back to `releases/latest`. **Real-time detection**: `VrcaApp` attaches a Firestore snapshot listener on `releases/{deviceHash}` that immediately shows the update dialog when the admin pushes a targeted release — no polling delay. The download uses Android's `DownloadManager` for in-app APK download, then triggers the system package installer. Old app versions that only know about `releases/latest` can still be reached via the global "Release to All" flow; once they update to a version with per-device support, directed releases work forever. **ALL releases are FORCED automatically (both global and directed)** — `requiredMinCode` is no longer consulted; any newer `versionCode` makes the client treat the update as required (`InAppUpdate.parseReleaseSnap` + the `VrcaApp` per-device listener + the legacy `targetedUpdateUrl` path all hardcode `forced = true`). The `UpdateDialog` is then a non-dismissable wall (`onDismissRequest` no-ops, no "Later" button). **Forced updates also hard-block OSC output**: `VrcaApp` calls `VrcaViewModel.applyForceUpdateGate(true)` when a forced update is pending, which sets `VrcaOsc.blocked = true` on both the remote and local OSC senders. `VrcaOsc.sendOscMessage` early-returns when `blocked`, so EVERY chatbox transmission (typing/input/realtime, from any sender loop) is dropped at that single chokepoint — the user can't keep driving the VRChat chatbox by backgrounding the app. The gate lives on the **app-scoped VM**, so it persists after Activity destruction; it's cleared only if the pending update resolves. **Caveat (cannot be backfilled)**: force-update logic must already be present in the installed APK. Versions predating `InAppUpdate.kt`/this gate never read `releases/*` or the forced flag, so no Firestore field can compel them — the only lever they honor is the moderation ban screen (repurposable as an "update required" wall via `banReason`, but that's a manual hack, not wired up). Force-update is forward-only by nature.
- `watcherActiveAt` (timestamp): **Admin-only write.** Refreshed every ~30s while an admin has this user's detail page open. User app reads it from snapshots and feeds into `AdminWatchState.updateFromTimestampMs` — if within 60s, live-mode loops start.
- `killSignal` (timestamp): **Admin-only write.** Written by admin kill switch button. User app reads it from moderation snapshot listener — if fresh (within 60s), kills the app process.
- VRChat presence fields (`vrchatUserId`, `vrchatDisplayName`, `vrchatState`, `vrchatLocation`, etc.): Only written while watched.
- NowPlaying / preview fields (`nowPlayingTitle`, `nowPlayingArtist`, `combinedPreviewText`, `activePackage`): **Volatile** — these change constantly during music playback. They are written to Firestore **only when an admin is present**, via two gated loops (never on the raw NowPlaying state emission, which previously caused a write storm even with no admin present): (1) the watcher-gated live-sync loop writes them every 10s while watched; (2) the browse-gated volatile loop (`startBrowseVolatileSyncWatcher`) writes them every 30s while an admin is on the dashboard/users list but not actively watching. With no admin present, NowPlaying changes update only local UI state — zero Firestore traffic. The `buildUserSnapshot` self-sync still carries the current preview values, but self-sync only fires on genuine content edits/toggles now, not on NowPlaying ticks.
- `lastReportedTime`, `cycleTrimWarning`, `lastTimeUpdateAt`: Only written while watched (live-mode loop).

**Friends are no longer in Firestore** — `savedFriendIds`/`savedFriendNames` are deleted via `FieldValue.delete()` on offline write. They live in local SharedPreferences only.

**Volatile subdoc `users/{deviceHash}/live/state`** (Phase 2 infrastructure — rules deployed, write migration deferred): Firestore rules allow the subcollection `users/{deviceHash}/live/{doc}`. It was intended to hold high-frequency volatile data (nowPlaying, VRChat presence, preview text) to keep them off the main doc. After the Phase 3 read-model change the admin detail view polls the **main doc** every 10s (no admin-side collection listener at all), so volatile fields stay on the main doc for now — splitting them out would require the admin detail poll to read two docs for no current benefit. The rules remain in place as future-proofing; revisit only if the user's own self-doc listener firing on watched-user volatile writes (echo-suppressed today) becomes a measured cost.

### Ban-evasion capture (tri-directional)
`VrchatBanChecker` (`com.vrca.vrchat`) implements deferred ban-evasion detection across three identifier types. Identity index: `bannedIdentifiers/{identifier}` → `{ banId, type, active }`. Full record: `bannedRecords/{banId}` → `{ deviceHashes[], vrchatIds[], authUids[], displayNames[], evasionAttempts[], ... }`. **Phase 1** (on bootstrap, deviceHash + authUid known): checks `bannedIdentifiers/{deviceHash}` and `/{authUid}`; if active, defers the ban screen and stores `pendingBanId` so the new alt VRChat ID can be captured after login. **Phase 2** (after VRChat login): checks `bannedIdentifiers/{vrchatId}`; if the VRChat ID is banned, the current device/auth are appended (new-device evasion); if Phase 1 flagged the device, the new VRChat ID is captured. **`appendIdentifiersToRecord` writes atomically via a single `WriteBatch`** — the up-to-3 new `bannedIdentifiers` index entries, the `bannedRecords/{banId}` array unions (`deviceHashes`/`authUids`/`vrchatIds`/`displayNames`/`evasionAttempts`), and the `moderationEvents` audit doc all commit all-or-nothing. Before this, they were 5 sequential awaited writes; a mid-way process death left the record inconsistent (an index pointing at a banId whose record never listed it, or a captured identifier with no audit event). The moderationEvent uses an auto-id doc reference added to the batch via `batch.set(collection.document(), ...)`. The whole operation is wrapped in try/catch (logged, non-fatal).

### Firestore Sync Architecture
The sync model is intentionally minimal — Firestore costs money and we only push to it when we have to. Three classes of writes:

1. **App-open / cold-open write (one)**: After `initialDataLoaded` flips, `applyRemoteContentBeforeSync()` reads the Firestore doc to pick up any admin edits made while the user was offline (messages, presets, intervals — not toggles, which always start OFF), then `performSelfSync(coldOpen = true)` runs once with the merged state (`isOnlineInApp=true`, `lastActiveAt`). On first install or when `lastSyncedValues` is empty, this is a full ~40-field snapshot write (handles doc creation). On subsequent cold-opens with a persisted baseline, this is a **delta write**: only liveness fields + any content that changed since the previous session are written — unchanged presets/chatbox stay untouched. **Cold-open liveness throttle (`COLD_OPEN_LIVENESS_THROTTLE_MS` = 20 min)**: the background-survival stack (`START_STICKY`, the ~15-min `PipelineWatchdogWorker`, `BootReceiver`, OEM killers) resurrects the process repeatedly, and EACH resurrection re-ran this cold-open delta write (4 liveness fields) plus a self-listener echo read — that per-restart cost × frequent kills was the dominant *"steady Firestore reads/writes even with no admin browsing"* source (each cold start also re-attaches ~4-6 snapshot listeners, whose initial reads stack into the periodic read spikes). The cold-open write is now SKIPPED when (a) it's `coldOpen`, (b) the delta is liveness-ONLY (no content changed — gated on `LIVENESS_KEYS`), and (c) the last *actual* write (`PREF_LAST_SELF_SYNC_MS`, persisted via `markSelfSyncWritten()`) was within the throttle window. The still-fresh `lastActiveAt` already proves online, so status is unaffected; the **hourly heartbeat is anchored to the last real write** (first tick delay = `HOURLY - sinceLastWrite`, floored 60s) so a liveness write still lands within the 65-min staleness window even when the cold-open is skipped. A 15-min churn cadence drops from ~4 writes/hr to ~2/hr; a pathological fast (<20 min) restart loop writes at most once per ~20-40 min instead of once per restart. The first-ever sync and any content delta are NEVER throttled.
2. **Hourly liveness + delta write (periodic, the ONLY steady-state periodic write)**: `VrcaViewModel.startHourlyHeartbeat()` fires once per hour after the cold-open write. Each tick calls `performSelfSync()` which always writes liveness (`lastActiveAt`, `isOnlineInApp`, `lastSeenAt`, `updatedAt`) and includes only content fields that changed since the last write (field-by-field delta comparison against `lastSyncedValues`). If nothing changed, only the 4 liveness fields are written — a single minimal merge. It is an **in-process coroutine**, NOT an AlarmManager wakeup: a swiped/OS-killed app stops firing it → goes stale → correctly counted offline.
3. **App-close write (one)**: `VrchatPipelineService.onTaskRemoved` / `AppShutdown` writes `isOnlineInApp=false, offlineAt, lastSeenAt` plus current VRChat presence fields if available. `VrcaViewModel.onCleared` writes `isOnlineInApp=false, offlineAt, lastSeenAt` via `GlobalScope` as a fallback for cases where the foreground service isn't running. The `offlineAt` server timestamp is the authoritative clean-shutdown marker the admin reads for instant swipe→offline (see "Admin online detection").
4. **Edits use a 30s idle-debounce write**: changing a toggle/message/preset persists to local DataStore immediately (as always) AND schedules ONE delta write 30s after the last edit via `startSelfSyncLoopIfNeeded()` (`SELF_SYNC_DEBOUNCE_MS = 30_000`). Each edit cancels+reschedules, so a burst of edits flushes exactly once. (This was briefly a true no-op during the Phase-1 cost reduction, but that made "edit a preset then close the app" revert on reopen — the app-open read overwrote the not-yet-synced edit — so the debounced write was restored in commit `e21103e`. `performSelfSync` writes only changed content + liveness, so an idle user who isn't editing schedules nothing. The call sites fire ONLY on genuine content/toggle changes, never on NowPlaying ticks or preview rebuilds.) Still pushed on the next hourly tick too (or instantly via the 10s live loop if an admin is watching). **Note: this means an actively-editing user, or a content change pulled in by cross-device sync, costs one write per 30s-quiet-period — it is NOT zero per-edit.**

**Hourly liveness model (Phase 1)**: Liveness is determined by `lastActiveAt`, written once per hour by `VrcaViewModel.startHourlyHeartbeat()` (anchored to cold-open) and every 10s while an admin watches this user. Admin online = `lastActiveAt` within ~65 min (or ~25s for a watched user). `lastSeenAt` is written as a legacy mirror (same timestamp) so older admin builds keep working. **Removed in Phase 1**: the 30s browse-gated heartbeat, the 5-min always-on heartbeat, the per-edit debounced self-sync, and the browse-volatile 30s loop — none of these write to Firestore anymore. An admin merely browsing the directory causes **zero** per-user writes; only opening a specific user's detail (which flips `AdminWatchState.isWatched`) starts that one user's 10s live loop.

**Browse heartbeat (FULLY REMOVED)**: Previously, when an admin was on the Dashboard/Users tab the admin app wrote `config/adminPresence.browsingAt` every 30s and public apps ran a 30s `lastSeenAt` heartbeat while that was fresh. Phase 1 made the public-side write a no-op but the admin still WROTE `browsingAt` and every public app still held a `config/adminPresence` snapshot listener feeding `AdminBrowsingState`. That listener was the single biggest admin-side read cost: every 30s `browsingAt` write fanned a billed read out to EVERY online user's listener (~120k reads/hour at 1k users) for ZERO benefit (nothing reads `AdminBrowsingState` to drive a write under the hourly model — `startBrowseVolatileSyncWatcher` is empty). Now **both sides are gone**: `AdminRuntime` no longer writes `browsingAt` (its loop only runs the local force-kill staleness sweep), and `VrchatPipelineService` no longer attaches the `config/adminPresence` listener. (`AdminBrowsingState` remains as dead code, unfed.)

**Slow always-on lastSeenAt heartbeat (REMOVED in Phase 1 — historical)**: The service used to write `lastSeenAt` every 5 minutes (`LASTSEEN_HEARTBEAT_MS`) while alive (~288 writes/user/day). This is replaced by the once-per-hour `lastActiveAt` write (~24 writes/user/day) owned by the ViewModel. The constant and `writeHeartbeat()` are deleted.

**Live-mode (watcher-gated)**: When an admin opens a specific user's detail page in the admin panel, the admin app refreshes `watcherActiveAt` every ~30s on that user's doc. The user app's snapshot listener feeds the timestamp into `AdminWatchState`; if fresh (within 60s), `isWatched` flips to true and two side-effects start:
- `VrcaViewModel.startLiveSyncWatcher` writes `buildLivePayload` (nowPlaying, preview, the feature toggles `afkEnabled`/`cycleEnabled`/`spotifyEnabled`/`timeEnabled`, `lastReportedTime`, `lastSeenAt`) every 10s (`LIVE_SYNC_INTERVAL_MS`). **The toggles stream here so the admin detail's Pinned/Cycle/Music/Time button states reflect a user's own toggle change within 10s while watching** (they also persist via the hourly delta + the 30s edit debounce — `captureStateForSync` carries them — so an unwatched toggle surfaces on the next hourly write)
- `VrchatPipelineService.startPresenceRefreshLoop` writes VRChat presence every 10s

`VrcaViewModel.startBrowseVolatileSyncWatcher` is now a **no-op** (Phase 1): an admin merely browsing the directory no longer causes this user to emit any writes. The directory is populated from the admin's own one-shot fetch; only opening this user's detail (which flips `isWatched`) starts the 10s live loop.

The live loop stops instantly when `isWatched` flips back to false (`collectLatest` cancels the inner loop). When nobody is watching, neither loop touches Firestore — the only periodic write is the hourly `lastActiveAt`.

**Force-kill detection (hourly model)**: If the user's app is force-killed, neither `onTaskRemoved` nor `onCleared` fires, so `isOnlineInApp` stays `true` in Firestore — but the in-process hourly loop stops, so `lastActiveAt` goes stale. The admin determines offline by `lastActiveAt` age (>~65 min, or ~25s for a currently-watched user whose 10s loop stopped). The admin-side staleness sweep (`AdminRuntime`) keys on `lastActiveMs` (canonical `lastActiveAt`, falling back to `lastSeenAt`) with `ONLINE_STALENESS_WINDOW_MS = 65 min` — past the 60-min hourly heartbeat with 5 min of grace, so a live unwatched user is never false-flagged. When an admin is browsing and a user's `lastActiveAt` exceeds the window, the sweep writes `isOnlineInApp=false` to that user's doc.

**Admin kill switch**: Admin can force-quit a user's app via the "Kill App" button in UsersTab. Writes `killSignal = serverTimestamp()` to the user's doc. The user's `VrcaViewModel` moderation snapshot listener reads `killSignal` — if fresh (within 60s), calls `Process.killProcess(myPid())`. Handled at most once per session via `killSignalHandled` flag.

**Admin watcher heartbeat**: When an admin selects a user in the admin panel's detail view, a `LaunchedEffect` writes `watcherActiveAt = serverTimestamp()` to that user's doc every 30 seconds. When the admin navigates away or selects a different user, the coroutine is cancelled automatically. The user app reads `watcherActiveAt` from its snapshot listener and feeds it into `AdminWatchState.updateFromTimestampMs()` — if within 60s, live-mode starts.

**Echo suppression** (per-field `lastSyncedValues` map): Every field (toggle or content) compares its incoming snapshot value against `lastSyncedValues` — what we last knew was on the Firestore doc. If `remote == lastSyncedValues`, the snapshot is an echo (from self-sync, watcher heartbeat, or live-mode write) and we skip. If `remote != lastSyncedValues`, an admin actually changed it and we apply. Comparing against current local state would break this: during admin watch, the heartbeat fires snapshots with the OLD field values (Firestore hasn't received the user's pending local toggle yet), so a `remote != local` test would revert whatever the user just toggled. Content fields fall back to current local state when no baseline exists yet. Both branches update `lastSyncedValues` immediately on every snapshot (whether applied or skipped), so subsequent self-sync echoes are correctly suppressed. The map is also bulk-updated after each successful `performSelfSync` write via `captureStateForSync()`. The first snapshot seeds the baseline via `seedLastSyncedFromSnapshot`. **`lastSyncedValues` is persisted to SharedPreferences** (`vrca_remote/last_synced_values_json`) as a JSON object after each successful sync so the delta writer has a baseline across cold starts — without this, every app restart would fall back to a full snapshot write.

**Admin read model (Phase 3, admin-side only)**: The admin panel uses NO live collection listeners — those re-read on every user-doc change across the whole base, the dominant admin-side Firestore cost.
- **Directory** (`AdminScreen.kt` + `UsersDirectoryCache.kt`): **locally cached, zero-read on open.** The full user list is persisted to the admin device (`UsersDirectoryCache`, SharedPreferences `vrca_admin_directory`, JSON with timestamps as epoch-millis). Opening Dashboard/Users renders the cached list **instantly with 0 reads**; online/offline is recomputed locally from each row's cached `lastActiveAt`/`offlineAt` (`isUserOnline`), so cached rows decay to offline naturally without traffic. A full `get(Source.SERVER)` pull (limit `sharedLiveLimit`, default raised **500 → 2000** so the whole base loads — `+500` can raise further) happens ONLY when there's nothing cached (first-ever load) or the admin explicitly refreshed / paged (gated by `lastFetchedKey = "$sharedLiveLimit:$refreshTick"`). **Incremental liveness refresh (reads scale with ACTIVITY, not user count)**: because the cache freezes between full fetches, the online dots would go stale on a long-lived admin process. So when the directory is shown with a *populated* cache older than `DIRECTORY_REFRESH_TTL_MS` (10 min), an **incremental** query re-reads only users whose `lastActiveAt` advanced since the last refresh: `whereGreaterThan("lastActiveAt", cursor).orderBy("lastActiveAt", DESCENDING).limit(sharedLiveLimit)`. The cursor is `lastDirectoryRefreshMs - REFRESH_SKEW_MARGIN_MS` (5 min, to absorb client/server clock skew), or `now - ONLINE_STALENESS_WINDOW_MS` on a session's first refresh (so it reads exactly the currently-online set). **Idle/offline users have a stale `lastActiveAt` that doesn't match the inequality, so they cost nothing** — their cached rows decay to offline locally for free. As users settle offline the read count DROPS toward ~1 (an empty query's minimum) instead of staying at the full cached count; the only users read are those who came online or whose **hourly heartbeat just kicked in** (which advances `lastActiveAt` past the cursor, so the next refresh re-reads them and the merge REPLACES their stale cached row). **A swipe-away does NOT advance `lastActiveAt`** — it only stamps `offlineAt` (and deliberately does NOT bump `lastSeenAt`) — so the `lastActiveAt` query MISSES a swiped user once their `lastActiveAt` drifts older than the cursor, leaving their `offlineAt` stuck out of the cache and the row falsely "online" until the ~65-min staleness decay. To fix this the incremental refresh runs a **SECOND query — `whereGreaterThan("offlineAt", cursor).orderBy("offlineAt", DESCENDING)`** — and merges its docs (de-duped by id via `associateBy`) with the `lastActiveAt` query, so a recent swipe's `offlineAt` reaches the cache and the row flips offline on the next refresh. Costs ~1 extra read per swipe (Firestore's per-query minimum when none), so it stays bounded by activity. The merge (`LinkedHashMap` over cached + fresh) also ADDS newly-active users not yet in the cache. This NEVER scans the whole collection. Both queries are factored into a shared local suspend `incrementalDirectoryRefresh()`. **Three triggers feed it: (1) directory tab entry / cold launch (the directory `LaunchedEffect`); (2) app foreground-return — a `LifecycleEventObserver` bumps `resumeTick` on `ON_RESUME`, folded into the effect keys (but deliberately NOT into `lastFetchedKey`, so a resume never forces a full scan); (3) a LIVE periodic loop — a separate `LaunchedEffect(needsUsers)` re-runs `incrementalDirectoryRefresh()` every `DIRECTORY_LIVE_REFRESH_MS` (30s) WHILE the Dashboard/Users tab is composed.** Trigger (3) is the fix for "a swiped user never shows offline until the ~65-min mark": the TTL-gated triggers (1)+(2) only fire on tab-entry / resume, so an admin who just SITS on the directory never re-read — the swiped user's `offlineAt` landed in Firestore but never reached `sharedUsers`, and the only thing that flipped the row was the local `nowMs` ticker decaying `lastActiveAt` past 65 min. The 30s live loop re-reads the `offlineAt` query so a swipe surfaces within one cycle; it skips a cycle if a full/TTL refresh just ran (`now - lastDirectoryRefreshMs >= DIRECTORY_LIVE_REFRESH_MS`, so it never double-reads) and auto-cancels when leaving the directory tab (`needsUsers=false`). **The live loop is ALSO gated on `isForeground`** (the `LifecycleEventObserver` now tracks `ON_RESUME`→true / `ON_PAUSE`→false): Compose keeps a composed `LaunchedEffect` alive when the admin app is merely backgrounded, so without this gate an admin app **left open on the Dashboard/Users tab in the background polled Firestore every 30s indefinitely** — the dominant "reads keep climbing even though no admin is watching anyone" cost (it has nothing to do with watching a specific user; just sitting on the directory tab, even backgrounded/screen-off, drove it). With the gate the loop pauses the moment the app backgrounds and resumes on `ON_RESUME` (which also bumps `resumeTick` → a TTL-gated refresh re-freshens the directory). The TTL clock (`lastDirectoryRefreshMs`, a process-lifetime `AtomicLong`) is stamped on SUCCESS only (a full fetch also stamps it) so a failure or a resume-cancel retries on the next entry/resume; plain tab switches / brief resumes within the TTL cost **0 reads**. A `Refresh` icon button (Users header) and the Dashboard refresh button bump `refreshTick` for an instant full pull. An open user's 10s detail poll also patches that one row live (`onUpdateUserRow`) regardless of the TTL. Sorted by `lastActiveAt ?? lastSeenAt` desc.
- **Aggregate stats** (`AdminScreen.kt` + `DashboardTab.kt`): `count()` server aggregations (total/warned/banned, ban-evasion) run **once on tab entry and on manual refresh** (keyed on `refreshTick`) — NOT polled on a timer. The old 60s poll burned reads for no benefit at that cadence. 1 read per 1000 docs counted.
- **Selected-user detail** (`UsersTab.kt`): the ONLY live read — a 10s `get(Source.SERVER)` poll loop scoped to the single open user, keyed on `selectedDocId` **AND `isForeground`**. Backing out (`selectedDocId → null`) cancels the coroutine so reads stop INSTANTLY. **Foreground-gated**: a `LifecycleEventObserver` in `UsersTab` flips `isForeground` on `ON_RESUME`/`ON_PAUSE`, and the poll's key includes it (with an early `return` when `!isForeground`), so leaving a user's detail page open and **backgrounding the admin app no longer keeps reading every 10s** — this was the dominant *"reads keep climbing even though no admin is browsing"* cost (the directory 30s loop was already foreground-gated; this 10s detail poll was NOT, the one loop that escaped the gate). The last loaded detail stays on screen while backgrounded and the poll resumes (re-fetching immediately) on `ON_RESUME`. **Live instance count**: the detail's `📍 world (N/cap)` count is fetched **live from the admin's OWN VRChat session** (`VrchatAuthManager.fetchInstanceCount` on the user's `vrchatLocation`, polled every 10s while the detail is open), overriding the Firestore-synced `vrchatInstancePlayerCount` so the admin sees an instant count independent of the user's sync chain; falls back to the synced value when the instance isn't visible to the admin / not logged in. **Self-invite ("Invite me to this instance")**: a footer button (gated on `VrchatAuthManager.isLoggedIn`) calls `VrchatAuthManager.inviteSelfToInstance(ctx, vrchatLocation)` → `POST /invite/myself/to/{location}` (the website "Invite Me" behavior) sending an invite to the ADMIN'S OWN VRChat account for the user's current instance — works for invite-only/friends+/group; the user is NOT notified. Reads the freshest location from `selectedDetail` (UserRow doesn't carry `vrchatLocation`); disabled when not a joinable `wrld_` instance. The loop shows a spinner on first load then refreshes silently. 10s matches the cadence at which the watched user app refreshes its volatile fields. **Watched fast-offline (`WATCHED_STALE_WINDOW_MS` = 25s, `WATCH_RAMP_MS` = 45s)**: a watched user's app writes a liveness timestamp every 10s — `lastSeenAt` via the ViewModel live loop (dependency-free, the RELIABLE heartbeat) and `lastActiveAt` via the presence loop (which can stall if VRChat's `fetchPresence` 401s on an IP-invalidated cookie) — so a heartbeat that stops advancing **while watched** means the app died/was swiped, far sooner than the 65-min unwatched window can prove. The detail poll tracks the **FRESHEST of `lastActiveAt`/`lastSeenAt`** (`maxOf`, so a stalled `lastActiveAt` never false-flags a live user whose `lastSeenAt` is still advancing) and the wall-clock time it last advanced. **Loop-confirmed detection**: once the poll has SEEN the heartbeat advance at least once (`loopConfirmed`), a stopped heartbeat flips offline after just `WATCHED_STALE_WINDOW_MS` (≈2.5 missed ticks) — no need to wait the full ramp; before the loop is confirmed (its 10s loop hasn't started yet, or **the user was already DEAD when the admin opened them** — force-killed/swiped with no `offlineAt` landing, so there is no heartbeat to observe) it falls back to the `WATCH_RAMP_MS` (45s, reduced from 90s) grace so a live user isn't false-flagged mid-ramp. The 45s ramp is the fix for "opening an already-offline user doesn't flip them offline": `AdminRuntime.setSelectedUser` fires the `watcherActiveAt` write IMMEDIATELY on open, so a genuinely-LIVE user's first heartbeat reaches the poll within ~15-25s — 45s clears that chain with margin while flipping a dead user offline far faster than the old 90s. (If the ramp ever false-flags a live user, it SELF-HEALS the instant the heartbeat advances.) When stale, the poll **synthesizes `offlineAt = now` on the in-memory `UserDetail`** (zero Firestore write). This flips `isUserOnline` offline in the detail AND, via `onUpdateUserRow`, in the directory + cache — and is the ROBUST swipe→offline path because it does NOT depend on the swipe-time `offlineAt` write landing during the chaotic shutdown (that write is the instant-when-it-lands bonus). It self-heals: when the heartbeat advances again the poll stops synthesizing and carries the doc's real `offlineAt`. **For this to clear correctly, both the detail-view row merge and `onUpdateUserRow` treat the loaded detail's `offlineAt` as AUTHORITATIVE (no `?:` fallback to the directory row's value) — a null `offlineAt` from the poll must be able to clear a stale/synthetic marker** so a healed user returns online.
- The `watcherActiveAt` heartbeat (`AdminRuntime`) writes every 30s while a user is selected. No periodic writes from the user app outside the watched-user live loop.

**Initial-data gate** (`initialDataLoaded`): `performSelfSync` returns early until a loader coroutine has read every user-content DataStore field into ViewModel state. Prevents cold-start sync from writing empty defaults.

**First-snapshot skip** (`initialSnapshotProcessed`): The very first Firestore snapshot after listener attach is dropped — DataStore is the source of truth on cold start.

**Cross-device content sync (multi-phone, same VRChat account)**: When the same VRChat user logs in on two phones, the installs have DISTINCT `deviceHash`es → two separate `users/{deviceHash}` docs. To keep presets/messages/intervals consistent without merging the docs, `VrcaViewModel.applyCrossDeviceSync()` (public build only, launched from `init`) waits for the pipeline to surface the user's `vrchatUserId` (`VrchatPipelineState.presenceFlow.first { it != null }`, 120s timeout), then queries `users` for sibling docs `whereEqualTo("vrchatUserId", myVrchatId)`. It picks the sibling with the freshest `updatedAt`; if that is newer than this device's own `updatedAt`, it pulls the sibling's content into local DataStore + ViewModel state via the shared `applyContentFromSnapshot(snap)` helper (extracted from `applyRemoteContentBeforeSync()` — applies afkMessage, cycleIntervalSeconds, cycleLinesText, afkPreset1-3, cyclePreset1-5, spotifyPreset, each guarded by a value-changed check) and rebuilds the preview. So editing presets on phone A surfaces on phone B's next app open. The query keys on the already-written `vrchatUserId` field (a single-field index Firestore auto-provides). It is read-only against siblings — no cross-device WRITE — so the only authority over a device's own doc remains that device + the admin. **The query returns the device's OWN doc too (same `vrchatUserId`), so its `updatedAt` is read from the result set inline — no separate own-doc `get()`.** **THROTTLED to once per 30 min** (`CROSS_DEVICE_SYNC_THROTTLE_MS`, persisted `last_cross_device_sync_ms` in `vrca_remote`): this runs on every VM creation, and the background-survival machinery recreates the VM after each OS kill, so without the throttle a device that's being killed+restarted repeatedly would re-run this collection read every few minutes (a real "reads climbed even with no admin" contributor). The throttle bounds it to one query per 30 min/device regardless of relaunch frequency; a genuine reopen after editing on the other phone is almost always >30 min from the last sync, so the feature is intact. **Admin directory dedup (`UsersTab.filteredUsers`)**: the directory now COLLAPSES rows that share the same `vrchatUserId` (the multi-phone duplicates) into one representative — `preferRow()` keeps the online row, then the most recently active. Rows with a blank `vrchatUserId` (never logged into VRChat) are never merged. Dedup happens at render time over the cached list (preserving sort order); the underlying separate device docs are untouched.

**Offline editing**: User-content edits land in DataStore immediately and survive process death. On reconnect, the next debounced write or app-close write pushes them to Firestore. Admin-content edits are preserved across user restarts via `applyRemoteContentBeforeSync()` (read-before-write on app-open). If both the user and admin edited the same field while the user was offline, the Firestore version (admin's) wins because it's applied before the app-open write.

**Admin online detection (liveness-driven, NOT the `isOnlineInApp` flag)**: `isUserOnline(u, nowMs)` in `UsersTab.kt` is driven by **`lastActiveAt` freshness**, deliberately IGNORING the `isOnlineInApp` boolean. A user is online ⟺ `(lastActiveAt ?? lastSeenAt)` is within `ONLINE_STALENESS_WINDOW_MS` (~65 min) **AND** there is no clean-shutdown `offlineAt` marker newer than `lastActiveAt`. **Why the flag was dropped**: pre-app-scoped-VM public builds wrote `isOnlineInApp=false` from `VrcaViewModel.onCleared()` on EVERY Activity destruction (normal under memory pressure / "Don't keep activities") **without advancing `lastActiveAt`**, so a perfectly-live user showed offline with a fresh 28-min-old timestamp — the "Cherubic shows offline while her chatbox is clearly updating" bug. `lastActiveAt` is the ground truth because the hourly heartbeat (every 10s while watched) only fires while the process is alive. Under the hourly model an unwatched user writes `lastActiveAt` once per hour, so the window is ~65 min (5 min grace past the 60-min heartbeat); a watched user (10s loop) shows online within ~25s. **Instant-offline on swipe via `offlineAt`**: a clean swipe-away (`AppShutdown.buildOfflineWriteTask` + `VrcaViewModel.onCleared`) stamps `offlineAt = serverTimestamp()`. When `offlineAt > lastActiveAt` the row is forced offline INSTANTLY (no 65-min wait). This can never false-flag a live app — the next heartbeat advances `lastActiveAt` past `offlineAt` (self-healing, no clear needed). If the swipe-time write races the 5s kill timeout and never lands (the long-standing "swipe doesn't consistently go offline"), the staleness window still flips the user offline within ~65 min — instant when the write succeeds, eventually-consistent when it doesn't. VRChat session state is irrelevant to all of this: the liveness write uses Firebase anon auth + device hash and is fully decoupled from VRChat auth (a VRChat un-auth never blocks or triggers an online/offline write; VRChat presence fields are only additively merged when present). **The Dashboard counter uses the SAME `isUserOnline` predicate** (`DashboardTab.kt`) so the count and the directory rows stay consistent. The admin-side staleness sweep (`AdminRuntime`) still flips `isOnlineInApp=false` for genuinely-stale users — now only to keep the raw flag roughly accurate for any OLD admin builds that still read it directly; the current build never reads it for the online decision. `UserRow`/`UserDetail`/`parseUserRow`/`UsersDirectoryCache` all carry the new `offlineAt` timestamp; `firestore.rules` `selfMutableKeys()` includes `offlineAt`. The shared user-list state is `mutableStateOf<List<UserRow>>` (whole-value assignment) populated by the one-shot directory fetch.

### Chatbox Rate Limit
VRChat's chatbox update limit is 0.5 seconds (`SEND_FLOOR_MS = 500L`). Music refresh is locked at 1 second (`MUSIC_REFRESH_SECONDS_LOCKED = 1`).

### NowPlaying
- Ad/DJ detection restricted to Spotify only (`com.spotify.music`) to prevent false positives on regular songs — EXCEPT a player-agnostic `advertisement*` (title OR artist) check, since Spotify now puts the advertiser brand in the artist field
- **Ad number display**: ads render as `"Ad 1 of 1"` using the player's OWN ad index, parsed via `parseAdIndex()` (regex `(\d+)\s*of\s*(\d+)`) from the ORIGINAL title+artist BEFORE they're blanked to `"AD"`, carried through `NowPlayingSnapshot.adInfo` → `nowPlayingAdInfo`. Falls back to the session `adSegmentCount` (coerced to ≥1, so it never shows "Ad 0") when the player exposes no index. The brand is never shown (location-leak prevention). **The ad-label block in `buildNowPlayingLines()` is gated on a dedicated `nowPlayingIsAd` flag (set from the collector's `isAdNow`), checked BEFORE `isSpotifyDj` with an early `return`.** This fixes "the ad number never shows": a Spotify ad blanks the artist (`title="AD"`, `artist=""`), which made `isSpotifyDj` (`safeArtist.isBlank()`) evaluate TRUE — so the old `if (nowPlayingSpecialActive && !isSpotifyDj)` guard was false and the whole ad block was skipped, falling through to render a bare "AD" title + progress bar with no "Ad N". An ad and a DJ segment both blank metadata; only the explicit `nowPlayingIsAd` flag distinguishes them, so the ad path must be checked first and independently of `isSpotifyDj`.
- Special window reduced to 10s (from 30s) for faster recovery after ads; cleared immediately once a real track with genuine metadata plays so "Ad N" doesn't linger over the next song
- **YouTube / YouTube Music ARE detected** (earlier notes claiming they can't be were wrong — they DO publish a MediaSession with title/artist/position). Two quirks are handled in `NowPlayingListenerService`: (1) **Pickup delay** — a freshly-started session used to surface only when the app posted its media notification (a few seconds late). An `MediaSessionManager.OnActiveSessionsChangedListener` (registered in `onListenerConnected`, unregistered in `onListenerDisconnected`) now wires the controller the instant the session goes active, so detection is near-immediate (future-proof for ALL media apps, not just YouTube). (2) **Progress kept moving while paused** — YouTube keeps reporting `STATE_PLAYING` + `playbackSpeed=1f` even when PAUSED, so the only reliable pause signal is that the raw `position` stops advancing across snapshots. That position-stall check lives in `NowPlayingState` and needs fresh samples every ~500ms, but YouTube's `MediaController` fires almost no callbacks while paused — so `ensureControllerForPackage` now starts a **continuous 500ms poll for YouTube packages** (`startPollForRealTrack`, exempt from the 10-min cap that the Spotify ad/DJ poll uses; it self-stops on controller change / teardown / session-destroy / notif-removed). The poll pushes a snapshot EVERY cycle for YouTube (other players still push only on real change / every 4s), so the stall detector reaches its 2-cycle threshold within ~1s of a pause → forces `isPlaying=false` → `effectiveIsPlaying` goes false → `buildNowPlayingLines` stops extrapolating and freezes the progress bar at the real snapshot. On resume the real position is being pushed every 500ms, so the bar continues from the true timestamp with no teleport.
- Motion-based play detection with YouTube-specific stall tracking
- **Last-track persistence across revival (`NowPlayingState.attach`/persist)**: the snapshot lives only in process memory, so after an OS-initiated process kill + headless ViewModel revival (`KeepAliveService` → `ensureRuntimeViewModel`) a PAUSED track had no active MediaSession to re-push and the chatbox NowPlaying line just blanked out. `NowPlayingState` now persists the last *detected, non-special* track (title/artist/duration/position/package) to SharedPreferences (`vrca_nowplaying`) inside `update()` and `pauseIfActivePackage()`, and `VrcaApplication.onCreate()` calls `NowPlayingState.attach(context)` to re-seed `_state` from disk **as paused** (re-anchoring `positionUpdateTimeMs` to `now`, `speed=0`, `isPlaying=false`) before any ViewModel collects — so the previous track shows immediately instead of disappearing. `attach` is idempotent and only restores while the in-memory state is still blank (never clobbers a live one). Ads/DJ/special windows are never persisted (restoring "AD" would be nonsense). A genuine hard clear (`clearIfActivePackage`) removes the persisted entry so a real stop doesn't resurrect a stale track. Also fixes the plain cold-start case, not just headless revival.
- **Blank-metadata push keeps the last track (close-blanking fix)**: closing the media app (vs Spotify, which keeps its MediaSession alive in the background) tears its `MediaSession` down — YouTube/YouTube Music in particular fire `onMetadataChanged(null)` / the 500ms poll reads empty metadata right around teardown, pushing a `detected=false` (blank title+artist) snapshot. The old `NowPlayingState.update()` wrote that blank straight into `_state`, instantly wiping the preview AND the OSC chatbox line ("closing YouTube removes the text immediately; Spotify doesn't"). The disk persistence above did NOT rescue this — `attach` only re-seeds when in-memory state is blank at *process start*, but here the process is still alive. **`update()` now treats a blank push for an already-`detected` track as a PAUSE: it freezes the last known title/artist (`speed=0`, `isPlaying=false`, clears `specialActive`/`adInfo`) instead of clearing**, mirroring `pauseIfActivePackage`'s keep-last behavior — so YouTube freezes the last track on close exactly like Spotify. A genuine hard stop still goes through `clearIfActivePackage()` (the only remaining blank path). **YouTube ad detection remains a known limitation**: during a YouTube ad the MediaSession keeps the VIDEO's title but reports the AD's (short) duration/position, so the progress bar shrinks to the ad then jumps back. `classifySpecial()` only flags ads when the title/artist starts with `"advertisement"` (Spotify's behavior); YouTube exposes no reliable ad flag, so this is intentionally left as-is rather than adding a fragile duration-collapse heuristic that would false-positive on Shorts / short videos / chapters.

### Remote Config (Admin Edits)
The public app's moderation snapshot listener on `users/{deviceHash}` also picks up admin-editable fields (feature toggles, messages, intervals, presets) and applies them in real-time. Each incoming snapshot is filtered by:
1. `initialSnapshotProcessed` — drop the very first snapshot (DataStore wins cold start)
2. Per-field `lastSyncedValues` comparison — if the remote value matches what we last wrote, it's our own echo and is skipped; if it differs, an admin changed it and it's applied

After those filters, the snapshot's content fields (afkMessage, cycleLines, presets) are written to DataStore so existing flow collectors propagate them into ViewModel state. Toggles are set directly on the ViewModel (they don't persist — see below).

### Toggle Persistence
Feature toggles (`afkEnabled`, `spotifyEnabled`, `cycleEnabled`, `timeEnabled`) survive Android process death (memory pressure) via `SavedStateHandle`, and survive Activity destruction because the runtime `VrcaViewModel` is now **app-scoped** (owned by `VrcaApplication`'s `ViewModelStore`, not the Activity's — see "Background Survival"). Content (messages, intervals, presets) DOES persist via DataStore as normal. Admin can still flip toggles in real-time via the Firestore snapshot listener, which writes directly to ViewModel state (and SavedStateHandle) without touching DataStore.

**OSC send gate (Start/Stop) — toggles configure WHAT, Start gates WHEN**: A master `VrcaViewModel.oscSending` boolean decides whether the enabled toggles actually transmit over OSC. **Toggling a feature no longer auto-starts sending** — flipping `afkEnabled`/`cycleEnabled`/`spotifyEnabled`/`timeEnabled` while `oscSending == false` only updates the local preview and persists the config; no OSC leaves the device and the VRChat chatbox is untouched (this lets the user set up their preview first). `startSending()` (Home "Start sending" button) flips `oscSending` true and launches the sender loops (`startAfkSender`/`startCycle`/`startNowPlayingSender` + `manageKeepaliveLoop`) for whatever toggles are on; each starter early-returns unless `oscSending && <its toggle>`, and every sender `while` loop also checks `oscSending` so the master gate hard-stops them. `stopSending()` (Home "Stop sending" button, replaces the old red **KILL**) flips `oscSending` false, stops all sender loops, and clears the VRChat chatbox **WITHOUT untoggling any feature** — so pressing Start again resumes exactly what was configured. While sending, toggling a feature applies live (starts/stops just that loop). `killStopAndClear()` still exists but is now reserved for the **ban path** (`VrcaScreen.kt` ban gate) — it additionally untoggles all four features. The Home UI shows a `SendStatusChip` (amber dot "Sending" / grey dot "Idle") in the header as the at-a-glance OSC indicator, and the Quick Toggles header sub-label flips between "Press Start when Ready" and "Edits show live". **Home layout (`HomePage.kt`)**: the original **"VRChat Preview"** `SectionCard` (title enlarged via `SectionCard`'s optional `titleStyle = headlineSmall`; subtitle "What will appear in VRChat.") — a 280dp `Box` with the centered tonal preview `Surface` (`surfaceVariant`, `shapes.large`) overlaid on the faint avatar-silhouette `Canvas` "character", the `SendStatusChip` in the card actions, the full-width Start/Stop button, the cycle-trim warning, and the **"Quick Toggles" `ElevatedCard` nested INSIDE the same SectionCard** (`surfaceVariant`). Only the Start/Stop OSC-gate button + `SendStatusChip` were added to this original layout; two redesign attempts (accent-gradient character / floating bubble / split toggles) were both reverted per user preference — the original preview+toggles visual is the intended look.

**Auto-restore after an OS kill (`FeatureSessionStore`)**: A deliberate **swipe** still starts clean (toggles OFF, not sending), but an **OS-initiated process kill** (memory pressure / Doze / OEM killer) is made invisible — the chatbox resumes on its own **only if the user was actually sending**. `FeatureSessionStore` (`com.vrca.app`, backed by the `vrca_remote` prefs file) persists the active toggle set **plus the `sending` gate** on every toggle/Start/Stop change and **arms** restore. `VrcaViewModel.restoreFeatureSession()` runs once after initial content load: it re-applies the toggle CONFIG directly (so the preview reflects what was set up), then resumes OSC sending via `startSending()` **only when the persisted `sending` was true AND something was enabled** — toggles configured but never started come back idle (no transmission). `AppShutdown.onTaskSwiped()` calls `FeatureSessionStore.disarm()` so a real swipe (the only deliberate stop) is NOT restored — an OS kill never runs `onTaskSwiped`, so it stays armed. This is the per-session source of truth for "was this stop deliberate?"; do not key restore on the `manual_kill_at` timestamp (it persists across sessions and can't distinguish a stale prior swipe from a fresh OS kill).

### Background Survival ("works as if on-screen; only a swipe stops it")
The runtime is decoupled from the Activity so everything keeps running while backgrounded, and recovers after an OS kill:
- **App-scoped ViewModel**: `VrcaApplication` implements `ViewModelStoreOwner` with a process-lifetime `ViewModelStore` (cleared only by `AppShutdown` on swipe). `VrcaViewModel` is obtained against it (`VrcaApp.kt`, `OverlayService.kt`), so the chatbox OSC senders, moderation/kill listener, NowPlaying consumer, and Firestore sync loops survive Activity destruction (`onCleared` only fires on a real swipe). The Factory uses `VrcaApplication.instance` (CreationExtras has no `APPLICATION_KEY` against an app store) and a plain `SavedStateHandle()` (an app `ViewModelStoreOwner` has no `SavedStateRegistry`, so `createSavedStateHandle()` would throw).
- **Headless ViewModel recreation**: after an OS kill the watchdog / `START_STICKY` / `BootReceiver` bring back `KeepAliveService` with no Activity — so the senders (which live in the VM) would stay dead. `KeepAliveService.onStartCommand` calls `VrcaApplication.ensureRuntimeViewModel()` (idempotent, main-thread `ViewModelProvider` create) **only when `FeatureSessionStore` restore is armed with `sending && anyEnabled`** (i.e. OSC was actively transmitting — that's the background work to revive; toggles configured-but-idle have nothing to resume), recreating the VM headlessly → `restoreFeatureSession()` resumes OSC sending with no tab-in.
- **Discord RPC / presence / notifications / timer** self-restore via the service layer: `VrchatPipelineService` restarts (sticky/watchdog/boot), auto-relogins from EncryptedSharedPreferences, and on `onOpen` re-reads `discord_rpc_enabled`+`discord_session_seeded` (DataStore) to auto-start `DiscordRpcService`; the RPC online timer has its own grace-window restore.
- **Discord WebView keep-alive WITHOUT an overlay**: the Discord gateway lives in a WebView whose JS Chromium throttles when it thinks the page is hidden (gateway drops ~45s after screen-off). Rather than a 1×1 `TYPE_APPLICATION_OVERLAY` window (which forces Android's "displaying over other apps" notification and looks sketchy), `DiscordRpcService` subclasses `WebView` and overrides `onWindowVisibilityChanged` to always report `View.VISIBLE`, plus `resumeTimers()` + `dispatchWindowVisibilityChanged(VISIBLE)` after creation. No overlay window, no system notification. (If this proves unreliable on some OEMs for long screen-off, the fallbacks are the overlay or a native OkHttp gateway — the latter weakens the "real Discord web session" anti-detection.)
- **Discord WebView cache cap (`startCacheMaintenance`)**: the long-lived WebView loads the full discord.com app, which persists an HTTP cache + DOM storage + IndexedDB + service workers that grow **unbounded and are never cleared** — the dominant contributor to the app's runaway on-disk "cache" size (it's scale-independent: it grows from the session being alive, not from the VRC-A user count). An hourly loop measures the `app_webview` data dir and, when it crosses `WEBVIEW_CACHE_CAP_BYTES` (80 MB), wipes web storage (`WebStorage.deleteAllData()`) + the HTTP cache (`clearCache(true)`) and `reload()`s. **The Discord session survives** because the auth COOKIE (`CookieManager`) is left untouched — Discord re-bootstraps its `localStorage` token from the cookie on reload; if that ever fails it lands on `/login` and the existing `onSessionExpired()` recovery kicks in. The loop is started when the WebView is created and cancelled in `teardown()`/`onDestroy()`. (Affects BOTH builds — Discord RPC isn't admin-gated.)
- **`PipelineWatchdogWorker`** (WorkManager, ~15 min): if logged in and the pipeline isn't connected, restarts `KeepAliveService` + `VrchatPipelineService`. Backs off when `AppShutdown.isManualKillFresh() || AppShutdown.isSwipedAway()` — the persistent `swiped_away` flag is what prevents this worker (which fires ~15 min after a swipe, long past the 15s freshness window) from resurrecting a deliberately-swiped app. An OEM/OS kill leaves the flag false, so the watchdog still recovers that. `BootReceiver` clears the swipe flag, restarts `KeepAliveService`, and reschedules the watchdog. `onTaskSwiped` best-effort calls `PipelineWatchdogWorker.cancel()`; `MainActivity.onCreate` re-schedules it on reopen.
- **`AdminRuntime`** (`com.vrca.admin`): process-lifetime singleton owning the force-kill staleness sweep and `watcherActiveAt` watcher heartbeat — moved out of Compose `LaunchedEffect` so they keep running while the admin app is backgrounded. Compose only registers intent (`setBrowsing`/`setSelectedUser`/`updateSweepData`). (The `config/adminPresence.browsingAt` heartbeat it used to write was REMOVED — see "Browse heartbeat (FULLY REMOVED)" above; `setBrowsing` now only gates the local sweep.) **Foreground gating (`setForeground`)**: the latched intent is the problem when the admin merely BACKGROUNDS the app (no swipe / Activity destroy) — `onDispose` never fires, so `browsing`/`selectedUser` stay set and the watcher loop kept writing `watcherActiveAt` every 30s indefinitely, holding that user in 10s live-sync while no admin was actually looking. `AdminScreen`'s `LifecycleEventObserver` now calls `AdminRuntime.setForeground(true/false)` on `ON_RESUME`/`ON_PAUSE`, and the watcher heartbeat, the immediate-on-select write, and the staleness sweep all gate their WRITES on `foreground.value`. The intent stays latched (not cleared), so returning to the foreground resumes exactly where it left off — but a backgrounded admin emits **zero** periodic writes. (This deliberately narrows the earlier "admin watches while backgrounded" intent in favor of cost: an admin who isn't on-screen shouldn't keep a user in live-sync.) **Directed-release APK picker state (`pickedApkState`/`ingestPickedApk`/`clearPickedApk`)**: the admin detail view's "Pick APK" (directed release) launches the system file picker (DocumentsUI). The heavy admin app (Discord WebView + foreground services + Coil loader) is routinely EVICTED while DocumentsUI is foreground, so on return the admin **Activity is recreated** — `AdminScreen.sharedUsers` (plain `remember`) resets to empty, the detail view (gated on `if (rawRow != null)`, i.e. the selected user being present in `users`) is briefly disposed, and any plain-`remember` picker state inside it is lost AND the file-copy coroutine on the composition scope is cancelled. That was the "picking an APK doesn't apply and resets the detail view" bug. Fix: the picked APK (cache path + parsed `versionCode`/`versionName` + filename + error, keyed by `docId`) lives in `AdminRuntime` and the URI→cache copy + `parseApkInfo` run on `AdminRuntime.scope` (process lifetime), NOT the composition. `UsersTab` reads it back via `pickedApkState.collectAsState()` filtered to the open `docId`, so the rebuilt detail view re-shows the pick. `ingestPickedApk(appContext, docId, uri)` uses the APPLICATION context (the Activity may not survive); `clearPickedApk(docId)` is called after a successful push (also deletes the cached file).
- **Limits (be honest with users)**: no app can guarantee the OS never kills it. Survival depends on the **battery-optimization exemption** (requested via `VrcaViewModel` / surfaced on Home + Settings) and, on Samsung, the user adding VRC-A to "Never sleeping apps" and keeping it out of "Sleeping apps". The architecture above maximizes survival AND makes the residual kill invisible via auto-restore.
